## 1. 读前须知：术语用大白话解释

| 术语 | 大白话 |
|---|---|
| **OPC / OPC DA** | 工业设备常用的“数据插座”标准，让上位机读 PLC/反应器的点位。传统 OPC DA 依赖 Windows 的 COM/DCOM，Java 直连要装中间件；本项目实际用的是**别人已经把 OPC 读出来、再包成 HTTP 接口的服务**。 |
| **NamedPipe（命名管道）** | Windows 本机进程间通信通道。检测子系统（BGA/Cedex/OSMO/ViCell）在工控机上开一个“管道名字”，本系统按名字连上去发订单、查状态。**必须与子系统在同一台/同一网段 Windows 机器上**。 |
| **REST / HTTP 接口** | 用网址 + JSON 报文调用的服务接口。跨机器、跨语言，最容易做监控和重试。 |
| **直读数据库表** | 不调接口，直接用数据库账号 `select` 对方系统的表。省事，但把对方表结构当成契约，对方改表就崩，且通常没有写权限。 |
| **`cdp_` 表** | 原系统（CDP/NPP）里以 `cdp_` 开头的业务表，例如培养、检测结果、在线指标。小试检测结果最终落在这些表里。 |
| **Inno** | 客户側的反应器在线参数平台（文档 Base URL `https://slms-nppwgq.wuxibiologics.com`），提供 pH/DO/温度/MFC 等在线参数。 |
| **LDMS** | 客户側的设备数据平台，提供 `/messageService/api/getDeviceData`、`/getDeviceListData` 按设备/时间拉数据。 |
| **证据归档（evidence archive）** | 每次外部调用把请求、响应原样落盘并做哈希，用于事后追溯“当时设备到底返回了什么”。本仓库补液适配层已实现。 |

**口径说明**：本文的“已实现”只表示源码里存在真实调用链（Controller/Service/Client），**不代表联调通过**；按 AGENTS.md §13.2，最多到 `IMPLEMENTED`，未做 HTTP/浏览器/现场验证的一律 `NOT_VERIFIED`。

### 2.3 两个选项各怎么做

**选项 A：NamedPipe 直连（订单 + 查询）**

- 已具备：`NamedPipeClient` + `NamedPipeRouter` + 各子系统服务 + `LabCommunication` 端点配置。
- 走通还缺：真实工控机环境、各子系统 pipeName、调用超时/重试策略、订单与批次的幂等键、失败后的可恢复语义（当前代码有 TODO 指出“管道调用成功不等于整批执行成功”）。
- 工作量：**小**。理由：收发与路由都已存在，剩下是现场参数、超时/错误码映射和验收，不涉及新架构。

**选项 B：直读子系统数据库表（订单 + 结果）**

- 结果侧：已实现（`NamedPipeResultFetchTask` 直查 `cdp_` 表），**无需新建**。
- 订单侧：**没有找到任何“写订单到子系统表”的实现**，`docs/接口文档/原系统数据库表结构/npp.sql` 与 `cdp.sql` 只有表结构，没有订单写入归属、没有写权限、没有表间约束说明。
- 走通需要：新建外部数据源（多数据源/JDBC 只读账号）、订单写入表映射、与子系统事务边界的约定、对方改表的兼容策略。
- 工作量：**大**。理由：不是“加一个 Mapper”，而是把对方私有表当公开契约；且订单写入在需求与资料中都没有依据。

### 2.4 风险对比

| 维度 | A. NamedPipe | B. 直读 DB 表 |
|---|---|---|
| 稳定性 | 受工控机进程/管道会话影响；管道断开需重连 | 受对方表结构与写入时机影响；对方升级/改表即失效 |
| 故障可见性 | 可拿到返回码/异常，易做健康检查；但“已接单未执行”需额外核对 | 只能看到“表里有没有数据”，看不到“订单为什么没执行” |
| 中间件 | 无需额外中间件，但**必须 Windows 环境**且与子系统同机/同网段 | 无需中间件，只需数据库网络可达 |
| 客户环境 | 需要工控机常驻管道服务（现状已有） | 需要开放数据库账号；客户 IT 通常更不愿开放 |
| 数据一致性/时序 | 请求-响应天然有先后；结果落表有延迟，需要轮询与超时判定 | 读写都异步，缺少“已受理”回执，订单与结果难对齐 |
| 历史回补 | 管道一般不提供历史查询，只能依赖 `cdp_` 表 | 表里天然有历史，回补容易 |
| 权限与审计 | 调用方身份由管道端点决定，审计靠应用日志 | 数据库账号权限粗，难做按用户审计 |
| 安全边界 | 本机/内网，暴露面小 | 直连对方库，等于把两套系统耦合到表级 |

### 2.5 对二期/后续的影响

- 选 A：二期若要统一到“设备接入网关”，管道只是一种 driver，可被包装；不会被锁死。
- 选 B（订单也走 DB）：二期统一网关时，DB 直读会变成“无法通过网关代理”的例外，且对方改表直接影响本系统，迁移成本高。
- 先 A 后补 B（结果回补）是现状路径，迁移成本≈0；先 B 后改 A 需要重建订单契约，成本中。

### 2.7 结论：已定（2026-11-04 用户裁决）

**已定：查对方数据库表，不再走 NamedPipe。**

裁决依据是**用户答复**，不是本节 2.2-2.6 的文档证据；上面的权衡分析保留，作为“为什么曾倾向 A + `cdp_`”的决策留档。

与裁决对应的变化：
- 订单侧：不再调用 `NamedPipeRouter`/`DetDeviceDispatchServiceImpl` 的管道分支，改为查子系统库表中的订单/任务表；
- 结果侧：本就走 `cdp_` 表（`NamedPipeResultFetchTask` 的查表逻辑可复用表名与映射，但需要去掉“仅 `communication_type = NAMED_PIPE`”的过滤条件）；
- 管道客户端本身不删除，保留为历史通道（二期若需要可再启用），但**不再作为本期主链路**。

现状评估：结果侧“查表”已有实现（GL-1，`IMPLEMENTED`）；订单侧“查表”**没有实现**，且缺少订单表写入/读取契约 → 见 §6.1 缺口。

### 3.3 两个选项各怎么做

**选项 A：OPC（controller 数据库 + OPC 标签）**

- 这里的“OPC”有两种可能实现：
  1. **继续用 `opcdaReadService`**（即现状）：本质仍是 HTTP，只是它内部连 OPC DA。不需要新建组件。工作量 **小**。
  2. **Java 直连 OPC DA**：需要引入 J-Interop/Utgard 或 OPC UA（Milo）客户端、部署在 Windows（DCOM）或客户 OPC UA 网关、做点位映射（`deltav tag表.xlsx` 有 150 个标签）、连接池/重连/断线缓存。工作量 **大**。
- 注意需求 18章 L1152 说的“controller 数据库”是另一条路：直读控制器库表（`CDP_BioReactor_ItemSerials` 类），与小试同源；但它只覆盖“读状态/参数”，**写泵速仍要接口**（写库风险高且需求未授权）。

**选项 B：现成 REST 设备服务**

- 已有：`opcdaReadService`（读罐数据 + 写泵速）、`messageService`（地秤/奥豪斯）、`M02HttpDeviceCommandAdapter`（命令型设备 HMAC 网关）。
- 走通还缺：现场 base-url、超时、点位绑定（`binding.feedback-point`/`set-point`）、STOP 审批证据文件、与补液调度的节拍（每罐一次 HTTP 的吞吐）。
- 工作量：**小**。理由：链路、编解码、证据归档、配置强校验都已存在，属于“配参数 + 联调”。

### 3.4 风险对比

| 维度 | A1. 现有 OPC 服务（HTTP 包装） | A2. Java 直连 OPC DA | B. REST 设备服务（含地秤/命令网关） |
|---|---|---|---|
| 稳定性 | 依赖 opcdaReadService 常驻；HTTP 超时可控 | 依赖 DCOM/网关，跨网段易断；需长连接与重连 | 与 A1 相同（A1 本身就是 REST）；地秤/网关各自独立，故障隔离好 |
| 故障可见性 | 有 HTTP 状态码 + 原文归档，可追溯 | COM 错误码晦涩，需自行封装 | 最清晰：有状态码、有证据文件、有命令受理/执行分离 |
| 中间件 | 只需部署/访问该 HTTP 服务 | **必须** Windows + DCOM 配置或 UA 网关 | 无额外中间件 |
| 客户环境 | 客户已有该服务（补料逻辑说明中 `OPC.DeltaV.1`） | 需客户开放 DCOM 端口/账号，IT 阻力大 | 客户已有 `messageService`/`opcdaReadService` |
| 一致性与时序 | 请求/响应同步，写后需回读确认（现状已把回读标为未验证） | 同 A1，但可做订阅 | 同 A1；地秤为只读，天然无副作用 |
| 历史回补 | 服务若提供历史接口可用；否则靠本地落库 | 订阅可缓存，但历史依赖 OPC 服务器 | 地秤有 `getOhausScaleDataList` 历史接口 |
| 权限与审计 | 服务侧鉴权 + 本系统证据归档 | 依赖 DCOM 账号，审计粗 | 命令网关有 HMAC + 执行器白名单 + 回执，审计最强 |
| 写入安全 | 现有适配层有 STOP 审批绑定、点位白名单、禁事务内调用 | 需自行重建同等防护，容易漏 | 已有防护，无需重造 |

### 3.5 对二期/后续的影响

- 选 B（现状）：二期若统一 OPC 接入，只需替换 `CustomerOpcTransport` 的 base-url 与协议，业务编排不变；**不会被锁死**。

## 5. 定稿后的组合形态：小试查库 + 中试/在线 HTTP 占位

**最终形态不是“三种技术并存”，而是“一条查库链路 + 两条待接入的 HTTP 占位链路”。**

| 通道 | 本期实际形态 | 对外状态 |
|---|---|---|
| 小试离线检测 | 只读查询对方库表（`cdp_` 系列 + 订单/任务表） | 订单侧 `BLOCKED_INPUT`，结果侧 `IMPLEMENTED`（未联调） |
| 中试补液 | 内部接口 + 空实现；客户客户端到位后按 HTTP 接入 | `BLOCKED_EXTERNAL` |
| 在线数据 | 内部接口 + 空实现；客户客户端到位后按 HTTP 接入 | `BLOCKED_EXTERNAL` |

### 5.1 监控与故障定位的注意点

1. **查库方案看不到“对方接口的健康状态”。** 数据库只反映结果，不反映“对方是否活着/是否拒单”。因此必须补**数据新鲜度监控**：按设备/表记录“最近一条写入时间”，超过阈值（例如检测结果 30 分钟无新增）即告警；否则故障表现为“页面一直没有新数据”，无法区分是没下单、对方没执行、还是表没更新。
2. **HTTP 占位链路没有真实端点，健康检查必须是“未接入”而不是“正常”。** 空实现期间若接入统一的健康检查，不能返回 UP，否则监控面板会显示“三条通道全绿”而实际两条没接。
3. **两类通道的失败语义不同。** 查库失败通常是连接/权限/SQL 问题（可重试）；HTTP 失败要区分“未配置、鉴权失败、超时、业务拒绝”。建议在告警文案里就区分这两类，避免运维按同一套预案处理。
4. **时间基准要对齐。** 查库看到的是对方写入时间，HTTP 返回的是对方采样时间；在线数据还要与培养开始时间、补液任务时间对齐。三者不统一时，图表会出现“数据在但时间错位”的假象。
5. **历史回补能力不对称。** 查库天然可回补；HTTP 占位链路在客户客户端未定时无法承诺回补，需要在业务上先约定“缺口可标记、不做静默插值”。

### 5.2 组合是否会造成运维麻烦

会造成，但麻烦集中在**配置与可观测性**，不在技术栈数量。现有代码已有两个抓手可复用：
- 通道注册：`LabCommunication`（子系统 IP/端口/管道名）+ `M02RegisteredCommunicationConfiguration`（各适配器独立通讯配置）；
- 证据归档：`CustomerRawTransport` 的请求/响应落盘 + SHA256；`M05DispatchStore` 的派发记录。

建议（非需求强制项，落地前需产品确认）：把“设备接入总览”做成一张表——通道类型、地址来源（库/HTTP）、最近成功时间、数据新鲜度、最近错误分类。否则查库链路的“静默失败”会是最难定位的一类问题。

## 6. 定稿后各通道的落地缺口

> 本节是“要通还缺什么”的清单，按“外部输入 → 内部先做什么 → 状态”三段写。状态用 AGENTS.md §13.2 词表，**不得在实现前表述为“已对接”**。

### 6.1 小试离线检测（查库）

**缺的外部输入**
- 数据库地址、端口、库名、账号（**只读权限**，且需明确是视图还是基表）；
- 订单/任务表与结果表的**表名 + 字段映射**（`sample_no` ↔ `SampleID` 已有一处映射，其余待补）；
- 字段字典：枚举、单位、空值语义、作废/重测标志；
- **时间基准**：对方写入时间是本地时间还是 UTC、是否有服务端时区偏移；
- 数据保留周期与归档策略（决定增量窗口）；
- 网络与防火墙策略（本系统到对方库的连通性）。

**内部要先做的**
1. 只读查询组件：独立只读数据源（不复用业务主库连接池），SQL 只查不写，超时与最大返回行数受限；
2. 增量策略：按“写入时间/自增 ID”水位线拉取，水位线持久化，重启不丢；对无时间字段的表用“上次最大 ID + 唯一键”兜底；
3. 失败重试：连接失败可重试（指数退避、上限），SQL/权限错误不重试（直接告警）；重试不改变业务状态；
4. 数据新鲜度监控：按设备记录最近写入时间，超阈值告警（见 §5.1 第 1 条）；
5. 幂等：结果写入以唯一键去重，重复拉取不重复落库。

**状态**：`BLOCKED_INPUT`（缺库连接与表/字段映射）。结果侧可先复用现有 `cdp_` 查表逻辑，但订单侧必须等输入。

### 6.2 中试补液（接口 + 空实现，倾向 HTTP）

**缺的外部输入**
- 客户提供的 **HTTP 客户端或协议文档/SDK**（含 base-url、路径、报文结构）；
- **鉴权方式**（Token/证书/签名/HMAC）与密钥分发方式；
- 罐号↔设备号↔点位映射；
- 超时、重试、限流约定；
- 泵速写后的**回读确认口径**与允许偏差；
- 错误码全集与“受理成功 ≠ 执行成功”的判定规则。

**内部要先做的**
1. 接口定义：读罐数据、写泵速、读地秤、查服务状态、重启（方法签名先定，实现可为空）；
2. 空实现必须返回“未接入”的明确结果/异常（见 §7），不得返回空对象或假成功；
3. 超时与幂等约定写进接口契约：写泵速必须带幂等键（任务 ID + 泵号 + 目标值），重复调用不重复执行；
4. 事务边界：外部调用不得包在本地数据库事务内（现有 `M02HttpDeviceCommandAdapter` 已有此约束，可作为范例）；
5. 证据归档：沿用现有“请求/响应原文 + SHA256”的做法。

**状态**：`BLOCKED_EXTERNAL`（缺客户客户端/协议）。现有 `futurefab-feeding-customer-adapter` 只能作为参考实现，不对外宣称已对接。

### 6.3 在线数据（接口 + 空实现，倾向 HTTP）

**缺的外部输入**
- 客户客户端或接口文档（Inno / LDMS / OPC 采集服务任一）；
- 鉴权方式（Inno 为请求体 `Request.Token`，需 Token 获取与刷新流程）；
- 设备/实验室标识映射（Inno 的 `LabKey`、LDMS 的 `devId`）；
- 指标映射表（pH/DO/温度/MFC/搅拌/重量 ↔ 对方字段名与单位）；
- 采集频率下限、数据延迟上限、历史回补接口；
- 时序数据的保留周期。

**内部要先做的**
1. 接口定义：按设备 + 指标 + 时间范围取数（单设备/批量两种粒度先定一种）；
2. 空实现返回“未接入”，并区分“无数据”与“未接入”两种语义；
3. 落库模型：时序表（设备、指标、时间戳、值、单位、来源）先建结构，不建采集器；
4. 聚合口径：12/24/48/72/144 档位在查询侧实现，采集侧只存原始粒度（避免双重聚合误差）；
5. 失败与补采：接口契约里预留“按时间范围补采”的方法。

**状态**：`BLOCKED_EXTERNAL`（缺客户客户端/协议文档）。

## 7. 空实现的风险（建议，仅写契约，不改代码）

接口已定、实现为空，是本期中试/在线两条通道的正常状态。风险不在“空”，而在**上层误以为已接通**。

建议在接口契约里就把以下几条写死：

1. **返回值语义**：空实现必须返回明确的“未接入”结果（例如专用错误码/状态枚举 `NOT_CONNECTED`），**不得返回空列表、空对象、0 或 `true`**。空列表会被业务当成“今天没有数据”，0 会被当成真实测量值，`true` 会被当成执行成功——这三者都是伪造成功。
2. **异常而非静默**：对“必须成功才能继续”的动作（写泵速、下发检测订单），空实现应**抛业务异常**并带可读文案（“该通道尚未接入，请联系管理员”），让上层走失败分支而不是继续推进状态机。
3. **健康检查**：不允许空实现参与“全部正常”的健康聚合；应单独暴露“未接入”状态，避免监控面板误报。
4. **日志与审计**：空实现每次被调用都要留一条 WARN 日志（谁、什么参数、哪个通道），便于发现“有人提前调了未实现接口”。
5. **契约冻结**：接口签名一旦定稿，后续客户客户端接入时只允许换实现，不允许改签名；若必须改，按变更流程处理，避免前后端/调用方反复适配。
6. **防误用开关**：建议在配置层提供“通道启用”开关，默认关闭；未启用时调用直接失败，启用后才允许走真实实现。

以上仅为建议，具体落点在后续“接口定义 + 空实现”的开发任务中，本文不改任何代码。
