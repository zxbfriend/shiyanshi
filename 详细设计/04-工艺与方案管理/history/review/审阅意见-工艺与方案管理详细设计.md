## 1. 总体评价

本模块在 M01 基础上进一步成熟，核心亮点：

1. **不可变版本模型设计优秀**：`prc_template`（身份/管理状态）+ `prc_template_version`（不可变内容+查询投影）+ `prc_template_binding`（按稳定 slotKey 固定来源版本与有效参数）+ `prc_template_version_model`（型号投影）+ `prc_template_import_map`（核准溯源）。五表职责干净，把"模板定义"与"培养使用快照"彻底分离（快照归 M03），避免了最常见的"改模板影响历史培养"陷阱。
2. **Q01—Q14 业务确认记录质量极高**：每条含问题背景、用户确认、理由、示例、技术落点、同步范围，是后续编码与验收的直接依据。Q01/Q02/Q03 组合把"嵌套版本冻结 + 禁用可沿用 + 实验室边界"讲透。
3. **强反伪造立场**：派生值服务端重算、只读历史快照（itemSnapshot/resourceSnapshot）从可写 DTO 严格剥离、hash 双重区分（canonicalHash vs effectiveHash vs packageHash）、`derived_from_binding_id` 服务端取证、RETAIN/SELECT/RELOAD 由服务端证明而非客户端自报。
4. **"模板保存通过 ≠ 设备可执行"贯穿始终**：Q11 灌注量程分阶段校验、PID 工程资料未核准即阻断、资源事实 UNKNOWN/INCOMPLETE 不假成功、Cedex 稀释能力使用时复核。这是设备类系统最容易翻车的地方，本稿守得很稳。
5. **静/动态校验分离**：Q08 取测 60 分钟冲突在模板保存时静态校验、任务生成时再次重检；模板保存不生成任务、不下发命令、不启动监控。
6. **SQL 工程规范**：5 表/67 列/24 条 CHECK/0 外键；前置核验（9 项守卫）→ 受保护建表（同连接+目标不存在）→ 后置核验 → 空表专用回退（先数行再 DROP、需人工确认变量、拒绝外键引用）。

规模统计（已核验）：六类模板、23 个 HTTP 目标接口 + 3 个内部服务、36 个功能码、5 表 67 列 24 CHECK、48 条存储用例、各类验收用例合计约 280 条。

## 3. 评审发现（P1 / P2）

### P1-1 ⚠️ Q13 + Q14 组合可能导致实验室类型变更被永久冻结

推导链（均出自本稿已确认内容）：
- M02-Q18：更改实验室类型前必须先移除工作流配置；
- Q14：清空需目标实验室**所有**待移除一级流程都无任何培养引用；
- Q13：引用范围包含已结束、已取消、**历史**培养；
- §12.1 明确："M03 逻辑删除培养也保留已存在的引用"。

**结论**：任一实验室只要曾经有过任意培养引用过任意一级流程节点，则永远无法清空工作流配置 → 永远无法更改实验室类型。且逻辑删除培养不解除引用，冻结是永久性的。

Q13 用户已确认"所有培养引用"范围，但**本稿未显式提示这一组合后果，也未提供例外路径**（如审批制强制变更、引用归档/迁移、超管核准覆盖）。
- 建议：评审时向业务方复述该后果并确认是否为预期；若非预期，需补充例外的申请/审批/审计路径与引用归档方案。

### P1-2 单 SYSTEM 管理守卫全局串行（继承自 M01 P1-1）

M04 复用 M01 `sys_management_revision` 单行守卫，模板保存/启停/删除/工作流配置/清空全部串行。M04 管理写频率（36 个功能码、六类模板高频编辑）高于 M01，风险更大。本稿仅写"接受 M01 已确认的跨页冲突"。
- 建议：与 M01 统一评估，给出压测阈值与拆分方案（按对象类型分 scope_key）；或明确 M04 上线后的并发预期。

### P1-3 可实施性受 7 项外部依赖约束，需明确"不可开发清单"

工程交接表 M04-DEP01—07 诚实标注未闭合，但目前状态下：
- **DEP03**（PID 工程资料、型号能力、体积规格、料桶字典映射）阻断 Config/灌注保存校验；
- **DEP02**（M02 `model_dict_code`、字典条目、逐实例映射）使 API13/14 在此之前返回 `RESOURCE_MAPPING_UNRESOLVED`；
- **DEP05**（M03 快照物理存储）阻断第 12 节固定包交接；Q13 引用未就绪时工作流移除/清空返回 `WORKFLOW_REFERENCE_UNAVAILABLE`。

- 建议：把"依赖未闭合的功能"显式列为**暂不可进入编码/联调**清单，避免把"接口已命名"误解为"功能可投用"。

### P2-1 存储契约章节编号缺失第 16 节
`模板内容存储契约.md` 由 §15（701行）直接跳到 §17（706行），缺 §16。属编辑残留。
- 建议：补编号或说明删除原因。

### P2-2 名称长度规则无数据库兜底
`template_name`/`live_name` 为 varchar(50)，CHECK 仅 `CHAR_LENGTH(TRIM(name))>=1`；而页面规则为 2—50 字（Config/灌注/取样/自动控制/补液）或 1—19 字符（泵速）。类型专属长度完全依赖应用层，DB 无兜底，泵速 1—19 与列宽 50 差距较大。
- 建议：若需强约束，可考虑按类型 CHECK 或在字典中明确"列宽为技术上限、业务下限由应用层强制"。

### P2-3 泵速策略 UI 无复制入口，但 API08 通用支持复制
§5.6.1 称"原文未列复制按钮，本页不新增必交付复制入口"；而 §9.4 API08 对六类模板通用开放复制。
- 建议：确认泵速是否允许复制（Q01 复制沿用嵌套内容的规则对无嵌套的泵速同样适用），或明确 API 层对 PUMP_SPEED 暂不开放。

### P2-4 旧数据导入工具未实现
`prc_template_import_map` 与核准要求已完整设计，但交付说明明确"工具未实现、真实核准行未提供"，且 NPP 高速占比 85 等旧值不允许自动截改。历史迁移目前为阻断态。
- 建议：纳入独立排期，不与 M04 编码混同验收。

### P2-5 24 条 CHECK 为基础约束（已声明，非缺陷）
JSON 合法性、hash 真实性、六类叶子业务校验仍需应用层验证器。本稿已明确说明，此处仅提醒验收时勿以"CHECK 通过"代替业务校验通过。
