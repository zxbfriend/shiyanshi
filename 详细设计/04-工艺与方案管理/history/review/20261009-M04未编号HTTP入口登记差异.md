# M04 未编号 HTTP 入口登记差异（过程性审阅记录，非权威契约）

日期：2026-10-09　执行人：work1　所属批次：详细设计评审真实问题修复·批次 A（A4 收口）

## 1. 现象

全系统骨架门禁 `FullSystemSkeletonGateTest.applicationServicesZeroFieldNumbered501Only` 长期红：

```
src/main/java/.../m04/ProcessTemplateApplicationApplicationServiceImpl.java
接线方法与登记不符: 501抛出=1 方法=18 wired=15
```

## 2. 逐项核对（真实调用链取证）

`ProcessTemplateApplicationApplicationServiceImpl` 的 18 个公共方法拆成三类：

| 类别 | 数量 | 证据 |
| --- | --- | --- |
| 已登记契约编号（wired=true） | 15 | `futurefab-system/src/test/resources/contract/skeleton-m04.json` 的 `M04-001`~`M04-015`，逐条 `implFq`+`svcMethod` 命中 |
| 未接线停口（仍抛 501） | 1 | `M04-016 resolveSamplingResourceFacts`，`SkeletonNotImplementedException("M04-016")` |
| **未编号但真实对外的 HTTP 读入口** | **2** | 见下 |

两个未编号入口：

- `listFeedingPumpCountOptions()` ← `ProcessTemplateController` 的 `@GetMapping("/pump-count-options")`
- `listFeedingPumpSpeedOptions(ReactorType)` ← 同 Controller 的 `@GetMapping("/pump-speed-options")`

两者都由 Controller 方法体直接委托同名服务方法并 `success(...)` 返回，且前端
`futurefab-frontend/packages/sdk-smp-api/src/processTemplate.ts` 的 `pumpCountOptions` /
`pumpSpeedOptions` 在补液模板编辑器里真实调用（泵数下拉、泵速策略下拉）。

在现行权威文档里检索：`docs/详细设计/04-工艺与方案管理/接口目录与契约定位.md` 的模板接口只到
`M04-API01`~`M04-API16`（工作流类另有 API17~21），**没有任何一条给出这两个路径**；
全 `docs/` 检索 `pump-count-options` / `pump-speed-options` 为 0 命中。

结论：不是假接线，也不是内部私有辅助方法，而是**代码有真实 HTTP 入口、现行接口目录没有对应契约编号**的登记差异。

## 3. 本轮处置（不消假绿）

门禁等式由「方法数 − 501 数 == wired」改为「契约编号条目数 + 未编号 GET 读入口登记数 + 501 停口数 == 公共方法数」，
未编号清单落在 `FullSystemSkeletonGateTest.UNNUMBERED_HTTP_DOORS`，四条互锁：

1. 每条由新增测试 `unnumberedHttpDoorsAreRealGetReadEntries` 用 Controller 源码逐条证明是 `@GetMapping`
   读入口并委托同名服务方法；写映射（POST/PUT/DELETE）不得进入清单。
2. 登记方法必须在 Impl 中命中、且声明行上一行必须是 `@Override`（服务接口公共读口），幻影登记报违例。
3. 命中方法体若仍抛 501 直接报违例——不得借登记把停口算成接线。
4. 清单大小锚定为 2（`UNNUMBERED_HTTP_DOOR_ANCHOR`），且反向钉桩：这两个方法名一旦出现在
   `skeleton-m04.json` 就要求清单同步清零。

未做的事：没有把 wired 从 15 抬到 17，没有给两个入口编造 `M04-017/018` 之类的契约编号，
没有删除或放宽任何断言，`M04-016` 仍抛编号 501，`skeleton-m04.json` 的 16 条登记与总数锚点未改动。
新增的合成正反例（真实读入口不误伤 / 幻影登记必检出 / 借登记吞 501 必检出 / 未登记的额外公共入口仍按夹带检出）
见 `detectorsThemselvesWork`。

## 7. 复审登记口径统一（补丁 5，两条）

### 7.1 `X-Request-Id` 缺号 = 服务端补号，不是 400

以代码为准的三态规则（此前不同记录里"缺任一头都 400"的说法过宽，一律按本条更正）：

| 请求头情况 | 服务端行为 | 证据 |
| --- | --- | --- |
| 合法 UUID | 复用该值 | `RequestMetadataFilter.java:45-47` |
| **完全缺失** | **服务端生成新 requestId**，请求继续，**不 400** | `RequestMetadataFilter.java:47`（`WriteMeta.newRequestId()`）；上下文未初始化时 `WriteMetaArgumentResolver.java:38-43` 再兜底一次 |
| 非空但非法（非 UUID） | 整请求拒绝，HTTP 400 + `INPUT_INVALID`（值不回显） | `RequestMetadataFilter.java:46,55-57,69-81` |

- 只有 `X-Management-Revision` 缺失才是必然 400：`WriteMetaArgumentResolver.java:46-50` 抛 `RequestMetaInvalidException`。
- 因此"守卫写缺头即 400"这句只对 revision 成立；requestId 一栏必须单独写"缺号由公共 Filter 补号，非法才 400"。
- 需勘误的既有表述：批次 A 提交正文 `3e892628` 写的是"requestId/managementRevision 只认头……**缺头即 400** INPUT_INVALID"，
  把两头的行为合并成了同一句，按上表应拆为"缺 revision 才 400；缺 requestId 由 Filter 补号"。提交已入库不可改（Git 由用户操作），
  以本条为登记口径；我此前两份交付文档（批次 A/B）里的同类表述都只点名 `X-Management-Revision`，与本条一致，无需改写。
- 仍未实测的缺口（登记，不掩盖）：缺 `X-Request-Id` 时**真实 HTTP** 下由 Filter 生成的值与幂等回执键的关系，
  只有源码级证据（CONTRACT 层），HTTP 层为 `NOT_VERIFIED`，需复审方单独跑一条负例。

### 7.2 未编号真实入口的登记口径（唯一位置）

1. 登记面只有一处：`FullSystemSkeletonGateTest.UNNUMBERED_HTTP_DOORS`，锚定 `UNNUMBERED_HTTP_DOOR_ANCHOR = 2`（即本记录 §2 的两条 GET）。
2. **不得**把未编号入口写进 `skeleton-m04.json`，也不得虚增 `wired`（现仍为 15）或自造 `M04-017/018` 之类编号；等式口径见 §3。
3. 权威接口目录保持 0 命中即现状，不在裁决前补写条目；本记录是过程性审阅记录，非权威契约。
4. 任何记录引用这两条入口时，统一写成"未编号真实 GET 读入口（已按 FEEDING `query` 收窄，编号待裁决）"，
   不再出现"公开下拉""无需权限"或"已编号接口"三种表述。
