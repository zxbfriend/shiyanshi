## 1. 总体评价

**结论：本系列中技术深度最高、物理安全意识最强的一份设计，可作为评审基线。但必须明确：设计完成 ≠ 可投用——当前状态下真实环境可执行路径为零（P1-1）。**

最突出的优点是**把"业务事实"与"物理事实"彻底分层，且每一层都防住了伪造**：

| 层次 | 设计 | 防伪造点 |
| --- | --- | --- |
| 业务状态 11 态 × 物理相位 10 态 × 结算 4 态 | 三维正交，`businessState` 明确声明是读模型 | "列表状态是业务投影，不能替代物理是否停下、是否已累计" |
| 命令生命周期 | `PREPARED→INVOKING→ACCEPTED/EXECUTED/FAILED/UNKNOWN`，**INVOKING 在网络调用前提交** | 进程崩溃后恢复一律先查原 commandId；UNKNOWN 先查不重发 |
| 回执语义 | ACCEPTED ≠ EXECUTED | "SET_SPEED 回读成功不足以证明物理泵速已达到；STOP 需实际速度/停止位与秤稳定证明" |
| 计量方向 | `rawDifference` 保持带符号 | "不得 `abs(rawDifference)`，否则返水会被算作补入" |
| 缺值处理 | 全部传 `null` + 原因 | "不用 0 代替未知"；"UNKNOWN 实际值不写 0"；"不把重启时当前量冒充 00:00" |
| 读数窗口 | 阶段/暂停/换 session 即截断重建 | "缺少窗口边界可比读数时不插值伪造稳定" |
| 账本 | 按 `(executionId, settlementKind)` 唯一结算，更正只追加 ADJUSTMENT | "事件重放不能重复累计"；"已经发生部分入罐即使最终异常也不能消失" |

其次是**公式全部可复算且经本次审阅数值重算完全正确**（见 §2），并给出了带完整中间值的算例——这在工程上极其罕见，通常设计只写公式不写算例，或算例与公式对不上。

第三是**Q01—Q04 业务确认被固化成服务端常量而非可配置开关**：`queueScope=CULTURE`、`feedingCompletionPolicy=TERMINAL_INCLUDES_CANCEL`、`dailyGenerationPolicy=ONCE_PER_RULE_DAY`，且明确"服务端设置并拒绝其他值，不提供实验室自行切换入口"。这是防止"配置漂移绕过已确认业务规则"的正确做法。

## 3. P1 需评审拍板

### P1-1　EXT01—EXT05 全部未核准 → 本期真实可执行路径为零（最需拍板）

**证据链**：主设计 §6 列出 5 项未完成输入及其"缺失时行为"：

| 编号 | 缺失项 | 缺失时行为（原文） |
| --- | --- | --- |
| EXT01 | NCS061 最小补糖阈值、单位、版本 | 动态补糖返回 `THRESHOLD_UNVERIFIED`，**不创建任务** |
| EXT02 | 小试当前重量由 SMP 还是 PLC 写入 | **未核准 writerMode 不可双写或启动依赖该数据的真实任务** |
| EXT03 | 秤净/毛重、皮重位置、正负方向、精度/新鲜度、稳定判据 | 保留 UNKNOWN；**读数不能驱动计算/停泵完成** |
| EXT04 | 各设备 Speed 代码/量程/校准换算、幂等/查询/停止回执、watchdog | **未验证能力不启用相应执行路径** |
| EXT05 | 50L 袋皮重原图核准 | 该实例保持未就绪 |

而 `任务状态调度与异常恢复.md` §3 规定的**启动前 13 项检查**中，至少 4 项直接依赖上述未核准项：
- 读数质量/新鲜度/稳定性 → **EXT03**
- 最终目标和阈值 → **EXT01**
- 袋内可用量 → **EXT05**
- 速度量程 → **EXT04**

**后果（必须明确写进评审结论）**：在 EXT01—05 核准前，**任何一条补液任务都无法通过启动前检查**，即：
- 0 条任务可启动 → 0 次实际补料 → 0 笔账可结算；
- 按规则动态补糖（M07-REQ04 核心能力之一）**完全阻断**；
- 小试依赖当前重量的任务（W03—W08 及全部小试任务）**完全阻断**；
- 停泵完成无判据 → `CASE073` 明确"通讯失联/watchdog 未验证 → 进入未知隔离及现场处理，**不宣称自动安全停止**"。

现状核对 §4 亦自认："独立采集与控制适配器的厂商协议、接收/执行证据、fence、watchdog 及恢复能力须有对应验收；**文档设计不能替代这些能力**。"

**评价**：失败关闭的立场完全正确，绝不应为了"先跑起来"而填默认阈值——设计在这点上的克制值得肯定。问题在于 **EXT01—05 没有责任人、没有时点、没有验收标准、没有"部分投用"的切分**，而验收 §3 只把它们记为"原有外部依赖，缺项只阻断依赖其事实的真实能力"。

**建议**：
1. 将 EXT01—05 提升为带责任人与日期的《现场核准清单》，逐项写明：谁核准、以什么证据核准、核准后影响哪些 CASE。
2. 明确切分**可离线验收的部分**（公式、状态机、不可变快照、迁移/回退、权限、Q04 额度）与**必须实机的部分**（读数方向、Speed 映射、停泵判据、watchdog、fence），前者现在就能推进，后者给出门禁。
3. 明确 EXT01—05 全部未决时的对外表述：**M07 设计完成但不可投用**，避免被误读为"补液功能已就绪"。

### P1-2　多实例部署被明令禁止，但无部署拓扑决策与 fence 验收标准

**证据链**：
- 泵速契约 §3："**只有 DB CAS 而设备网关不支持拒绝旧 epoch 不足以保障单执行者；该能力未实现时不能部署多实例主动控制同设备。**"
- `CASE072`："只有 DB 锁没有设备 fence ｜ 多实例真实控制保持未就绪。"
- 现状核对 §2："WinForms 单实例 Mutex **不适用于多实例 Java**。"
- 主设计 §1："沿用 futurefab-system 领域服务及独立运行适配器，**不要求新建一个 Maven 微服务**。"

**冲突点**：M07 不新建微服务 → 运行在 `futurefab-system` 内；而 `futurefab-system` 作为微服务通常按多副本部署。设计禁止多实例主动控制同设备，但**没有给出部署拓扑决策**：
- 是"控制面多实例 + 执行器单例"？
- 还是"必须等设备网关实现 fence 后才允许扩副本"？
- 或者"按设备分片（每个副本只控制固定设备子集）"？

同时 `fence` 能力本身是 EXT04 的一部分（"幂等/查询/停止回执"），两者耦合但文档未打通。

**后果**：这是会在**生产部署阶段**才暴露的阻塞项，届时改造成本远高于设计阶段。

**建议**：在 §6 或运维章节补一节《部署拓扑与 fence 验收》，明确上述三选一、fence 的验收判据（如何证明旧 epoch 被拒）、以及 fence 未就绪时的降级部署形态（如固定单副本 + 快速故障转移）。

### P1-3　高频写入表无保留期、归档策略与容量估算

**证据链**：
- 全文检索 `保留期 / 归档 / 容量估算 / 清理 / purge / retention / 历史表`：**0 命中**（仅命中"W08 废液清理""清理旧表"等无关语义）。
- 但本模块是**全系统写入量最大的模块**：
  - `run_execution_sample`（16 列，含 `raw_readings` JSON 数组）按 `intervalSeconds` 连续采样；
  - `run_command`（22 列）每次物理意图一条 + `result_evidence` 每次新证据写 event；
  - `run_event`（17 列）**兼审计与发件箱**，"对象具体形状限本表模式"，且 `publish_*` 可变 → 会被 UPDATE 而非纯 INSERT。
- 字段字典称"历史活动槽不物理删除""资源 fence 释放后仍保留递增值"，即**只增不减**是既定设计。

**后果**：长期运行下三表无界增长，且 `run_event` 被 UPDATE 会阻碍单纯按月分区的归档方案。

**建议**：给出保留期分级（如原始样本热数据 N 天、事件 M 年、命令与账本永久）、归档形态（分区 + 历史库）、以及按"培养数 × 采样频率 × 运行时长"的容量估算表。这是唯一一条在 M05 审阅中已提出、M07 同样存在且更严重的问题，建议跨模块统一处理。

## 6. 建议的签署前动作

1. **决议 P1-1**：产出《现场核准清单》（EXT01—05 逐项：责任人 / 证据形式 / 时点 / 影响 CASE），并明确"可离线验收"与"必须实机"的切分与门禁。
2. **决议 P1-2**：确定部署拓扑（执行器单例 / 设备分片 / 等待 fence），给出 fence 验收判据。
3. **决议 P1-3**：给出保留期分级、归档形态与容量估算（建议与 M05 合并处理）。
4. **隔离库迁移演练**：`01 → 02 → 03`，确认 18 表 / 314 列 / 48 CHECK 落地；再演练 `04` 回退的 21 道守卫（故意破坏任一条件，确认均被拒）。
5. **离线可验收部分先行**：公式算例（CASE031—037）、状态机与 Q04 额度（CASE041—049、083—088）、权限与八流程（CASE001—018）可在无设备条件下完成。
6. **实机部分待 EXT 核准后**：泵速/恢复/停泵（CASE063—076）与设备联调，按"先离线故障注入、再逐型号实机"的顺序。
