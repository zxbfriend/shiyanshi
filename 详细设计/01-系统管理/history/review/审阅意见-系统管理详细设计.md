## 1. 总体评价

这是一份**达到评审稿水准**的业务模块详细设计，严格遵循 `00-编写规范与公共约定.md` 的必备章节（范围、业务规则、状态机、页面交互、数据库、接口、时序、一致性恢复、运行验收）。其突出优点：

- **安全底线扎实**：口令/令牌/挑战/密钥明确禁止进入日志与 DTO；bcrypt 比较而非摘要字符串比较；历史防重；脱敏白名单。
- **状态建模清晰**：账号 `status` / `del_flag` / `locked_until`（派生锁）/ `online`（派生会话）四类互不混淆；密码状态 `INITIAL/EXPIRED/EXPIRING/VALID` 为派生值，**不新增库列**。
- **并发与失败处理有时序图支撑**：单终端会话、并发替换、在线过期重认证、改密历史防重均有 SEQ 图与失败分支。
- **数据库工程到位**：无外键、生成列唯一键支持软删除后重建、撤销/回退保留失败版本不 `DROP`、迁移脚本带 preflight 守卫与显式"未评审不执行"开关、备份表与逆序回退脚本齐备。
- **需求闭环完整**：REQ/UI/API/表/状态/CASE 相互对应，验收用例 C01–C24 覆盖广。
- **反复声明"设计稿 ≠ 运行验收"**，符合规范，未把文档产出伪装成可交付。

## 3. 评审发现（按 P0 / P1 / P2 分级）

### P1 — 签署编码前建议澄清/压测

**P1-1 单 SYSTEM 管理版本行作全局写锁的并发瓶颈**
`sys_management_revision` 固定一行（scope_key='SYSTEM'），所有组织/角色/用户/字典/参数写均串行于该行（设计 17.1、23）。文档已承认"全局粗粒度冲突是本稿技术选择，管理量较低且先保证树/授权一致性，需压测后再决定是否拆分守卫"。
- 建议：在评审结论中明确"上线前按实际管理并发压测"；给出拆分守卫的触发阈值与方案，或在设计中补充降级策略（如按对象类型分 scope_key）。

**P1-2 `sys_user_password_history.id` 生成规则未钉死**
表主键为 `varchar(20)`（基线 ymsw.sql 用 '1'/'2' 类字符串）。迁移用 `LEFT(SHA2(...),20)` 生成 BASELINE 行，但新建用户 `INITIAL_CREATE` 与每次改密的历史行 **id 由谁生成、格式如何文档未指定**（仅写"复用扩展"）。若新应用沿用雪花 ID 字符串需确认长度 ≤ 20。
- 建议：在字段字典或第 9 节明确 history.id 的生成规则（与 user_id 雪花 ID 一致或独立方案），避免实现期各写各的。

**P1-3 M02 用户授权契约未实现即被 USR 依赖**
用户编辑/新建的 `authorizedLabIds` / `labAuthorizationVersion` 依赖 M02 内部契约 `LabAuthorization`（设计 20 节，已标注"未实现"）。在 M02 设计完成前，用户新建/编辑缺少授权闭环。
- 建议：第25节验收矩阵补充 M02 联调前的降级处理（如授权字段仅持久化、不校验），并标注 USR 相关用例为"待 M02 联调"。

### P2 — 观察项 / 文案对齐（不阻塞签署）

**P2-1 order_num 目标默认值不对称且迁移未强制对齐**
- 字典/07：venue `order_num` 默认 1、dept `order_num` 默认 0。
- `VenueSave` 不传 orderNum（依赖 DB 默认 1）；`DeptSave` 传 orderNum（默认 1，但 DB 列默认 0 实际不被用到）。
- DD02 迁移未 ALTER 这两个 `order_num` 默认值，故"目标结构(07)"与"实际迁移后结构"在默认值的口径上可能不一致（取决于当前库默认值）。
- 建议：在 DD02 显式 `ALTER ... order_num` 对齐 07，或在 07 头部注明"仅参考、以迁移脚本为准"。

**P2-2 `is_default` 字典项默认值无 API 设置入口**
`DictDataSave` 不含 `is_default`，恒为 'N'。文档 3.14 提及"同一类型/父项最多一个有效默认"，但当前无任何接口可设置默认值。
- 建议：确认是否需 DIC 接口支持 `is_default`，或明确由初始化数据写入、不接受运行期设置。

**P2-3 `status` 注释措辞文档与 DDL 略有差异**
如 `sys_oper_log`：字典写"0成功/1失败"，DDL 注释写"0正常/1异常"；值一致、无功能影响。
- 建议：统一注释口径，避免后续维护误解。

**P2-4 `sys_management_request.expires_at` 为 NOT NULL 且无 DB 默认**
完全依赖应用填充 `now+24h`（设计 3.22）。属内部表，风险低。
- 建议：在内部契约注明"由管理服务必填"，或评估加生成列默认。

**P2-5 迁移部分失败恢复与整批回退脚本存在操作张力**
文档写"01部分失败按已完成语句清单逐项恢复"，但 03/06 整批回退脚本 preflight 会因 `sys_user_auth_state` / `m01b2_*` 已存在而直接报错。
- 建议：在 03/06 头部补充"部分失败后必须人工清理已建对象再重跑，严禁直接套用整批回退"，降低误操作风险。

**P2-6 文档体量巨大，建议分批签署**
登录功能组（第1–13节）与系统管理功能组（第14–25节）集中于一份。质量高但一次性大评审易遗漏。
- 建议：评审时按功能组分批签署，每批带独立结论。

## 4. 设计亮点（值得肯定）

1. **安全建模**：口令/令牌/挑战/密钥不进日志；`authProof` 仅服务端持有、绝不返浏览器；`X-Login-Challenge`/`X-Auth-Proof` 禁记日志；`oldPassword/newPassword/confirmPassword` 排除出通用 `@Log`。
2. **派生状态不落库**：密码四态为派生值，避免库列与逻辑漂移；账号/锁/会话/在线四类明确分离，杜绝"压成一个 status"。
3. **软删除后可重建**：生成列 + 唯一索引在 `del_flag='0'` 时生效、删除后 NULL，允许同名重建而不占唯一键，且保留历史。
4. **迁移安全工程**：preflight 守卫、显式 `@dd01_reviewed=0` 防误跑、原样备份表（`dd01_bak_*`、`m01b2_*`）、回退保留失败版本不 `DROP`、前置检查遇冲突即停"不自动删重"。
5. **需求–设计–验收闭环**：REQ/UI/API/表/状态/CASE 五维对应，C01–C24 覆盖登录/组织/角色/用户/字典/参数/日志/幂等/迁移/集成。
