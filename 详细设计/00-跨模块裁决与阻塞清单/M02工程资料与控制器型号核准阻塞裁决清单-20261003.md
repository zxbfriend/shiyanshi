# M02 工程资料与控制器型号核准实施阻塞裁决清单

2026-10-03。M02 长期开发负责人（电脑2）批次二开工前盘点。范围：M02-225 `GET /system/lab/engineering/profiles`、M02-226 `POST /system/lab/engineering/profiles`、M02-227 `POST /system/lab/controllers/{connectionId}/model-verification`、ENG-I01（SVC-M02-E01）`resolveEngineering`。

**结论：四条链路当前都不可在不臆造口径的前提下落码。** 下列 9 项中 D-1—D-5 属设计文本互相冲突或关键集合未登记（必须设计裁决），D-6—D-7 属共享登记窗口与菜单基线（必须总控协调），D-8—D-9 属外部事实源与公共外壳（分别由用户已下达的暂停裁决与 M01 承载）。代码面已逐项核对：三条接口的 Controller/ApplicationService/DTO/VO 骨架、两张目标表的开发基线 DDL 与拥有方登记均已就位，缺的只是判定口径，不是文件。

## 1. 作用域身份与哈希输入（D-1、D-2、D-3）

### D-1 INSTANCE 作用域是否同时携带型号对

| 证据 | 口径 |
| --- | --- |
| `工程资料维护与解析逐接口契约.md:11` | MODEL 只带 kind/modelKind/modelId；**INSTANCE 必须 modelKind/modelId 为 null** |
| `控制器型号与工程参数收尾契约.md:15` | “MODEL必须只有型号对有效，INSTANCE必须只有设备对有效”（与上一行一致） |
| `service/port/m02/model/EngineeringScope.java:8,17`（PKG-00 §6.2 冻结 Port 输入） | “kind=INSTANCE 时五个判别字段均须构成唯一、互斥的作用域”，字段注释“**MODEL 与 INSTANCE 作用域均按已登记型号种类取值**” |

冲突后果不是措辞问题：`scope_key=SHA256(scopeKind,modelKind,modelId,deviceKind,deviceId)`（`收尾契约.md:15`）是 `lab_engineering_profile.uk_close_engineering_scope` 唯一键（`docs/开发基线/01-完整建表.sql:1387,1399`），也是 M02-225 读取和 226 写入的唯一定位入口。两种口径生成的 scope_key 不同，一旦按其中一种建数据，另一种口径下全部读不到且无法在线纠正（唯一键不可双写）。另外 ENG-I01 §5 的 INSTANCE 解析“先取型号版本再叠实例版本”，若输入不带型号对，服务端必须先从设备实例反查其型号，这条反查链在两份 HTTP/DDL 文档中没有任何登记。

可选方案：a) 按 HTTP 契约互斥口径，INSTANCE 只带设备对，服务端用 deviceKind/deviceId 反查型号身份后再叠加；b) 按 Port 注释口径，INSTANCE 同时带型号对与设备对，HTTP 判别联合与 404/400 规则随之改写。
**倾向 a**（HTTP 契约与 DDL 注释两处一致，Port 注释只有孤立一句，且 226 的判别联合 Body 已按 a 冻结）。需设计确认，并同步修正 `EngineeringScope.java` 注释。

### D-3 deviceKind 取值集合与身份存在性表映射

M02-225 规定“身份对象不存在/无权才404，无 profile 返回 200+INCOMPLETE”（`逐接口契约.md:15`）。要实现这条，服务端必须能按 deviceKind 判定实例身份是否真实存在并取归属实验室。现有登记互相矛盾且不足：

- `service/port/m02/model/DeviceRef.java:8` 列出 9 种：BENCH_REACTOR/INTEGRATED_REACTOR/CONTAINER/FLOOR_SCALE/DETECTOR/PERISTALTIC_PUMP/AIR_PUMP/ANALYZER/BENCH_CONTROLLER；
- `domain/vo/m02/DeviceRef.java:12` 却登记“取值组合源自 Identity v1 设备字段，**外部结构未逐项命名**”；
- 两份工程契约从未给出 deviceKind 枚举，也没有 kind→实例表→labId 的映射登记；M02 现有代码里也没有可复用的跨 9 设备表身份解析器（`service/impl/m02/` 无 DeviceRef/kind 解析实现，通讯配置侧 `service/impl/application/m02/LabCommunicationApplicationServiceImpl.java:109-119` 只登记 DETECTOR/FLOOR_SCALE/DOWNSTREAM_DEVICE 三种，不能借用为工程资料白名单）。

需裁决：工程资料 INSTANCE 的 deviceKind 白名单与逐 kind 的身份表/labId 解析口径（含 ANALYZER 与 BENCH_CONTROLLER 两个非 `lab_*` 单表形态的对象归属）。没有这份映射，225 的 404 分支只能靠猜。

## 2. 响应外壳与判定集合（D-4、D-5、D-9）

### D-4 M02-226 响应 VO

`docs/开发任务/00-全接口契约骨架清单.md:5573` 冻结“响应VO：`MutationResult`”，`skeleton-m02.json:17052` 的 M02-226 `respTypeFq` 同值，骨架门禁按该类型逐字断言服务/实现返回签名（`SkeletonEngine:346,389-392`）。而 `逐接口契约.md:158` 要求成功 data 固定为 `profileId、versionId、versionNo、status、objectVersion、managementRevision、issues`。`MutationResult` 是 PKG-00 §3 冻结外壳，字段集不可增删（`domain/vo/common/MutationResult.java:9-20`），全部可承载字段为 `applied:29、requestId:32、managementRevision:35、objectId:38、objectVersion:41、credentialVersion:44、policyVersion:47、nextAction:50、warnings:53`：**versionId、versionNo、status、issues 四项无处承载**（warnings 只是 `List<String>` 原因码，不含 path/message）。同时该外壳 javadoc `:21` 自己写明“领域设计已声明专用 `*MutationResult` 时以专用类型为准，不强行压成本外壳”，可作为方案 a 的外壳侧依据。

可选方案：a) 改冻结登记为专用 `EngineeringProfileSaveResult`（同步 `00-全接口契约骨架清单.md:5573`、`skeleton-m02.json` 的 `respTypeFq/respFields` 与骨架门禁）；b) 维持 `MutationResult`，把 versionId/versionNo/status/issues 全部降级为“226 提交后由调用方重发 225 读回”，并据此改写 `逐接口契约.md:158`。
**倾向 a**（前端核准页要在同一响应里确认版本与核准状态；b 会诱导并发窗口下用旧 revision 重复提交）。需设计＋骨架登记双方确认，不得由实现侧单方面改 `respTypeFq`。

### D-5 225 读取的 state/issues 判定集合

`逐接口契约.md:15-17` 只说 GET“默认返回当前 profile 及有效解析结果”，且“身份对象不存在/无权才404”，§5 的 `requiredPaths` 明确只属于内部 resolve 入参（`:238`）。但响应样例 `:71-82`（`REQUIRED_PATH_MISSING` 定位 `capabilities.pumpCount`）又在 225 的草稿结果里给出 `capabilities.pumpCount` / `REQUIRED_PATH_MISSING` 这种“按运行用途判定”的缺项。读口没有 purpose 入参，也没有任何文档登记“GET 的默认必填路径集”。

需裁决：225 的 state 是否只按版本状态推导（DRAFT→INCOMPLETE、VERIFIED 且未被撤销→COMPLETE、REVOKED→REVOKED），issues 只报结构/身份/解码问题；还是额外挂一份“默认路径集”（若后者，请给出集合与来源文档）。这决定 225 能否在没有任何核准资料时给出稳定的 200 语义。

### D-9 400 的 fieldErrors 载体

`逐接口契约.md:183-196` 要求 400 响应携带 `fieldErrors` 且必须定位具体 `EngineeringProfile` 路径。当前统一响应外壳没有任何 fieldErrors 构造能力：`service/guard/ManagementGuardExceptionHandler.java:34-42` 只写 `errorCode/retryable/currentManagementRevision`，`futurefab-common/futurefab-common-security/.../handler/GlobalExceptionHandler.java:143-149` 只取第一条字段错误消息、连 errorCode 都不带，全仓 `src/main` 无 `FieldError` 承载类型（仅 M04 的 VO 注释提到“fiel...”，如 `domain/vo/m04/Issue.java:7`）。补齐属公共响应外壳改造（M01/公共 SDK 范围），不能由 M02 自建平行外壳。

需裁决：由公共外壳统一增设 `fieldErrors`，或改写 226/227 契约为“路径定位只进 issues/ message”。在裁决前，实现侧只能把路径定位放进 message 文本，不满足契约字面要求。

补充事实（非阻塞，但登记）：`逐接口契约.md` 多处要求“未知字段拒绝”。本项目 Spring Boot 4 + Jackson 3 的 `FAIL_ON_UNKNOWN_PROPERTIES` 默认关闭，`@RequestBody` 今天会静默丢弃未知字段；实现必须在服务端做白名单结构校验才能满足该条，已在实现面记为必做项，不需要裁决。

## 4. 外部事实源（D-8）

M02-227 的事务内重验要求“已占用、任务未结束或存在 UNKNOWN 物理命令时阻断结构性改映射”（`收尾契约.md:11`、`逐接口契约.md:220`）。UNKNOWN 物理命令事实的唯一提供方是 `DeviceCommandPort`（CMD-I01/I02），该能力已因 §2 三项裁决未落而被明确暂停、不排期（`docs/开发任务/59-M02接口台账与批次计划-20261003.md` §4；56 号报告 §2/§8）；“任务未结束”事实需要 M07 侧占用查询，M02 无本地替代表。缺这一事实就不能实现“判定不可得时 503 RESOURCE_FACTS_UNAVAILABLE”，也不能实现 409 RESOURCE_IN_USE——把 227 落成只查字典的映射写会静默削弱守卫，违反“不得弱化权限/校验”。**227 维持 501，状态 `BLOCKED_EXTERNAL`（等 DeviceCommandPort/M07 事实裁决），M02 不自建第二套物理命令事实。**
