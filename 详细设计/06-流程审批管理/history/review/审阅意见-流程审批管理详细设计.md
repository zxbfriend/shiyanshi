## 1. 总体评价

**结论：设计稿质量高、内部一致性经程序化复核零差异，可作为评审基线。建议签署前先决议 P1-1。**

本模块最突出的优点是**把业务不变量下沉到了数据库约束层**，而不是停留在应用代码约定：

| 不变量 | 落地方式 | 强度 |
| --- | --- | --- |
| DIRECT / DIRECT_REASON 永不生成审批单 | `ck_apr_request_policy` 强制 `$.entry.reviewMode IN ('BATCH','PROJECT')` | DB 级，无法绕过 |
| Q01 职责分离（申请人≠审核人≠批准人） | `ck_apr_request_stage_actors` 三组 `<>` 两两互斥 | DB 级，改名/同名无效 |
| 单级不伪造批准人 | `ck_apr_request_stage` 按 `approveMode` 分叉校验 approver 空/非空 | DB 级 |
| 同业务变更最多一个活动审批 | `active_change_key` 生成列 + `uk_apr_active_change` 条件唯一（NULL 不入唯一） | DB 级，槽自动释放 |
| 原因必填 | `ck_apr_action_reason` 对 REJECT/WITHDRAW/SOURCE_INVALIDATE 强制 1—500 字 | DB 级 |
| 终态不可改 | `ck_apr_request_state` 四态与 applyState/cancelKind/decisionVersion 全绑定 | DB 级 |

其次是**失败关闭（fail-closed）立场彻底且无例外缝隙**：政策未核准→阻断而非默认 DIRECT；成员/权限服务故障→UNAVAILABLE 而非"按候选为空扩大权限"；项目也无人合格→保持待办而非向管理员兜底；成员离线≠无资格。**每一条都明确堵死了"降级直通"这条最容易出事的路。**

第三是**状态机设计干净**：审批四态（PENDING_REVIEW/PENDING_APPROVAL/APPROVED/CANCELLED）与生效六态（NONE/NOT_APPLICABLE/PENDING/APPLIED/CONFLICT/FAILED/UNKNOWN）正交分离，"APPROVED 不代表已执行或设备已停"贯穿全文，页面单独标"业务待生效/已生效/冲突/失败/结果待核实"。

第四是**场景可追溯性为本系列最强**：47 个场景逐条带源行（r3—r49）、源文件 SHA256，且回退脚本 guard 9 把 47 行的全部字段硬编码校验一遍——不是只数总数。

## 3. P1 需评审拍板

### P1-1　UNKNOWN 永久占用变更槽，且无重试上限、无释放路径（最需拍板）

**证据链**：

1. `apr_request.active_change_key` 生成列定义：
   `CASE WHEN state IN ('PENDING_REVIEW','PENDING_APPROVAL') OR (state='APPROVED' AND apply_state IN ('PENDING','UNKNOWN')) THEN change_key ELSE NULL END`
2. 字段字典明确："CONFLICT/FAILED 为不再自动生效的终结阻断才释放槽"——即 **UNKNOWN 不释放**。
3. 全文检索 `退避 / backoff / 最大尝试 / max_attempt / 重试次数 / 放弃 / 死信`：**0 命中**。`apr_delivery.attempts` 无上限，`next_attempt_at` 无退避策略。
4. 全文检索 `强制 / 人工干预 / 管理员`：仅命中"不强制恢复过期 READY""不继续向系统管理员转交"——**无任何人工对账/强制释放入口**。
5. `M06-CASE39` 只描述"UNKNOWN 查询原 delivery，不重复业务或设备命令"，未定义查询失败后的终局。

**后果**：拥有模块长期不可用时，该 `change_key` 对应的业务被**永久冻结**。例如 `CULTURE:{cultureId}:MODIFY_CULTURE_ID` 槽被一条 UNKNOWN 审批占用后，该培养的培养 ID **永远不能再修改**，且界面只显示"结果待核实"，无任何处置入口、无告警升级、无超时兜底。

**评价**：UNKNOWN 不自动释放本身是**正确的安全立场**（因为变更可能已实际生效，释放槽会导致重复生效）。问题不在立场，而在**缺少配套的运营兜底**——设计只定义了"如何进入 UNKNOWN"，没定义"如何离开"。

**建议（择一或组合，均须留审计）**：
- 定义重试上限 N 与退避曲线；达上限后转 `FAILED` 的前置条件是**拥有方显式返回"从未生效"的可核验回执**，不得本地单方面判定；
- 或提供"人工对账"动作：运维在取得拥有方书面/系统证据后，写入 `APPLIED` 或 `DISCARDED` 的事实证据 + 独立审计记录，从而自然释放槽；
- **明确禁止**无证据的直接释放（那等于承认可以绕过审批重复生效）。

### P1-2　12 个 SUPPORTED 场景中，3 个 M03 场景依赖未定型的设计

**证据链**：

| 项 | 事实 |
| --- | --- |
| 场景分布 | SUPPORTED **12** / OWNER_GATED 21 / EXCLUDED 14（共 47） |
| SUPPORTED 归属 | **M07 占 9**（SC001—SC009，任务类）＋ **M03 占 3**（SC027 培养ID、SC028 培养时间、SC029 培养模式） |
| M03 状态行 | "首轮设计与业务确认中，**非最终评审版**" |
| M03-REQ07 | "M06给审批结果，M03拥有培养生效数据 ｜ 保留接口边界，**依赖模块设计后补齐**" |
| M03 §146 | "**未实现 M03 物理候选存储或接口联调**" |

**后果**：M06 声称的 12 个 SUPPORTED 场景，实际可投用的只有 9 个 M07 任务场景；而 M07 自身也处于"详细设计完成、运行验收待执行"。**M06 首期真正端到端可用的入口，取决于 M03 补齐候选/生效契约的时点，而该时点未定。**

**建议**：在场景映射文档中将 SC027—SC029 显式标注为 `SUPPORTED（依赖 M03 候选/生效契约未就绪）`，避免把"已命名接口"当成"功能可投用"；或要求 M03 先输出《培养变更候选与生效契约》作为 M06 编码的前置条件。

### P1-3　Q39 初始化资料未落地 → 全部实验室恒为 UNVERIFIED，业务全量阻断，无灰度方案

**证据链**：
- 02 脚本**不初始化任何实验室档位**（此点设计正确，未用样例值污染）；
- `apr_lab_policy.readiness` 默认 `UNVERIFIED`，且 `ck_apr_policy_ready` 强制 `READY → current_revision_id NOT NULL`；
- §2"政策不存在、未核准或版本未知时阻断需政策的业务入口，不能自动按 DIRECT 执行"；API02"来源未核准明确 UNVERIFIED，不能造默认 DIRECT"；
- §8"上线导入须核准真实 labId、四档/三档、配置来源 hash 及功能码分配，缺映射保持未就绪"；
- 47 场景中 OWNER_GATED 21 + EXCLUDED 14 = **35 个本就不会触发**。

**后果**：Q39 资料核准并导入前，**任何实验室的全部可用场景均被阻断**，M06 交付的运行时价值为零。设计虽已诚实声明"缺映射保持未就绪"，但**没有给出 Q39 核准计划、缺映射实验室清单、以及"部分实验室先 READY"的灰度策略**，也没有估算导入工时。

**评价**：这属于**交付依赖风险而非设计缺陷**——失败关闭立场本身正确。但作为签署前需拍板项，评审会应明确：Q39 由谁核准、何时导入、是否允许按实验室灰度放行、未放行期间业务如何运行。

**建议**：补一节《Q39 初始化接入计划》，含真实 labId 清单、逐实验室档位映射审核人、导入批次与回滚方式、未就绪实验室的业务替代方案。
