## 2. 架构与边界评价（亮点）

- **限界上下文清晰**：M02 明确不拥有 培养占用(M03)、检测派发/结果(M05)、泵执行(M07)、采集归档(M08)、告警(M09)、工作流定义(M04)、审批设置(M06)，仅提供上下文与页面入口。与模块划分目录完全一致。
- **设备语义防混淆**：反复强调"保存配置成功 ≠ 已加载/在线/执行成功"、"ACCEPTED ≠ EXECUTED"、"UNKNOWN 先查结果不盲重试"，避免把数据库提交成功误判为物理动作成功——这是生物制药设备系统的关键正确性护栏。
- **失败不伪装**：依赖不可用返回 503 而非用 0 假装可禁用；版本冲突不伪装网络故障；范围外授权不泄露实验室名称。符合安全与最小暴露原则。
- **可逆性意识**：迁移/回退 SQL 设计稿齐全（01–06），并明确"未知数据不冒充可投用""阻断检查失败要停止而非清洗问题行"。
- **静默行为纠偏**：首轮发现现有 `normalizeLabs` 缺等级写 0、删旧重建、按登录时间排序等问题，已列为纠偏记录而非默认接受。

## 3. 重点风险与待决项（按优先级）

### P0 — 跨模块契约前置，阻塞编码

**R1｜M03"未结束业务"口径被 M02 硬依赖，但 M03 尚未设计**
- 影响面：M02-Q13（禁用关联用户检查）、M02-Q19（IP/端口修改阻断）的正确性完全取决于 M03 对"未结束项目/批次/培养"的定义与"统一业务引用查询"契约。
- 风险：M02 在 M03 之前设计，若 M03 终态/计数口径变化，M02 禁用与连接参数逻辑需返工。
- 建议：在 M03 详细设计启动前，冻结并双向评审"未结束业务统一查询"契约（入参 `labId`、出参 项目/批次/培养 计数与终态定义），作为 M02 与 M03 的共享 ADR。

**R2｜工作流 tab 的"节点级使用校验"归属悬空**
- 需求 02 §8.4.4 明确："当该实验室存在使用该一级流程的培养时，不允许取消勾选"。该规则既不是纯 M02 主数据，也不是纯 M04 模板定义，而是**实验室×工作流节点×培养**的运行时使用校验。
- 现状：M02 仅声明"M04 拥有工作流定义与选择配置"，M02-Q18 只覆盖"类型变更 vs 工作流配置存在性"，未覆盖"取消勾选某流程被在用培养阻断"。
- 建议：明确该节点级使用校验的实现模块与接口（建议 M04 提供"实验室+一级流程是否被在用培养引用"查询，M02 页面保存时调用），补入 M02 验收场景，避免接缝漏检。

**R3｜M01 三个授权契约尚未实现，且现有行为冲突**
- M02 大量复用 M01 第 20 节 `prepareUserEdit / replaceUserLabs / removeUserLabs` 及 SYSTEM 守卫、管理版本。文档已声明"不声明现有代码已经实现这些新方法"，且现有 `normalizeLabs` 与 Q01/Q05 目标冲突（缺等级写 0、删旧重建、按登录时间排序）。
- 风险：M02 授权正确性建立在 M01 改造之上；若 M01 改造滞后或语义偏差，M02 授权全部失准。
- 建议：将"M01 授权契约改造"列为 M02 编码的前置阻塞项，并先用 M01 当前真实行为做基线差距清单。

### P1 — 一致性机制的落地细节

**R4｜"12 类实例"表述不一致**
- 主文档 §1 边界表列出 13 个条目（台式反应器及控制器、默认泵连接、天平、蠕动泵、空气泵、检测设备、集成反应器、培养容器、地秤、下游设备、声光报警器、打印机、继电器），而 §2/§10/§12 称"12 类实例及控制器"。实例设计实际覆盖 12 类实例 + 台式控制器 + 默认泵连接。
- 建议：统一计数口径（如"12 类设备实例 + 台式控制器/默认泵连接 2 项配套"），避免评审误判漏类。

**R5｜SYSTEM 守卫的锁粒度与并发模型未定义**
- 文档说"共用 SYSTEM 守卫与固定锁顺序"，但未说明 SYSTEM 是行级、表级还是进程级互斥。若为全局单一锁，所有实验室授权/主数据写将串行化，可能成为写入热点与可用性瓶颈。
- 缺失项：①锁粒度（建议按 `labId`/`userId` 维度或独立 version 表行锁）；②失败退避与超时；③"版本冲突 409"与"requestId 幂等"在重试时的交互（同 requestId 重试是否跳过版本校验？）。
- 建议：补充 SYSTEM 守卫 ADR，明确粒度、超时、与幂等/版本冲突的优先级。

**R6｜跨表编号唯一（Q15）的并发防重机制未定**
- 13 源跨表唯一在"同一事务"内校验+写入，并强调"各表入口均接入守卫"，但跨 13 张表无法用单表唯一索引保证；文档验收断言"并发同号新增不能同时成功"，却未说明是否有全局编号空间的分布式锁或串行化机制。
- 建议：明确①全局编号空间的加锁策略（应用层分布式锁或串行化入口）；②迁移期重复号盘点与阻塞升级的处置流程。否则并发同号仍有双成功风险。

**R7｜负责人派生来源的建立时间普遍缺失时的排序预期**
- Q03/Q12：负责人来源无可靠建立时间时 `associatedAt=null`，列表按 `associatedAt` 倒序、未知置后、再按 `userId` 数值倒序。若历史负责人关系时间普遍缺失，列表实际按 userId 排序，可能与用户"按授权时间"的预期不符。
- 建议：在验收中明确接受该排序，或补充负责人来源建立时间的可靠来源。

**R8｜"负责人+直接授权并存"的历史数据去重计数**
- 迁移前核验 SQL 需确认关联用户计数逻辑与 Q13"直接授权∪负责人去重"口径一致（尤其某用户既是负责人又有直接 0 授权时计 1 人）。
- 建议：核对 `01-设备资源迁移前核验.sql` 的关联用户计数与 Q13 一致。

### P2 — 低优先级/文档保洁

- **R9**：`labType=2` 小试下游"只读不可新建"，需核对型号库与实例设计是否对小试下游有对应"只读/不可新建"约束，保持全链路一致。
- **R10**：审计 schema 需支持"按来源区分负责人派生 vs 直接授权"（文档已警示，但 M01 公共审计结构需配套，避免把负责人派生等级误记为直接授权变更）。
- **R11**：38 表清单建议显式标注"本模块主责表 / 只读外部依赖表（如 sys_user_lab 等）"，便于评审区分改造责任（符合编写规范 §3）。
- **R12**：离线告警设置（搁置）已正确排除，但 M08/14 模块未设计，接缝待定，建议在跨模块契约登记。

## 4. 一致性设计评价（状态/权限/事务）

- **实验室状态机**（§8.3）：`status` 仅对应 `lab_lab.status`，删除标志/连接状态/培养占用分别处理；禁用预检与正式写入共用同一计数规则——自洽。
- **授权等级模型**：0 可见 / 1 可操作 / 2 管理；负责人派生 2 但保留直接授权来源；`effectiveAuthType` 只读。模型严谨，但 `effectiveAuthType` 展示"管理"不等于当前可执行（仍受账号/实验室状态/功能权限限制）——已在 Q12 明示，正确。
- **事务边界**：用户+授权+审计+管理版本+回执同事务；负责人/状态/主数据"一起提交或一起回滚"——符合一致性要求。
- **幂等**：`requestId` + `X-Request-Id` + `X-Management-Revision`。**缺口**：版本冲突 409 与同 requestId 重试的交互未定义（见 R5）。
