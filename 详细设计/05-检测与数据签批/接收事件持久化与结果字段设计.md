## 2. 原文、身份与多成员映射

每份已认证且可接收的观测分配独立event_id，保存raw_payload原始字节、raw_hash、规范normalized_payload、semantic_hash、payload_meta及固定contract_version。observation_id、native_event_id、dedup_hash均不唯一；同标识不同值、同语义不同原始表示均能保留。payload_meta记录编码、媒体类型、可信来源和源时间原文，不保存认证密钥。字段长度或数据库包大小超限必须显式报接收失败并使源端可重投；不得截断原文后确认接收。实际大小限额需按协议样本和数据库配置核定。

dedup_key为完整规范键，包含稳定源命名空间、经核准的任务/运行隔离及原生事件键/修订，或协议认可的快照标识。dedup_hash为其UTF-8规范字节SHA256，仅加速查找；必须再按二进制规范比较完整键和完整规范语义，不能用哈希相等证明事件一致。无可靠键时二者均NULL，每份观测独立处理；相同数值不证明同一次检测。去重键构造及规范化规则纳入contract_version审阅；应用升级不得随意改变既有源事件空间。

resolved_bindings是数组，每项含dispatchId、sampleId、resultId、occupancyGeneration、sourceTaskRef、sourceMemberRef、correlationEvidence及当次项目映射版本。批量原始包可关联多个样品，不能用单一result_id丢失其他成员。优先对照调用前固定的det_dispatch_log.item_bindings，不根据当前current_dispatch_id或最新sample_no推断历史归属。无法唯一匹配任一需要应用的成员时，整个包先保存UNMATCHED/AMBIGUOUS，不偷偷部分更新；绑定全部核准后再按固定原包原子应用。只含位置事实的包允许没有结果成员，但必须有可信设备/当前代次证据。

det_result.collection_basis固定本次dispatch/sample/位置代次和非空expectedItems数组，每项目包括稳定目标身份、源编码/子样品映射、单位依据及映射版本。内容与原发送绑定一致，不在轮询时从当前字典重建；修复历史依据要有证据及版本，不改变既有签批快照。

当前det_result_item唯一键仍是(result_id,item_code)。源同编码多子样品首先完整保存在事件items；source_evidence记录贡献源项/子样品、源修订、事件集合及核准聚合版本。若目标需要多个独立业务明细，而现有唯一键不能表达，先停自动映射并记录冲突，待专项明确后调整模型；本包不拼接编码假造项目，也不逐条覆盖。ERROR/NO_MEASUREMENT不填0，数字字段按事实可为空。全部失败可以终结采集，但不因此开放无值自动上传/签名。

## 3. 并发去重、回执与事务

1. 网络读取在事务外；按已认证设备进入短接收事务，先按公共管理守卫→lab_detector行锁取得同设备串行权。用索引查同detector_id/dedup_hash候选，逐一比较完整键和规范语义。所有入口（定时、刷新、后续推送）必须同一路径。
2. 无原件则保存RECEIVED；同键同语义保存本份观测为DUPLICATE并关联最早规范原事件；同键异语义保存CONFLICT和相关事件。始终先耐久提交再给接收确认，失败不得推进源游标越过未保存包。重复指向原件并不代表原件已经APPLIED：原件仍RECEIVED/RETRYABLE_ERROR时回执明确待处理，恢复调度继续处理原件。
3. 已持久化事件的应用事务按公共管理守卫→设备→按主键排序样品→按主键排序结果→明细/有效动作→事件回执锁序，复核身份/代次及receipt_version。禁止先锁事件再等待设备，避免和接收路径反序。读取本事件原文不等于先加事件行锁。
4. 重新查询同键冲突与关联状态，冲突/歧义先退出自动应用。同键不同值若原件此前已经应用，保留已应用事实和新增冲突，不回滚既有签批；记录source_progress待核验更正，并阻断依赖该冲突的自动覆盖/位置释放。不能声称事后冲突可以撤销已发生的物理动作。
5. 同原始包兼容事实一并更新结果/明细、样品当前有效投影、设备位置版本和APPLIED回执；applied_versions数组保存每个受影响结果的before/afterObjectVersion，纯位置事实可为空数组。只增加有实际业务变化的结果版本；明细新增、值更正、完整性/状态变化纳入版本，纯重放、处理重试不增加。位置投影改变另增queue_revision，样品变化增object_version。
6. 事务失败不留下部分领域更新；原RECEIVED可重试。失败后另开短事务，以原receipt_version条件追加processing_history、错误和退避回执，若其他处理已成功则不得覆盖成功回执。RETRYABLE_ERROR重试原事件，不调用设备发送。暂时无法保存错误时仍保留原RECEIVED，由恢复任务再次扫描。

事件原文、标准化载荷、接收时间、源身份和解析契约版本写入后不可修改。processing_history追加关联修复、重试及应用前后回执版本；解析升级或业务更正生成新观测并关联原件，不重写已应用证据。related_event_id只存直接原件/对照事件，完整同键冲突集合通过索引查询。保留期限及容量需按审计要求确认，不沿用HTTP回执24小时清理；不在此脚本删除任何事件。

## 4. 采集、时刻与历史默认值

| 字段/状态 | 含义与使用 |
| --- | --- |
| result_completeness | UNVERIFIED历史/依据缺失；NONE已知期望但尚无结果；PARTIAL部分终态；COMPLETE固定非空期望集合全有终态 |
| device_completion | UNKNOWN缺完成依据；NOT_FINISHED可信未结束；FINISHED可信正常结束；失败/取消的明确终态另存source_progress，不伪造正常完成 |
| collection_state | UNVERIFIED待历史核准；OPEN持续采集；RECONCILING超时/未知/冲突核对；CLOSED正常完整结束；CLOSED_EXCEPTION可信失败/取消等异常终结 |
| next_collect_at | 只控制只读核对调度，不控制新派发；OPEN/RECONCILING且NULL也必须被调度视为待安排，不能永久漏扫 |
| last_event_id | 最近实际修改事件指针，仅用于快捷追溯，完整历史查事件绑定；重复包不改指针 |
| actual_started_at | 独立可信实际检测开始时间，不能从上样时间复制 |
| completion_observed_at | 本系统首次观测可信终结的时间；设备源结束时间未知也可有此值 |
| time_evidence | 每时刻独立quality、sourceEventId、sourceTimestampRaw、sourceTimezone、precision及转换依据；NULL整体按历史未核验 |

新增时刻统一存UTC DATETIME(3)，展示转Asia/Shanghai；旧testing_start_time仍按原上样含义，旧testing_end_time原值不改、原时区不猜。time_evidence逐字段表达旧值时区及可信度，新事件只在证据充分时按既有字段的已核准存储时区写testing_end_time，不能把旧列整体改成UTC导致历史混读。若旧列存储时区尚未核准，保留可信源时刻于事件/time_evidence并阻断旧列自动回填。不能为保持两个时间非空而复制本地观测时间。**「2026-11-04 修订」：本段“证据充分时可写 `testing_end_time`”仅适用于历史兼容/其他模块；M05 新结果链按本文末“双通道唯一性与完成时间增量条款”不写该列，完成时间统一用 `time_evidence.completedAt`。**

2026-10-13 B3 开发落点：上述证据的 JSON 读取格式冻结为 `{schemaVersion:1,loadedAt?,completedAt?,actualStartedAt?}`。各时间槽独立为 `{quality,normalizedAt,sourceEventId,sourceTimestampRaw,sourceTimezone,precision,conversionBasis}`；quality 为 VERIFIED/UNVERIFIED，UNVERIFIED 或缺槽返回 null。VERIFIED 要求其余六键均为非空文本，normalizedAt 为带明确 offset 的 ISO-8601 时间，sourceTimezone 为 IANA 时区或明确偏移，precision 为 SECOND/MILLISECOND/MICROSECOND。loadedAt 来源是成功发送/接受证据，completedAt 来源是设备完成证据，actualStartedAt 来源是实际检测开始证据，三者不得互代。sourceEventId 可引用不可变派发接受记录或设备事件，conversionBasis 记录实际转换依据。无 schemaVersion 的旧证据仍保存原文，读取不得猜测其路径或自动升级；声明新版却残缺的 VERIFIED 证据按 RESULT_PROJECTION_UNAVAILABLE 拒绝。此项只是新写入/读取协议，不核准任何现有历史时间；B4/B5 负责生成可信证据，未完成前旧行可能无法命中 047 必选日期。

det_result的时间/完整性是每次结果事实；det_sample时刻只同步仍属于该样品当前有效运行的结果，和样品版本同事务更新。历史事件可以修复原结果，但不能改新一次发送的样品投影或同位置新代次；应用前核对current_dispatch_id与不可变绑定。不假设一sample_id永远只有一result_id。

SQL不根据旧tested/uploaded/signed/reviewed自动填COMPLETE，不将旧item_value非空核准为VALUE，不重新计算旧签批。历史默认UNVERIFIED/UNKNOWN、证据与新时刻NULL，object_version=1仅是启用版本基点，不伪造此前只有一次修改。历史只读展示保留原值；涉及自动上传、位置释放、签批或后续计算时仍按对应动作证据要求判断。

新发送创建结果时由已核准非空collection_basis显式初始化NONE＋OPEN；device_completion依事实填写，没有未结束证据仍UNKNOWN。旧库迁移不批量激活历史采集；上线必须提交未完成/未知旧调用的逐项接管清单，UNVERIFIED不得当空闲。稳定分页按状态/next_collect_at/result_id扫描，另外扫描RECEIVED/RETRYABLE_ERROR事件；已删除、timeout或tested/PARTIAL不能被UI过滤切断。CLOSED也允许合法迟到更正进入收件，签批事实受版本守卫保护。

## 2026-11-04 双通道唯一性与完成时间增量条款

**性质**：现场已确认小试设备命名管道与 HTTP 两条通道都在用，同一批结果可能被两条通道各取一次。**2026-11-04 用户裁决：采用「一台设备只允许一种通道」**；通道中立唯一键方案**已否决**。本条据此定稿，作为实现依据。原条款保留，冲突处按本条标注修订。

### 1. 已否决备选：通道中立唯一键

> 该方案已否决，仅保留结论与否决理由，不再作为实现依据。

- **原候选键**：`deviceId + businessSampleNo（或 resultId 对应样品单号）+ sortedItemCodeSetHash + trustedCompletedAt(UTC, ms)`。检测项集合按冻结 `expectedItems` 的 `itemCode` 排序后哈希；完成时刻取 `time_evidence.completedAt`（源标记完成），缺失时该键不可用并转 `UNVERIFIED` 待人工。
- **否决理由一（要改表）**：需新增列或去重表，DDL 须另行评审并同步字段字典、目标 DDL、开发基线生成物与来源清单，与当前“零新增结构”的接收包边界冲突。
- **否决理由二（要回填）**：历史结果与在途派发需回溯生成该键；旧数据缺可信完成时刻/订单号时无法可靠构造，回填结果不可信，且会与“历史值不自动核准”原则冲突。
- **否决理由三（现场不存在同设备双通道场景）**：现场核查确认一台设备实际只使用一种通信方式，跨通道重复是由“人为给同一台设备配两条通道”制造出来的，不是现场事实；为一个不应存在的配置引入改表与回填不划算。
- **保留价值**：仅作为“若未来确需同设备双通道”时的备选记录；启用前须重新裁决，并同步改造表结构、回填、采集与测试。

### 2. 已裁决：单设备只允许一种通道（2026-11-04 用户裁决）

#### 2.3 切换流程（不得双跑）

1. **停用旧通道**：在 M02 通信配置中将旧通道置为不可用于结果采集（按现有 `desired_revision`/`applied_revision`/`apply_state` 机制使旧修订失效）；停用后旧通道不再产生新派发。

4. **记录切换时间与操作人**：沿用配置的 `desired_revision`/`applied_revision`/`apply_state` 与审计前后快照记录切换人与时间，不得只改库不留痕。

- **精度与时区**：默认 SECOND；源提供毫秒/微秒时保留并声明精度；来源时区未核准 → `UNVERIFIED`，不写、不推算。

### 4. 幂等落地要求（单设备单通道 + 通道内幂等 = 跨通道防重）

1. **通道内 upsert**：同一通道重复轮询按稳定 `dedup_key`（`detector_id + 原生键/修订`）查重，重复只追加 `DUPLICATE` 回执或历史，不新增 `det_result`/`det_result_item` 行。
2. **已签批/已审核/已更正结果不被后续重复数据改写**：重复只追加回执，不产生业务版本；受控更正走独立流程。
3. **冲突写入独立留痕**（`CONFLICT` 事件 + `source_progress`/审计），保留双方原文与来源通道，供人工裁决。
4. **为什么等价于跨通道防重**：任一台设备任一时刻只有一种通道（2.2 校验收口），同一物理结果不可能同时从两条通道进入本系统；切换流程（2.3）保证旧通道在途清零后新通道才启用，历史不重算（2.4）。跨通道重复只可能由配置错误制造，而配置错误已被“保存校验→启动巡检→调度拒绝”三层拦截。因此“单设备单通道”把跨通道问题收敛为“同设备不可能双取”，通道内既有幂等负责“同通道重复轮询不新增、已签批不被覆盖”，两者组合即覆盖原“跨通道唯一键”的全部目标，且无需改表/回填。
5. 上线前须以隔离库验证：同通道重复轮询、切通道后旧在途收尾、签批后重复、配置缺失/非法拒绝调度四类用例。

### 5. 与原文章节的冲突处理

- 本文 `:22` 的 `dedup_key` 规则继续用于单通道，**是唯一幂等键**；已否决的通道中立键不再作为上层补充。
- 本文 `:32-33` 的 `detector_id + dedup_hash` 全键比较与 `DUPLICATE/CONFLICT` 回执继续有效。
