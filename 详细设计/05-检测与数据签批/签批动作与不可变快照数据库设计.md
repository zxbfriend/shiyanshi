# M05 签批动作与不可变快照数据库设计

## 1. 增量范围和前置

det_result新增active_sign_id、active_review_id、active_void_id及sign_chain_state四列；det_result_sign_record新增八列，见[字段字典](签批动作与快照字段字典.md)。本包两表新增12列，累计目标det_result 38列、det_result_sign_record 26列，共64列；新增9个CHECK、4个普通索引和1个幂等唯一索引，无外键和新表。

前置为发送20列包和[接收数据库包](接收事件持久化与结果字段设计.md)，共同结果版本继续使用det_result.object_version，不另加result_version。三个包累计既有表增量49列（20＋17＋12），另有30列技术收件表；不同包的累计目标DDL含重叠结果表，不可简单相加其目标列数。15目标包含结果接收字段，10目标作为前一阶段基线保留，不覆盖历史包。

本轮定向读取原SQL两表CREATE及接收目标结果DDL、主设计11节，另读DetResultWorkflowServiceImpl的buildSignRecord/buildActionSignRecord/buildVoidSignRecord：所读构建方法写动作类型、名称和时间，未写稳定signer_user_id。图index_status/check_index_coverage均Transport closed，以上仅定向文本证据，不宣称全部写入口核对完成。Mapper已有身份写入差距沿原核对清单，工程接入仍需消除通用更新/删除动作日志的旁路。

## 2. 有效指针与动作链

sign_chain_state为VERIFIED/UNVERIFIED/CONFLICT。新迁移旧记录一律UNVERIFIED、三指针NULL，原状态和显示文本保留；不能从sign_by/review_by相同、活动记录最新一条或当前登录人推断身份。新业务结果在证实无历史链并完成初始化后显式VERIFIED，三指针NULL；这表示链可核验，不表示结果完整或已经签名。

| 动作 | 前置指针/状态 | 新动作关系与提交后指针 |
| --- | --- | --- |
| SIGN | uploaded；三指针空；链VERIFIED | 写SIGN，active_sign_id指新记录；状态signed |
| REVIEW | signed；有效SIGN唯一可核验 | 新REVIEW.related_action_id指该SIGN；active_review_id指新记录，保留SIGN；状态reviewed |
| REVOKE_REVIEW | reviewed；当前审核人本人 | 新动作关联原REVIEW；标原REVIEW被本动作撤销，清active_review_id，保留SIGN；状态signed |
| REVOKE_SIGN | signed；无有效REVIEW；当前签名人本人 | 新动作关联原SIGN；标原SIGN被本动作撤销，清active_sign_id；状态uploaded |
| VOID | UI03仅uploaded；检测分析tested入口另按可信用途开放 | 新VOID保存准确before_status，active_void_id指新动作；状态voided；无签名审核指针 |
| RESTORE_VOID | voided；唯一有效VOID、原状态tested或uploaded | 新动作关联原VOID，标原VOID被撤销并清指针；准确恢复原状态，不恢复签名审核 |

核对指针时验证被指记录属于同一result_id/sample_id、是正确operation_code、成功且未撤销、版本与链关系可核验。REVIEW必须指当前SIGN，不能跨结果或引用旧一轮签名。旧void_from_status继续作为显示/兼容投影，但必须与有效VOID.before_status一致才允许恢复。指针和状态的基本形状有CHECK，跨行身份与关系由锁内领域校验，不由CHECK或无外键暗示自动正确。

原action_type字段保留供既有历史显示/兼容读取；新增operation_code只用于action_contract_version=1的六动作精确语义，解决旧通用revoke/approve等分类不宜自动推断新动作的问题。新写时服务端按已核准兼容映射填写旧字段，不能接受客户端自由填写；新判定只读operation_code。未核准旧动作值的历史记录不自动转换，旧查询/导出须接入新契约再启用新写入。

全部动作仍要求功能权限、当前有效对象范围及状态。审核遵守Q01成员关系或Q02真实无培养实验室可操作权限；审核人与签名人不同。撤销仅当前原操作者，管理员无例外。M05-Q08本人暂存权限不替代签批权限。作废、撤销、恢复不调用设备取消、删除订单或重新派发。

## 3. 不可变内容快照

content_snapshot结构固定为{schema,content,actor,authorization,action}。schema含快照契约版本及规范化版本；content含当时已锁定的resultId/sampleId、业务编号、真实实验室/项目/批次/培养关联（允许真实null）、检测设备与型号快照、上样及源时刻证据、完整性、固定项目依据、全部结果明细及来源；明细保留稳定ID、编码、名称、原文本、精确数值字符串、单位、告警界限、项目终态、项目作废状态及来源映射版本。不能只存当前结果表引用或今天的项目字典。

actor保存稳定userId及当时用户名/显示名；authorization保存动作使用的功能码、管理版本、实际范围与Q01/Q02核验依据快照；action保存操作类型、原因、before/after状态和版本、相关动作ID、请求ID及操作时间。actor与authorization解释当时行为，不能用于授予今日权限。签批日志已有signer_user_id必须与actor.userId一致，来源为认证上下文。

本节"明细保留稳定ID、编码、名称、原文本、精确数值字符串、单位、告警界限、项目终态、项目作废状态及来源映射版本"是**承载要求清单**，不是键名清单。`snapshot.content.items[]` 元素的权威键名、可空口径与取值域以
[自动检测与跨模块结果契约](自动检测与跨模块结果契约.md)4.1（INT-11 冻结，2026-10-07）为准，与结果版本快照同源同表；本节顶层 `{schema,content,actor,authorization,action}` 与结果版本快照的 `ResultSnapshot` 是两个不同对象，不得互相冒充。

content_hash只对snapshot.content的规范UTF-8字节计算SHA256；规范固定对象键排序、稳定明细排序、ID/精确小数字符串、null语义、时间表示，不把JSON数据库重新序列化后的任意文本当原规范字节。action、actor、authorization不进入该内容摘要，因签名/审核操作者、流程状态和版本必然不同；完整snapshot仍整对象不可变保存，不以内容hash相等宣称全部审计字段一致。HASH是内容一致性辅助，不等同数字证书签名或数据库防篡改机制。

SIGN和REVIEW在各自锁定版本保存完整快照。REVIEW必须与当前SIGN的content进行规范比较，并核对摘要；不同则拒绝审核、转更正核对，不能把新内容沿用旧签名。签名后流程版本会变化：例如SIGN 7→8、REVIEW 8→9、撤销审核9→10；再次审核使用当前10版本校验，但仍引用有效SIGN及其原内容，不错误要求SIGN.result_version_after永远等于当前版本。内容无变化的流程动作可以推进共同版本，不能据版本不同单独推断数据被篡改。

撤销/恢复也保存动作时点完整快照并关联原记录。允许改变原记录的仅is_voided、revoked_by_sign_id、voided_time及必要更新审计字段；原操作者、动作原因、内容快照、内容hash、目标版本、时间和相关动作不可覆写。新撤销记录是独立成功动作，不删除原记录。撤销审核后再审核形成新REVIEW，保留旧审核/撤销链；再次签名同理。快照中结果状态位于action，不能因状态切换影响纯内容比对。

已签名/审核/作废结果接收更正时仍按接收契约保留待核验事实，不覆盖当前签批内容。RESTORE_VOID只恢复状态，不回灌历史检测值；若作废期间内容与有效VOID快照不一致，阻断自动恢复并核对来源。专门的结果更正授权、单项作废和异常项上传规则不由本包开放。

## 4. 版本、幂等与原子提交

六动作遵循原预检/确认契约：预检可以列出不合格项，正式只提交确认集合，任一项失败则全部不写。每项操作写一条成功领域记录，result_version_before为锁内当前object_version，after严格加1；公共动作失败日志不得伪装action_contract_version=1成功签批记录。失败事务的记录、指针、状态及版本全部回滚，不能留下看似有效的部分签名。

统一锁顺序细化为SYSTEM公共管理守卫→真实labId升序→detectorId升序→sampleId升序→resultId升序→明细/动作。这是对主设计11.5的设备锁补充，与接收/占位共用顺序，所有参与入口须一致；在预读定位后锁内重新校验关联，不能根据客户端labId锁错范围。写动作前先验证整个集合，再分配动作主键并提交更新；UPDATE结果须带expectedObjectVersion及预期状态/指针，影响行数必须1。

状态、指针、对象版本、新动作、原动作撤销标记、必要样品当前有效投影、公共审计及M01幂等回执在同一本地事务提交。样品只在当前真实运行关联一致时同步，旧结果签批不能覆盖新发送的样品状态。签批不修改设备实际位置事实，也不因结果变signed释放占位。

唯一索引(signer_user_id,request_id,result_id)确保同操作者请求对同一结果最多一条新领域动作。它是M01整请求幂等的补充：不能凭该索引实现跨结果批量原子性或识别异负载，仍由M01先核对操作类型、确认集合和规范化负载。新v1成功记录三列不得NULL；历史新增request_id保持NULL，MySQL唯一索引允许历史保留，不强造UUID。

领域request_id与动作快照长期留存，不随24小时HTTP回执清理。回执过期后再次遇到同操作者/UUID且已有领域记录，先查完整动作集合并重新验证读取权限；能够重建原完整回执才回放，否则明确提示请求已处理需查证，禁止执行为一次新动作或通过改UUID绕过未知结果。不同操作者可使用相同UUID，但各自仍须取得当前动作权限；同人同请求异动作/异负载拒绝。结果版本上限必须在领域层显式拒绝递增，不能溢出归零。

数据库CHECK约束枚举、版本及状态基本关系；JSON schema内部身份、内容hash、UUID格式、跨行指针和快照不可变均需应用层校验。新契约不能继续通过通用CRUD任意更新/删除签批日志；最小数据库写权限及旁路整改需工程验收，脚本本身没有建立审计防篡改权限体系。

## 5. 历史接管和迁移边界

旧状态、sign_by/review_by、时间、动作记录与撤销关系原样保留，新增链状态UNVERIFIED，三个指针NULL，新增动作字段NULL。历史uploaded不自动视为从未签名；历史signed/reviewed不能用当前结果内容生成“当时快照”。历史已有多个活动候选、无操作者稳定ID、悬空result_id或作废前状态冲突，进入逐项接管清单，不按最新一条自动择优。

接管证据至少包括旧原始审计/账号生命周期映射、相关结果身份、确切原动作含义及当时内容来源。只有证据足以支撑目标身份和链关系时，才可另行设计受控接管；本包不提供自动历史回填脚本，也不创建虚假v1动作。未核验旧签批仍允许有权查看原历史，签批/撤销/恢复返回原ACTOR_IDENTITY_UNVERIFIED或状态证据问题，不能借管理员放行。历史正常无签批结果也须验证链为空而不是仅看文本状态。
