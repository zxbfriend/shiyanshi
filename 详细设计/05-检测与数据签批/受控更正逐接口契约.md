# M05 受控更正逐接口契约

版本DD-20260913-T8-R11。本文展开[受控更正主设计第5节](受控更正与审计保留设计.md#5-接口及持久幂等)7个HTTP接口。ID/版本均为十进制字符串，时间ISO8601。样例为模拟数据；设计补齐不代表代码、SQL或联调完成。

## 1. 公共对象、权限与事务

CorrectionChange={itemId:string,field:VALUE/UNIT/ITEM_MAPPING/VALIDITY/NOTE,newValue:string|boolean|null,unit:string|null,evidenceRefIds:string[]}；不接收oldValue、操作者、状态、设备时刻。EvidenceRef={attachmentId,version,sha256}均必填，1—20项。reason首尾去空1—500。CorrectionRow固定correctionId,resultId,baseObjectVersion,baseCorrectionId:null|string,state:SUBMITTED/APPROVED/REJECTED/WITHDRAWN/STALE,candidateHash,reason,changedPaths:string[],submittedBy,submittedDisplayName,submittedAt,reviewDecision:null|APPROVE|REJECT,reviewedBy/reviewedDisplayName/reviewedAt/reviewReason可空,resultRevisionId可空,version,allowedActions:string[]。

提交/预览须detect:correction:submit＋detect:sign:sign＋当前结果操作范围；决定预览/决定须detect:correction:review＋detect:sign:audit＋当前审核资格且与提交者不同；撤回只允许SUBMITTED申请人且仍有当前结果操作范围；详情/历史沿结果读取用途权限。无权与不存在统一404 FORBIDDEN_OR_NOT_FOUND，依赖鉴权不可用503 DEPENDENCY_UNAVAILABLE。

预览只读且不写管理版本。提交、决定、撤回带X-Request-Id、X-Management-Revision，在SYSTEM→实验室→设备→样品→结果→申请锁序内写领域记录、审计、管理版本和持久幂等回执；网络/附件原件读取在事务外完成，事务内只验证已固定摘要。相同键同体重放原回执，异体409 REQUEST_CONFLICT。

### 3.1 候选全文的承载体与生命周期（2026-10-12 用户确认，来源等级【已确认】）

上节 Body 只允许传令牌，但提交时须把候选**全文**（`candidate_snapshot` / `changed_paths` / `evidence_refs` / `base_content_hash` / `submission_signature`，建表定义均 NOT NULL）写入 `det_result_correction`。指纹只能证明"内容有没有变"，**不能还原全文**，此前预览只留 `candidateHash` 与 `changedPaths`、服务端无处取回全文。本轮用户已确认：**由 M05 在服务端保存短期预览快照，前端仍只提交令牌。**

| 步骤 | 口径 |
| --- | --- |
| 1 预览 | M05 读取原结果与可信附件，生成不可变候选全文并计算 `candidateHash` |
| 2 短期保存 | 以**不可猜测的 `previewId`** 保存全文，含操作者、结果身份、基线版本、证据摘要、理由、到期时间 |
| 3 发令牌 | 绑定 `previewId`、本人、候选指纹、基线版本与管理版本，5 分钟有效 |
| 4 提交 | **只接收令牌**；服务端找回全文、**重新计算指纹**，并在守卫事务内重验权限、版本、未决申请 |
| 5 落库 | 原子写入更正申请、候选快照、提交签名、审计与幂等回执 |
| 6 过期/丢失 | 拒绝并要求重新预览，**不得让页面补传候选内容绕过校验** |

**两条硬约束**：

- **不得在提交前删除缓存。** 应先查同次写的持久回执；事务成功后即使缓存已失效，同 `requestId` 重试也能返回原回执——避免响应丢失后重复申请。
- 现有 `ResultCorrectionTokenSupport` 绑定的是**更正申请身份**，**不得未经区分直接套用于尚未正式提交的预览身份**。

⚠️ **【技术建议·待 owner 评审】** 用户选定的载体方向为「服务端短期存储」，但**具体存储选型（Redis 或独立预览草稿表）属技术实施建议**。若选 Redis：`futurefab-modules/futurefab-system/pom.xml` **当前未依赖 `futurefab-common-redis`**，主源码无 Redis 引用，须先补模块依赖（属模块依赖变更，须在批次中显式声明）；若选独立表：须新增表与清理规则，并先解决"预览只读、不写数据库"的现行约定。**该选型评审通过前不得落码。**

⚠️ **【需求已有·已由建表 CHECK 固定】** 提交时**只生成提交者签名**；审核者签名在**批准时**生成。依据 `docs/开发基线/01-完整建表.sql`：`ck_m05_corr_terminal` 规定 `state='SUBMITTED'` 时 `review_signature IS NULL`，`ck_m05_corr_approval` 规定 `state='APPROVED'` 时 `review_signature IS NOT NULL`。**不得在提交时预填两份签名。**

⚠️ **【需求已有】** `det_result_revision` **不只供更正使用**——接收、上传等真实结果变更同样应生产版本快照。更正链不通是单独缺口，**不得据此认定所有可信结果都必须经过更正**。

### 3.1 2026-10-13：048 持久提交回执

提交签名 `submission_signature` 除原签名字段外，固化 `submitTokenHash`（令牌 SHA-256，不保存令牌明文）、`submitReceipt`（首次 SUBMITTED、version=1、原结果基线、resultRevisionId=null）、`committedManagementRevision`。均与申请和公共守卫在同一事务提交，批准/拒绝/撤回不得改写原提交签名。

成功同键重试先通过当前身份及现有结果读取范围，再核对原令牌摘要和原申请身份/基线/候选摘要，回放首次提交的业务响应和顶层管理版本。即使 Redis 快照已删、令牌过期或申请已批准，也不重建申请、不返回后来的申请状态；查询最新状态使用详情接口。异令牌为 REQUEST_CONFLICT；旧行没有完整回执证据时返回 RESULT_PROJECTION_UNAVAILABLE 并要求查询详情，不推算历史回执。

本改造没有完成 B7 全部能力：原版完整摘要、证据版本核验、STALE 持久化与发布/M07 消费闭环仍需后续实施；现有更正范围底座的项目/培养历史授权还需与 B3 统一。

### 2026-10-16：批准发布与记录读取一致性修复范围

本批按既有 schema2 契约实现完整候选及正式快照：首次更正从当前结果绑定和明细冻结完整基线，后续更正读取已校验的当前不可变版本；批准生成非空 revision ID、`CORRECTION_APPLIED` 事件、双签名及 `M05_RESULT_V2` 最终摘要，保留原值、来源和未知设备事实，不覆盖原结果业务列或明细。该基线摘要仅绑定本次候选，不重算或替代历史 schema1 revision 的摘要。

申请终态写齐原因、操作者、时间、`terminal_request_id`、`terminal_payload_hash`；批准另写 `review_signature` 和 `result_revision_id`。决定令牌绑定候选、申请版本、管理版本、决定和原因；决定/撤回的领域终态键支持公共回执过期后的同体重放，并返回首次提交的管理版本。

检测记录及签批记录的列表、详情与既有导出读取当前正式版本，状态和签批人筛选在数据库分页前取当前 revision；返回前由 `M05EffectiveResultReader` 校验批准关联、完整双签名及摘要。更正版缺失或损坏时返回 `RESULT_PROJECTION_UNAVAILABLE`，不回退原明细。此处是代码与契约验证范围，不代表目标数据库、部署 HTTP 或浏览器验收。后续收口范围与仍未验收的依赖见下节，不能据本批宣布 B7 全部完成或开放更正入口。

### 2026-10-16：第 7 项剩余链路实现边界

决定时持锁核对结果版本和更正指针；APPROVE 或 REJECT 遇到基线变化，先在管理守卫事务中写入 STALE、终结身份、审计及回执，提交后返回 `409 CORRECTION_BASE_CHANGED`。同终结键重放仍返回原冲突，不重复写版本。旧 `detresult`、`detresultitem` 及工作台的当前结果读取接入有效快照；查询筛选发生在分页前，已更正结果的刷新不再拉取设备值覆盖当前显示。

`M05ResultRevisionPublishTask` 定时扫描持久待发/重试记录；显式设置 `futurefab.m05.result-events.publisher-enabled=true` 才装配，默认关闭。批量键 `futurefab.m05.result-events.batch-size` 默认 50、范围 1—100，间隔键 `futurefab.m05.result-events.publisher-delay-ms` 默认 5000。schema2 发布前核验更正身份、双签摘要和正式内容摘要；仅 `Transport.publishAndAwaitAcknowledgement` 返回真实持久 broker ACK 后写 PUBLISHED。缺传输实现继续保留待发，ACK 后数据库故障允许同 eventId 重投，不制造新版本。

可信消息适配调用 `ResultRevisionDelivery.deliver`，核对持久事件元数据与精确版本证据，再将实收 payload 的规范 JSON SHA-256 交给 M07（摘要覆盖整个 payload，包括 contentHash）。M07 在 `M07_RESULT_CHANGED_CONSUME` 资源事务内以 `M05:<eventId>` 长期去重：首次读取精确版本并校验摘要；同摘要重放原回执；异摘要持久记录 CONFLICT；失败回滚影响和回执。历史计算及执行账本保持原值，只使旧版本确认、未来候选和生成状态失效，并在资源占用前重验检测来源。失效候选占用只释放本次可证明的指针，其他屏障保留；旧计算不能通过启动重验。

**部署和验收边界**：消息中间件及连接配置尚未确定，仓库没有默认 broker 发送/接收适配；上述调度与消费接线不等于实际消息闭环已验收。接收适配需在持久回执后 ACK，CONFLICT 进入可追溯处置，异常保留重投。M07 订阅只路由权威 revision 中确有培养归属的事件；合法的非培养结果仍由 M05 正常发布，不进入要求 culture_id 非空的 run_event。该路由条件须核对权威快照，不能信任实收 payload 的培养字段，过滤也不能冒充 M07 已消费。M07 消费还需启用现有 `futurefab.resource-transaction` 配置及有效预算。可信观测时刻缺失时，现行 M05 精确 Port 仍失败关闭；M07 来源确认所需冻结字段不足、任务原地重算/换绑及真实发泵一致性屏障属于现存接入边界，本批不伪造数据或放开。已准入 READY 任务可沿原取消/变更入口处理，未准入 CREATE 候选只保留失效历史，不宣称已有恢复重建入口；失效候选的旧审批交付仍失败关闭。证据原件版本核验、现有对象授权统一、目标 MySQL SQL/事务、broker 故障重投、HTTP/浏览器及现场执行仍需独立验收。

## 2026-10-16 后续收口：附件、规范范围、真实影响及恢复边界

本节承接本文件前述同日实施登记中的剩余项。用户确认附件采用M05私有原件表；M07按精确版本快照的VERIFIED测量证据与有效指标准入、不强制已有签名；更正后通过重新选源、60秒确认、新计算及同一未执行任务的新候选重新审批恢复，保留历史和当日生成额度。更正双签不升级旧UNVERIFIED测量证据。中间件保持待定。
