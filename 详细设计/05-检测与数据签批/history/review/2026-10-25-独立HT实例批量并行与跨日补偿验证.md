设备调用跨度由 `MIN(start_time)` 至 `MAX(end_time)` 计算，列本身为秒精度。它不是 HTTP 响应时间，也不是 SYSTEM 行锁持有时长。`guardedMs` 等是现有服务日志阶段计时，也不能直接等同于行锁时间。三个真实 HT 批次未出现旧构建的 70–89 秒守卫窗口。

锁采样使用 `ENGINE + ENGINE_LOCK_ID` 精确关联 data_lock_waits/data_locks，按请求事务 ID 去重。240 秒、2369 个快照：752 个快照存在等待，最大同时等待事务 3 个；最长连续非零等待采样区间约 4.346 秒（不是单条事务实际等待时间）。

仍有两次自然产生的后台 `CannotAcquireLockException`，分别在正常批和 WA 批准备窗口，作用于旧 resultId `1311534166935998465`。因此不能宣称零锁等待或零告警。后续两次告警与下述主动持 SYSTEM 锁的 QA 故障注入重合，应单独标记，不能归因于自然发送性能。观察窗口未出现跨日扫描失败刷屏。

## 跨日锁失败、重试与保护

使用忽略目录内 Java QA 驱动，实例化**生产 M05DayRolloverProcessor、真实 Mapper、Druid、DataSourceTransactionManager 和 ResourceLockWaitBudget**。只调用新 detectorId 的 `apply()`，Clock 固定为下一个上海零点（2026-10-25T16:00:00Z）。未改 OS 时间、未回写样品时间、未直接 UPDATE 业务表。

每次先由独立事务短暂持 SYSTEM 行锁，确认生产处理器约 3.4 秒抛 CannotAcquireLockException，释放阻塞事务后执行原处理器重试：

| 45 条可信完成，WC/WD 未完成 | 3442ms | 45 | 0 |
| WC/WD 已完成，WE/WF 活动/超时 | 3444ms | 2 | 0 |
