## 2. 总体评价

**质量显著高于 M01/M04，可作为评审基线。** 核心判断：

1. **反伪造立场是全模块最突出的优点，且贯穿到 DDL 层。** 状态不伪造（`tested` 不等于采集完整、不等于可腾位；`cancelled` 只消费可信设备反馈；不为凑 `COMPLETE` 填 0）、时间不伪造（`actual_started_at` 不能从上样时间复制；未知时区不填假 UTC；历史未核验保留 null 并标 `UNVERIFIED`）、身份不伪造（稳定 userId 而非显示名；历史身份不可核准返回 `ACTOR_IDENTITY_UNVERIFIED` 而非猜本人）。这些不是口号——它们落实成了 CHECK 约束（如 `ck_m05_rx_expected` 禁止空期望集推出 COMPLETE，`ck_m05_sign_ptr_state` 禁止 UNVERIFIED 链携带指针）。

2. **"两个维度必须分开"的拆解非常扎实。** 结果完整性（`NONE/PARTIAL/COMPLETE/UNVERIFIED`）与设备完成（`NOT_FINISHED/FINISHED/UNKNOWN`）独立；发送粒度（`sendMode`）与锁定范围（`lockScope`）、排队、容量单位、遮挡解耦；左侧腾位与右侧结果删除分离；清空/删除/取消三者互不推导。M05-Q03 的修订（推翻早期"column 必然锁整列"）说明团队能根据更具体的业务说明修正既有结论，并在多处标注"此结论已被替代，不得继续作为开发依据"。

3. **数据库工程严谨度达到可交付水准。** 四包（02/07/12/17）各有迁移前核验、增量、迁移后核验、未启用回退、累计目标五件套；增量脚本 9/16/12/29 处 SIGNAL 守卫；显式确认变量（`@m05_*_maintenance_confirmed` + `@m05_*_baseline_verified`）；DDL 隐式提交风险被明确写出（"不声称整个包可事务回滚"）；回退依赖顺序 19→14→09→04 已固化；备份表不被回退脚本删除；原需求与基线 SQL 的 SHA256 每轮核对。

4. **报告附件核对是真做了的。** PDF 8 页逐页渲染 + 两工作簿 25 sheet 表头/合并范围读取 + 三个 SHA256 记录；并明确指出"原样例没有操作日志附录，但目标按 09 正文补操作记录，不能据样例省略需求"——没有把样例当需求。

规模：7 类需求、5 个页面、8 个工作台写接口 + 6 个签批写接口 + 3 个查询接口、14 表 267 列、59 个既有表增量列 + 2 张新表、276 条设计验收场景。

## 3. 需评审拍板的问题（P1）

### P1-1 历史签批结果将永久丧失撤销/恢复能力，且当前没有接管方案

**事实链（设计文件自述，非审阅推断）：**

1. 12 迁移脚本与 `ck_m05_sign_ptr_state` 共同规定：迁移后历史记录 `sign_chain_state='UNVERIFIED'`，`active_sign_id`/`active_review_id`/`active_void_id` 全为 NULL，且 CHECK 强制"非 VERIFIED ⇒ 三指针必须 NULL"。
2. 主设计 11.2：REVOKE_SIGN 要求"当前操作者 = 当前有效签名人"，REVOKE_REVIEW 要求"当前操作者 = 当前有效审核人"，RESTORE_VOID 要求"存在唯一可验证原作废动作"。
3. 有效指针为 NULL ⇒ 上述三条均无法满足 ⇒ 存量已签/已审结果**只能查看，不能撤销签名、不能撤销审核、不能恢复作废**。设计已确认此行为（`签批动作与不可变快照数据库设计.md` §5："签批/撤销/恢复返回原 ACTOR_IDENTITY_UNVERIFIED"）。

**问题：** 设计明确"本包不提供自动历史回填脚本，只有证据足以支撑目标身份和链关系时，才可另行设计受控接管"——但**没有接管方案、没有存量量级估算、没有工时，也没有"若不接管"的书面接受**。做保守的安全设计是对的，但"永久只读"这个后果没有摆到业务方面前确认。

**建议（评审前补齐）：**
- (a) 存量 `signed`/`reviewed` 结果数量，以及其中 `signer_user_id` / `create_by` 可一对一映射到稳定 userId 的比例；
- (b) 受控接管的准入证据清单与门槛（例如是否允许"原签名人本人 + 原审核人本人双方在线确认"作为接管依据）；
- (c) 若决定不接管，需业务方书面接受"存量历史签批结果永久只读、不可更正"这一范围。

### P1-2 全局锁串行化无容量指标、无压测计划

**事实：** M05 是所有模块中写频率最高的，但每条写路径都要依次取多把串行锁：

| 写入路径 | 锁序（设计明文） |
| --- | --- |
| 签批六动作 | SYSTEM 公共管理守卫 → 真实 labId 升序 → detectorId 升序 → sampleId 升序 → resultId 升序 → 明细/动作 |
| 接收事件应用 | 公共管理守卫 → lab_detector 行锁 → 样品主键序 → 结果主键序 → 明细/有效动作 → 事件回执 |
| 工作台发送/删除 | 公共管理/设备/列/位置/样品稳定顺序锁 |
| 报告冻结 | M01 管理守卫 → 实验室 → 设备 → 样品 → 结果 |
| 样品 ID 占号 | 真实 `lab_id` + `detect_class` 全表串行核验（含 `det_sample_id_history` 别名） |

叠加继承的 **M01 单 `SYSTEM` 管理版本行全局写锁**（M01/M04 已列为 P1，本模块未重新评估）。设计自认"不新增位置表的代价是同设备操作短时串行"，但：
- 两份 `现状核对` 已确认 `OfflineDispatchRetryTask` 默认每 5 分钟扫描、`SDMSResultFetchTask`/`NamedPipeResultFetchTask` 定时轮询——后台写与前台写争同一把 SYSTEM 锁；
- 全文件集中**没有任何目标并发量、锁等待阈值、超时或压测计划**。

**建议：** 给出目标指标（同时在线工作台数、每设备每小时派发数、采集轮询频率、批量签批并发数），在测试库做真实压测；若 SYSTEM 守卫成为瓶颈，需与 M01 统一设计拆分方案（如按 labId 分片管理版本），M05 不应单独承担这个决策。

### P1-3 设备协议能力未闭合，且未产出"暂不可投用"清单

**事实：** `AdapterCapabilities` 的七个维度（`acceptanceEvidence` / `startEvidence` / `completionEvidence` / `queryDispatchSupport` / `positionSupport` / `cancelFeedbackSupport` / `resultFetchSideEffect`）在七型号上基本为 `UNVERIFIED`；`设备适配与结果采集核对清单.md` §5 已列出需工程方提供的 7 类证据（真实下单/拒绝/超时/部分成功样本、稳定设备任务 ID、结果原文与多子样品含义、项目失败终态、开始/完成/取消状态定义、圆盘位置与重启序号、查询副作用）。

**而 M05 的核心能力全部依赖这些证据：** 完整性判定（`deviceCompletion` 必须来自"型号适配契约认可的完成事实"）、位置释放、Vi-CELL 圆盘物理轮询（`PHYSICAL_CYCLE` 需可信位置与开始事实）、HT 列锁释放。设计已声明 `ready=false`，但**没有把这些依赖关系物化成一份可跟踪的清单**。

**风险：** 把"契约已定义"当成"功能可投用"，D2/D3 阶段空转，或带 UNVERIFIED 能力上线。

**建议：** 评审输出《设备能力核准清单》——七型号 × 7 项能力矩阵，逐格标注「已核准 / 待工程提供 / 不适用」，绑定责任人与截止日期；并明确"哪些型号在哪些能力核准前不进入 D2 验收"。

---

### P1-4 D1 阶段依赖的上游模块尚未定型，Q01 实际不可实现

**事实：** `M05覆盖矩阵` D1 准入条件写明需要"M01 身份/版本/回执、M02 已核准型号与真实 lab_id、M03 用途权限"。而：
- M02、M03 的详细设计目录仍在并行编写（M05 已引用 M02 的 `06-设备资源目标表结构.sql` / `07-检测规则增量补丁.sql` / `08-回退`）；
- **M05-Q01 审核资格要求"沿 M03 继承关系解析有效负责人/普通成员"** —— M03 的用途权限模型未定型，Q01 就无法落地为代码；
- 同理 Q02（无培养按"真实所属实验室可操作 1 以上"）依赖 M03 的实验室等级语义。

**建议：** 在 D1 准入条件中把"M03 用途权限与继承关系接口"列为关键路径交付物，并给出 M01/M02/M03 各自的具体验收点；否则 D1 名义上可启动，实际第一个 Sprint 就会阻塞。
