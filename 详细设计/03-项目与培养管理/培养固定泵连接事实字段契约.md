## 状态与版本

`res_culture_pump_connection_revision` 每次创建不可变版本；`res_culture_pump_connection_state` 每培养唯一，分别指向生效版本和至多一个活动候选。`EMPTY` 没有生效或候选；`PREPARED` 是尚无审批单的活动候选；`PENDING` 对应真实待审审批单；`APPLIED` 只有生效版本。`PREPARED` 和 `PENDING` 可以同时保留原生效版本，候选不能冒充原方案。撤回或拒绝保留历史版本，清除活动指针后恢复 `APPLIED` 或 `EMPTY`；有效事实不变。

2026-11-07 确认：默认连接撤回成功后应展示撤回前的生效配置，并恢复编辑。SC026 撤回在审批事务提交后复用 M06 交付执行器处理原 DISCARD，再由页面重读；尚无独立生效固定泵版本时，按既有来源规则读取生效补液方案或初始化配置。撤回不把待审修改写入原方案，不恢复为待审批内容；交付失败仍保留待处理候选，按原决定核验后继续清除。

2026-11-08 撤回事务补充：真实审批为 `CANCELLED/WITHDRAWN` 的 SC026 DISCARD，使用既有 M07 交付可写事务，先锁 SYSTEM，再复用实验室、培养、固定泵状态锁及原回执/CAS 清候选逻辑；不依赖 `futurefab.resource-transaction.enabled` 或定时 worker 开关。M06 专用证明口对照原审批、原交付及完整决定核验，仅接受本人撤回，不放宽 APPLY 或其他取消决定。只读查询核对原决定、候选指针和已存回执，不锁设备、不检查被撤回配置的运行条件；待清理返回 PENDING，已清理返回原 DISCARDED。失败回滚本次清理，保留原生效配置；重复决定不重复写入。该补充是下文后台资源事务约束的撤回例外，不变更批准应用路径。

审批通过并实际生效后，默认连接展示新生效版本并恢复编辑；再次修改从该版本发起新候选，按当次实验室审批配置处理。若有正在执行的任务，继续按既有安全屏障等待，尚未生效时不把待审值冒充生效值。

状态 `object_version` 用 CAS 保护指针，版本的 `base_effective_revision_id` 固定来源。首次创建状态受培养唯一键保护，重复或并发写入须重读核验，不能覆盖其他请求。相同 `request_key` 必须比较完整 `request_hash`：同载荷只返回原结果，不同载荷拒绝；持久化候选、审批和决定回执时遵循现有管理守卫与原决定投递协议。SQL 的外键采用项目既有逻辑关联方式；服务端必须检验所有版本均属于同一培养、实验室和控制器，且有效与候选身份不同。培养重新绑定控制器时，不得修改历史版本的设备身份，也不得把原控制器保存事实直接当作新控制器已保存；应按当前事实核验并产生新版本。

`plan_version` 原样冻结培养主记录的日期计划并发版本，允许非负整数；无完整日期计划的新建草稿为 `0`，有完整日期计划新建为 `1`，之后沿合法计划变更递增。该值不表示是否配置补液方案，也不等于固定泵状态版本。保存输入 `expectedPlanVersion`、候选信封、不可变版本、应用回执和来源读取须一致接受字符串 `"0"`，并与当前培养值精确比较；拒绝 null、负数、前导零、非整数及超过有符号 bigint 范围的值。不得为了保存固定泵而把主记录版本从 `0` 改成 `1`，也不将后续回到草稿的合法正版本归零。培养对象版本、固定泵状态版本和非空身份仍须为正整数；草稿、预约及运行场景的原权限、占用与状态校验不变。

`channels_json` 必须是服务端重新核验的完整、稳定通道集合，具体闭合格式和摘要见下节。当前 SQL 只提供承载，不代表资源冻结或生效链已实现。

`occupancy_id` 与 `occupancy_version` 必须成对；无占用草稿为空，预约或运行应固定并重验同培养的有效占用及其版本。占用待核验释放时依现行安全屏障处理，不以非空占用自动允许写入。草稿仅关联设备，必须核对培养自身的设备身份与通道，不得修改该设备的实验室默认配置。

## 方案与审批边界

已选补液且已有生效 FEEDING 方案时，同事务保留方案规则、生成并生效符合当前业务策略的培养方案快照，并在状态 `feeding_snapshot_id` 和生效回执中精确记录真实关联。未选补液或未产生新方案快照时该字段为空，不虚构方案。规则缺失、不匹配、无法冻结或存在活动候选时，按相应场景拒绝，不能将半成品当完整方案。

占用控制器修改属于 M07 所有的 SC026，提交需填写变更原因；M07 核实权限、设备占用、审批策略和任务安全屏障，经 M03 内部接口创建、读取及应用固定泵版本，M06 保留原审批和撤回事实。只有可信直接决定或审批通过并成功生效后才能推进生效指针。原审批通过但应用失败时不得显示已保存。反应器详情的默认连接入口及实验室泵默认连接入口在控制器空闲时，均依 [M02 空闲默认连接规则](../02-实验室与资源管理/默认连接与打印排版接口契约.md)读取并直接保存实验室初始化默认连接；无论是否关联草稿或草稿是否已有固定泵，都不回填或覆盖草稿。空闲弹窗中的外置泵字段置灰、不可更改，不增加空闲外置泵选择存储。

空闲控制器默认连接的保存不触发 M03 草稿固定泵版本、方案快照或批量同步；不得把实验室通道 `pump_id` 当成培养外置泵。独立培养配置的真实保存事实与补液规则仍按各自现行入口和契约核验，不能把实验室默认连接写入伪装成培养已保存。

W03 必须分别核验当前培养及控制器对应的固定泵有效保存事实，以及已选补液和必要计算规则的持久化事实；两个条件都满足才能显示已设置。2026-11-06 用户确认：该展示标识不要求 FEEDING 补液方案已经生效，不能用生效快照是否存在代替判断。补液勾选来自培养 `workflow_selection_json`，计算规则来自该培养 `res_culture_feeding_config` 的启用记录及完整五项配置。关联培养、实验室或控制器变化时须重核；不以历史记录存在、状态指针非空或当前候选代替有效性校验。运行准入独立校验开始完成、占用、有效方案、设备等条件，已设置不等于可执行。

## 固定泵内容与生效回执 v1

本节冻结实现输入与校验口径，不声明已有生产者或现存数据符合此格式。ID、版本及摘要从可信服务端事实取得；客户端不能提交资源名称快照、审批决定、生效回执或摘要作为权威。对象未知字段、重复键、尾随内容、错误类型或不支持的 schemaVersion 均拒绝；不可读按事实不可用处理，不解释成未保存。

`revision.channels_json` 是对象，字段闭合为 `schemaVersion`（整数 1）与 `channels`（数组）。数组按正整数 `pumpNo` 升序冻结，每项字段闭合如下：

| 字段 | v1 含义与约束 |
| --- | --- |
| `channelId`, `pumpNo` | 当前控制器的稳定通道 ID（正整数十进制字符串）、泵号（正整数 JSON 数字）；各自唯一；服务端核验完整通道集合及控制器归属，不能按显示顺序或名称猜 ID。 |
| `mediumId` | 培养基主数据 ID（正整数十进制字符串）或 null；其允许为空的条件与下方速度分支一致。 |
| `consumable` | null 或闭合对象 `{kind, id}`；台式非空时 `kind` 为 `BUCKET`、`id` 为正整数十进制字符串。 |
| `speedSelection` | 闭合对象 `{kind, code, slotKey}`；严格沿用 FEEDING 对 `UNUSED`、`CODE`、`TEMPLATE` 的组合校验。`UNUSED` 的 mediumId/consumable/code/slotKey 均为 null；`CODE` 的 code 为 `Speed1`～`Speed10`、slotKey 为 null；`TEMPLATE` 的 code 为 null、slotKey 为 `pump/{pumpNo}/speed`。非 UNUSED 的培养基、耗材及对应速度绑定按现有 FEEDING 校验。 |
| `speedBinding` | 非 TEMPLATE 时为 null；TEMPLATE 时为闭合对象 `{kind, strategyId, sourceTemplateId, sourceVersionId, effectiveSchemaVersion, effectiveParameters, effectiveApplicability, effectiveHash}`，所有键必须存在。`kind=LEGACY_STRATEGY` 时只有 `strategyId` 为正整数十进制字符串，两个 source 字段为 null；`kind=VERSIONED_TEMPLATE` 时只有 `sourceTemplateId` 和 `sourceVersionId` 为正整数十进制字符串，`strategyId` 为 null。两种身份互斥，服务端按槽位和实验室类型校验有效策略或模板与真实版本归属；后四字段分别冻结拥有方真实提供的有效版本号、参数、适用范围与摘要，名称保存在下述资源快照。旧策略只有目录 ID，不把 ID 自身当作真实版本，也不把模板 ID 当作策略 ID。已有 FEEDING 投影可能同时输出 `strategyId` 与 `sourceTemplateId`：应按真实来源类型提取身份，不能直接照抄造成混传或仅按两个数字是否相等猜类型。 |
| `externalPumpId` | 未使用外置泵为 null；否则为当前实验室有效外置泵 ID 的正整数十进制字符串，由服务端校验归属及现行引用约束；不代表物理连接或占用。UNUSED 行为 null。 |
| `resourceSnapshot` | 服务端生成的闭合对象 `{mediumName, consumableName, speedStrategyName, externalPumpName}`；对应资源不存在或对应可空身份为 null 时为 null，否则填经核验的名称。名称只作历史展示，不作为身份、完整性或唯一匹配依据。 |

`content_hash` 是上述闭合 `channels_json` 的 SHA-256 小写 64 位十六进制摘要：对象键按字符串字典序递归排序，数组保留上述泵号顺序，数字去除小数末尾无意义的零后使用十进制无指数形式（如 `100.0000`、`100.0`、`1E+2` 均为 `100`，不舍入、不丢精度），JSON 字符串标准转义，显式 null 不省略，无多余空白，以 UTF-8 字节计算。固定泵内容 schema 1/2 的生成、读取核验、展示投影和 M04 派生来源核验共同调用 `NormalizedPayloadHasher.canonicalJsonWithNormalizedNumbers`，避免数据库 JSON 字段改变数字表示导致同值摘要失配；原始节点仍须通过整数等字段类型校验。普通管理请求幂等摘要及 M04 补液包自身摘要规则不变。排序、校验和摘要计算由 M03 拥有方封装，写入和读取使用同一实现；不得通过依赖 M07 内部实现类跨模块调用。内容摘要只证明通道内容，不等于审批候选摘要。

SC026 的候选摘要另对以下**闭合候选信封 v1**计算。所有键均须存在，不能添加其他键；信封可由不可变 revision 行与服务端已经验证的内容重建，字段名与类型固定如下：

| 键 | 类型及约束 |
| --- | --- |
| `schemaVersion` | JSON 整数，固定为 `1`。 |
| `revisionId`, `cultureId`, `labId`, `controllerId`, `cultureVersion`, `createdBy` | 非空字符串，均为无前导零的正整数十进制文本，分别对应 revision 行的同名身份、版本和可信创建人。 |
| `planVersion` | 非空字符串，非负整数十进制文本；`"0"` 为合法无日期计划初始版本，非零值不得有前导零，原样对应 revision 行的 `plan_version`。 |
| `baseEffectiveRevisionId` | 字符串或 null；非空为无前导零的正整数十进制文本，与 revision 行对应。仅首次、没有原生效版本时为 null。 |
| `occupancyId`, `occupancyVersion` | 均为字符串或均为 null；非空时为无前导零的正整数十进制文本，与 revision 行对应。草稿没有自己的占用时均为 null；预约、运行时必须固定同培养的有效占用及其版本。 |
| `contentHash`, `requestHash` | 非空字符串，分别与 revision 行的 `content_hash`、`request_hash` 一致；均为小写 64 位十六进制摘要。 |
| `requestId` | 非空字符串，与 revision 行及管理守卫的原请求 ID 一致；按项目写接口的 UUID 格式校验。 |
| `reason` | 字符串或 null，与 revision 行 `reason` 对应；占用培养的 SC026 变更须去除首尾空白后为 1—500 字符。草稿直存沿其入口现行原因规则，未提供时为 null；提供时去除首尾空白，空串归一为 null，非空不超过 500 字符，不因草稿虚构审批政策或原因。 |
| `createdAt` | 非空 JSON 字符串；revision 行 `created_at` 的真实 UTC 时刻，ISO-8601 写为 `yyyy-MM-dd'T'HH:mm:ss.SSS'Z'`，精确到毫秒。写入时截断到毫秒，重建时按 UTC 解释数据库值并保持三位小数；不能用当前时间替换原创建时刻。 |

`candidateHash` 是对完整信封使用上文相同规范化及 SHA-256 算法计算的小写 64 位十六进制字符串；信封及其原文与 M06 候选身份、摘要同源固定，不以客户端传入值覆盖。不得将 M04 的 packageHash 或本表 contentHash 直接冒充候选摘要。草稿直接保存仍使用自身的真实同事务证据，不由此引入 SC026 审批或政策。

SC026 审批候选以不可变 `revisionId` 为 `candidateId`，该候选的 `candidateVersion` 固定为十进制字符串 `"1"`；每次新变更新建 revision，重试保持同一候选身份和内容。此版本不代替培养对象版本、日期计划版本、固定泵状态版本或占用版本，各版本仍按各自事实校验。M06 申请来源、结构化候选引用及 `ChangeSnapshot` 正文的 `ownerModule` 均为 `M07`，目标类型为 `CULTURE`；M03 保持 revision、通道及候选信封的事实拥有方，M07 通过内部契约获取真实事实并编排 SC026。`ownerSchemaRef` 应指向已核准的 M03 固定泵候选 schema，引用该 schema 不改变审批拥有方。

SC026 审阅快照由 M07 按 M06 `ChangeSnapshot` 契约生成：结构化引用和正文的目标身份、期望目标版本、候选 ID、候选版本、候选摘要、schema 引用和影响类型一致；正文的培养、实验室、项目、批次须与申请中的真实祖先一致，`relatedTask` 为 null。差异字段及前后段使用真实固定泵通道事实，包括培养基、耗材、泵速策略与外置泵；资源名称只用于展示，不作为身份。来源方案版本 ID 仅在存在真实方案版本身份时填写，不以日期计划版本冒充；影响说明只描述经事实支持的影响。

培养基和耗材以资源 ID 判断是否变更；展示名称优先使用来源快照，缺失时提交审批前按 ID 批量解析主数据并冻结在审阅原件中。来源与候选的 ID 相同时不生成该字段的变更项。后续核验使用已冻结的审阅名称，不重新读取当前主数据；无法取得名称时显示空值，不将 ID 当作名称。已有终态审阅原件与回执不得因展示规则变更而改写。

泵速策略的前后身份及有效参数均来自固定事实：旧策略按策略 ID，版本化模板按模板 ID 和版本 ID 判断；身份和冻结的有效参数一致时不生成变更项。数值按实际数值比较，事实不完整时保留原有严格判断。

候选建立时，在管理守卫事务与一致性锁下固定变更前事实、校验后的变更后事实和真实原因，并持久化与该候选的关联，以支持之后原样审阅和核验。前值依次选择本培养固定泵生效版本、本培养已生效 FEEDING 方案、实验室默认连接；只有前一来源明确不存在时才可考虑下一来源，来源存在但无法核验时拒绝，不得降级。不可在审批查看或生效时用后来发生变化的当前值重建历史前值。已生效固定泵前值按草稿 v1 或 SC026 v2 严格分派；v2 再对照真实 M06 原件，不能按草稿解析而拒绝后续正常修改。

### SC026 前值原件与候选信封 v2

本节冻结占用培养 SC026 的原件协议，不改变草稿直存继续使用的 v1。目标表及空库开发基线已补齐下述前值与审阅原件承载；候选保存与审阅原件核验已有真实生产实现，具体运行验收另记。不能只修改 codec 或以 M06 审批单代替 M03 前值原件。

SC026 的 `channels_json` 使用内容 schema 2，闭合为 `{schemaVersion,channels,frozenBindings}`；草稿直存的内容 schema 1 不变。`channels` 沿用上节完整字段及校验，`frozenBindings` 按 `slotKey` 升序保存同次资源冻结得到的 M04 标准完整绑定，不重新读取审批后的当前模板。TEMPLATE 泵速对应完整 `{slotKey,parentRuleId,source,effectiveSchemaVersion,effectiveParameters,effectiveApplicability,effectiveHash}`；`source` 保留真实 `templateId/versionId/versionNo/templateKind/nameSnapshot/contentSchemaVersion/calculationProfile/canonicalHash`，与通道内速度身份、有效参数及摘要一一核对。外置泵对应同次核验设备事实的 `{bindingKind,slotKey,pumpNo,pumpId,label,deviceNo,model,spec,pumpSpeed}`，其中 `bindingKind=EXTERNAL_PUMP`。CODE/UNUSED 不产生泵速模板绑定，未选外置泵不产生外置绑定；多余、缺失、重复或错配绑定均拒绝。完整内容参与 `content_hash` 及 v2 候选摘要。展示接口只在完整验真后投影原 v1 通道 DTO，不更改页面样式或字段；该投影不充当持久化原件。内容 schema 2 与候选信封 schema 2 是各自独立的制式，不能用其中一个跳过另一个校验。已有 `channels_json` 承载本次结构，无新增表列；本批不处理 SC026 旧内容格式。

候选建立时，M03 以候选 revision ID 持久化不可变前值原件，原件闭合为 `{schemaVersion, sourceKind, cultureId, labId, controllerId, baseRevisionId, baseContentHash, workflowNodeId, feedingSnapshotId, feedingSlotVersion, feedingParameterGeneration, feedingPackageHash, channels, currentFeeding, lifecycleState, occupancyState}`。`schemaVersion` 为整数 1；三个身份均为正整数十进制字符串，必须与候选 revision 一致；所有键必须存在，不允许额外键。本前值格式尚无生产写入，按本次确认直接采用此单一格式，不引入历史兼容分支，草稿候选 v1 不受影响。来源按下列顺序判断，只有已证明上一级不存在才可使用下一级；来源存在但损坏、不可见、存在歧义或核验失败时拒绝，不能回退：

- `sourceKind=EFFECTIVE_REVISION`：`baseRevisionId`、`baseContentHash` 分别为真实生效 revision ID 和该版本重算后的内容摘要，均非空，且 ID 与候选的 `baseEffectiveRevisionId` 相同；五个 `feeding`/工作流字段及 `channels` 为 null。读取时须检验被引用版本的培养、实验室、控制器、内容与摘要，不复制或重建该版本。
- `sourceKind=FEEDING_PLAN`：仅当无固定泵生效版本且存在唯一可核验的本培养生效 FEEDING 方案时使用。`baseRevisionId`、`baseContentHash`、`channels` 为 null；`workflowNodeId`、`feedingSnapshotId`、`feedingSlotVersion`、`feedingParameterGeneration` 为真实身份或版本的十进制字符串，`feedingPackageHash` 为真实固定包摘要。须核验同培养、实验室、控制器及工作流节点，当前槽位生效指针、槽位版本、参数代次、不可变快照、真实应用原件及回执一致，并由 M04 按其固定包规范复核完整包与摘要；不得把当前模板或待审候选作为生效方案。前值从已核验包的固定泵内容、泵速绑定及外置泵绑定按真实泵号投影，严格保留身份和空值，不合成缺失绑定；原包中的补料和补糖规则完整保留，固定泵修改生效时仍按现行方案替换和安全屏障规则处理。槽位版本和参数代次不互换；原件不复制可变当前方案，审阅按固定快照和摘要重读并核验。
- `sourceKind=DEVICE_DEFAULT`：仅当无固定泵生效版本且已确认无培养生效 FEEDING 方案时允许，`baseRevisionId`、`baseContentHash`、五个 `feeding`/工作流字段均为 null；`channels` 是同次一致性读取的完整控制器通道数组，按正整数泵号升序，通道 ID、泵号分别唯一。每项闭合为 `{channelId, pumpNo, materialNameRaw, feedContainerRaw, speedStrategyRaw}`：`channelId` 为正整数十进制字符串，`pumpNo` 为正整数 JSON 数字，三个 `Raw` 值为数据库实际字符串或 null，保留原文、空串和 null 的区别。通道、实验室和控制器身份由服务端核验；不能把控制器通道的 `pump_id` 当成外置泵。默认连接没有培养侧外置泵事实，审阅前值应表现为未知或不适用，不能推断为不使用。

`lifecycleState` 和 `occupancyState` 保存同次持锁核验的培养生命周期和占用状态，供 M07 提审安全屏障判断；预约未开始为 `NOT_STARTED` + `RESERVED`，运行培养为 `RUNNING` + `RUNNING/RELEASE_PENDING`，延期仍沿用真实合法占用状态。重放从该不可变原件读回，不以当前状态替换。`CultureOperationFactsPort` 登记 `M07-PUMP-CONNECTION-PREPARE` 只读用途，仍核当前可信会话和培养操作范围；该读值不能代替锁内复核。

`currentFeeding` 独立记录同次锁内确认的本培养生效补液方案，不由 `sourceKind` 推断。没有生效方案时为 null；有方案时闭合为 `{workflowNodeId, snapshotId, slotVersion, generation, packageHash, applicationId}`，除小写 64 位摘要 `packageHash` 外均为正整数十进制字符串。`applicationId` 来自唯一的真实 `res_culture_parameter_application` 生效原件，须核对其政策、原回执、快照、代次和固定包。无论前值是否优先取固定泵版本，提交都须核对客户端从对应读取取得的 snapshot/slot/generation 期望值；`FEEDING_PLAN` 来源的五项值须与此对象相等，`DEVICE_DEFAULT` 必须为 null。当前槽位最近的 application_receipt 可能来自后续丢弃，不得以其替代原生效应用回执，也不得因最近回执不同抹去原有效方案。保存后重放按冻结身份核验不可变快照和应用原件，不从后来生效方案重建。M07 使用此独立身份声明真实任务替换影响，候选保存本身不替换方案或任务。

默认原始文本不是培养固定泵 `channels_json`：旧代码、名称、不可解析值及空值应原样保留，不通过名称猜主数据 ID，不把未解析值伪装成 `UNUSED` 或无变更。审阅可同时展示服务端能从可信来源确认的名称，但名称和解析结果不能覆盖原件；不能证明泵号、完整通道集合或读取一致性时拒绝提交。原件作为候选前值证据，不得将其本身视为培养固定泵已保存事实。

`beforeHash` 对完整前值原件按本节已定义的 JSON 规范化和 SHA-256 计算，为小写 64 位十六进制字符串。SC026 候选信封 v2 的字段集合与上文 v1 完全相同并增加必填 `beforeHash`；其中 `schemaVersion` 改为整数 2，其余字段含义和取值约束不变。`candidateHash` 对完整 v2 信封按相同规范计算。不得修改 v1 的闭合字段、哈希规则或已保存原件；读取时按 schema 版本严格分派，未知版本拒绝，不能将 v1 重新解释为 v2。`candidateId` 为真实 revision ID、`candidateVersion` 为 `"1"`，M06 的 producer、候选引用及快照正文 owner 均为 `M07`；M03 负责冻结原件与校验摘要，M07 按授权内口取得可信事实并编排，不接受客户端声称操作者、摘要或审批身份。

前值原件、后值 revision、候选及 M06 提审快照须在同次管理守卫事务中从可信事实生成并绑定；前后展示内容、原因、关联培养祖先及目标版本应与候选、申请一致，M06 真实申请的 `change_snapshot` 保存审阅副本。冻结的审阅正文或其可验证原件还须支持无审批路径和重试，不得用后续可变培养信息重建原申请。所有相关默认连接写入口须遵守共同锁协议，或由拥有方提供能够证明完整通道集合与无幻读的等价并发控制；需同时核验培养、状态、占用、来源和资源版本，提交前任一变化或可信事实不可得则拒绝。首次初始化状态通过培养唯一约束和 CAS 防并发覆盖；原件、revision、审批关联、状态和审计任一写入失败整体回滚。

同一请求重试复用原 request ID、请求摘要、revision、前值原件和候选摘要；不同载荷使用同一幂等身份须拒绝。审批通过、撤回或拒绝均绑定同一候选及真实审批身份；审批通过不等于业务已生效，重放时核验原件而不是重取当前默认值。源码和契约测试不声明数据库或 HTTP 验证通过。

### v2 原件的最小持久化与读取分派

继续使用 M03 的三张固定泵事实表，不增设旁路候选表。在 `res_culture_pump_connection_revision` 增加以下列，与既有后值、来源身份、请求、操作者和原因在同一不可变行中一次插入：

| 列 | 类型、空值与含义 |
| --- | --- |
| `candidate_schema_version` | `bigint NOT NULL DEFAULT 1`，仅允许 `1`、`2`。这是候选信封格式，不是 revision 业务版本、前值原件格式或 M06 正文格式。新 SC026 必须显式写 `2`；默认 `1` 只保持既有 v1 写入形状，不能用来容错降级。 |
| `before_original` | 可空 JSON；v2 必须为本节闭合前值原件对象，其自身 `schemaVersion=1`；v1 必须为 SQL NULL。保存完整规范化原件，不能只存摘要或只存 M06 单据引用。 |
| `before_hash` | 可空 `char(64)`，`ascii/ascii_bin`；v2 为完整前值原件的规范化 SHA-256 小写十六进制摘要，并作为候选信封的 `beforeHash`；v1 为 SQL NULL。 |
| `review_original` | 可空 JSON；v2 必须为 M07 按现行 M06 `ChangeSnapshot` 契约生产并核验的完整审阅正文，正文自身 `schemaVersion=1`、`ownerModule=M07`；v1 为 SQL NULL。直接/免审和提审路径均保存，不以是否创建审批单决定保留与否。 |
| `review_hash` | 可空 `char(64)`，`ascii/ascii_bin`；v2 对完整 `review_original` 使用同一 JSON 规范化及 SHA-256 规则计算；v1 为 SQL NULL。摘要不放进正文，避免自引用。 |

候选 v1 仍使用原闭合字段、规范化、`contentHash`、`candidateHash` 和应用回执格式；新增存储列不参与 v1 摘要。v2 候选仅按上节增加 `beforeHash`，不将 `reviewHash` 塞入候选或改变 M06 正文格式。`review_original` 自带的 `candidateHash` 必须等于从该行可信字段及前值原件重算的 v2 候选摘要；培养、实验室、控制器、祖先、目标版本、候选身份、schema 引用及影响字段均须与同次冻结事实一致。原因以同一行 `reason` 冻结，M06 `submissionReason` 与之保持一致，不给 `ChangeSnapshot` 擅加字段。

M07 通过授权内部协作取得 M03 已校验的前后事实，生成可信审阅正文后由 M03 在同一管理守卫事务中一次持久化完整 revision。不得先插入不完整 v2 行，再更新不可变行补审阅证据；审阅生成或任何一项持久化失败全部回滚。实际提审时 M06 `change_snapshot` 保存与该原件规范化后完全相同的审阅副本；免审路径虽没有 M06 审批单，也保留同样原件及真实直接决定证据。管理审计和短期幂等缓存不能代替该原件。

读取先按 `candidate_schema_version` 明确分派：`1` 必须四个新增原件/摘要列均为 SQL NULL；`2` 必须全部存在且通过各自闭合格式、身份、内容与摘要核验；其他版本拒绝。JSON null 不等于 SQL NULL；v2 原件必须是对象。缺失或损坏 v2 证据不得尝试 v1、重取当前默认连接或补写历史原件。重放和历史查看只按原 revision 校验冻结证据，不要求原 revision 仍为当前生效版本。

DDL CHECK 约束 schema 值域、v1/v2 的完整空值组合、JSON 对象、摘要长度和小写形状，以及 v2 必有占用身份/版本和非空原因；既有正身份、占用成对、非负 `plan_version` 与唯一请求键继续生效。完整 JSON 字段、十六进制值、来源可用性、摘要重算、跨行身份与共享锁仍由拥有方服务核验，CHECK 不替代应用守卫。没有新增业务种子或更新/删除历史原件的路径；已有库不能重跑空库 DDL，本次只同步设计来源和安装生成物，运行结构升级须另行审查。

`state.application_receipt` 是 M03 生效后同事务写入的闭合 v1 对象，字段为：

| 字段 | v1 含义与约束 |
| --- | --- |
| `schemaVersion`, `result` | 整数 `1`、固定字符串 `APPLIED`；候选建立、送审、审批通过未生效、拒绝和撤回不得写成 APPLIED。 |
| `cultureId`, `labId`, `controllerId`, `effectiveRevisionId`, `contentHash`, `candidateHash` | 生效时的真实身份和摘要，分别与 state、生效 revision、重算内容及原候选信封核对；ID 为正整数十进制字符串。 |
| `previousRevisionId`, `feedingSnapshotId` | 本次生效前版本及同事务实际生成的 FEEDING 快照 ID；无对应事实时显式 null，不创建占位快照。 |
| `stateVersion`, `cultureVersion` | 生效后的状态版本及生效时重新核验的培养对象版本，均为正整数十进制字符串。 |
| `planVersion` | 生效时重新核验的日期计划版本，非负整数十进制字符串；允许 `"0"`，与不可变版本冻结值一致。 |
| `occupancyId`, `occupancyVersion` | 生效时校验的占用 ID、版本，同为正整数十进制字符串或同为 null；预约或运行必须具有同培养有效占用。 |
| `decision` | 闭合对象 `{mode, decisionKey, decisionHash, approvalId, decisionVersion, policyRevision}`。mode 仅 `DRAFT_DIRECT`、`POLICY_DIRECT`、`APPROVAL`；其余均为字符串或 null。草稿直存不造政策和审批，`approvalId`、`decisionVersion`、`policyRevision` 显式为 null；政策直存要真实政策版本及可信直接决定原件，审批身份为 null；审批生效要真实审批 ID、决定版本、政策版本和可信 APPLY 决定原件。`decisionKey`、`decisionHash` 均绑定各模式真实决定原件；不从场景、空审批号或页面值推断豁免。 |
| `checkedAt`, `appliedAt` | 非空 JSON 字符串，分别为真实校验和生效时刻，使用 UTC `yyyy-MM-dd'T'HH:mm:ss.SSS'Z'` 格式并精确到毫秒；取同次事务可信时间，不能编造。 |

`DRAFT_DIRECT` 只有在 M03 草稿保存守卫事务内实际生成并持久化了可验证的原始决定证据时才允许使用：证据至少绑定可信操作人、培养及控制器、原请求 ID 和请求摘要、候选摘要、原状态版本、保存时刻及结果；`decisionKey` 指向该原件，`decisionHash` 为该原件按本节规范计算的摘要。读取当前生效配置时须核验原件、回执和当前生效版本的一致性；重放历史成功请求时核验原请求对应的不可变版本与同事务应用原件，不要求它仍为当前生效版本。该证据不构成 M06 审批或政策；来源不可得时必须拒绝生效或报告事实不可用，不得合成直接决定。

不可变原件存于 `res_culture_pump_connection_application`：`application_id` 为真实原件身份，关联培养、实验室、控制器、固定泵 revision、可信请求操作者及原请求 ID；请求摘要和候选信封摘要分别固定为 `request_hash` 和 `candidate_hash`。`previous_state_version` 是应用前已持久状态版本；`previous_revision_id` 记录原实际生效版本，可为 null。`decision_mode` 区分 `DRAFT_DIRECT`、`POLICY_DIRECT`、`APPROVAL`，`decision_original` 保存可信决定；`decision_key` 唯一，`decision_hash` 采用对应真实决定摘要。`outcome` 为 `APPLIED` 或 `DISCARDED`；前者必须有实际 `applied_at`，后者仅清除该候选并保留原生效版本，`applied_at` 和 `feeding_snapshot_id` 均为 SQL NULL。`checked_at` 保存本次真实核验时刻；`feeding_snapshot_id` 仅在同事务产生真实 FEEDING 快照时填写。原件仅插入，不更新、不删除；原件、状态 CAS、派生快照、任务替换与管理审计一并提交或回滚。管理请求 24 小时回执及审计日志不能代替长期决定原件。

`DRAFT_DIRECT` 的 `decision_original` 是闭合 v1 JSON：`schemaVersion` 固定整数 1；`mode` 固定 `DRAFT_DIRECT`；`decisionKey`、`requestId`、`requestHash`、`candidateHash` 与原件行同名列一致；`applicationId`、`cultureId`、`labId`、`controllerId`、`revisionId`、`actorUserId`、`previousStateVersion` 为相应正整数列的十进制字符串；`previousRevisionId`、`feedingSnapshotId` 为对应列的十进制字符串或 null；`result` 固定 `APPLIED`；`checkedAt`、`appliedAt` 按本节毫秒 UTC 格式对应原件行真实时间。无其他字段；`decisionHash` 不属于原件正文，按本节 JSON 规范对该对象计算，避免自引用。原件字段同时与可信会话、revision、状态及事务结果核验，不信任客户端提供的原件或摘要。

`APPROVAL` 采用闭合原件 `{schemaVersion,mode,applicationId,cultureId,labId,controllerId,revisionId,actorUserId,previousStateVersion,previousRevisionId,feedingSnapshotId,requestId,requestHash,candidateHash,reviewHash,decisionKey,decisionHash,result,checkedAt,appliedAt,approvalDecision}`。格式版本为 1；`feedingSnapshotId` 为真实派生快照或 null；`result` 对应 APPLIED/DISCARDED，DISCARDED 的 `appliedAt` 为 null。`approvalDecision` 保存 M06 完整决定，`decisionKey=M06:<approvalId>:<decisionVersion>`，`decisionHash` 使用 `ApprovalDecisionDigest.v1`。后台写入与重放必须经 `FixedPumpWorkerDecisionProofPort` 对照真实审批单、交付和冻结政策，不能以客户端命令代替。批准从 PENDING CAS 为 APPLIED，撤回/拒绝 CAS 清候选并保留原生效回执。`POLICY_DIRECT` 使用同样公共字段，将 `approvalDecision` 替换为 `directDecision`；其值为既有 M06 `DirectParameterDecisionPort.Evidence`，`workflowNodeId=null`、`packageHash=固定泵contentHash`。仅原 `M07-PUMP-CONNECTION-PREPARE` 管理守卫事务内由 M06 `requireCurrent` 认可的原件可直接应用，空审批号不构成依据。历史核验用 `requireOriginal`，不授予当前写入权限。

`CulturePumpActivationPort` 的批准及非本人撤回的 DISCARD 通过唯一 `M03_PUMP_CONNECTION_APPLY` 后台资源事务，持久身份为已提交固定泵 revision，资源集合为其培养；本人撤回按上文撤回事务补充执行，政策直存使用原管理守卫事务，不嵌套后台资源事务。先核验真实 M06 决定及原发起人当前权限，再按实验室、培养、占用、固定泵状态和补液槽顺序复核，取得 M07 安全事实和 M02 持锁完整通道。`WorkerProof.labId/cultureId` 与候选和锁内培养逐项一致。运行中的任务不被中断，应用等待其结束；未执行任务通过既有计划代次替换端口作废并按新配置、当前任务审批政策重新生成。已有 FEEDING 时，M04 以旧固定包和候选内完整冻结绑定派生新包，保留补液计算规则；该派生不伪装成独立补液快照审批。合法 NOT_STARTED+RESERVED 尚未连接且无任务时，M07 返回 WAITING_CONNECTION，保存新 FEEDING，回执 barrier 为 null，不创建虚构运行或任务。待审补液方案或未决物理动作仍阻止应用。结果查询先核原 M06 决定；已有原件重放 APPLIED/DISCARDED，确认仍待应用时返回 PENDING，不将审批通过视为生效。

SC026 派生 FEEDING 的 `res_culture_parameter_application.result_json` 使用回执 schema 3，保留现有公共快照/代次/校验/屏障字段，`policy=null`，不含 `directDecision`，新增 `pumpConnection={applicationId,revisionId,candidateHash,contentHash}`；`policy_evidence` 保存同一关联对象。该对象精确指向同事务固定泵应用及其真实决定，不能将 revision 或固定泵摘要冒充补液参数候选审批。读取须核固定泵应用、M06 原件、旧方案身份与代次、新快照身份、申请人和原请求，并核 M04 包摘要。`CulturePumpFeedingSourcePort` 与 `CulturePumpPlanReplacementSourcePort` 仅在同一原应用事务中提供已验真的旧固定包、已保存派生快照及原代次替换事实；回调结束立即清除，不能由页面传入证明。

生效前服务端重验当前培养、控制器、占用及状态版本、完整通道和资源身份。运行期方案变更须落实 M07 任务及设备安全屏障；草稿尚未启动工作流时只保存该培养的配置，不修改运行方案、不占用或控制设备，持培养锁复核草稿状态、未启动及自身无有效占用，不能借此放行运行期变更。已有生效补液方案时，固定泵版本与保留规则后的新 FEEDING 快照及其真实应用回执同事务生效；失败回滚，不推进指针。撤回或拒绝保留旧生效版本及旧生效回执。重复决定以原决定身份、原件和回执验证重放，不创建第二个版本。

W03 配置展示读取时校验 state、生效 revision、规范内容摘要及实际应用原件/回执的培养、实验室、控制器与生效身份一致；原件损坏按事实不可用处理。用户确认设备初始化后通道编号正常不可修改，因此“已设置”不附加当前设备通道映射比对；正常按泵号读取数据和保存原件的完整性校验保持不变。补液勾选和计算规则独立核验，不读取或要求生效 FEEDING 方案。`feedingSnapshotId` 记录固定泵保存时实际关联的历史方案，不能作为“已设置”的必要条件；后续仅调整计算规则或方案快照不得因此抹去有效保存事实。PREPARED/PENDING 存在旧有效版本时仍核验并展示旧版本的保存事实，新候选本身不算已保存；只有候选而没有旧有效版本时为未设置。

`W03ConfigurationStatusPort` 是 M03 拥有的只读批量端口，先核验当前操作者的完整培养查看范围，再按实验室和精确培养集合分批连接读取培养、计算规则、固定泵 state/revision/application，每批最多 200 条。缺配置或五项未填完整为未设置；原件损坏按事实不可用拒绝。普通默认连接读取与 W03 共用核验：DRAFT_DIRECT v1 保持草稿规则；APPROVAL v2 验 M03 原件后按批调用 M06 `verifyApplied` 对照真实审批与投递，逐项比对；POLICY_DIRECT 验 M06 原始免审证据，不查询或制造审批单。后续变更以前一 SC026 v2 为前值时仍验真实决定，历史原件不依赖当前生效指针。普通来源读取独立返回 `currentFeeding={snapshotId,slotVersion,parameterGeneration}`，无生效方案明确为 null；即使展示 SAVED_REVISION 也不省略。活动固定泵候选另投影 `pending={revisionId,approvalId,applyState}`，展示仍取旧已生效版本。W03 不新增生效补液方案要求；实际执行另核占用、方案和设备。HTTP、浏览器、审批投递和设备联调须分别验证。

变更此模型须同步 M03 当前字段字典、目标 DDL 来源、开发基线三份安装文件中的相关结构与核验、拥有方清单及来源/产物摘要；独立部署升级方案不得冒充空库安装链。真实数据库、HTTP、浏览器和设备均须独立验证。
