## 1. 唯一拥有方和政策

M03 拥有培养模式、初始培养重量和 res_culture_change_candidate；M06_SC029/M06_SC030 的 candidate/apply/query/seal 均由 M03 提供。M07 仅提供计量读取、执行屏障与快照消费，不另建培养重量可写主表。2026-10-26 用户确认：运行中的 MODE/INITIAL_WEIGHT 变更必须填写原因并由 M06 真实 APPROVAL 政策建单；禁止业务端把 DIRECT 改成 APPROVAL。只有从未开始（firstWorkflowStartedAt 为空且不在 RUNNING/DELAYED）的草稿/未开始/已过期 MODE 保留原 Q31 及场景政策；免审批不放宽动作准入。已有首次开始事实的培养即使状态回到 NOT_STARTED，仍需原因与审批。

SC030 目录拥有方更正为 M03，来源 readiness 在本文、字段迁移、M03/M07 同事务屏障和 M06 owner 注册均实现后才可 READY；保持 OWNER_GATED 到部署验收，不能只改目录就开生产。已有 SC030 候选/审批不可原地改 owner/hash：上线前枚举并保留原拥有方只读/原协议结案；未结案旧记录阻止该实验室新 SC030 入口，其他场景不受影响。既有完整实验室政策内容不因更换技术拥有方重新导入或改档。此处培养模式变更的业务审批仍按原规则，政策自身无须单独核准、启用或暂停。

## 2. 页面及公开协议

沿 M03 Authorization、W0={requestId:UUID36,managementRevision:Version}、字符串 ID/Version、统一错误外壳。只接受下表字段，不允许改 sceneCode、actor、candidateHash、审批人或状态。

| 接口 | Body/Query | 输出和权限 |
| --- | --- | --- |
| B05-M POST /resource/culture/{cultureId}/mode | W0、expectedVersion、mode:REACTOR、reason:运行变更须去空白 1..500 字，仅从未开始且原政策允许时可 null | RuntimeChangeView；resource:culture:mode＋Q28/Q29 当前身份、实验室操作权及原中试/单向/设备条件 |
| CU-W01 GET /resource/culture/{cultureId}/initial-weight | 无 | InitialWeightView；resource:culture:query＋当前对象读取范围 |
| CU-W02 POST /resource/culture/{cultureId}/initial-weight-changes | W0、expectedVersion、expectedWeightRevision、initialWeightG、reason:去空白 1..500 字 | RuntimeChangeView；resource:culture:edit＋Q25/Q29 身份及实验室操作权 |

InitialWeightView={cultureId,cultureVersion,weightRevision,initialWeightG:null或十进制字符串,unit:"g",displayUnit:"g"或"kg",effectiveAt:null或UTC时刻,sourceCandidateId:null或ID,allowedActions:[VIEW,CHANGE],issues:[{code,message}]}。展示规格≤15 L用g，>15 L用kg；规格未知仍可明确按g显示，不伪造规格。kg 只展示 initialWeightG/1000，不转换为体积。输入框固定标注g，接种与培养基由人员合计录入。服务端 initialWeightG 必须为正整数的规范字符串，范围 1..99999999999999；不是IEEE浮点数，不接受科学计数、0、负数、额外小数或隐含密度换算。该范围为 DECIMAL(20,6) 的技术存储上限，不代替设备/工艺限制。

CU-W02 的首次录入（原值null、weightRevision=0）与后续修改走同一链。按14正文，须存在本培养任一工作流已完成的可信事实，并且当前 RUNNING/DELAYED；仅创建工作流或正在运行不足以放行。首次输入未就绪前只阻止依赖初始重量的计算/执行，不阻止无此依赖的资源查询或工作流步骤；不能补0来解锁。终态不可改。接续培养存在已安装基线时返回 STATE_CONFLICT，须沿原接续 ADJUSTMENT 对账，不用改初始值改变接续基线。

RuntimeChangeView 沿运行变更契约全部字段，operation 扩充 MODE/INITIAL_WEIGHT。运行变更 reason 始终必填；仅从未开始 MODE 保留原 DIRECT 可 null、DIRECT_REASON/APPROVAL 必填规则。MODE 的 before/after 仅 cultureMode 与固定设备身份/版本；INITIAL_WEIGHT 仅 initialWeightG、weightRevision（after=before+1）。服务端按动作映射 SC029/SC030，实际不变返回 INPUT_INVALID，不创建空候选。运行变更政策不是 APPROVAL 时返回 POLICY_UNVERIFIED，要求配置实验室真实批次或项目审批；旧候选、原回执和从未开始 MODE 的免审批链不改写。响应必须区分 PENDING/APPLIED/CONFLICT/UNKNOWN，不能把已提交显示为已修改。

CU-R01 仍只允许 CODE/DATES，不接受 MODE/INITIAL_WEIGHT，避免第二写入口。已有 CU-R02/03/04 扩展为上述四种 operation 的共用只读查询；按当前读取权限返回，原 requestId 查询仍仅本人。它们使用同一活动候选槽（PREPARED/PENDING/UNKNOWN），不得并行提两种基础修改绕过占用。

CultureOperations.overview 的模式组件调用 B05-M；balance 中嵌入 M03 初始重量组件，GET CU-W01→编辑原因/数值→CU-W02→CU-R 查询。待审弹窗显示前后值、审批状态且只读；有合法撤回权才调用 M06 API08 WITHDRAW，不能 CU04 撤回草稿。M06 撤回后等待 M03 DISCARDED 才解锁。超时按原 UUID 查询/同载荷重试，绝不改键重做 UNKNOWN。

B05-M 返回类型为目标契约变更：旧客户端只能在 APPLIED 后收到其兼容同步 W，PENDING/UNKNOWN 不得伪装 W.applied=true。上线前更新调用方；客户端不支持候选状态时禁止启用需要该分支的入口，不自动降级 DIRECT。

## 3. 候选版本、权威字段与事务

2026-10-13 实施细化：MODE 只允许 DRAFT/NOT_STARTED/EXPIRED/RUNNING/DELAYED，拒绝终态；M02 锁定实际实验室并核准中试类型、设备归属、启用/删除及当前配置。当前集成反应器表无独立对象版本，固定设备配置使用 M02 生成的白名单配置 SHA-256 指纹（deviceVersion，非培养版本或 SYSTEM 管理版本）；审批生效必须与固定指纹相同，配置变化返回 CONFLICT，不自动迁移候选。INITIAL_WEIGHT 数值未变化须在派生新 revision 前拒绝。


新 MODE/INITIAL_WEIGHT 候选采用 schemaVersion=2；既有 CODE/DATES schema1 及旧 MODE schema1 保留原字节/hash/原读写协议结案。未知schema拒绝。schema2 的 hash 输入使用公共规范化规则，完整包括 schemaVersion、operation、cultureId、expectedTargetVersion、sceneCode、before、after、reason、policyEvidence、impact；值固定后不可改，派生值也由服务器生成。policyEvidence 沿M06原固定结构，不能重取审批时新政策替换原证据。

新系统物理表必须显式保存 `schema_version`、`operation_code`、`management_revision`、`expected_weight_revision` 和 `impact_snapshot`，而不是仅靠scene或JSON内容反推。`scene_code/operation_code`严格一一对应：SC027/CODE、SC028/DATES、SC029/MODE、SC030/INITIAL_WEIGHT、M03_DEVICE_CHANGE/DEVICE；INITIAL_WEIGHT必须携带expectedWeightRevision和非空reason，其他操作不得伪填expectedWeightRevision。DDL见23完整目标；这组CHECK是静态行形状保护，hash不可变、状态迁移和跨行并发仍由领域守卫负责。

impact 对 MODE={kind:MODE,invalidatesUnstartedCalculations:true}；INITIAL_WEIGHT={kind:INITIAL_WEIGHT,oldWeightRevision,newWeightRevision,invalidatesUnstartedCalculations:true,preserveDayStart:true,preserveExecutedSnapshots:true}。此结构为拥有方候选证据，不向M06通用枚举偷加值；审批显示 before/after 和此拥有方影响明细。

M06 ChangeSnapshot.impact 使用既有 kind=NONE、oldPlanVersionId=null、taskTypes=[]；description写明拥有方计算预览失效及历史保留规则，ownerSchemaRef指向本文schema2。NONE表示不取消业务任务，不表示省略M07计算失效屏障。计算输入schema2增加initialWeightRevision、cultureVersion并使用原算法版本，旧计算输入保持原schema/hash；启动前必须具备v2消费能力。

新增 res_culture 的目标列：initial_weight_g DECIMAL(20,6) NULL、initial_weight_revision BIGINT UNSIGNED NOT NULL DEFAULT 0、initial_weight_effective_at DATETIME(3) NULL、initial_weight_candidate_id BIGINT NULL。原值未知保持null/0/null/null；合法值必须>0且整数、revision>=1，时间及来源候选必填。候选保存每个历史值、来源原因、版本和回执；不将袋初始量、秤皮重或旧volume列自动搬来。迁移设计见[重量字段增量](history/sql/20-初始重量字段增量设计.sql)；旧18目标结构须叠加此增量，当前完整参考为23，均不直接操作生产。

锁顺序复用 SYSTEM→实验室→M03培养/变更守卫→M07培养运行守卫→设备稳定键→候选/交付。M03 和 M07 同库同事务；拆服务须等价版本屏障，不以异步事件替代提交保护。准备及生效再次检查当前权限、状态、工作流完成证据、cultureVersion/weightRevision、设备事实和执行屏障。存在 EXECUTING/PAUSED/未结算物理动作/UNKNOWN 命令时返回 STATE_CONFLICT，不修改重量/模式，不发送补偿停止。审批旧 expectedVersion 不匹配返回 CONFLICT，不自动覆盖。

生效同事务更新M03主值/版本、candidate=APPLIED、长效回执及审计；weight变更递增weightRevision，培养object_version/runtime_version沿既有规则递增；mode不伪增weightRevision。M07由内部 applyCultureInputChange(cultureId,candidateId,operation,expectedCultureVersion,newCultureVersion,oldWeightRevision,newWeightRevision) 将未开始计算候选标为过期并记录来源事件，调用幂等键=candidateId。失败整体回滚，外部通知用可靠outbox；不把初始重量变化写成“补液量”账本。

未来 INITIAL 基准使用生效后的初始重量；CURRENT 小试使用生效后初始重量加真实补入减真实取测，中试仍取可信秤值。日初快照已经存在时保持原值/来源版本；下一业务日首次生成按当时有效值。排队任务在真正开始计算/执行前重新取得当前M03版本并固化 initialWeightRevision；不能沿用过期预览。已执行计算、结算、历史检测、已冻结日初和旧执行快照不回写；日额度、历史任务及接续基线不重建。
