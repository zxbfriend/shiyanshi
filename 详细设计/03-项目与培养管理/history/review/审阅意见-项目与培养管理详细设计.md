## 1. 总体评价

**结论：可作为评审基线。业务规则密度与"反伪造"立场为本系列最高，但收尾包（09—13）在两处明显低于本模块自身已建立的水准——DB 约束缺位，且跨模块契约是单方面声明。**

### 1.1 最突出的优点

**（1）前后两次口径更正都被显式记录并反向回写，而不是悄悄改掉。**
§9「已过期修改时间与重新预约（用户术语更正）」明确记录："2026-09-09 用户将上一条中的'已延期'更正为'已过期'……此前基于口误加入的'已延期解除占用'设计已撤销"。Q10 同样撤回了"迟到完成开始培养即自动恢复"的推测转换。这种**把"我们曾经想错、现已撤销"写进设计稿**的做法，比直接改成正确结论更能防止后续开发沿旧稿实现，是本系列独一无二的做法。

**（2）"三个维度必须分开"的拆解贯穿到底。**
占用 vs 状态（草稿关联≠预约、终态业务状态≠物理停机）、完整性 vs 设备完成、计划日期 vs 实际事件时间（Q46 明确"开始天/结束天"是计划日期语义，不是实际事件）、创建人身份 vs `create_by` 用户名字符串（明确"不因用户改名、重用用户名而重新认领项目"）、MEMBER vs SHARE（同一人两条独立期限，禁止取最大日期提升全部能力）。每一处都落到了字段或 CHECK。

**（3）权限模型拒绝了"并集放大"这一最常见的越权来源。**
UI04-D 批量分享：上级并集**仅用于展示**，"不是将每个继承用户授予所有所选培养"，每行须标明覆盖对象；Q29 三项交集、Q31/Q32 实验室可见因子独立计算、不把可见等级 0 升级为可操作；`evaluateAction` 输出明确"不同来源覆盖的动作不能合并成最大有效期"。这是本系列对授权边界最严密的一次表述。

**（4）旧数据不猜、不洗。**
`member_setup_state` 三态（NEVER/CONFIGURED/UNKNOWN），历史未知不当 NEVER；`facts_status` REVIEW 映射 UNAVAILABLE 而非猜测；旧 `permission_type=admin/view` "不能按名字猜成新的成员或负责人"，"证据不足不能凭名字拆分"；核准表要求指纹 + 核准人 + UTC 时刻 + 受保护证据引用，"没有示例填充或数字推断状态"。

### 1.2 与同系列的比较

相对 M01/M04/M05/M06/M07，M03 的**业务规则密度最高**（Q01—Q32 全部带"业务例子 + 已确认规则 + 回写落点"），但其**收尾包（2026-09-10）质量明显低于其基础包（2026-09-09）**：基础包 2 张新表各有 3—4 个 CHECK，收尾包 5 张新表 CHECK 数为 0；基础包跨模块依赖诚实标注"待 M07 冻结"，收尾包改为"不再写'等待 M07/M09 设计'作为未完成设计理由"，但对端模块实际并未定义这些方法（详见 P1-2）。**"宣称完成"不能替代"契约闭合"**。

## 3. P1（评审前须拍板）

### P1-1 · DELAYED 状态没有已设计的离开路径，且归属在三个模块间形成真空（最需拍板）

**事实链**：

1. M03 §3 状态表：`DELAYED 已延期` — "持续占用；**必须变为已取消或已结束才释放**，不能靠延期或改时间释放"。
2. M03 Q10/TR11 给出唯一恢复路径：「已延期经合法流程**延长结束时间**后恢复进行中」。
3. M03 §7.6 明确关闭了所有旁路："运行态也不能经 PATCH 延长结束时间；**Q10 的合法运行变更由 M07 后续契约处理**"；CU02-B 亦"不混入已过期重约"。
4. M03 收尾契约 §4 进一步确认：`DELAY_RESOLVED` 事件的 `resolution.action = EXTEND_END`，`sourceRequestId` 来自"合法流程"。
5. **但 M07 全部 16 个文件检索「延长结束时间 / END_DATE_CHANGE / 计划变更 / 变更计划 / endDate / 延期」= 0 命中。** M07 只在两处以消费者身份提到 M03 的 DELAYED（"已延期但仍占用且运行资格有效按 M03 放行"、"状态名统一'已延期'，真实状态由 M03 提供"），**没有任何一处设计"延长结束时间"这个动作本身**。
6. M09 又反向指向 M03：`告警规则与源事件映射.md` 第 862 行 — "**延期解除以 M03 可信事实为准**，迟到开始完成不能由 M09 自行恢复培养状态"。

**后果**：培养一旦进入 DELAYED，除了 Q36 已排除的 FINISHED/CANCELLED 生产入口外，**没有任何模块设计了出口**；而 DELAYED 又"持续占用设备、必须变已取消/已结束才释放"——即**该设备的占用在当前设计下不可解除**。

**叠加风险（须与相邻模块联合决议）**：
- M07 EXT01—EXT05 全部未核准 → 真实可执行路径为零（M07 审阅 P1-1）；
- M06 的 UNKNOWN 永久占变更槽且无离开路径（M06 审阅 P1-1）；
- 本项 DELAYED 无恢复路径。
三者同型且叠加：**任一培养在启动后进入异常/延期，M03 占用、M06 变更槽、M07 任务三条链会同时卡死，且均无人工处置入口**（M03 全文检索"强制/管理员/人工干预 释放"亦无对账或释放入口）。

**建议**：
1. 明确归属——要么 M07 补《培养结束时间变更流程》并定义 `END_DATE_CHANGE_EFFECTIVE` 的完整生产者；要么 M03 在合法审批通道（M06）下补一条 DIRECT/审批驱动的延长结束时间动作。二者必选其一，**不能继续互相指向**。
2. 无论选哪条，都须补充：DELAYED 最长滞留时长、滞留超期的告警升级（现仅 M09 X005/R027 告警，无处置）、以及"确需人工释放"时的受控接管流程与审计要求。
3. 与 M06 P1-1、M07 P1-1 合并为一次跨模块专项决议。

### P1-2 · 收尾包 5 张新表零 CHECK 约束，与本模块及全系列已确立的"不变量下沉 DB"原则直接冲突

**实测数据**：

| 表 | 来源包 | CHECK 数 |
| --- | --- | --- |
| `res_culture_occupancy` | 基础包（08） | **4**（`ck_m03_occupancy_kind/state/identity/release`） |
| `res_culture_notice_outbox` | 基础包（08） | **3**（`ck_m03_notice_type/state/lease`） |
| `res_culture_parameter_snapshot` | 收尾包（13） | **0** |

| `res_culture_parameter_application` | 收尾包（13） | **0** |
| `res_culture_runtime_event` | 收尾包（13） | **0** |
| `res_culture_workflow_reference` | 收尾包（13） | **0** |

5 张新表有唯一键（`uk_close_parameter_slot` 等）但**无任何枚举/取值约束**，枚举仅存在于列注释：

- `res_culture_parameter_state.apply_state` = `NONE/PENDING/APPLIED/DISCARDED/CONFLICT`
- `res_culture_parameter_application.outcome` = `APPLIED/DISCARDED/CONFLICT`
- `res_culture_runtime_event.apply_state` = `RECEIVED/APPLIED/IGNORED/BLOCKED`
- `res_culture_runtime_event.event_type` = 6 值；`source_module` = 3 值；`stream_sequence` 应为正整数
- `res_culture_workflow_reference.source_kind` = `SNAPSHOT/WORKFLOW_SELECTION/LEGACY_VERIFIED`

**为何这是 P1 而非 P2**：这些恰是本模块最强调防伪造、防重放的核心状态机，且直接对应 6 条收尾验收用例——M03-CLOSE-07（精确审批 hash/ID 不匹配拒绝）、CLOSE-11（物理任务阻断旧指针不变）、CLOSE-15（乱序缺前序保持 BLOCKED）、CLOSE-17（基线冲突恢复固定原包）、CLOSE-09（旧回执重放不倒退）。**DB 层无约束意味着这些不变量只靠应用代码保证，而本系列 M01/M04(24 CHECK)/M05/M06(27 CHECK)/M07(48 CHECK) 全部选择了下沉到 DB。M03 基础包自己也这么做了（7 个 CHECK）。这是同一模块内部标准不一致，不是"尚未细化"。**

**建议**：至少补 5—6 个枚举 CHECK（上列 5 处）+ `stream_sequence >= 1` + `parameter_generation >= 0` + `object_version >= 1`（基础包所有表都有 version CHECK，新表没有）。成本极低，且能直接支撑 CLOSE-07/09/11/15/17 的验收。

2. 组织一次 M03×M07 联合冻结（连同 P1-1 的延期恢复路径一并处理）。

## 5. 结论与后续建议
