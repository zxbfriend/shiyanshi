- 第 1 口：入参是 `pageSessionId`（CLOSE 时）或无需 ID（OPEN 时）。**不涉及工作流 ID、不涉及批次 ID。**

关键拒绝：400 ×1（kind 非法）、403 ／409 ×2（lab 范围与类型）、404 ×1（回执存在但 lab 或 kind 不符）。

**两处设计—源码差异（本口最重要）**：

| 设计原文 | 源码事实 | 判定 |
|---|---|---|
| `开始培养工作流详细设计.md:301` 要求 `requestState=NOT_FOUND/PENDING/APPLIED/REJECTED/UNKNOWN` **五态** | 源码只产出 **`APPLIED`** 与 **`UNKNOWN`** 两态（`:321`、`:324`），无 `NOT_FOUND`、无 `PENDING`、无 `REJECTED` | **设计—源码差异**。不判缺陷、不补状态、不据此新增字段 |
| 同处要求「只读，按原 actor＋lab＋当前资格查询；跨 owner 不泄露；NOT_FOUND 不等于可重发或未执行」 | 源码对「不存在」与「他人请求」**返回同一个 `UNKNOWN`**，无法区分。不泄露是成立的，但「NOT_FOUND 语义」在源码里不存在 | 语义被压成两态，**「不泄露」目标达到，「NOT_FOUND 可判别」目标未达** |

观察一：`UNKNOWN` 分支在写库**之前**返回，因此它同时覆盖「请求从未到达」与「请求已提交但尚未写回执」两类。这意味着**客户端不能据 `UNKNOWN` 判定失败**，只能重查或人工核对。源码注释已经把这条写死。

观察二：`findReceipt` 只返回四个字段（`sessionId`、`labId`、`workflowKind`、`operation`），**不返回原响应正文**。设计 `:301` 写「原回执/原因」，源码未实现该字段。与「正文不回读」的设计表述（同处后半句）一致，但与前半句的「原回执」不一致。

未核（F）：`run_start_culture_receipt` 的唯一键组成（`actor_user_id`＋`request_id`？还是加 `operation`？）；`operation` 字段的实际取值分布；回执保留时长与清理策略。

## 4. `step` — POST `/run/workflow-batches/{batchId}/steps`（W02 整页推进）

| 项 | 值 |
|---|---|
| 类级映射 | `@RequestMapping("/run/workflow-batches")`（`PilotReplacementBatchController.java:15`），本口 `:20`—`:25` |
| 权限／标记 | `run:workflow:operate`、`@ManagementGuardedWrite` |
| 设计位置 | `接口目录与契约定位.md:90`（守卫码 `M07-025-W02-BATCH`）；`Controller请求调用时序设计.md:74`；`任务页面与接口契约.md` §W02（2026-10-21） |
| 应用服务 | `PilotReplacementBatchService#operateBatchStep:70`—`:102` |
| 守卫码 | `M07_025_W02_BATCH`（`ManagementOperation.java:571`，值 `M07-025-W02-BATCH`） |
| 消费者 | `runWorkflowApi.pilotBatchStep:680`；页面 `views/pilot-replace/index.vue`（2 处） |

与已核的 `getBatch` 的边界：`getBatch:53`—`:68` 已在 `05-…md` §6.2 核过（作为批次详情第 4 路兜底）。本口只核 `operateBatchStep`，**不重做 `getBatch`**；但写操作末尾会调用 `getBatch` 作为返回体，故只记「返回整批详情」这一事实。

正常路径：

1. `:71` `requireNoOuterTransaction()`：外层事务已存在 → `input()` 即 `INPUT_INVALID` 400「工作流批次写入入口不支持在已有事务内调用」。
2. `:72` `id(batchId)` 正 bigint；`metadata(writeMeta)` 要求 `requestId` 与 `managementRevision` 均合法（`WriteMeta.isValidRequestId`／`isValidManagementRevision`），否则 400「批次写须携带合法双头」。
3. `:73` `stepCode` ∈ {`START`, `REPLACE_BAG`, `PRIME_FILL`}（常量 `STEP_CODES:38`）且 `action` ∈ {`NEXT`, `SAVE`, `COMPLETE`, `SKIP`}，否则 400「批次步骤或动作非法」。**注意：本口的动作词表既不同于 W03 的 `SAVE/NEXT/COMPLETE/SKIP`（这里多一个 `SAVE` 但少了 `BACK`），也不同于开始培养的 `VALIDATE_NEXT/BACK/...`。**
4. `:74` `stepItems`：非空、每项 `workflowId`／`stepId`／两个版本均为正 bigint、无重复，否则 400。
5. `:75` `currentActor()`：会话键缺失 → `SESSION_INVALID` 401；请求 ID 缺失或解析失败或 `authzVersion` 非法 → `AUTH_DEPENDENCY_UNAVAILABLE` 503；`bindActor` 校验守卫内外身份一致。
6. `:76` `readBatch(rootId, actor, false)`（守卫外预检）→ `exactIds(batch, items.keySet())`：提交成员必须**恰好等于**冻结清单，否则 400「整页操作必须提交全部且仅属于本页的成员」。
7. `:77` 组 payload（`batchId` ＋ 完整 command）。
8. `:78` `guard.execute(M07_025_W02_BATCH, meta, payload, callback)`。回调内：
   - `:80` 重读 `readBatch(rootId, trusted, true)`（加锁）→ `sameBatch(batch, locked)`：根 ID／lab／创建人／请求 ID／冻结清单任一变化 → 503「批次冻结来源已变化」；`exactIds` 再校验一次。
   - `:81` `lockAllSteps(locked)`：逐成员锁 3 个步骤行，必须恰 3 行、`stepOrder` 1／2／3、`stepCode` 依次 `START`／`REPLACE_BAG`／`PRIME_FILL`、`stepInstanceId` 唯一且为正，否则 503「批次固定三步身份非法」。
   - `:83` `pageHasPrime(allSteps)`：任一成员第 3 步快照的 `simulationState.history` 含 `PRIME_START` 即为真。
   - **第一轮只校验、不写**（`:85`—`:89`）：逐成员比对工作流版本，按 `stepCode` 定位步骤并比对 `stepId` 与步骤版本。任一不符 → `VERSION_CONFLICT` 409「批次成员版本已变化，请刷新整页」。
   - **第二轮只准备、不写**（`:90`—`:97`）：逐成员构造 `WorkflowStepOperationCommand` → `PilotReplacementSimulationService#prepareBatchStepLocked(row, stepId, operation, trusted, pageHasPrime)` 得到 `PreparedStep`。
   - `:98` `applyAll(prepared, "工作流步骤/操作")`：**第三轮才写**。逐 `mutation.apply()`，校验 `outcome.applied` 与 `id` 非空，收集 `affected`；`affected` 为空或重复 → 503；`before`／`after` 按 `objectId` 排序；`outcome.id = affected[0]`。
9. `:100` `validateReceipt(applied, actor, stepIds)`：`applied` 为真、`actorUserId` 与 HTTP 身份一致、`affectedIds` 数与集合恰等于提交的 `stepId` 集合、`affected[0]` 在集合内。否则 503「批次回执对象或操作者不完整」。
10. `:101` `assertCurrentBatchAccess(rootId, actor, requestId)`：当前身份（`actorUserId`／`sessionKey`／`requestId`）必须与写前一致（否则 `PERMISSION_DENIED` 403「批次守卫与当前HTTP身份不一致」），并再跑一次 `readBatch(rootId, current, false)`。注释 `:201` 说明理由：「A successful guarded write advances authzVersion; recheck scope with the current version.」
11. `:101` 返回 `getBatch(batchId)`——**写口返回整批详情**。

| 调用点 | 方法 | 语句 |

| `readBatch:134`（`lock=false`） | `#selectMembers` | XML `:16`（谓词片段 `:11`—`:15`） |

Port：无跨模块 Port。`PilotReplacementSelection.validate` 是同模块静态校验（`:149`，捕获后转 503「批次泵身份重复或不完整」）。

关键拒绝：

| # | 条件 | 位置 | 结果 |
|---|---|---|---|
| 1 | 外层事务存在 | `:71` | 400 |
| 2 | `batchId` 非正 bigint | `:72` | 400 |
| 3 | 双头不合法 | `:72` | 400 |
| 4 | `stepCode`／`action` 非法 | `:73` | 400 |
| 5 | 成员为空／ID 非法／重复 | `stepItems:212` | 400 |
| 6 | 会话键缺失 | `currentActor:226` | 401 |
| 7 | 请求身份缺失或不可信 | `currentActor:227`—`:230` | 503 |
| 8 | 提交成员不等于冻结清单 | `exactIds:210` | 400 |
| 9 | 守卫内外身份不一致 | `bindActor:233` | 403 |
| 10 | 批次冻结来源变化 | `sameBatch:209` | 503 |
| 11 | 步骤数或身份非法 | `lockAllSteps:169`—`:172` | 503 |
| 12 | 成员版本或步骤版本变化 | `checkVersion:238` | 409 |
| 13 | 步骤不属于该成员 | `selectedStep:185` | 400 |
| 14 | 预检结果或应用结果不完整 | `applyAll:190`—`:194` | 503 |
| 15 | 回执对象或操作者不完整 | `validateReceipt:220`—`:222` | 503 |
| 16 | 事后身份或范围变化 | `assertCurrentBatchAccess:202`—`:206` | 403 |

观察一：**这是全组唯一采用「全量预检 → 逐成员准备 → 统一应用」三段式的写口**。注释 `:82` 明确「No owner writes, CAS, event or audit until every member's versions/permissions/real core rules pass.」。与同模块 W08 的「共享 close 循环」相比，W02 的失败面更早收敛到 400／409，而 W08 是在循环中逐个 CAS。两者都是全批回滚，但**回滚点的位置不同**，不能互相套用「已核」结论。

观察二：写口返回 `getBatch(batchId)`，因此**一次写请求会再跑一遍批次读链**（含逐成员 `detail` 的 VIEW 判定）。这条读链在写成功后可能因授权版本前进而产生不同结果（`assertCurrentBatchAccess` 已在写后重校验，故不一致会被 403 拦下）。登记为观察。

观察三：本类注释为英文（`:13` `/** W02 page-level transitions. Pump start/stop remains on the existing per-pump operation endpoint. */`），与**旧版 AGENTS 的「注释使用中文」条款（当时编号 §13）**不一致。属既有代码风格，**不判缺陷、不据此改注释**（**旧版编号 §3.4**：没有被要求的格式化一律不做）。
**引用版本更正（本轮补记）**：上面两个编号是**取证当时的旧版 AGENTS 编号**，现行 `AGENTS.md`（§0—§14）**没有 §3.4，也没有「注释使用中文」条款**，§13 全文亦无该表述；现行最接近的是 §12「不执行……无范围格式化或其他破坏性操作」。**本句结论不依赖这两条**——不改注释的直接依据是本轮范围禁令（不改源码与源码注释）与现行 §12「只修改当前任务必要文件」，故「不判缺陷、不改注释」维持不变。逐条对照登记见 `03-…md` §10.1。

未核（F）：`PilotReplacementSimulationService#prepareBatchStepLocked` / `apply` / `operationLocked` / `cancelLocked` 的内部规则；`hasPrime` 依赖的 `simulationState.history` 结构与写入方；`pageHasPrime` 对预填充动作的具体约束。

## 5. `cancel` — POST `/run/workflow-batches/{batchId}/cancel`（W02 整页取消）

| 项 | 值 |
|---|---|
| 权限／标记 | `run:workflow:operate`、`@ManagementGuardedWrite`（`PilotReplacementBatchController.java:27`—`:32`） |
| 设计位置 | `接口目录与契约定位.md:91`（守卫码 `M07-027-W02-BATCH`）；`Controller请求调用时序设计.md:77` |
| 应用服务 | `PilotReplacementBatchService#cancelBatch:104`—`:122` |
| 守卫码 | `M07_027_W02_BATCH`（`ManagementOperation.java:597`，值 `M07-027-W02-BATCH`） |
| 消费者 | `runWorkflowApi.pilotBatchCancel:702`；页面 `views/pilot-replace/index.vue`（2 处） |

与 `step` 的差异（`:104`—`:122`）：

| 环节 | step | cancel |
|---|---|---|
| 二次确认 | 无（`skipConfirm` 走命令字段） | **必须** `command.cancelConfirm()==TRUE`，否则 400「整页取消须二次确认放弃本次换袋」 |
| 成员载荷 | `stepItems`：`workflowId`＋`stepId`＋两个版本 | `cancelItems`：`workflowId`＋`expectedWorkflowVersion`（**无 `stepId`、无步骤版本**） |
| 步骤锁 | `lockAllSteps` 并逐成员定位步骤 | 仅 `lockAllSteps`（锁行但不定位步骤） |
| 逐成员准备 | `prepareBatchStepLocked(..., pageHasPrime)` | `prepareBatchCancelLocked(row, expectedWorkflowVersion, requestId, cancelConfirm, trusted)` |
| 应用标题 | 「工作流步骤/操作」 | 「工作流/取消」 |
| 回执校验集合 | `stepId` 列表 | `workflowId` 列表 |
| 返回 | `getBatch(batchId)` | `getBatch(batchId)` |

其余（外层事务拒绝、双头校验、`currentActor`、`bindActor`、`readBatch`、`sameBatch`、`exactIds`、`assertCurrentBatchAccess`、`validateReceipt`）**与 step 完全共用同一批私有方法**，不是两套实现。

关键拒绝：与 §4 的 16 类同构，差异仅两点——① 缺 `cancelConfirm` → 400；② 无「步骤不属于该成员」的 400（因为不传 `stepId`）。

观察一：`cancel` 与 `step` **共用守卫执行骨架，但不同守卫码**。按守卫码统计会得到两个独立操作；按实现统计只有一个骨架 + 两个回调。两种口径都对，但报告里必须写明用的是哪一种。

观察二：**整页取消不经过 `M07_027`（单实例取消）**，且单实例 `cancelWorkflow` 对带 `batchRootWorkflowId`／`batchWorkflowIds` 的 W02 实例会先被 `requireSingleReplacementInstance` 挡回（`RunWorkflowApplicationApplicationServiceImpl:2218`—`:2223`，409「本次更换料液须通过整页批次接口统一推进或取消」）。因此两条路径互斥，不存在「单台取消绕过整页」的缝隙。

未核（F）：`prepareBatchCancelLocked` 的内部规则（是否要求成员处于特定步骤、是否处理已预填充的成员）；取消后资源守卫与泵的收尾（本批不展开设备释放链）。

## 6. 五口共性对照

| 维度 | 事实 |
|---|---|
| 权限码 | 4 口 `run:workflow:operate`（session／action／step／cancel）、1 口 `run:workflow:query`（receipt）。**5 口只用两个权限码**，没有独立的批次权限码 |
| 路径变量名 | `{id}`（action）、`{requestId}`（receipt）、`{batchId}`（step／cancel）。同一前缀下三种命名 |
| 守卫码 | `M07_SC_OPEN`／`M07_SC_SESSION`／`M07_SC_ACTION`／`M07_025_W02_BATCH`／`M07_027_W02_BATCH`，**5 口 5 码**；但 `M07_SC_OPEN` 与 `M07_SC_SESSION` 同属 `session` 一个 handler |
| 返回体 | 2 口返回整组聚合（session 的 `sessionView`、action 的 `aggregate`）、1 口返回回执状态（receipt）、2 口返回整批详情（step／cancel 的 `getBatch`）。**没有一口返回单实例** |

| 消费者 | 5 口都有真实页面在用（开始培养页、中试更换页）。**不存在「后端已实现但无消费者」的情况** |
| 运行层 | 5 口全部 `NOT_VERIFIED` |
