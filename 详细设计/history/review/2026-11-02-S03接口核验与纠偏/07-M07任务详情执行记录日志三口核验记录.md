## 2. 三口身份集合

模块归属：M07 补液运行与任务执行；包 `com.futurefab.system.controller.run`；实现服务 `futurefab-system`。
网关依据：`nacos-config/futurefab-gateway-dev.yml:57-60` 把 `/run/**` 路由到 `futurefab-system` 且**不带** `StripPrefix`，故网关外部路径等于服务内路径。

| 口 | 契约号 | HTTP 与服务内路径 | 文件与完整 handler 身份 | 权限与标记 |
|---|---|---|---|---|
| 任务详情 | M07-002 | `GET /run/tasks/{id}` | `controller/run/RunTaskController.java::com.futurefab.system.controller.run.RunTaskController#getTask(RunTaskDetailQuery,String)`，方法在 `:64` | `@RequiresPermissions("run:task:query")`（`:61`）、`@CurrentManagementRevision`（`:62`） |
| 执行记录 | M07-012 | `GET /run/tasks/{id}/executions` | 同文件 `#listTaskExecutions(TaskExecutionPageQuery,String)`，方法在 `:194` | `@RequiresPermissions("run:task:query")`（`:192`）；**无** `@CurrentManagementRevision` |
| 日志 | M07-011 | `GET /run/tasks/{id}/logs` | 同文件 `#listTaskLogs(TaskLogPageQuery,String)`，方法在 `:185` | `@RequiresPermissions("run:task:query")`（`:183`）；**无** `@CurrentManagementRevision` |

身份补充事实：

1. 三个 handler 均为 `AjaxResult` 返回、无 `@RequestBody`、无 `@ManagementGuardedWrite`；三者都用 `@PathVariable("id")` 取任务 ID 后写入查询 DTO 的 `id` 字段，Controller 不做业务判断。
2. 三口的 `taskId` **只能来自路径**：Controller 在任何调用前 `setId(id)`（`:66`／`:187`／`:196`），服务层取值表达式为「`getId()` 非空则用它，否则用 `getTaskId()`」（`:335`／`:565`／`:600`）。DTO 另带可绑定的 `taskId` 字段（`RunTaskDetailQuery:13`、`TaskLogPageQuery:14`、`TaskExecutionPageQuery:14`），但路径已先写入 `id`，故查询串里的 `taskId` **不会**改变目标对象。
3. 三口**没有**别名展开、没有重载、没有多实现：`RunTaskApplicationApplicationService` 只有一个实现类 `RunTaskApplicationApplicationServiceImpl`（`:150-151`）。

### 4.2 查询范围

| 环节 | 事实 |
|---|---|
| `taskId` 解析 | `pathId`：空/空白 → `INPUT_INVALID`「任务ID不能为空」；非十进制 → `INPUT_INVALID`「任务ID必须为十进制字符串」。**未做正数校验**：`parseId` 直接 `Long.valueOf`，`-1` 通过并进入查询（结果自然为 404）。这与本模块写口用 `number()` 正数校验的做法不同 |
| 功能权限 | `@RequiresPermissions("run:task:query")` 由 `PreAuthorizeAspect:58` → `AuthUtil.checkPermi` → `AuthLogic#checkPermi:136-147` → `getPermiList:335-346` 判定，来源是 `LoginUser.getPermissions()`，即**登录会话快照**（AGENTS §7.6 已列为待改造路径，非本批新增问题） |
| 数据范围 | `resolveScope:662-692`：`SecurityUtils.getUserId()` 为空 → `PERMISSION_DENIED`；`smpPermissionService.resolveScope(userId)` 为真 `isAllAccess` → 两集合留空；否则取 `viewLabIds`／`visibleCultureIds`，两集合皆空返回 `false` |
| 范围进入 SQL | `selectTaskDetail` 用片段 `taskScopeFilter`（XML `:167-181`）：两个参数都非 null 才追加 `AND ( t.lab_id IN (...) OR t.culture_id IN (...) )`；某集合为空时服务层传 `null`，该侧条件不生成 |
| 存在性与可见性 | 同一条件内完成：`WHERE t.task_id = #{taskId}` 加可选范围片段；查不到返回 null，服务层 `:344-347` 统一 `NOT_FOUND`「任务不存在或不在可读范围」 |
| 子记录是否受同一任务约束 | 是。`selectTaskHandoffEvents` 的 `FROM run_task t JOIN run_execution x ON x.task_id=t.task_id AND x.execution_id=#{executionId}` 加 `WHERE t.task_id=#{taskId} AND t.lab_id=#{labId} AND t.culture_id=#{cultureId}`（XML `:261-264`），即用已授权任务行的三键再钉一次；`selectLatestStartWithdrawal` 同样带 `t.task_id / t.lab_id / t.culture_id`（XML `:14`）；`selectScope` 无 lab/culture 谓词，但它的 `executionId` 只可能来自前一步已授权的 `prior.executionId()` |
| 范围为空／无权／不存在 | 三者统一 404，不区分，不泄露存在性（与设计「不存在/范围外统一 404」一致） |

一致性校验与鉴权分开记：

- `M07TaskSafetyProjection` 的 `require` 失败（保护状态身份不符、恢复基线身份不符、停止意图身份不符）→ 记 `EVIDENCE_CONFLICT` 并把 `reconciliationBlocked=true` 从而收窄 `allowedActions`；这是**事实一致性**判定，不是鉴权。
- `M07TaskHandoffProjection` 的 `require` 失败 → 返回 `UNKNOWN` 视图；同样是事实校验。
- `M07NotSentWithdrawalHistory#withdrawn` 的 `require` 失败抛 `IllegalArgumentException`，被 `M07TaskStartWithdrawalProjection:29` 的 `catch` 捕获为 `UNKNOWN`。因此**历史数据不自洽不会让详情 500**，只会降级为 `verificationState=UNKNOWN`。

### 4.3 分页与排序

详情**不分页**：`RunTaskDetailQuery` 只有 `taskId`／`id` 两个字段（20 行），无 `pageNum`／`pageSize`；`selectTaskDetail` 以主键定位单行，无 `ORDER BY`、无 `LIMIT`。设计 API02 同样没有分页要求。

### 4.5 正常与关键拒绝路径

**正常路径**（静态，一次请求）：

1. 解析路径 ID；2. 解析会话身份与数据范围；3. 一条 `selectTaskDetail` 取任务行（含候选 `approval_id` 与当前执行投影列）；4. 一条 `selectTaskHandoffEvents`（有当前执行时）计算 `safetyHandoff`；5. 一条 `selectLatestStartWithdrawal`，命中则可能追加 5 条查询（命令、安全事实、执行范围、两个计数、再次 `selectTaskHandoffEvents`）；6. 一条 `selectCalculationById`（任务有关联计算时）；7. 一条 `selectDayStartCalculation`；8. 组装返回。

## 10. 源码内部观察项（不进第 1—5 类，仅登记事实）

**G1（分页夹页）**：`pagehelper.reasonable=true`（`application-dev.yml:67`）使超界页号被夹到末页并返回末页数据；而 `listTaskLogs:586`／`listTaskExecutions:657` 把 `pageNum` 写成**请求值**，`PageResult:17-18` 又声明「越界页返回空列表」。三者对同一情形的描述不一致。

**A1（读一致性）**：`RunTaskApplicationApplicationServiceImpl` 无 `@Transactional`（`:150-151` 仅 `@Service`），三个读方法也未标注。故详情的最多 11 条查询、执行记录的 2 条查询、日志的 2 条查询（闸门 ＋ 列表）都不在同一事务快照内。静态判断：这是**非原子读**，不是错误；但对「详情里的 segments/计数/快照必须互相自洽」的场景，源码另有身份校验（`M07TaskSafetyProjection`、`M07TaskHandoffProjection`）作为兜底，不是靠事务。

**P1（闸门成本）**：`requireTaskInRange:703` 复用 `selectTaskDetail`，即用**完整详情投影**（含保护状态、恢复基线、停止意图等多层 `JSON_EXTRACT` 子查询）做存在性与范围判断，而非 `count(*)` 或窄列查询。日志与执行记录各付一次该成本。

**T1（时区）**：Mapper 文件注释（`M07TaskQueryMapper.xml:20`）声明「时间列均为 UTC DATETIME(3)」，而数据源 `serverTimezone=GMT+8`（`application-dev.yml:47`）。写侧 `run_event.occurred_at` 取自 Java `Date`（`RunEventMapper.xml:18`），读侧 `offset():1791-1794` 把 `Date` 当瞬间转 UTC 输出，前端再转回 `Asia/Shanghai`。若读、写两侧都经同一连接时区，往返自洽，但库内墙钟是 GMT+8 而非注释所称 UTC；若同列存在以 SQL 函数（如 `UTC_TIMESTAMP(3)`）写入的记录，两类来源会相差 8 小时。本批三口读取的列未见 SQL 函数写入，故静态判断往返一致，**运行期未验证**。

**S1（会话快照权限）**：`allowedActions` 与 `@RequiresPermissions` 都用 `LoginUser.getPermissions()`（`AuthLogic:335-346`），是会话快照；数据范围走实时查库的 `resolveScope`。AGENTS §7.6 已把「基于会话快照的路径需改造」列为已确认事项，本批不重复立项、不改代码。

**L1（负 ID）**：`pathId` 只判空与非十进制，`-1` 会通过并进入 SQL（`parseId:1747-1763`）。结果自然是 404，不是 400。与本模块写口用 `number()` 做正数校验（`06-…md` 已记）做法不同。是否应统一不在本批判断范围。

**U1（页面分支与取数不匹配）**：`feeding-tasks/index.vue` 的 `executions` 只在 `source === "api"` 时赋值（`:352-371`），而执行＋分段描述列表只在 `source` 既非 `api` 也非 `mock` 的分支渲染（`:1005-1040`）。两个条件互补但不重叠，导致 api 模式取到的执行数据在该模板分支不可见。

**U2（前端只取前 10 条却假设含最新）**：`run-tasks/index.vue:280-290` 用 `executions()` 的第 1 页（`attempt_no ASC` 前 10 条）在客户端降序取「最新一次」。尝试次数超过 10 时会选到第 10 次。这是前端假设与接口分页/排序的组合结果，接口本身行为与设计一致。

**R1（事件证据硬上限）**：`selectTaskHandoffEvents` 以 `ORDER BY e.event_id LIMIT 9` 收口（XML `:283`）。该上限没有在设计里找到对应条目；若匹配事件超过 9 行，`one(...)` 的唯一性判定仍成立但可能缺件，从而降级为 `UNKNOWN`（不会报错）。登记为事实，不据此提出新需求。

**B1（日志字段面窄于落库内容）**：`run_event.payload` 中有 `actor.displayName`、`change.before/after`、`result`，本口都不返回（§6.4）。这是当前字段面的事实，不等于缺陷。
