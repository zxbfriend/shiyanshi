| 问题 | 取消申请 | 修改申请 | 暂停 | 恢复 |

### 4.2 正常路径（两条，均只写本事务内事实）

1. 锁读任务：`selectTaskForUpdate`（`RunTaskMapper.xml:75-82`）按主键 `FOR UPDATE`，**SQL 无 lab/actor/范围谓词**。
2. 依次判定：行存在（否则 404）→ `object_version` 等于 `expectedVersion`（否则 409）→ `business_state ∈ {READY, PAUSED}` 且 `admitted=1`（否则 409）→ 若有 `current_execution_id` 则必须已 `PAUSED`（否则 409）→ `current_candidate_id` 为空且 `scheduler_held=0`（否则 409）。
3. 取培养操作事实：`CultureOperationFactsPortImpl:37`，要求 `sourceModule=M07` 且 `sourceAction` 属登记白名单，`selectCultureGuardFacts(cultureId, actorUserId, false)`（:62）；返回的 `labId/cultureId` 必须与任务行一致，否则 409「任务培养归属事实已变化」（:184）。
4. 生成候选哈希：`before`/`after` 快照 + `candidateHash = SHA256(afterJson)`；`after` 写 `actionKind=CANCEL`、`approvalSceneCode`、`remainingPlanDisposition=CLOSE_WITHOUT_SUPPLEMENT`（:140）。
5. 判政策：`ApprovalPolicyQuery` 带 `contextRef=M07-007:{requestId}`、`changeKey=TASK:{taskId}`、候选引用、场景码；`DIRECT` 或 `DIRECT_REASON` 记 `direct=true`；`APPROVAL` 走 `submit`；其他值 503（:150）。
6. 写入：
   - `APPROVAL`：先 `submitApproval`（回显校验候选 ID 与哈希 :215），再插候选（`state=PENDING`、`approvalId` 非空），再 `holdForCandidate`（只改 `scheduler_held=1`、`current_candidate_id`、`modified_at`，**不动 `object_version`**）。
   - `DIRECT` 且 `READY`：插候选（`state=APPLIED`、`decision_snapshot`/`application_receipt` 非空、`applied_at`），再 `applyDirectCancel`：置 `CANCELLED`、`object_version+1`、`scheduler_held=1`；SQL 额外要求 `business_state='READY' AND current_execution_id IS NULL AND started_at IS NULL`（`RunTaskMapper.xml:167`）。
   - `DIRECT` 且 `PAUSED`：插候选后调 `pausedFinalizer.finish`，`changed` 直接置 1（:163）。
7. 事件与返回：`M07_TASK_CANCEL_REQUESTED` 同事务落账（失败 503 回滚 :268）；返回 `state` 为 `CANCELLED` 或 `PENDING_REVIEW`，`applicationState` 为 `APPLIED` 或 `PENDING`，`objectVersion` 为 `expectedVersion+1`（直接）或 `expectedVersion`（审批）（:170—:173）。

`PAUSED` 直通分支的收尾链（`M07PausedTaskCancelFinalizer#finish:67`）内部规则未展开：它在锁序 runtime → task → candidate → execution → segment 下，要求末段 `CLOSED`、`stop_reason=USER_PAUSE`、结算 `NONE`、全部命令闭合、资源组仍 HELD，再走结算政策 `authority.approve` 与 `finalizeCancellation`（`==2`）；其中 `authority` 为可选注入，缺装配时 `require` 抛 503（:72、:151—:152）。该链内部判定只登记入口，不宣称已核（F）。

### 6.7 事务、审批与外部副作用

1. 事务入口：`guard.execute`（单一 `TransactionTemplate`）。本地写入顺序：`insertCommand` → `registerResourceUsage` → `updateSegmentStopIntent` → `requestPauseByVersion`（2 行）→ `insertEvent` → 审计。
2. 无审批：暂停口不建候选、不调 `ApprovalSubmissionPort`。
3. 设备动作：**不在事务内**。`pause:106` 与 `dispatchPrepared:96—:99` 双重拒绝在事务/守卫上下文中调用设备；设备调用发生在守卫提交之后。
4. 失败处理：
   - 守卫内任一步失败 → 整组回滚，HTTP 报对应码，**无停止意图**。
   - 守卫已提交但 `dispatchPrepared` 失败（如登记门禁不可用抛 503，`:103—:112`）→ 停止意图与命令已落库，HTTP 返回错误。此时任务/执行已是 `PAUSE_REQUESTED`，命令仍是 `PREPARED`。这是**「已写入但响应失败」的真实窗口**，恢复靠同 `requestId` 重放（守卫回执）＋ `PREPARED` 命令的后续派发，不靠重发新请求。
5. 设备回执未知：`dispatchPrepared` 捕获运行期异常后按 `UNKNOWN` 落回执并保留占用，不自动重发（:126—:131）；注释明示「不泄露底层地址/凭据」。
6. 重复提交与重放：守卫四元组命中即回放原 outcome，`dispatchPrepared` 因 `PREPARED→INVOKING` CAS 只有一个胜者，不会二次调用设备（:93 注释）。

### 7.7 事务、审批与外部副作用

1. 事务入口：`guard.execute`。**事务外**先做 M02 读数（`M07ResumeReadingFetcher:46` 显式拒绝事务内调用）。
2. 事务内顺序：读准备事实 → 写新段 → 写 SET_SPEED 命令 → 写续段交接 → 任务/执行双行 CAS → 登记通信资源 → 写事件 → 审计。
3. 无审批。
4. 设备动作：提交后 `dispatchPrepared`，与暂停口共用派发器；`continuationGate.ensureActivated` 未取得持久回执时 503（`M07TaskPauseDispatcher:108—:112`）。
5. 失败处理：守卫内失败整组回滚（段、命令、CAS、事件一起）；守卫已提交而派发失败时，任务已是 `EXECUTING`、命令仍 `PREPARED`，HTTP 报错。
6. 重复提交：守卫回执重放 ＋ `PREPARED→INVOKING` CAS 单胜者，不会二次起泵。
