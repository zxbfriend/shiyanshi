## 3. 现行契约核对结论（Q1：003 是全域管理权限，还是必须限制实验室/对象范围？）

**必须限制。M09-003 不是全域管理写。** 依据链（现行权威，不依赖历史报告）：

1. `详细设计.md:55` 把"处理"与"详情、导出、快捷跳转"并列，明确"**与列表同源鉴权**"。列表的鉴权定义是"先查询功能权限，再应用 M01/M02/M03 当前可见域"。因此功能权限标识 `alarm:alarmRecord:handle`（`物理接口与骨架字段设计.md:19`）只回答"能不能做这个动作"，**不构成数据范围豁免**；该文件通篇没有为 API03 登记任何全域例外。
2. `详细设计.md:57` 在可见域之上**再叠加**接收人资格：本人稳定ID ∈ 该告警接收人集合；仅 `recipient_state=KNOWN_EMPTY` 时可退让为"可见 + 处理功能"；`UNKNOWN` / 旧 JSON 解析失败 / 成员服务异常一律不得退让。
3. `通知投递与恢复契约.md:9` "配置角色不授予跨实验室数据权限"、`验收与实施顺序.md:20-22` CASE14/15/16 同向。

4. **数据范围（可见域）豁免**与**接收人资格**是两层不同的闸门，须分开描述，不能合并成一句"管理员全域"：
   - **可见域层**：现行共享片段 `alarmDataScope`（`AlarmRecordMapper.xml:69-71`）对受保护管理员不加范围条件，这是设计登记的既有分支；就 003 的**可见性闸门**而言，管理员口径与其在列表/详情一致（全域可见）。该分支只解决"看得见哪些行"。
   - **接收人资格层**：`详细设计.md:57` 是在可见域**之上再叠加**的独立条件（本人稳定ID ∈ 接收人集合，仅 `KNOWN_EMPTY` 可退让），其文本**未区分管理员与非管理员**，也未登记任何"管理员免资格"的例外。因此本轮**不自行添加管理员资格豁免**：按现行条文，管理员同样要么命中 `alarm_recipient`，要么依赖 `recipient_state=KNOWN_EMPTY`。该空档登记为 B-9，由裁决确认（若裁决为豁免，须同步在 `详细设计.md` §3 明文登记，不得由实现批次推断）。
   - 结论同上：契约没有把 003 定义为"全域管理写"接口；`物理接口与骨架字段设计.md:19` 只登记功能权限标识，`AlarmRecordMapper.xml` 的 admin 分支只登记可见域豁免，两者都不能读成"处理动作对管理员免资格、对全域开放"。

**因此本预检不接受"端点已有权限注解 + 守卫已加锁 = 全域可见合理"的读法**；也不把"SQL 没写范围条件"直接当 IDOR 结论——见 §5 的 C-4：管理员可见域分支与调度专用语句（`selectUnhandledOfflineAlarms`）属设计明确许可，只有**写路径缺少上述两层闸门**才是缺陷。

## 4. Q2 答复：当前 SQL 与服务层能否共同保障该边界？

**不能。** 三点闭合失败：

- **写闸门与读闸门不同源**：002 对同一 `alarmId` 走带范围 SQL（`XML:168-176`）并返回 404（`Service:182-187`），003 走不带范围的 `selectAlarmRecordV2ById` / `selectAlarmRecordForUpdate`（`XML:179-183,307-319`）并允许写成功。服务层 `handleRecord`/`writeHandle`（`:203-339`）没有任何一处补做范围或资格判定，因此不存在"SQL 不做、服务层做"的兜底。
- **响应侧同样越界**：`Service:268-281` 用无范围单行读装配 `current`（含 `labName / alarmContent / detectorName / cultureCode / handler.displayName / recipients`，见 `fillAlarmRow:362-419` 与 `loadRecipients:440-492`），把"处理"变成一条跨域读取通道；同时 `resolveAllowedActions:422-437` 只判功能权限与 `handle_status`，服务端裁剪输出也不含可见性/资格。
- **重放路径绕过对象闸门**：`Executor:243-263` 命中回执即回调零执行，`Service:268` 仍在事务外做无范围读并整行返回。撤权后 24h 回执有效期内用原 `requestId` 重放即可取回整行，与 `详细设计.md:55`"接收历史快照不能永久授予已撤销项目内容"、`页面与接口契约.md:181,189`"所有列表结果仍重新核验当前权限"与 G05-A03"失权后不得返回旧缓存/总数"的口径不一致。

另有**边界外溢**（不属 003 实现缺陷，但决定"收紧 003 是否等于边界成立"）：同一权限标识 `alarm:alarmRecord:handle` 下仍暴露旧入口 `POST /alarm/alarmRecord/handle`（`AlarmRecordController.java:83-89` → `AlarmRecordServiceImpl.java:99-137`）。它按已退役的 `notify_users` 用户名判资格（`:120-130`，`数据库JSON与事务契约.md:27` 已声明该列不再是授权源），`notify_users` 为空即对所有持该权限者放行，且**不做可见域、不做 CAS、不进守卫、不写审计**。同前缀还有 `/alarm/alarmRecord/{id}`、`/list`、`/export`、`add/edit/remove`。**只收紧 V2 写口不会闭合业务边界**，旧入口处置需单列裁决（见 B-7）。
