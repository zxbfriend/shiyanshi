## 2. 公共请求与响应字段

请求头Authorization采用M01当前机制，不把token放URL。凡后端标注 `@ManagementGuardedWrite` 的写请求，前端必须携带 `X-Request-Id` 与 `X-Management-Revision`；服务端以 `WriteMeta` Header 为权威，Body 自报的 `requestId`、`managementRevision`、`baseRevisionId` 不得替代 Header。更新Body仍可按业务字段携带`expectedVersion:string`或配置`baseRevisionId:string|null`，首次创建null须由服务器验证无现行配置。幂等键作用域=用户+接口+目标，写证据至少与业务审计记录同寿命；同键同规范hash返回原结果，异hash为IDEMPOTENCY_CONFLICT。未知Body字段拒绝。

M09 已确认守卫写接口的 revision 来源：API03 使用 API01/02 顶层 `managementRevision`；API05 使用 API04；API07 使用 API06；API09 使用 API08；API13 使用 API12；API15 使用 API14；API16 使用 M02-081 读口 `GET /lab/soundalarm/{alarmId}` 的 `@CurrentManagementRevision`；API19 使用 API17；API21 使用 API20。API11 当前源码未标注 `@ManagementGuardedWrite`，前端不得按“全模块 10 条”猜测；若后续放行守卫写，必须先补 Controller 注解、契约清单和对应读口 revision 来源。API13 于 2026-10-10 放行守卫写（Controller 已加 `@ManagementGuardedWrite` 与 `WriteMeta` 形参，读口 API12 已带 `@CurrentManagementRevision`），双头制式与其他守卫口一致，Header 为权威、Body 不得覆盖。API16 于 2026-10-13 放行守卫写（M09+M02 联合接线）：Controller 已加 `@ManagementGuardedWrite` 与 `WriteMeta` 形参、路由 `{deviceId}` 对 Body 同名字段权威覆盖；声光目标无独立版本列，Body `expectedVersion` 必须与 `X-Management-Revision` 头同值，不一致按 INPUT_INVALID 拒绝（防“新头+旧体”混搭）。

分页Query：pageNum:int=1≥1、pageSize:int=10，推荐白名单10/20/50/100；历史兼容可接受1..100时由后端校验收敛。服务端白名单排序，不接受SQL片段。Filter日期startDate/endDate可选成对；keyword:string≤100默认空。列表结果鉴权后分页计total，不先分页再剔除无权项。标注 `@CurrentManagementRevision` 的分页读口在统一外壳顶层返回 `managementRevision`；未标注读口不得作为守卫写 revision 来源。

## 5. 示例与错误

处理请求：`{"requestId":"m09-demo-h1","expectedVersion":"3","action":"1","remark":"已到现场检查"}`。成功data：`{"requestId":"m09-demo-h1","outcome":"APPLIED","objectId":"91001","version":"4","issues":[]}`，附当前AlarmRow；示例ID不是生产数据。

离线提交：`{"requestId":"m09-demo-c1","cultureId":"88001","detectClass":"Cedex","baseRevisionId":"87001","reason":"调整下限","rows":[{"itemId":"86001","lowerLimit":"0.0000","upperLimit":"8.0000"}]}`；若需审批，applied=false、applyState=PENDING且revisionId/approvalId非空，页面旧阈值继续生效。

| 错误码 | 响应与页面处理 |
| --- | --- |
| UNAUTHENTICATED / FORBIDDEN / NOT_FOUND | 401/403/404，按统一存在性隐藏策略；清除敏感详情 |
| VALIDATION_FAILED / ROW_SCOPE_MISMATCH | 400，issues精确field/rowId，整组未保存 |
| VERSION_CONFLICT / IDEMPOTENCY_CONFLICT / EVENT_CONFLICT | 409，返回可见最新版本/既有请求引用，不覆盖 |
| ALREADY_HANDLED / DELIVERY_NOT_FAILED | 409，刷新当前记录，不重复写动作 |
| RECIPIENT_UNKNOWN / DEPENDENCY_UNAVAILABLE / POLICY_UNVERIFIED | 503或业务阻断，保留候选输入，不能降级当空/通过 |
| CHANNEL_UNCONFIGURED / SMS_TEMPLATE_TOO_LONG / MISSING_ADDRESS | 投递FAILED/SKIPPED原因，对其他通道继续；无秘密回显 |
| EXTERNAL_RESULT_UNKNOWN | outcome=UNKNOWN明确展示，不提供重复发送成功提示 |

批量失败默认原子，唯一例外是独立投递各通道结果；不把通知多通道部分失败回滚业务事件/站内成功。UI提示保存候选、审批通过、应用成功、命令接受、真实执行分开使用准确文案。

## G05 API17通知联合查询补充（2026-09-17）

API17新增recipientKeyword:string≤100、contentKeyword:string≤100，均可选默认空；trim后空串不加该条件，未知字段仍拒绝。新UI09展示“通知用户”和“标题/内容”（sms为“短信内容”）两个独立输入框。字段长度超限或非法通道/状态组合沿既有400 INVALID_ARGUMENT，错误指出字段但不回显联系方式。

1. 不同条件按AND：当前授权范围 AND channel AND 日期 AND 状态 AND 收件人条件 AND 内容条件。禁止把两个输入拼成一个keyword进行大OR。
2. recipientKeyword框内按OR：site匹配用户名/显示名；email另匹配该次投递的邮箱；sms另匹配该次投递的手机号。用户名/显示名通过稳定接收用户ID关联有权当前用户资料，历史缺失则只使用已有可信姓名快照，不伪造身份；地址必须取原投递目标，不用当前联系方式改写历史。
3. contentKeyword框内按OR：site/email匹配该条标题或正文，sms只匹配短信正文。采用字面子串匹配，参数化查询，%/_按字面字符转义，不把输入当SQL/正则。输入不拼接日志。
4. SELF始终约束当前本人，拒绝非空recipientKeyword（400），不得用该参数探测其他用户；SELF可按contentKeyword筛选。ADMIN沿既有受保护管理员权限，不因增加查询参数授予普通用户全局数据访问。
5. 旧keyword仅在两个新字段都为空时兼容原UI的单框联合搜索（有权收件人字段或标题/正文任一匹配；SELF仍仅本人）。非空keyword与任一新字段同时提交拒绝400，防止新旧筛选叠加歧义。新UI不发送keyword。
6. 先鉴权、日期/通道/状态筛选，再完成两框匹配与total计数，最后分页；site排序isRead ASC、createTime DESC、notifyId DESC。email/sms的DeliveryRow增加只读firstAttemptAt:ISO|null，取该投递已有attempt.startedAt最小值作为列表“首次发送时间”，无尝试为null；不新增持久字段。外部日期过滤与排序均用firstAttemptAt（DESC、null最后、deliveryId DESC），重试详情仍显示每次尝试时间；不能用scheduledAt计划时间冒充实际发送。日期条件存在时无尝试记录不命中，无日期条件的PENDING查询可见该记录且时间显示“未发送”。
7. isRead只适用于site，state只适用于email/sms；不适用的非空参数返回400。成功/失败沿SUCCEEDED/FAILED；UNKNOWN必须保留可查询且不能误归FAILED或开放重发。

### 地址/正文加密与查询实现边界

复用既有受保护原通知内容和投递地址，不新建明文联系方式/正文搜索副本。数据库密文不能直接LIKE，整值HMAC也不能冒充任意子串匹配。

无可用的核准安全搜索能力时，先在有权范围和时间/通道/状态上形成一致候选集合，在服务端受控内存中按批解密原地址/正文、完成字面匹配，再生成匹配ID集合及total后分页。原始值不得进入响应列表、应用日志、缓存或临时明文文件；返回仍按原DTO脱敏。候选规模和执行时限设置部署容量上限，超限明确400 INVALID_ARGUMENT要求缩小时间范围，不截断候选后返回伪完整total。密钥/归档内容读取失败沿503 DEPENDENCY_UNAVAILABLE，不当成不匹配或返回空列表。该受控搜索需独立审计访问人/用途/范围，但不记录明文搜索词；所有列表结果仍重新核验当前权限。后续优化必须证明结果与此语义等价，不通过取消模糊搜索偷减需求。

并发变化下每次请求的rows与total来自同一候选读取视图；普通翻页可以因新消息变化，界面保留筛选并显示本次查询时刻，不承诺跨多次请求冻结快照。不在发信事务中做查询解密，不新增发送或标已读副作用。

### B06 API01本人待办及旧路径桥接（2026-11-07）

### SC046离线配置提交、在途读取与原请求恢复（2026-11-07）

API13仍携原双头，管理修订仅取API12顶层managementRevision；baseRevisionId为API12最近APPLIED组修订。新运行/延期候选由M09在原守卫同事务创建PENDING/v1、同库提交真实M06_SC046并一次完善approval_id，首次外部可见版本仍1；后续APPLY/DISCARD/CONFLICT才状态版本+1，任一步失败整组回滚。初次运行档提交自行核当前lab OPERATE及既有lab:offlinealarm:edit；M03 M09-013用途仅提供真实祖先/绑定，不替代M09授权，也不借M07成员范围。旧生命周期DIRECT及其他kind/历史hash口径不扩。

AlarmConfigMutationResult沿用公共写结果全部原字段，仅新增revisionId:string、approvalId:string或null、applyState:ConfigApplyState。PENDING时applied=false、两个ID非空，APPLIED才applied=true；不增加outcome枚举。原UUID重放返回首次提交身份与结果，候选后来APPLIED/DISCARDED不把原PENDING提交回执改作“本次阈值已生效”；当前状态由API12或M06刷新。API12在同只读快照内读取原有效rows/APPLIED基线及本scope在途元数据；原修订为null就保留null，不拿PENDING ID补base。在途仅设置approvalId/applyState展示，allowedActions仍沿原编辑权限，不从PENDING推导禁用所有保存或合法DIRECT；当前政策及活动审批槽由正式写链校验。null映射、多候选或错scope均失败关闭，不选第一条或默认为无审批。
