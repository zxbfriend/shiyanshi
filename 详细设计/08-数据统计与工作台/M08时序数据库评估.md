## 1. 裁决结论

**已裁决（2026-11-04）：采用 QuestDB，承载 L0 原始层。** 原“待裁决问题：TSDB 是否承载 L0”于裁决后关闭，以下为裁决边界。

### 1.1 裁决边界

| 项 | 裁决内容 |
| --- | --- |
| QuestDB 承载范围 | **仅 L0（1s 原始观测）**；不承载 L1 1min、L2 5min、L3 1h、L4 1d |
| 汇总层（L1—L4） | **仍由我方自写**：QuestDB 无物化视图/连续聚合，不得假设其可替代 `m08_agg_obs_*` / `m08_stat_*` 聚合任务 |
| 业务权威源 | **MySQL**：培养/设备/指标主数据、业务表、统计读模型、归档任务元数据、口径版本 |
| 跨库查询 | **不做数据库层联表**：MySQL 业务表与 QuestDB 时序数据由程序侧分别取回后在应用层合并（规则见工作分解 §0.1.4） |
| 口径版本化 | `calc_version` 与 `m08_stat_definition` **仍自建**，不交给 QuestDB |
| 归档 | 仍按工作分解 §0.1.6 的对象存储 + manifest 设计；QuestDB 自带 TTL 不得替代“全量留存” |
| 新鲜度水位 | QuestDB 只提供“最后写入时刻”，分档水位、滞后判定与告警仍自写 |

### 1.2 已否决候选（简述）

| 候选 | 未选原因（一句话） |
| --- | --- |
| TimescaleDB | 连续聚合最贴合 L1/L2，但需 Linux/Docker，客户 Windows 内网默认不满足；降为“环境允许 Linux 时的更优替代”（§11.3） |
| InfluxDB 3 | 3.x 无 Windows 版，且需新学 Flux/任务模型，收益未超过 QuestDB |
| TDengine | 压缩最好但社区版 AGPL，商业交付需另购授权，合规成本高 |
| Apache IoTDB | 工业设备对齐模型契合、Apache 2.0，但 SQL/聚合能力与生态成熟度不如 QuestDB，需额外学习与验证 |
| ClickHouse | 官方不提供 Windows 生产支持，且为分析库、非严格 TSDB，不适合作为 L0 在线写入层 |
| MySQL 8 日分区（原方案） | 未选为主方案：90 天热区需 140—190 GB 含索引；降为**回退备选**（§11.2） |

## 2. 数据量与压缩

### 2.1 口径

- L0 热区 90 天：2,332,800,000 行（≈23.33 亿）；按 40 B/行估算约 93.3 GB 数据，MySQL 含索引 140—190 GB〔本项目，见工作分解 §0.1.6.10〕。
- 全量留存 3 年：约 1.17 TB 未压缩，年增约 378 GB〔本项目〕。
- 压缩比均以“93.3 GB / 1.17 TB 未压缩估算”为基数；40 B/行本身是估算值，压缩比会有 ±20% 波动。

### 2.2 压缩后容量对比〔厂商宣传 + 推算，未经本项目实测〕

| 方案 | 压缩机制 | 厂商公开口径 | 90 天热区（数据） | 3 年全量（数据） | 备注 |
| --- | --- | --- | --- | --- | --- |
| QuestDB 8.x | 列式 + 分区 + WAL，按列压缩 | 官方称高压缩、时序场景通常 5—10×〔厂商〕 | **9—19 GB** | 117—234 GB | 已裁决方案的容量区间 |
| TimescaleDB | PostgreSQL 列式压缩（chunk 级） | 官方称典型压缩 90%+，即 ≥10×〔厂商〕 | 6—12 GB | 80—160 GB | 需 Linux/Docker |
| InfluxDB 3 / 2.x | TSM/列式 + 专用编码 | 官方称典型 10× 左右〔厂商〕 | 7—12 GB | 100—160 GB | 3.x 无 Windows 版 |
| TDengine 3.x | 列式 + 一/二级压缩 | 官方称 10—20×〔厂商〕 | 5—9 GB | 60—120 GB | 社区版 AGPL |
| Apache IoTDB | TsFile 列式 + 编码 | 官方称 10× 以上〔厂商〕 | 6—12 GB | 90—180 GB | 工业设备模型契合 |
| ClickHouse | 列式 + 多种编码 | 经验 5—10×〔推算〕 | 9—19 GB | 117—234 GB | 官方不提供 Windows 生产支持 |
| MySQL 8 日分区（现状） | InnoDB 行存 + 二级索引 | 无压缩，索引膨胀 | **140—190 GB（含索引）** | 约 1.4—1.9 TB 在线 | 90 天热区即需独立实例 |

**结论**：TSDB 能把 90 天 L0 热区从 MySQL 的 140—190 GB 压到约 5—20 GB（数据），差一个数量级；这直接缓解 §0.1.6.10 的“90 天热区需独立表空间”压力。但**压缩比是厂商宣传值，必须以客户环境的实际数据分布压测复现**，不得据此直接采购磁盘。

## 3. 写入能力

- 本项目写入规模：300 行/秒、2,592 万行/天、单批可按设备/批次聚合为 45—300 行/秒〔本项目〕。
- 这是**低吞吐场景**：上述任一候选的单机写入能力都远高于 300 行/秒（厂商公开均为每秒数十万到数百万行级别〔厂商〕），写入不是选型分差点。
- 真正的差异在**写入语义**：
  - 断线补写：现场设备/网关断连后可能一次性补写数小时数据（如 4 小时 × 45 路 ≈ 64.8 万点），要求乱序写入与幂等去重。
  - QuestDB：WAL 表支持乱序提交；`DEDUP UPSERT KEYS(observed_at, series_id, calc_version)` 可做幂等覆盖〔厂商，需按目标版本核实语法〕。
  - TimescaleDB：PostgreSQL 堆表 + chunk，乱序与 upsert 天然支持（`ON CONFLICT`）〔厂商〕。
  - TDengine：支持乱序写入与更新，但需建库时指定 `UPDATE` 行为〔厂商〕。
  - InfluxDB 3：支持乱序写入，去重语义依赖 tag/field 与版本〔厂商〕。
  - IoTDB：支持乱序写入与对齐序列〔厂商〕。
- **一致性边界**：任何 TSDB 写入都**不能与 MySQL 业务事务组成同一个本地事务**。M02 必须先提交“接收事实/合法化”业务记录，再异步写 TSDB；失败进本地 outbox 重试，不得反向用 TSDB 成功与否决定业务事务提交。

## 4. 查询模式匹配

| M08 查询模式 | QuestDB | TimescaleDB | TDengine | InfluxDB | IoTDB | 判断 |
| --- | --- | --- | --- | --- | --- | --- |
| 培养/设备 + 指标 + 时间窗聚合 | `SAMPLE BY` + 条件过滤，满足〔厂商〕 | `time_bucket` + 连续聚合，最贴合〔厂商〕 | 时间窗口函数，满足〔厂商〕 | Flux/InfluxQL 任务，满足〔厂商〕 | `GROUP BY TIME`，满足〔厂商〕 | 均满足 |
| 最近 15 分钟 1s 明细（≤50,000 点） | 强（时序索引 + 分区裁剪） | 强 | 强 | 强 | 强 | 均满足 |
| 多指标时间对齐（同一设备多测点） | `ASOF JOIN`/`LATEST ON` 支持〔厂商〕 | SQL join 灵活 | 超级表 + 多列模型天然对齐 | 需 pivot/join，较绕 | **对齐序列原生支持** | IoTDB/TDengine 模型最贴合 |
| 跨档位降采样（1s→1min→5min→1h→1d） | 无内置连续聚合，需自建任务 | **连续聚合原生**，可替代自写〔厂商〕 | 流计算/窗口可做，需配置 | 任务（task）可做 | 内置能力随版本变动，需核实 | TimescaleDB 最优 |
| 90 天—3 年趋势（读 L2/L3） | 若只存 L0 则仍需 MySQL 读模型 | 连续聚合可覆盖 | 可覆盖 | 可覆盖 | 可覆盖 | 取决于是否把汇总也放进 TSDB |

**关键判断**：若 TSDB 只承载 L0（本文件默认口径），则**只有 L0 明细查询与压缩收益**，L1—L4 汇总仍走 MySQL；若把 L1/L2 也放进 TSDB，只有 TimescaleDB 的连续聚合能显著减少自写聚合代码，代价是口径版本化仍要自己实现。

## 5. 与现有系统集成（裁决落地口径）

### 5.1 已裁决：QuestDB 8.x 单机

**版本选择理由**：8.x 已具备 WAL 表、去重键与稳定的 PostgreSQL 线协议；选 8.x 稳定线而非最新大版本，是为了避开新版本 API/存储格式变动，便于客户环境冻结版本。具体补丁号由 DBA 在实施时按当时 8.x 最新稳定版锁定〔厂商〕。

**部署形态与最小资源**（单机，与 MySQL 共存于 1 台服务器时）：

| 项 | 建议 | 说明 |
| --- | --- | --- |
| 部署形态 | 单机单进程（systemd/Windows 服务或 Docker），独立数据目录 | 不做集群；单机即可满足 300 行/秒 |
| CPU | 4—8 vCPU | QuestDB 按核并行查询；写入 300 行/秒占用极低〔推算〕 |
| 内存 | 8—16 GB 给 QuestDB（另计 MySQL 与 Java 应用） | QuestDB 走 mmap/页缓存，内存越大查询越稳〔厂商〕 |
| 磁盘 | NVMe/SSD，专用卷 ≥200 GB；IOPS ≥3,000 | 90 天热区数据 9—19 GB，预留 WAL、快照、归档缓冲与 2 倍增长空间〔推算〕 |
| 与 MySQL 共存（仅 1 台机） | **可以，但有条件**：总内存 ≥32 GB、总 vCPU ≥8、TSDB 与 MySQL 使用**不同物理盘/卷**，并给两者设 IO/内存上限 | 同盘会互相拖慢 WAL 与 InnoDB flush；不得共用数据目录 |

**备份与恢复**：QuestDB 支持数据库级备份/恢复（`BACKUP DATABASE` / 快照式备份，版本差异需核实命令名〔厂商〕）；建议每日全量 + WAL 目录快照，恢复演练按 RTO ≤2 小时、RPO ≤15 分钟设计。备份产物仍落对象存储或独立盘，不与在线数据同盘。

**监控要点**：写入速率、WAL 应用滞后（commit lag）、磁盘增长与剩余空间、查询 P95/P99、mmap 页错误率、进程重启次数、失败写入计数；Prometheus 指标端点与告警阈值在实施设计阶段细化。

### 5.2 数据分工（绝不双写同一份权威数据）

| 数据 | 存放位置 | 说明 |
| --- | --- | --- |
| 培养/批次/项目、设备与指标主数据、映射关系 | **MySQL（权威）** | 业务事务、外键、权限、审计都在 MySQL |
| 业务表（M02 接收/合法化、M03 培养、M05 检测、M07 执行） | **MySQL（权威）** | TSDB 不存 |
| L0 1s 原始观测 | **QuestDB（唯一副本，权威时序源）** | M02 写；MySQL 不保留第二份 1s 原始，避免双写 |
| L1/L2/L3/L4 汇总与读模型 | **MySQL（按现设计）** | 若后续评估把 L1/L2 放进 TSDB，须单独裁决，不在本次裁决范围内 |
| 归档副本（>90 天） | **对象存储 + manifest** | TSDB 或 MySQL 都不承担“唯一归档”责任 |
| 归档任务/访问审计/口径版本 | **MySQL** | 业务元数据不进 TSDB |

“绝不双写”指：同一条 1s 观测不得既在 MySQL 又在 TSDB 各存一份权威副本；切换期若需双写，只能有一侧标记为“临时校验副本”，并在切换完成后删除。

### 5.3 Java 侧接入

| 项 | 口径 |
| --- | --- |
| 官方驱动 | QuestDB 提供 PostgreSQL 线协议，使用 PostgreSQL JDBC 驱动（42.x）连接〔厂商〕；另有 HTTP/ILP 接口 |
| 连接池 | HikariCP（Spring Boot 既有依赖），独立 DataSource，不与业务 MySQL 共池 |
| 批量写入 | 高吞吐写用 **ILP（InfluxDB Line Protocol）** 或批量 `INSERT`；读用 JDBC〔厂商〕 |
| 能否走 MyBatis | **能**：MyBatis 基于 JDBC，可复用 XML Mapper；但 SQL 必须是 QuestDB 方言（`SAMPLE BY`、`LATEST ON`、`ASOF JOIN`），不能直接复用 MySQL 写法 |
| Spring 集成成熟度 | 无官方 Spring Boot Starter，需要自定义 `DataSource`/`JdbcTemplate`/事务管理器；**不得把它并入业务主 DataSource 的 `@Transactional`** |

### 5.4 断线补写、乱序与失败补偿

- 写入路径：M02 业务事务提交 → 写本地 outbox（同库表）→ 异步批量写 TSDB → 成功回写 outbox 状态；失败按指数退避重试，超过阈值告警。
- 幂等：以 `(series_id, observed_at, calc_version)` 为去重键；重复补写不产生重复行（QuestDB 需在建表时启用 DEDUP，且仅对指定表生效〔厂商〕）。
- 乱序：允许乱序提交；查询按 `observed_at` 排序，不依赖写入顺序。
- 一致性边界：TSDB 写入失败**不阻塞** M02 业务事务，但必须留下“未落入 TSDB”的可见缺口（outbox 状态 + 告警 + 可重放），页面 `asOf`/水位必须反映真实缺口，不得显示为完整。

## 6. 用 TSDB 之后，M08 设计能简化哪些、不能简化哪些

逐条对应 [M08设计工作分解](M08设计工作分解.md) §0.1：

| 现有设计项 | 用 TSDB（仅 L0）后 | 替代范围 | 仍需自写 |
| --- | --- | --- | --- |
| L0 1s 存储与分区（0.1.6.2、0.1.7） | **简化**：TSDB 原生按时间分区、列式压缩，无需手工日分区与索引维护 | 分区滚动、压缩、时间窗裁剪 | 序列 ID 注册、培养/设备/指标映射、权限过滤、`calc_version` |
| L0 90 天热区/归档边界（0.1.6） | **部分简化**：热区容量下降，边界仍由 M08 判定 | 仅存储与查询侧 | 归档判定、manifest、校验、审计仍自写（TSDB 原生 TTL 会删数据，违反“全量留存”） |
| L1 1min / L2 5min 聚合（0.1.5） | **不简化**（QuestDB 无连续聚合） | — | 聚合任务、唯一键 upsert、幂等、回补、版本化全部自写 |
| L3 1h / L4 1d 读模型（0.1.5） | **不简化** | — | 仍为 MySQL 读模型与离线任务 |
| 归档任务（0.1.6.5） | **不简化** | — | 触发、状态机、校验、断点续跑、`m08_archive_job`、对象存储上传全部自写 |
| 新鲜度水位（0.1.5） | **部分简化**：TSDB 可提供最后提交时间 | 仅“最后写入时刻” | 分档水位、业务滞后判定、告警阈值、页面 `asOf` 仍自写 |
| 查询路由（0.1.6.8） | **不简化** | — | 热区/归档自动路由、跨边界合并排序分页去重仍自写 |
| 导出上限（0.1.7） | **不简化** | — | 行数/大小上限、异步导出、1s 不导出仍由应用层控制 |
| 口径版本化（0.1.8） | **不能交给 TSDB** | — | `calc_version`、`m08_stat_definition`、历史报表不退化必须自写 |
| 实时查防护/QPS/缓存（0.1.4） | **不简化** | — | 档位路由、限流、缓存分级、越界拒绝仍在应用层 |

**结论**：TSDB 只让“L0 存储与热区查询”变简单，**不会让整个 M08 设计变简单**；它不替代聚合任务、归档、版本化、路由与防护。若仅为压缩与 L0 查询引入 TSDB，收益是容量与查询性能，成本是多一套存储与一致性边界。

## 7. 运维成本

| 项 | 评估 |
| --- | --- |
| 部署 | 单机进程，比 MySQL 集群简单；但需要新学一套配置、目录布局与升级流程 |
| 备份/恢复 | 需单独备份策略与恢复演练；不能复用 MySQL 备份链 |
| 监控 | 需接入既有监控（Prometheus/告警），新增指标与阈值 |
| 升级 | 大版本升级需停机窗口与回归；QuestDB 存储格式跨大版本升级需按发布说明验证 |
| 扩容 | 单机纵向扩容（加盘/加内存）；数据量增长到 90 天热区以上时需重新评估分片或归档 |
| Windows Server/客户内网 | QuestDB 为 Java 应用，可在 Windows 运行；但仍需 JRE、服务化、防火墙端口与内网离线安装包。**不得假设“能跑 MySQL 的机器就能跑 TSDB”**，需现场验证 |

**与 1 台服务器共存**：技术上可以，条件是总内存 ≥32 GB、CPU ≥8 vCPU、TSDB 与 MySQL 分盘、分别限流；若客户只有 1 台且配置不足，回到 §11 保守备选。

## 9. 迁移回退与锁定风险

- **切换路径**：MySQL 保留权威业务数据；L0 由“MySQL 分区表”切到 TSDB，需一次性/分批迁移既有 1s 数据并双读校验（迁移期只允许一侧为权威）。
- **回退路径**：保留 MySQL 分区表结构与 M02 写 MySQL 的代码开关（feature flag），TSDB 异常时切回 MySQL 写入；回退窗口内 TSDB 数据导出为 Parquet 后可回灌 MySQL。
- **锁定风险**：查询方言（QuestDB `SAMPLE BY`、InfluxDB Flux、TDengine SQL 方言）会渗透到 Mapper/查询层；缓解方式是**把时序查询集中在 M02/M08 的 Port 实现内**，业务层不直接写方言 SQL。存储格式锁定次之，可用 Parquet 归档保证可迁移。

## 10. 与归档策略（0.1.6）的关系

- TSDB 自带的 TTL/retention 会**删除**数据，与“全量留存、不删除”直接冲突；因此：
  - **不得**用 TSDB 的自动过期替代 0.1.6 的归档；
  - 归档仍由 M08/M02 导出 Parquet + manifest 到对象存储，校验通过后才允许回收热区；
  - TSDB 的降采样（若有）只能替代 L1/L2 的**计算**，不能替代**归档副本与审计**。
- 若未来采用 TimescaleDB 连续聚合，可减少 1min/5min 自写聚合代码，但 `calc_version` 与“历史报表不退化”仍需自写。
- 结论：**TSDB 不能替代自写归档**；最多降低热区容量与查询成本。

## 11. 裁决结果与保守备选（回退）

### 11.1 已裁决采用：QuestDB 8.x 单机（仅承载 L0 1s 原始）

**一句话理由**：在客户 Windows 内网、允许新增单机服务的条件下，QuestDB 是唯一同时满足“Apache 2.0 无传染风险、Java 可在 Windows 运行、PostgreSQL 线协议可复用 MyBatis、列式压缩把 90 天热区从 140—190 GB 降到约 9—19 GB”的候选。**2026-11-04 用户裁决采用；本节原“首选/待裁决”表述保留为留痕，裁决后关闭。**

**成立前提**：
1. 客户确认允许新增独立服务且为单机（已确认，2026-11-04）。
2. 目标机满足 §5.1 的最小资源，且 TSDB 与 MySQL 分盘。
3. 法务确认 Apache 2.0 可用（预期无风险，仍需走流程）。
4. M02 接受“业务事务 + outbox + 异步写 TSDB”的写入链路改造。

**反转条件**（出现任一条即改判）：
- 客户只允许一台服务器或不允许新增服务；
- 目标环境无法安装/服务化 QuestDB（如缺少 JRE、端口受限、离线包不可得）；
- 写入吞吐或 WAL 滞后在压测中不达标（如持续 >1 分钟滞后）；
- 跨库一致性方案被 DBA/架构否决；
- 法务对 Apache 2.0 或厂商支持期有异议；
- 归档必须由 TSDB 自身完成（本方案不支持）。

### 11.2 保守备选：MySQL 8 日分区表 + 对象存储归档（现行设计）

即 [M08设计工作分解](M08设计工作分解.md) §0.1.5—§0.1.7 的现方案：
- L0 按日分区，90 天热区约 140—190 GB（含索引），需独立实例/表空间；
- 1min/5min/1h/1d 汇总与读模型全部在 MySQL；
- 归档由 M08/M02 导出 Parquet + manifest 到对象存储。

**采用条件**：上述任一反转条件成立，或 TSDB 的容量收益不足以抵消多一套存储的运维与一致性成本。

**回退触发信号（具体可判定）**：
| 信号 | 判定方式 | 动作 |
| --- | --- | --- |
| 无法部署 | 目标机安装失败/无 JRE/端口不可用 | 立即回退 MySQL 分区 |
| 运维不接受 | DBA 书面否决新增存储 | 回退 |
| 跨库一致性不可接受 | 架构评审否决 outbox 双写 | 回退 |
| 写入不达标 | 压测 WAL 滞后持续 >1 分钟或丢写 >0 | 回退 |
| 授权不合规 | 法务否决 | 回退 |
| 容量收益不足 | 实测压缩比 <3× | 回退 |

### 11.3 环境允许 Linux/容器时的更优替代

若客户实际可提供 Linux + 容器（与“Windows 内网”假设相反），则 **TimescaleDB 优于 QuestDB**：其连续聚合可直接替代 L1/L2 自写降采样任务，SQL/事务语义更接近现有 MyBatis 经验。但该分支**不改变 2026-11-04 已裁决的 QuestDB 结论**，仅在客户环境实际变为 Linux 时重新评估。
