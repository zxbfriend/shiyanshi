### 3.3 读投影与契约差异

1. 010当前返回 `AjaxResult.data=PageResult{rows,total,pageNum,pageSize}`，不是旧总述所写顶层TableDataInfo。SDK按实际外壳适配并保留元数据。
2. 最新专题和服务默认pageSize=10；接口目录残留20，以当前专题/代码10为准。前端显式传pageNum/pageSize，不依赖未传时的SQL参数默认。
3. personKeyword当前SQL主要查人员ID字符串，未实现用户名/显示名语义；日期SQL将起点OR与终点OR分开，可能被不同列分别命中。BE04要求按每一时间列完整区间OR修正，前端不能先拉全部后过滤。
4. labName、reviewer/approver姓名当前可能为空；operator当前从initiator构造，不完全等于最后操作人。快照缺字段不得拿当前姓名假装历史姓名。
5. 011没有deliveryId、交付诊断、活动reconciliationId；001需已知deliveryId、005需已知reconciliationId。不能让用户猜ID或从内部数据库找ID完成页面跳转，BE07。
6. `TypedValue.value`目标为string/boolean/null，当前Java为String。布尔、NULL、DECIMAL显示协议需BE05明确；不能用`Boolean("false")`或`Number(null)`转换。
7. 既有m06-blocked将全部403归为菜单缺失、全部503归为外部回执缺失，过于宽泛。新页按errorCode区分权限、政策未核准、授权服务故障和拥有方故障。

## 4 公共协议与业务约束（FE00）

### 4.1 请求、版本与幂等

- 所有ID和Version保存为十进制字符串，禁止转JS Number；政策未建根的objectVersion为`"0"`是明确特例，新审批/对账对象版本从1开始。
- HTTP路径沿项目请求client和网关配置，不硬加`/system`；Authorization沿会话，不从页面接收actor/userId/权限/状态。
- managementRevision、审批objectVersion、政策objectVersion/currentRevisionId、baseDeliveryVersion、candidateVersion、decisionVersion分别存储，不互换、不客户端自增。

| 接口组 | 写元数据实际位置 | 版本来源与页面要求 |
| --- | --- | --- |
| 006政策启停 | X-Request-Id、X-Management-Revision头；Body expectedVersion/action/reason/evidence | 同一实验室政策上下文007/008正式读外壳；expectedVersion来自008；状态缺口另见BE02 |
| 009整份保存 | 同上；Body expectedObjectVersion/entries | 008外壳管理版本和data.objectVersion |
| 014审批动作 | 同上；Body action/expectedObjectVersion/reason | 011详情顶层managementRevision和row.objectVersion；013不能替代读管理版本 |
| 002/003/004对账写 | **当前非ManagementGuardedWrite**；requestId在JSON Body；baseDeliveryVersion或expectedVersion也在Body | 001交付版本或005对账版本；DTO虽然还有managementRevision，当前服务未消费，不伪造其值或假设Header生效 |
| 013预检 | 只读POST，Body action/expectedObjectVersion；不需要守卫写头 | 没有M05式confirmationToken，不自行增加令牌协议 |

对账组与模块旧“所有写统一Header”总述存在实际差异，按当前Controller分组封装，未来如统一须同步契约和SDK（BE08）。路径`{id}`覆盖Body自报id，001/005的deliveryId/reconciliationId也是路径确定，浏览器不发送冲突双身份。

用户一次明确提交生成UUID；重复点击/超时核实保留原ID和原载荷。内容改变属于新意图，需重新加载并确认。已未知的写不能靠换新UUID重试；M01回执到期也不代表长期审批动作可以再做一次。

014当前新提交data.actionId/requestId可能为null；不能客户端生成actionId补齐。保留原请求ID，成功后重读011/012核对；完整回执与长期重放差异见BE10。

### 4.3 资格、四档政策与职责分离

| 审核reviewMode | 批准approveMode | 业务结果 |
| --- | --- | --- |
| DIRECT | 强制NONE | 不建审批单、不要求业务原因；仍有技术审计/幂等 |
| DIRECT_REASON | 强制NONE | 不建审批单，原因落来源记录；仍有技术审计/幂等 |
| BATCH | NONE/BATCH/PROJECT | 当前有效批次成员审核，按批准档决定是否第二级 |
| PROJECT | NONE/BATCH/PROJECT | 当前有效项目成员审核，按批准档决定是否第二级 |

- 资格=阶段功能权限∩实验室OPERATE∩当前有效MEMBER范围∩状态/版本/来源准入；历史SHARE、负责人称谓、超级管理员身份不自动绕过。
- 申请人不能审核/批准自己，审核人与批准人必须不同稳定userId；显示名更改或同名无影响。
- 批次阶段扣除申请人、无资格者和第二级的首级审核人后无人，才按NO_ELIGIBLE回退当前项目MEMBER。离线不等于无资格，服务故障不等于无人；项目也无人保持待办，不转管理员/自动通过。
- differentStageActors=true、batchFallback=NO_ELIGIBLE为服务端固定规则，不做可编辑开关。
- SYSTEM申请initiatorUserId为空，不用用户0；系统单没有普通“管理员代撤回”，由来源合法失效事件结束。
- Q31培养草稿/未开始/已过期的修改删除先走来源免审批分支，不把场景政策改成DIRECT，也不扩为通用任务免审。

### 4.4 公共交互与错误

列表/详情具备加载、真正空结果、权限不足、依赖不可用、未核准、读取失败和未知态。切实验室、筛选、详情对象时取消旧读请求并丢弃迟到响应；写请求取消不代表服务端回滚。关闭未保存弹窗提示保留/放弃；保存中禁重复提交。

| 错误 | 处理 |
| --- | --- |
| INPUT_INVALID/INVALID_ARGUMENT、REASON_REQUIRED | 定位字段，保留非敏感输入；不把空原因换成预设假原因 |
| POLICY_UNVERIFIED | 政策未核准，关闭需政策的写；不当成DIRECT或默认审批通过 |
| AUTHORIZATION_UNAVAILABLE、OWNER_UNAVAILABLE | 明确依赖不可核验，阻止动作；不当作无人可审/无记录 |
| MANAGEMENT_CONFLICT、VERSION_CONFLICT | 刷新同对象、对比草稿、重新确认；不自动覆盖 |
| SOURCE_STATE_CONFLICT | 区分ENABLED政策未先暂停、审批终态、职责分离、来源状态冲突；按具体上下文说明 |
| SELF_APPROVAL、STAGE_ACTOR_CONFLICT、FORBIDDEN/PERMISSION_DENIED | 当前无资格，保留只读范围；当前部分分离错误实际返回SOURCE_STATE_CONFLICT也需处理 |
| CULTURE_CODE_CONFLICT | 显示“修改后的培养ID不唯一”，禁止通过；仍可合法驳回 |
| REQUEST_CONFLICT、ACTIVE_CHANGE_EXISTS | 原请求/活动变更冲突；不自动生成新键绕过 |
| NOT_FOUND/404 | 不存在或无对象范围统一展示，不泄露真实存在性 |
| 501 | 功能尚未接入；不能显示空数据或成功 |
| 网络超时、UNKNOWN | 显示原请求结果待核实；重读原对象，禁止自动重复生效 |

## 5 页面开发说明

### 5.1 FE01 实验室审批政策

从实验室列表的“审批流/审批设置”操作打开，labId固定只读。读取008和007 `purpose=POLICY`，不要在弹窗内换实验室后带原版本保存。

表格列：一级模块、二级模块、操作、审核四档、批准三档、范围说明；按服务端sortOrder分组。POLICY仅SUPPORTED+OWNER_GATED，FILTER可含EXCLUDED。**整份保存集合以当前POLICY返回值为准，不硬编码47条或某个可配置数量。**

008未建根时policyId/currentRevisionId为空、objectVersion="0"、entries空、readiness=UNVERIFIED：显示未配置；将目录渲染成待填写行，不自动填DIRECT。每行两个档位均必填；DIRECT/DIRECT_REASON时批准强制NONE；切回BATCH/PROJECT保持NONE，不偷偷恢复旧隐藏值。

保存009只传expectedObjectVersion及完整entries，每项sceneCode/reviewMode/approveMode；不得漏行、重复、超集、空数组清空或逐行PUT。Header用008管理版本；成功显示新版本并重新读取，readiness回落UNVERIFIED，新版本不继承旧verifiedBy/verifiedAt。

只有lab:approval:edit+真实MANAGE且allowedActions含SAVE可编辑；普通lab:lab:edit不能替代。只读用户可读008，但POLICY目录需要MANAGE，不得为了渲染用FILTER绕过；只读标签投影不足记BE02。

ENABLED政策要先PAUSE再保存，直接保存409 SOURCE_STATE_CONFLICT；对象版本变化才是VERSION_CONFLICT。暂停及保存均需用户独立确认，不在点击保存时自动代执行暂停。核准导入属于实施流程，前端没有“标记已核准”或自报verifiedBy按钮。

### 5.6 FE06 日志

### 5.7 FE07 业务生效与交付诊断

现有011可显示applyState，足以做“业务待生效/结果待核实”的基本标签；完整诊断还需deliveryId、原decisionVersion、candidateHash、unknownSince、重试预算、最近拥有方结论和活动对账标识，当前缺可导航投影（BE07）。

从原交付上下文进入，完整流程：001预览 → 002申请 → 005详情 → 不同人003复核或本人004撤回 → 005查看拥有方最终结果。暂不存在专用对账列表API，不发明 `/reconciliations/page`；BE07解除前仅做有真实上下文的组件和Mock。

| 步骤 | 页面内容/请求 |
| --- | --- |
| 001预览 | 原approvalId/deliveryId/decisionVersion/decision、candidateId/hash、deliveryState/applyState、unknownSince、retryBudget、baseDeliveryVersion、evidenceRequirements/maskedEvidence、allowedResolutions/issues |

| 003复核 | Body requestId、expectedVersion、APPROVE/REJECT、reason、evidenceHash；同意必须绑定原摘要；当前代码两种动作都要求原因 |
| 004撤回 | Body requestId、expectedVersion、reason；仅本人SUBMITTED；RESOLVING不能撤回拥有方正在做的操作 |

目标处理方式：

- VERIFY_APPLIED：只用于APPLY，核实拥有方原子生效回执；成功才将原业务标APPLIED、交付ACKNOWLEDGED。
- SEAL_NOT_APPLIED：拥有方需原子证明从未生效并永久封禁原决定；APPLY可据可信封禁结果转失败并释放活动槽，DISCARD按DISCARDED回执完成取消，不改成APPROVED。已生效事实优先。
- 提交人与复核人必须不同稳定userId；当前功能权限、实验室及原业务范围均需校验，管理员口头判断不替代证据。

**当前差异**：001把两种resolution全部返回且maskedEvidence=null；002实现只允许APPLY→VERIFY_APPLIED、DISCARD→SEAL_NOT_APPLIED，尚未满足目标APPLY封禁分支；003只检查摘要形状，未见与原证据摘要相等及正文摘要复核的完整链。resolve/seal端口也未闭环。将这些列为BE08/09，不能由前端选择项过滤掩盖后端缺失。
