# 骨架文件所有权与并行任务包

版本：PK-20260918-02 · 日期：2026-09-18 · 分支：cloud · 范围：M01—M07、M09（M08完全排除）

> 权威输入：[00-全接口契约骨架清单.json](00-全接口契约骨架清单.json)（532条canonical HTTP接口、71个内部契约）、[00-全接口契约骨架问题收口决策.md](00-全接口契约骨架问题收口决策.md)、[开发实现结构与事务编排约定](../详细设计/00-开发实现结构与事务编排约定.md)及各模块现行物理设计。
>
> 本文只冻结骨架文件所有权、接口先行批次和并行门禁，不实现业务逻辑，不执行SQL，不改Java/XML/Vue代码。

## 0. 修正结论

原版把JSON中的367个`suggested_owner_files`当成全部骨架文件，遗漏DTO/VO、部分Service接口与实现、Mapper接口、Port和公共错误码；原三批排程也会使第一批消费者依赖第二批提供方尚未创建的Port接口。上述问题已在本版修正。

本版采用“**PKG-00接口先行 → 8个业务包全并行 → PKG-09整合**”模型：

1. PKG-00先生成依赖中立的错误码/认证契约、system公共响应外壳以及全部本地跨模块Port接口和Port DTO/VO。
2. PKG-00合入后，PKG-01—PKG-08只修改各自模块拥有的Controller、Service、ServiceImpl、Port适配器、Mapper、XML和模块DTO/VO，可同时并行。
3. PKG-09只做整合校验，不新建业务实现。

计划状态：**`SKELETON_PLAN_READY_V2`**。该状态表示文件归属规则和执行顺序已可执行，不表示任何Java/XML/SQL已实现。业务包不得绕过PKG-00提前创建公共类型或Port接口。

## 2. 完整文件所有权解析规则

### 2.1 权威顺序

每条接口按以下顺序解析文件，前一层优先于后一层：

1. JSON中的`controller_class`、`service_interface`、`service_impl_class`、拆分后的`mapper_interface` FQCN。
2. JSON中的`mapper_xml_statement`所含`mapper/**/*.xml`物理路径。
3. JSON中的`request_dto`、`response_vo`表达式，按本节DTO/VO规则解析原始类型和泛型参数类型。
4. [开发实现结构与事务编排约定](../详细设计/00-开发实现结构与事务编排约定.md)中的公共契约和Port物理位置。
5. `suggested_owner_files`只用于提示已有文件和迁移目标；与1—4冲突时，以1—4为准并修正提示。

禁止根据URL或契约ID临时猜类名；规则只能把已经冻结的类名转换成路径。

### 2.2 FQCN与文件路径

| 构件 | 路径解析 | 唯一所有者 |
| --- | --- | --- |
| Controller | FQCN转`src/main/java/<package>/<Class>.java` | 该接口`module`对应业务包 |
| Service接口 | `service_interface` FQCN转Java路径 | 对应业务包 |
| ServiceImpl | `service_impl_class` FQCN转Java路径 | 对应业务包 |
| Mapper接口 | 先按`;`拆分多个FQCN，再分别转Java路径 | 表拥有方业务包 |
| Mapper XML | 从`mapper_xml_statement`提取每个`mapper/**/*.xml` | 与对应Mapper接口相同 |
| 普通请求DTO | system接口落`futurefab-modules/futurefab-system/src/main/java/com/futurefab/system/domain/dto/m0x/<Type>.java`；auth接口落`futurefab-auth/src/main/java/com/futurefab/auth/domain/dto/m01/<Type>.java` | 对应业务包 |
| 普通响应VO/Row/View | system接口落`futurefab-modules/futurefab-system/src/main/java/com/futurefab/system/domain/vo/m0x/<Type>.java`；auth接口落`futurefab-auth/src/main/java/com/futurefab/auth/domain/vo/m01/<Type>.java` | 对应业务包 |
| 公共原始类型 | 使用§3固定路径，不按接口模块重复生成 | PKG-00 |
| 本地跨模块Port接口/模型 | `service/port/m0x/**` | PKG-00先行创建，业务包后续只读 |
| Port适配器 | `service/impl/port/m0x/**` | Port提供方业务包 |

泛型表达式必须拆分。例如`PageResult<ProjectRow>`解析为PKG-00拥有的`PageResult.java`和M03拥有的`ProjectRow.java`；不得创建名为`PageResult<ProjectRow>.java`的文件。

## 5. 表拥有方与事务审计口径

原版“87张表双写为0”实际只统计了`transaction_owner_table`主事务根，不能证明关联表没有被多模块写。本版改为以下两个层次：

1. **骨架阶段门禁**：`transaction_owner_table`的87个不同值无跨模块重复；Mapper接口及XML只能归《表结构与模块拥有方清单》规定的模块。骨架不得写SQL，因此本阶段只验证文件和调用边界。
2. **业务实现阶段门禁**：每个应用方法必须登记`transaction_root`、完整`write_tables[]`、`read_tables[]`和调用的Port；按完整`write_tables[]`再次检查双写。M06的`apr_action/apr_delivery/apr_policy_revision`、M09的`alarm_recipient`等关联写表必须进入完整写集合，不能只登记主表。

在完整`write_tables[]`审计通过前，只允许生成Mapper方法/XML statement空骨架，不允许补SQL或业务写逻辑。这与当前“先生成全接口契约骨架、具体逻辑后补”的开发方式一致。

## 6. M08边界

M08在本轮保持：

- 零M08拥有的Controller/Service/Mapper/表写入；
- 零对M08 Java包或Maven模块的编译依赖；
- 不生成M08消费者、统计查询或统计表SQL。

M02/M03/M05/M07/M09可以保留各自拥有的业务事实事件/outbox发布接口。`RunEventPublisherPort`允许发布M07业务事件；当前只有已纳入范围的消费者参与联调，未来M08可按`eventId`接入消费，但不得回写或阻塞业务模块。这不属于“M08泄漏”。

## 8. 公共文件变更流程

1. 申请必须写明物理文件、契约ID、原因和所有消费包。
2. 只有文件唯一所有者可修改；业务包不得直接修改PKG-00文件或其他包文件。
3. 公共契约变化必须同步JSON/MD、问题收口决策和本文，并重跑全量门禁。
4. PKG-00完成后，两个POM、公共错误码、公共类型和Port接口全部只读；业务包只实现本模块适配器。

## 9. 骨架硬门禁

生成前和合并后必须同时满足：

1. 532条canonical记录，重复method+path为0，M08记录为0。
2. Controller、Service接口、ServiceImpl和拆分后的Mapper FQCN跨模块冲突均为0。
3. 每个`REQUIRED`接口的Mapper接口/方法/XML statement齐全；`NOT_APPLICABLE`不生成Mapper。
4. DTO/VO表达式中的每个业务类型都能按§2落到唯一文件；公共原始类型只能命中§3单一文件。
