## 3. 任务 5：ORG10 预检 vs ORG18 删除口径差异登记（**只登记，不改行为**）

### 3.1 精确取证（当前 HEAD）

- **ORG10 预检 `DeptApplicationServiceImpl.deleteCheck`（M01-019，:167-188）**只统计**单节点**两项：
  - `deptMapper.checkDeptExistUser(deptId)` → `userCount`（该部门在册用户），命中置 `DEPT_HAS_USERS`；
  - `deptMapper.hasChildByDeptId(deptId)` → `childCount`（**直接**子部门），命中置 `DEPT_HAS_CHILDREN`；
  - `allowed = (userCount + childCount == 0)`，`referenceCount = userCount + childCount`。
- **ORG18 删除 `writeDeleteDept`（M01-030，已接线守卫写，:386-412）**按 §15.1 展开**合并子树**（根 + 全部有效后代去重升序），**逐节点**调 `deptMapper.countRelatedDeptUsage(id)` 重验，引用面覆盖**用户 + 有效实验组 + 实验室 + 项目部门配置**，任一节点命中即整批 `REFERENCE_EXISTS`。

### 3.2 口径差额（两个维度，均真实存在）

1. **节点范围**：预检只看单节点，删除看整棵合并子树 → 预检 `allowed=true` 时，删除仍可能因**深处后代**的引用而整批失败。
2. **引用类型**：预检只数"用户（+ 把'有子部门'当阻断代理）"，删除还数"实验组 / 实验室 / 项目部门配置" → 预检 `allowed=true` 可能漏判这三类引用；反向地，预检因 `DEPT_HAS_CHILDREN` 判 `allowed=false`，但删除口本可**连带软删整棵子树**，预检在此**过度阻断**。

### 3.3 若改 ORG10 行为的影响面（为何本批不动）

- `DeletePrecheckResult` 是**已合并的冻结契约响应面**（`referenceCount`/`reasonCodes`/`allowed`/`managementRevision`），前端删除预检弹窗据此提示；改 `reasonCodes` 词表或 `allowed` 语义会牵动前端提示与既有契约测试，属**跨端契约变更**，需设计裁决。
- 预检要升级到子树 + 全引用类型，需扩读 `countRelatedDeptUsage` 的子树聚合与实验组/实验室/项目部门引用——后者跨 M02/M03 事实，是否允许 ORG10 只读聚合亦待裁（与场地侧 BLK-02 同族）。

### 3.4 建议方案（提请裁决，本轮不改行为）

- **方案 A**：ORG10 升级为"全子树 + 全引用类型"预检，与 ORG18 权威口径对齐（最一致，但改动面最大、需补 reasonCode 词表与可能引入跨模块只读聚合）。
- **方案 B（保持现状，推荐默认）**：ORG10 维持轻量单节点预检，**删除口 ORG18 为权威 fail-closed**；预检定位是"快路径提示"而非"可否删除的保证"。
- **方案 C**：在 B 基础上，前端预检文案追加"**预检仅供参考，最终以删除结果为准**"，并把 `DEPT_HAS_CHILDREN` 与"有引用"在 reasonCode 上区分（子部门存在≠不可删除）。

> 场地侧同族差额已在上一批 `VenueApplicationServiceImpl` 注释登记（BLK-02）；本轮把部门侧（ORG10/ORG18）差额一并落到本文档，二者应由同一裁决收口。
