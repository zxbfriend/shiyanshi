## 1. 结论摘要

M05-014 由显式 501 骨架接为**真实只读查询口**：按原请求号读 M01 幂等回执，合并 `det_dispatch_log` 的关联派发最新事实，
供前端在"发送时网络卡住、页面没回执"时用同一个请求号问"那次到底送出去了没有"。

裁决依据（用户已写明）：*M05-014 查操作状态可以先接真实持久记录查询，不必等所有设备通道核准。
但没有真实派发记录时，不得制造『已接受/已完成』。*

本实现严格遵守该边界：**查不到派发记录就如实返回"未找到派发事实"，绝不凭空返回 ACCEPTED/已完成。**

## 3. 权限：怎么保证"请求 ID 不可作为绕过凭据"

契约原文（设计 §3 末段）：*GET 操作状态只能查有当前读取权限且属于本人的操作，系统恢复使用内部用途；
请求 ID 不可作为绕过权限的凭据。*

实现为**三层并列校验，缺一即失败关闭**（`M05OperationStatusQueryService.queryCurrent`）：

### ① 功能权限 —— `detect:workbench:query`

经 `M05AccessSupport.requireCurrent(PERMISSION_QUERY)` 按**当前服务端会话**解析出的可信身份判定，
不复用页面进入时的授权结论。功能码取设计 §3"表中 query/add/edit 完整码前缀为 `detect:workbench:`"。

### ② 对象读取范围 —— 派发事实所属实验室

每条派发事实的 `detector_id` 经 **M02 内部服务** `ILabDetectorService` 读出 `lab_id`（不跨模块直取
`lab_detector` Mapper），必须落在本人 VIEW 可见集合内；`allAccess` 直接放行，范围服务返回 `null` 时
按 `DEPENDENCY_UNAVAILABLE` 失败关闭，**不得降级成"无派发事实"**。

### ③ 属于本人 —— 复合主键等值查（关键）

回执一律按 **`(actor_user_id, request_id)` 复合主键等值查**：

```java
SysManagementRequest receipt = receipts.selectReceipt(actorId, requestId);   // actorId 来自可信身份
if (receipt == null || receipt.getActorUserId().longValue() != actorId || !requestId.equals(receipt.getRequestId())) {
    throw notFound();
}
```

- `actorId` 由服务端会话推导，**不接受**请求体/路径传入；
- 本口**不提供**任何"仅按 requestId 查回执"的语句——`SysManagementRequestMapper` 的唯一 `<select>`
  强制带 `actor_user_id` 条件，请求号在**结构上无法单独可达**（由
  `noMapperStatementCanReachAReceiptByRequestIdAlone` 用例钉死）；
- "回执不存在"与"是别人的回执"归一为**同一原因**`FORBIDDEN_OR_NOT_FOUND`"操作记录不存在或无权访问"，
  请求号因此不能用作存在性或归属的探测凭据；
- 额外 fail-closed：即使 Mapper 返回的行自称属于他人（数据污染/并发改写），也一律拒绝。

## 4. 查不到派发记录时返回什么

**如实返回"未找到派发事实"，不制造任何成功态。**

| 位置 | 取值 | 依据 |
| --- | --- | --- |
| `operationState` | **原回执里的 `operationState` 原样透出**（如 `UNKNOWN`），不因查不到派发记录而改写 | 回执不篡改 |
| `items` | **空列表**——不凭空造行，尤其不造 `ACCEPTED` 行 | 无行可读即无行 |
| `queueStatus` | 逐行 `null` | 无设备队列事实 |
| `reasonCode` | 不产生（无行即无行） | — |

明确**不**做的三件事：

1. **不**因"查不到"就断言未调用——设计 §2 `queryDispatch`："仅查不到不能证明未执行"；
2. **不**返回 `ACCEPTED` 或任何已完成态——这是裁决明令禁止的"制造"；
3. **不**把读失败降级成"无派发事实"——读取异常统一 `DEPENDENCY_UNAVAILABLE`，范围不可核验统一 503，
   回执 `operationState` 缺失或取值非法统一 `RESULT_PROJECTION_UNAVAILABLE`（不默认 `UNKNOWN` 掩盖证据缺失）。

### 派发事实存在时的状态映射（取值不猜测）

| `device_status` | `dispatch_lifecycle` | `dispatchState` |
| --- | --- | --- |
| `accepted` | 任意 | `ACCEPTED` |
| `rejected` | 任意 | `REJECTED` |
| `unknown`/NULL | `PREPARED`/`INVOKING` | `INVOKING`（调用中，**不**称已接受） |
| `unknown`/NULL/其它 | 其它或 `RESOLVED` | `UNKNOWN` |

比对方向按建表列注释分别归一：`device_status` 小写（`accepted`/`rejected`/`unknown`），
`dispatch_lifecycle` 大写枚举——**两者不可用同一归一方向**（这是实现中实际踩到并修复的一个缺陷）。

## 5. 其它两条硬约束的落实

### 原 HTTP 回执不篡改

`operationState` **只取回执原文**，不据派发事实回推、不回写回执、不追溯改写历史状态。
用例 `unknownReceiptStaysUnknownEvenWhenDeviceAcceptedLater` 钉死：回执为 `UNKNOWN` 时，
即便派发事实显示设备已接受，总体仍为 `UNKNOWN`；**逐行** `dispatchState` 才反映最新事实
（这正是"界面通过 GET 获取后续变化"的价值所在）。

### httpRequestId 与 dispatchId 分开

- 顶层 `requestId` 恒为 **HTTP 幂等请求号**；
- `items[].dispatchId` 取自 **`det_dispatch_log.request_id`**（真实设备调用ID），
  与 `client_request_id` 在 SQL 层分列、不混用；
- 由 `httpRequestIdAndDispatchIdAreReportedAsSeparateIdentities` 钉死，并用例断言
  `dispatchId` **不得**回填成 HTTP 请求号；
- SQL **只按 `client_request_id` 连接**，不按 `request_id` 反查（避免把设备调用身份当成 HTTP 操作身份）。

### 只读口

`@Transactional(readOnly = true, isolation = REPEATABLE_READ)`；不调任何设备命令、不重下单、不改任何状态。
新增 Mapper XML 经断言**不含 `<insert>`/`<update>`/`<delete>`**，绑定后 SQL 以 `SELECT` 开头且不含 `FOR UPDATE`。

## 7. 实现过程中发现并修复的 4 个真实缺陷

均为契约测试先失败暴露，随后定位到根因修复（非改测试迁就实现）：

1. **`dispatchId` 取错列**：初版 SQL 写成 `log_id AS dispatchId`（主键），
   而设计要求 `dispatchId` 是**真实设备调用ID**（`det_dispatch_log.request_id`）。已改正，
   Row 字段随之由 `Long` 改为 `String`（该列建表为 `varchar(64)`）。
2. **设备状态大小写归一方向错**：`device_status` 建表注释取值为小写 `accepted/rejected/unknown`，
   初版用大写归一后与小写常量比较，导致**所有真实 `accepted` 都被判成 `UNKNOWN`**——
   也就是把"已接受"错报为"未知"。已改为按列分别归一（小写比 device、大写比 lifecycle）。
3. **MockMvc advice 装配错误**：`setControllerAdvice` 连调三次互相覆盖，
   导致 `ManagementGuardRejectException` 无人处理而冒泡。已改为单次 varargs 调用。
4. **HTTP 用例的 `X-Request-Id` 非 UUID**：`RequestMetadataFilter` 对非法值先以 400 拒绝，
   会把"回执不存在 404"的断言掩盖成入参错误。已改用合法 UUID 并在注释中写明该陷阱。
