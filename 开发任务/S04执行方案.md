## 3. 每组如何执行、修改什么

每组按以下步骤完成：

1. **建立差异与影响表。**  
   每条记录包含：S02章节编号、两版原文位置、有效澄清、现行设计位置、实际代码链、变化分类、目标行为、受影响模块和处理结论。分类为保持、修正、新增、删除或替代。

2. **只读核实现状。**  
   沿实际页面和SDK追踪Controller、Service、Mapper／跨模块接口及相关测试，区分“设计已有”“实现已有”“设计待改”“实现待改”。不重新开展全仓库接口深审。

3. **先落实跨模块规则。**  
   对D0、审批副本、人工任务前置、培养终态与占用等共享规则，明确唯一拥有方和消费方式，避免各专题分别解释。

4. **定向补齐设计。**  
   写清正常路径、关键失败路径、页面结果、请求响应、权限、状态、审批、单位精度、事务、并发、重复提交、审计和外部边界。只增加有依据的行为，不自行补业务门槛。

5. **同步受影响文档。**  
   修改原模块专题及必要的接口、时序、错误码和字段说明；跨模块变化同步提供方与消费方。数据结构变化登记目标差异，交S05汇总，不提前改SQL。

6. **静态推演并回填覆盖表。**  
   检查页面、接口、服务和数据能否形成完整流程；记录已闭合部分及精确剩余项，不把业务确认或文档检查标成运行验收。

公共API、字段或类型如需变化，必须明确：复用或调整哪个现有接口、输入输出变化、调用方影响、版本与历史读取处理。确需新增接口时先进入现有编号体系，不另起一套目录。

## 4. 遇到需要澄清的问题如何处理

**先查证和分类，再决定是否问你。**

| 情况 | 处理方式 |
|---|---|
| 旧文档与已确认规则冲突 | 查完整后续答复和覆盖关系，按最新确认同步；不重复提问 |
| 文字、原图或原型不一致 | 对照原始DOCX、配图、原型及附件；无法可靠识别图片时，单独展示相关图片并请你补充含义 |
| 接口命名、内部数据组织等技术设计问题 | 沿项目既有架构和契约完成设计，标明技术决定；不包装成客户业务题 |
| 缺设备协议、点位、单位编码或真实回传事实 | 先查现有接口附件，再记录精确缺口、提供方和影响动作；不能让你凭选项猜设备事实，也不编默认值 |
| 原文与全部有效澄清仍无法确定、且会改变业务行为 | 才向你提出新的澄清问题 |

真正需要提问时，采用既定“一问一答＋选项”方式。每题必须包含：

- 两版文档名称、章节及必要的原文引用；
- 已有相关澄清，以及为何尚不能解决本题；
- 一个符合实际业务的例子和具体影响；
- 建议及有实际区别的选项，明确建议尚未生效。

编号衔接当前澄清序列，提问前核对最新编号。不同页面属于已统一规则的，不再逐页重复问；不得把互相独立的决定捆成一个选项。

**等待答复期间：**

- 不把未答复视为同意，不按推荐值固化设计。
- 暂停该决定直接影响的部分，继续无依赖的核对和设计。
- 用户取消或暂缓时，如实记录状态，不转成默认批准。
- 无真实新问题时直接登记无新增待确认事项，不为完整性扩题。

**收到答复后：**

1. 记录问题、日期、原话、确认规则、适用范围和替代关系。
2. 在旧条目增加后续指向，保留历史证据。
3. 同步拥有方、消费方及必要入口文档。
4. 回填章节覆盖和验收场景。
5. 区分“业务已确认”“设计已同步”“实现尚未修改”，再继续下一项。

## 5. 输出、复核与结束条件

每组交付：

- 差异与改造影响表；
- 更新后的现行详细设计和接口契约；
- 待开发改造清单；
- 验收场景及分类剩余项。

重点推演已确认的边界：Nothing输出、人工任务无工作流关联、自动规则重复触发、D0任务重排及审批、结束时不同任务状态的处置、分类型签审导出，以及适用的权限、版本冲突和未知结果分支。

一组设计可以收口的条件是：受影响行为有依据，提供方与消费方一致，开发者不需要猜业务规则；缺外部输入的动作有明确边界。仍待业务答复的部分不能标设计完成。

验证采用文档差异、链接、章节回填和场景静态推演；不运行业务测试或设备操作，不宣称SQL、HTTP、浏览器及现场验收通过。

**从第1组Config／灌注开始，先交付差异与影响表，再修改受影响设计；各组完成后沿原计划交接S05—S08。**
