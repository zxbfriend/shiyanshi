## 1. 结论先说

1. **矩阵复核：INT-30 的 `provider_filters_del_flag` 取值准确**，9 类逐条从真实 Mapper XML 重测仍为 **4 过滤 / 5 不过滤**（§2）。
2. **新取证（本批实质增量）**：软删差异的根因不是「SQL 写歪了」，而是 **CAP-I01 提供方的 Java 判决面完全不看 `delFlag`**（只判「行是否为 null + `lab_id` 是否相等」），软删语义 100% 由那 9 条 SQL 自己决定（§3.1）；而那 5 条不过滤的语句**被 M02 自己的删除审计依赖**（软删后要回读该行做 after 快照），所以**不能简单地给它们补上 `del_flag = '0'`**（§3.2）。
3. **M09 层不能安全规避**：判决链路上四个面（读口行 VO、`alarm_monitor_policy` DDL、监控策略 Mapper XML、监控策略应用服务）都没有设备软删事实，CAP-I01 白名单也没有任何软删/状态路径可取（§4）。M09 若自建 kind→表 或 kind→软删 副本，正是 87 号 §1.4 与 INT-10 裁决禁止的第二事实源。**本批不实现，只登记 + 阻断**。
4. 交给 M02 owner 的最小工单：**统一 CAP-I01 by-id 查询软删过滤语义**，推荐落点是提供方 Java 守卫（对齐 M02 已有的 `loadExisting` 惯例），而不是改那 5 条 SQL（§5）。

**别名维度是复核方法的关键，不是细节**：DETECTOR 与 BENCH_CONTROLLER 的语句文本里都真实出现 `del_flag = '0'`，但那是连接表（`ll`/`dm`/`lc`、`l`/`fs`）的谓词。用「SQL 文本含 del_flag」作判据会把 DETECTOR 误分为过滤类。本批的测试按**权威表自身别名**判谓词，并反空转地钉住「DETECTOR 文本仍含 `ll.del_flag`、但其 `d.del_flag` 必须不出现」。

### 2.1 一条口径边界（属 INT-30 推导规则，不属矩阵错误）

INT-30 用 `COALESCE(df.instance_del_flag, '0') <> '0'` 判「已软删」。开发基线里 9 张权威表有 **8 张 `del_flag` 可为 NULL**（`DEFAULT '0'`，仅 `lab_downstream_device` 为 `NOT NULL DEFAULT '0'`）。后果：

- `del_flag IS NULL` 的设备行：4 个过滤类的 SQL（`= '0'`）把它**隐藏** ⇒ CAP-I01 404；而排查包把它记成 `OWNER_MATCH`（正常）。
- 即：**NULL 行在 4 类上是漏报面**。这是「存量已软删」分类的第三态，不是取值列写错。

已在 INT-30 SQL 的 S0 注释块追加一行「见 INT-37」的引用登记该边界（只加注释，不动查询逻辑）。

## 3. 本批新增取证：差异的成因与修复面的约束

### 3.1 提供方的 Java 判决面不判软删 ⇒ SQL 是唯一裁判

对 9 类分别用 Mock Mapper 造两形状（契约测试用例 3）：

- 形状 A：Mapper **供应**一行 `lab_id` 相符、`del_flag='2'` 的行 ⇒ `resolveDeviceConfiguration` **照常 ready**（9 类同形，无一拒绝）。
- 形状 B：Mapper 返回 null ⇒ 9 类统一 `NOT_FOUND`，且「不存在」与「不属于声明 labId」同文案（87 号 §1.3 既有口径）。

结论：软删设备是否被 CAP-I01 放行，**完全取决于那条 SQL 有没有把行供应出来**。因此修复面只能落在 M02（SQL 侧或 provider Java 侧守卫），落在 M09 的任何做法都不构成事实判定。

### 3.2 那 5 条不过滤的语句被 M02 自己的删除审计依赖（关键约束）

5 个不过滤种类的删除回调在把 `del_flag` 置 '2' 并 update 之后，**再用同一条按 ID 语句回读该行**构造审计 after 快照：

- `LabAirPumpApplicationServiceImpl.java:521`、`LabFloorScaleApplicationServiceImpl.java:531`、`LabDetectorApplicationServiceImpl.java:467`、`LabPeristalticPumpApplicationServiceImpl.java:525`、`LabCultureContainerApplicationServiceImpl.java:365`

而 4 个过滤种类做不到这一点，它们的审计改用**内存里的 `existing` 对象**：`LabBenchReactorApplicationServiceImpl.java:488`、`LabIntegratedReactorApplicationServiceImpl.java:724`。

⇒ **「给那 5 条 by-id 语句补 `del_flag='0'`」这一最直觉的修法会连带把 M02 删除审计的 after 快照变成 null**，属跨接口回归，不是单点纠正。任何统一软删语义的工单都必须显式避开或先处置这一耦合。

### 3.3 M02 服务层其实早有统一惯例，缺的是 CAP-I01 没用它

9 个种类中，**8 个种类的自有服务带同一条 `DEL_FLAG_DELETED.equals(...getDelFlag())` 守卫**兜底软删；
这 8 类里属于「SQL 过滤类」的只有 **3 个**（BENCH_REACTOR / INTEGRATED_REACTOR / ANALYZER，即 SQL + Java 双保险），
其余 5 个是「SQL 不过滤类」，Java 守卫是它们唯一的软删屏障：

```java
if (row == null || DEL_FLAG_DELETED.equals(row.getDelFlag())) { throw reject(NOT_FOUND, ...); }
```

坐标（在交付基线 `4d20e024a` 上逐条重测）：`LabAirPump:554`、`LabFloorScale:564`、`LabDetector:480`、`LabCultureContainer:377`、`LabPeristalticPump:558`、`LabBenchReactor:509`、`LabIntegratedReactor:848`、`LabDownstreamDevice:510`。
第 4 个过滤类 **`BENCH_CONTROLLER` 不在这 8 类之内**：其自有服务全文 0 命中 `DEL_FLAG_DELETED`
（`LabBenchReactorControllerApplicationServiceImpl.java` 实测计数 0），软删语义只由 `c.del_flag='0'` 一条 SQL 承载，
没有 Java 侧双保险。

⇒ CAP-I01 provider 是这套惯例里**唯一没接软删判定的消费点**。统一语义因此可以做成「向既有 M02 惯例对齐」，而不是新发明规则。

## 5. M02 owner 最小工单

**标题**：统一 CAP-I01 by-id 查询的软删过滤语义（9 类同判）

**问题**：9 类设备种类的按 ID 只读语句中 4 类过滤软删、5 类不过滤，而提供方的 Java 判决不判 `delFlag` ⇒ 「设备已软删但 `lab_id` 相符」的实例在 4 类上被 CAP-I01 判 404、在 5 类上被判归属成立。

**推荐落点（方案 1，最小回归面）**：在 `M02DeviceConfigurationAdapter` 的归属判决里追加软删守卫，向 M02 自有服务的 `loadExisting` 惯例对齐——即 `row == null || 非可用 del_flag ⇒ NOT_FOUND`（同码同文案，不泄露差异，不改 `DeviceConfigurationPort` 签名、不改任何 SQL）。
**必须避开**：直接给那 5 条 by-id 语句补 `del_flag='0'`（方案 2）会打断 M02 删除审计的 after 快照回读（§3.2 的 5 处坐标），影响 M02-1xx 设备删除接口，属跨接口回归，需 owner 自行决定是否同时改审计取数。
**口径决策点（owner 必须显式裁一条）**：4 个过滤类的可观测语义是「只放行 `del_flag='0'`」（NULL 与其他值都隐藏），而 M02 自有 Java 惯例只拒 `'2'`。DDL 值域注释为「0 存在 2 删除」，域内数据两者等价；**在 `del_flag IS NULL`（8/9 张表可空）上不等价**。统一为 `'0'.equals(...)` 取反才能与现状 4 类完全一致；统一为拒 `'2'` 则 NULL 行仍会留下种类间差异。

**验收面（owner 侧，不属本批）**：
- 契约测试：9 类软删行 ⇒ CAP-I01 统一 `NOT_FOUND` 同文案；9 类存活且归属相符 ⇒ ready（现矩阵测试 `M09DeviceSoftDeleteFactSourceContractTest` 用例 1/3 须与修复同批复写，不得只改断言）；
- M02 自有删除/状态接口回归（审计 before/after 快照不丢）；
- 实库以一条真实软删设备 + 相符 `lab_id` 的 `alarm_monitor_policy` 行做 M09-014 GET 与 M09-015 PUT 联调，确认种类间行为一致。

**对 M09-014 / M09-015 的影响（裁决前现状）**：
- 存量软删且归属相符的设备，其监控策略行在 4 类（BENCH_REACTOR / INTEGRATED_REACTOR / ANALYZER / BENCH_CONTROLLER）上 **GET 404、PUT 亦被同一 NOT_FOUND 关闭**；在 5 类（CONTAINER / FLOOR_SCALE / DETECTOR / PERISTALTIC_PUMP / AIR_PUMP）上 **GET 照常回行、PUT 照常可保存**。
- 即：**同一业务语义（设备已软删）在 9 类里得到两种对外行为**，运营方可为已删设备继续配置监控开关而不被拒。M09 读写两侧的失败映射本身对称（`Impl:431-477` 与 `:371-410` 同构），差异完全来自提供方。
- 排查面：INT-30 包 S4 段专数这 5 类的残留缺口（`STILL_READABLE_RESIDUAL_GAP`），NULL 口径边界见 §2.1。**存量数量仍 NOT_VERIFIED**（该包未实库执行）。
