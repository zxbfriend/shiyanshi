### 1.2 请求头规则（写口 vs 读口）

```bash
# 通用导出（TOKEN 由登录流程取得，本批不涉及 auth 服务验收）
export GW=http://127.0.0.1:9090
export TOKEN=<登录后拿到的 token>

# 守卫写口必需（两枚）
export RID=$(uuidgen)              # X-Request-Id：必须合法 UUID；缺失时服务端自生成，非法值直接 400
export REV=<当前 managementRevision>  # X-Management-Revision：必须来自同模块读口响应顶层，缺失/非法 → 400 INPUT_INVALID
```

- 读口（M02-006/234）**不需要**任何写元数据头；响应顶层的 `managementRevision` 由服务端从 `sys_management_revision` 的 SYSTEM 行读取。
- 写口的 `REV` 只能取自本模块读口响应的顶层字段（AGENTS §13.3）。`REV` 与 DB 当前值不等 → 409 `MANAGEMENT_CONFLICT`，响应体额外带 `currentManagementRevision`。
- 禁止把 `REV` 硬编码进脚本。**取值优先用 M02-006**（它带 `@CurrentManagementRevision` 且在演示库上返回 200）：

```bash
export REV=$(curl -s "$GW/lab/observation-mappings?deviceKind=DETECTOR&deviceId=9601&channelCode=TEMP-01&rawMetricCode=temperature" \
  -H "Authorization: Bearer $TOKEN" | jq -r .managementRevision)
```

  > 不要默认用 M02-234 取 `REV`：演示库上它返回 503（§8 第 1/2 项）；错误响应体是否带 `managementRevision` 取决于 `@CurrentManagementRevision` 前置组件是否已写入上下文，属未实测事项。
  >
  > 跨接口取 `REV` 是否合法，取决于版本源本身：`sys_management_revision` 主键为 `scope_key`，安装链只插入唯一一行 `('SYSTEM', 0)`，即**本服务只有一个全局管理版本**。因此同服务任一带 `@CurrentManagementRevision` 的读口返回的都是同一个当前值，脚本用它给实验室写口当 `REV` 在数值上成立；AGENTS §13.3 的"不得从无关模块借 revision"约束的是前端页面流程，不是这里的取值等价性。仍建议优先用**同一接口族**的读口取值，并把这条口径交 work6 裁决。

### 1.3 响应外壳与错误码表

成功：HTTP 200 + `AjaxResult{code:200,msg:"操作成功",data:{...}}`，`RequestMetadataResponseAdvice` 在顶层补 `requestId`（读口为服务端自生成 UUID）与 `managementRevision`。

失败：`ManagementGuardRejectException` 由 `ManagementGuardExceptionHandler`（最高优先级 Advice）映射为 canonical HTTP + `AjaxResult{code:<http>,msg:<服务端文案>,errorCode:<canonical 码>}`，可重试时带 `retryable:true`，版本冲突时带 `currentManagementRevision`。

本批六接口用到的码（`FutureFabErrorCode` 逐条核对）：

| errorCode | HTTP | retryable | 出现面 |
|-----------|------|-----------|--------|
| `VALIDATION_ERROR` | 400 | 否 | **仅 OBS 侧**（M02-006/007）入参形态、profile 模式、区间方向 |
| `INPUT_INVALID` | 400 | 否 | **实验室侧**（M02-234/236/238/239）形态与枚举；写元数据头非法；守卫层未登记 operationCode |
| `NOT_FOUND` | 404 | 否 | 设备/检测项/实验室不存在或已软删；OBS 读侧"不在设备管理范围"与"不存在"同码（不泄露存在性） |
| `PERMISSION_DENIED` | 403 | 否 | 实验室侧对象级 MANAGE 不足；OBS 写侧 OPERATE 不足；actor 身份非十进制 |
| `NAME_CONFLICT` / `CODE_CONFLICT` | 409 | 否 | 实验室名称全局有效唯一 / `labCode` 被跨来源资产号占用 |
| `REFERENCE_EXISTS` | 409 | 否 | 存在授权或负责人关系；存在未结束**项目**；已配工作流时变更类型 |
| `RESOURCE_IN_USE` | 409 | 否 | 存在未结束**批次/培养**；变更中转地址时命中未结束业务 |
| `VERSION_CONFLICT` / `MAPPING_OVERLAP` | 409 | 否 | M02-007 版本 CAS 不符 / 生效区间重叠（只允许关闭同键最新开放区间） |
| `REQUEST_ID_CONFLICT` | 409 | 否 | M02-007 请求体 requestId 与头不一致（控制器层） |
| `REQUEST_CONFLICT` | 409 | 否 | 守卫回执层：同 actor 同 requestId 的 operationCode 或 payloadHash 不一致；或回执已过期 |
| `MANAGEMENT_CONFLICT` | 409 | 否 | `X-Management-Revision` 与 SYSTEM 当前值不等；或版本 CAS 未命中（整体回滚） |
| `MANAGEMENT_BUSY` | 503 | **是** | 锁等待超时/死锁（`PessimisticLockingFailureException`/`QueryTimeoutException`） |
| `DEPENDENCY_UNAVAILABLE` | 503 | 是 | **写口**（236/238/239）未结束业务事实不可核验 |
| `RESOURCE_FACTS_UNAVAILABLE` | 503 | 是 | **只读预检**（234）事实不可核验：M02 侧自raised 与 M03 提供方给出的 `DEPENDENCY_UNAVAILABLE` 都在此换码 |

> 关于 234 换码范围的准确表述：`LabUnfinishedBusinessReader#requireFacts` 把提供方异常原样透传，但提供方（`ResourceUsageGuardAdapter`）用的**就是** `ManagementGuardRejectException(DEPENDENCY_UNAVAILABLE)`，因此它在 `#requireFactsForPrecheck` 的 catch 里**会**被换成 `RESOURCE_FACTS_UNAVAILABLE`。实际效果：**M02-234 上任何 503 都是 `RESOURCE_FACTS_UNAVAILABLE`；M02-236/238/239 上任何事实故障都是 `DEPENDENCY_UNAVAILABLE`**。提供方抛的 `INPUT_INVALID`（如可信上下文缺字段）不换码，两侧都按 400 透出。

### 1.5 判权数据口径（脚本能否跑通的第二道门）

`SmpPermissionQueryMapper#selectLabIdsByAuthLevel` 取并集：`sys_user_lab.auth_type >= minAuthType` **union** `lab_lab_leader` 全部行（负责人并集**不分级**）。因此：

- 演示库上 9001 对 9301 同时满足 OBS 读侧 OPERATE、OBS 写侧 OPERATE、实验室侧 MANAGE —— 全部来自 `lab_lab_leader` 那一支，而不是 `sys_user_lab`（其默认 `'0'` 只到 VIEW）。
- **换账号即换结论**：若清理 `lab_lab_leader` 而只留 `sys_user_lab(auth_type='0')`，M02-006 对该设备返回 404（读侧把"不在范围"折叠为"不存在"），M02-007 返回 403，M02-234 返回 403。这类差异必须按 §9 的口径记录，不得当成代码缺陷。
- `@RequiresPermissions` 是**功能权限**，与上面的对象级判权是两道门。

### 1.6 BLOCKED_MENU：功能权限种子在本仓安装链里不存在

实测（`grep`，只读）：`docs/开发基线/01-完整建表.sql`、`02-基础数据初始化.sql`、`05-开发调试测试数据.sql` 中**没有任何 `sys_menu` 插入语句**，也没有任何 `lab:lab:*`、`lab:observation:maintain` 权限串；`02-基础数据初始化.sql` 只 `INSERT INTO sys_config / sys_management_revision / apr_scene`。

- 非超管账号在本批六接口上会先被 `@RequiresPermissions` 挡在 403/未授权，**与业务实现无关**。
- 因此本批脚本默认**以超管身份（`SecurityUtils.isAdmin` 旁路 + `*:*:*`）跑通链路**，把"菜单/权限种子"登记为 `BLOCKED_MENU`，不得据超管绿就宣称权限已验收。
- 需要非超管分支时，只能由运维在目标库补 `sys_menu`/`sys_role_menu`/`sys_role` 行——这属目标库写入，本批不执行。

## 2. M02-006 `GET /lab/observation-mappings` 验收脚本

**权限**：功能 `lab:observation:maintain` + 读侧设备管理范围 OPERATE（超管旁路）
**入参绑定**：`ObservationMappingQuery` 四个 String 字段，全部来自 query 参数，全部必填（trim 后非空）
**成功外壳**：`data = ObservationMappingListView{ rows: [ ObservationMappingRow × N ] }`，行字段 = `mappingId, mappingVersion, deviceKind, deviceId, channelCode, rawMetricCode, itemId, rawUnit, unit, profile, effectiveFrom, effectiveTo, approvedBy, approvedAt`；`profile` 为 MappingProfile v1 对象；`rows` 按 `mapping_version` 降序（实现登记偏差）；**无 `total`**。

### 2.1 正例

```bash
curl -sS -X GET \
  "$GW/lab/observation-mappings?deviceKind=DETECTOR&deviceId=9601&channelCode=TEMP-01&rawMetricCode=temperature" \
  -H "Authorization: Bearer $TOKEN" \
  -o resp.json -w '%{http_code}\n'

# 断言（jq）
jq -e '.code==200 and (.data.rows|type=="array")' resp.json
jq -e '.managementRevision != null and .requestId != null' resp.json
jq -e '.data.rows | (map(.mappingVersion|tonumber)) as $v | $v == ($v | sort | reverse)' resp.json
```

**主数据前置**：`lab_detector` 存在 `detector_id=9601 ∧ del_flag<>'2'`（演示库满足）；调用方对 `lab_id=9301` 有 OPERATE（§1.5）；`lab_observation_mapping` 允许**零行**——零行返回 `rows: []` 且 HTTP 200，不是 404。

### 2.2 失败路径触发（预期逐条按源码）

| 触发 | 构造 | errorCode / HTTP | 源码依据 |
|------|------|------------------|----------|
| 种类不在白名单 | `deviceKind=INTEGRATED_REACTOR`（可用演示行 9920 的种类） | `VALIDATION_ERROR` / 400 | `#requireWhitelistedKind` |
| 种类缺失/空白 | `deviceKind=`（省略或全空格） | `VALIDATION_ERROR` / 400 | 同上 |
| 设备 ID 非十进制 | `deviceId=abc` | `VALIDATION_ERROR` / 400 | `#requireDecimalId`（OBS 侧本地化，**不是** `INPUT_INVALID`） |
| 设备 ID 为 0 或负 | `deviceId=0`、`deviceId=-1` | `VALIDATION_ERROR` / 400 | 同上（正则 `^[1-9][0-9]*$`） |
| 设备 ID 超 long | `deviceId=99999999999999999999` | `VALIDATION_ERROR` / 400（"超出可表示范围"） | 同上 |
| 通道空白 | `channelCode=%20%20` | `VALIDATION_ERROR` / 400 | `#requireText` |
| 通道 >64 字符 | `channelCode=$(printf 'C%.0s' {1..65})` | `VALIDATION_ERROR` / 400 | `#assertMaxLength` |
| 原指标码缺失 | 省略 `rawMetricCode` | `VALIDATION_ERROR` / 400 | `#requireText` |
| 原指标码 >100 | `rawMetricCode=$(printf 'M%.0s' {1..101})` | `VALIDATION_ERROR` / 400 | 同上 |
| 设备不存在/软删 | `deviceId=999999` | `NOT_FOUND` / 404（"观测设备不存在"） | `#resolveDeviceLabIdOrThrow` |
| 不在设备管理范围（非超管） | 换无 OPERATE 的账号 | `NOT_FOUND` / 404（与不存在同码） | `#requireManageScope` |
| profile 列损坏（库内既有行） | 需人为把某行 `profile` 写成空/非法 JSON | `IllegalStateException` → **500**（非业务码） | `#readProfile` |

最后一条是 §9 登记的"不得验收项"：500 分支需改库才能触发，本批不制造该数据。

## 3. M02-007 `POST /lab/observation-mappings` 验收脚本

**权限**：功能 `lab:observation:maintain` + 守卫事务内按可信 actor 重判 OPERATE
**校验次序（必须照此断言）**：控制器体头一致性 → 守卫前形态/profile 校验（**零触库**）→ 守卫取 SYSTEM 锁 → 事务内设备解析 404 → MANAGE/OPERATE 重判 403 → 检测项 404 → 版本 CAS 409 → 区间重叠 409 → 落库 1 行 + 旧开放版本关闭 1 行 → 审计 → 版本 CAS 递增 → 回执。
**成功外壳**：`data = ObservationMappingMutationResult{ mappingId, mappingVersion }`（均十进制字符串）；顶层 `requestId`、`managementRevision`（提交后新值，由 `putCommittedManagementRevision` 回填）。

### 3.1 正例（通道级 + IDENTITY 恒等；改 AFFINE 只需换 `conversion`）

```bash
export RID=$(uuidgen)
export REV=$(curl -s "$GW/lab/observation-mappings?deviceKind=DETECTOR&deviceId=9601&channelCode=TEMP-01&rawMetricCode=temperature" -H "Authorization: Bearer $TOKEN" | jq -r .managementRevision)   # §1.2 口径

curl -sS -X POST "$GW/lab/observation-mappings" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "X-Request-Id: $RID" \
  -H "X-Management-Revision: $REV" \
  -d @- <<'JSON' -o m007.json -w '%{http_code}\n'
{
  "deviceKind": "DETECTOR",
  "deviceId": "9601",
  "channelCode": "TEMP-01",
  "rawMetricCode": "temperature",
  "itemId": "9602",
  "rawUnit": "celsius",
  "unit": "celsius",
  "expectedMappingVersion": 0,
  "effectiveFrom": "2026-10-05T00:00:00Z",
  "effectiveTo": null,
  "profile": {
    "schemaVersion": 1,
    "sourceRevision": "1",
    "dimension": "temperature",
    "conversion": { "kind": "IDENTITY", "scale": 1, "offset": 0 },
    "timeProfileRef": "TP-DEBUG-001",
    "qualityProfileRef": "QP-DEBUG-001",
    "measurementScope": "CHANNEL",
    "approvedEvidenceRef": "EVD-DEBUG-001"
  }
}
JSON

jq -e '.code==200 and (.data.mappingId|test("^[1-9][0-9]*$")) and (.data.mappingVersion=="1")' m007.json
```

要点（照抄基文档样例会在第 0 步就 400）：

- `measurementScope: "CHANNEL"` 必须配非 `"DEVICE"` 通道；若写 `"DEVICE"` 则 `channelCode` 必须恰为 `"DEVICE"`。
- `sourceRevision` 是**十进制正整数字符串**（`"1"`），不是 `"REV-001"`。
- IDENTITY 分支要求 `scale` 显式为 1（缺 `scale` 也判不合格），`offset` 允许省略（按 0）。AFFINE 分支要求 `scale` 非零非空且 `offset` 非空。
- 首次核准用 `expectedMappingVersion: 0`；库内同键已有最新开放版本时，先跑 M02-006 读回 `mappingVersion` 再 +1 提交。
- **请求体不要写 `requestId`**；写了就必须与头逐字一致，否则 409 `REQUEST_ID_CONFLICT`。`managementRevision` 体字段同样被头覆盖。

### 3.2 失败路径触发

## 9. 不得验收项清单（本批禁止据此判"通过/失败"）

1. **OPERATE vs MANAGE 口径（批次十五 §6④）** —— M02-006 读侧用 `listAuthorizedLabIds(userId, OPERATE)`、M02-007 写侧用 `canOperateLab(...)`，两者都取 **OPERATE**；但"设备管理范围"这个词在契约里是否等价于 OPERATE 级尚未裁决，且"实验室侧 MANAGE（2）∪ 负责人并集（不分级）"的实现使负责人天然拿到最高级。验收只能用"已知有 OPERATE 的账号"跑通，**不得据此宣称权限分级已验收**；裁决收紧到 MANAGE 时需整批重验。
2. **`REQUEST_CONFLICT` / `MANAGEMENT_CONFLICT` 是否在登记错误码集合内（§6①）** —— 守卫层确实会返回这两码，脚本可以观测到；但 02 模块《错误码全集》对 M02-007 的登记集合尚未含它们，属"已验但集合待补"。不得把"返回了 REQUEST_CONFLICT"写成契约符合性通过，也不得写成违规。**同一项下还登记一处代码注释漂移**：观测服务 Javadoc 写"同 requestId 换 payload → `REQUEST_ID_CONFLICT`"，而守卫实现落的是 `REQUEST_CONFLICT`；`REQUEST_ID_CONFLICT` 只在 Controller 判"请求体 requestId 与头不一致"时出现。验收一律以 `ManagementGuardExecutor` 的行为断言，不得据 Javadoc 判实现失败。
3. **请求头元数据的 canonical 码（§6②）** —— 缺/非法头由公共层返回 400 `INPUT_INVALID`（`RequestMetadataFilter`/`WriteMetaArgumentResolver`），不是 OBS 业务字段的 `VALIDATION_ERROR`。两者边界尚未裁决，脚本必须**按现状分别断言**，不得为"统一成一个码"而放宽校验。
4. **`IllegalStateException` 是否应转 `DEPENDENCY_UNAVAILABLE`（§6③）** —— 现状：`ObservationApplicationServiceImpl#readProfile`（profile 列空/非法 JSON）、`#canonicalProfileJson`、`NormalizedPayloadHasher`（HMAC 缺失）、`ManagementGuardExecutor`（基线破坏/回调伪成功）都抛 `IllegalStateException` → **500**。是否应改为 503 属待裁项；本批只登记现象、不改码、不把它当失败。
5. ~~**检测项"有效"的判定面** —— `#requireDetectorItemExists` 只排除 `del_flag='2'`，不看 `status`。停用中的检测项目前会放行；这是实现事实，登记备核，**不得在验收脚本里私自加 status 条件**（改了就是改契约）。~~ **【已撤案】** 经 `M02-运行验收数据与菜单只读核查包-20261005.md` §6 E-2 复核：`dev_detector_item` 的 DDL **根本无 `status` 列**（实际列 `item_id/detect_class/item_code/…/del_flag/m02_active`），故库内不存在"停用中的检测项"这一状态——原登记项属**伪前提**，并非实现缺陷，予以**撤案**。验收脚本仍不得私自加 `status` 条件（该列不存在，加了即 SQL 报 Unknown column）；若业务未来确需"检测项停用"语义，应另列为新增字段 / 设计需求（独立议题）。
6. **`MAPPING_OVERLAP` 与幂等重放的完整矩阵** —— 需要"同键多版本 + 区间交叠 + 同 requestId 换 payload"三组数据同时存在才能覆盖，且涉及守卫回执表状态；本批不制造该数据，只跑单层分支。
7. **观测快照参数** —— `futurefab.observation.query.snapshot-ttl-seconds` / `...snapshot-max-ids` 只服务 M02-002（仍 501），与 M02-006/007 无关；基文档把它们列在本批 BLOCKED_INPUT 下属串批。本批不得据"参数缺失"判 006/007 失败。
8. **非法枚举值的反序列化层** —— `conversion.kind` 或 `measurementScope` 传枚举表外的字符串，由 Jackson 在进入 `normalize` 前失败，返回码不在业务码集合内；不得据此判"校验缺失"，也不得为凑码而改 DTO。
9. **浏览器验收** —— 六接口本批全部无前端操作路径记录，一律 `NOT_VERIFIED`；不得用 curl 200 外推 `BROWSER_VERIFIED`（AGENTS §13.4）。
10. **并发/锁序结论** —— `MANAGEMENT_BUSY` 与"写内重算消除竞态"都未经连库验证；提供方明确"不自开事务、不自取锁、不 FOR UPDATE"。不得把守卫实现叙述成已消除并发窗口。
