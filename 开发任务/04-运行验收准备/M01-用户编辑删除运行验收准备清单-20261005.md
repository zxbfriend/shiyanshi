## 2. 前端静态链路追溯

- **API 封装**：`sdk-smp-api/src/modules/system/user.ts:49-63`（`updateUser`→PUT `/system/user`、`delUser`→DELETE `/system/user/{ids}`，均带 `GuardedWriteMeta`）；`guarded-write.ts:20-27` 注入 `X-Request-Id`（crypto.randomUUID）与 `X-Management-Revision`（仅在 revision 非空时携带）
- **网关**：`/system/**` → `lb://futurefab-system` 路由块 `nacos-config/futurefab-gateway-dev.yml:35-47`（`Path=/system/**` + `StripPrefix=1` + 内部契约 BlackList 过滤），即前端 `/system/user` ⇔ 服务侧 `/user`
- **revision 流**：主捕获＝列表读取 `index.vue:566-568`（每次列表响应顶层 `managementRevision` 写入页面 ref）；props 传弹窗（`usePropRevision`，user-editor.vue:47）与兜底重取 `:299-322`（`reloadRevision`）→ `ensureRevision()` 本地不可信/吃过 409 才补取 → 拿不到即短路不发写（user-editor.vue:362-368）→ 写回执 `managementRevision` 覆盖本地值（:369-372）
- **前端删除侧**：`index.vue:707-743` `handleDelete` → 确认框 → `ensureRevision()`，**无 revision 直接 reject"未获取到管理版本"，不发 DELETE 请求** → 有版本才 `delUser(userIds, writeMeta(revision))` → 回执覆盖本地版本 → catch 中除 `cancel` 外一律显式提示并 `invalidateOnConflict`
- **不可管理授权只读**：`authorizedLabOptions`（user-editor.vue:123-147）= 可授予候选 ∪ `currentAuthorizations` 全量回显，`manageable=false` 条目 disabled 展示 `disabledReason`；提交集合 `directAuthorizationIds` 只剔 `isLabLeader` 派生项，**不可管理直接授权保留在选择集内**（保存不丢项，M02-Q03）
- **失败关闭**：候选未就绪（503/权限/加载异常/版本缺失）禁用提交、不伪造候选与授权版本（:168-194、:334-344）；新增不得调 `getUser('')`（:297）
- **409 分流**：`use-guarded-write.ts:81-100` REFERENCE_EXISTS 给"先变更负责人"口径而非"刷新重试"；其余 409 标记 stale、下次写前强制重取

## 3. HTTP 验收清单

通用前置：真实 token（携带对应权限）；网关路由命中 futurefab-system；两个 HMAC 密钥均已实际发布到 Nacos 且取值经核对——`futurefab.management.receipt-hmac-key`（管理写幂等 payload_hash，`nacos-config/futurefab-system-dev.yml:18`）与 `futurefab.auth.proof-hmac-key`（守卫身份解析/AuthProof，同文件 :10；`NormalizedPayloadHasher`/AuthProof 缺失即启动 fail-fast）；dev 假值不得带入共享环境；每次尝试记录 request payload、response body 与后端异常日志（AGENTS §13.4）。

### M01-051 修改用户

```http
PUT /system/user
Authorization: Bearer <token(system:user:edit)>
X-Request-Id: <uuid，每次新请求重新生成>
X-Management-Revision: <GET /system/user/list 顶层 managementRevision>

{
  "userId": "<测试用户ID>",
  "nickName": "验收用户改名",
  "deptId": "<操作者可授予范围内部门ID>",
  "roleIds": ["<可管理角色ID>"],
  "labGroupIds": ["<USR07叶子组ID>"],
  "authorizedLabIds": ["<可管理labId>", "<不可管理但既有授权的labId（保留提交不丢项）>"],
  "authorizationChanges": [
    { "labId": "<可管理labId>", "authType": "1" }
  ],
  "labAuthorizationVersion": "<只能取自 GET /system/user/editor-options 的回传值>",
  "email": "", "phonenumber": "",
  "notifyInsite": "1", "notifySms": "0", "notifyEmail": "0",
  "status": "0"
}
```

**成功响应应核对**（`MutationResult`）：HTTP 200，`data.applied=true`、`data.requestId`=请求头值、`data.managementRevision`=新 SYSTEM 修订（字符串）、`data.objectId`=userId、`data.warnings` 为数组（可空列表）；随后重读 editor-options：授权集合=提交集合、`labAuthorizationVersion` 已变化。

**关键失败路径**：

| 场景 | 触发 | 预期 |
|---|---|---|
| 缺 `X-Management-Revision` | 删头提交 | 绑定层终结，非 501、非伪成功、零写库（契约测试 `M01UserUpdateDeleteWiredWriteContractTest:2446-2466` 已断言"绝不 applied:true"；HTTP 层实测外壳/码型后登记） |
| ASSIGNMENT_DENIED | deptId/roleIds/labGroupIds 任一越出 USR07 候选边界 | 409 类拒绝，整次失败，不静默丢项 |
| VERSION_CONFLICT | `labAuthorizationVersion` 非当前值（先在另一会话改授权使其过期） | M02 AUTH-I02 CAS 拒绝（`M02LabAuthorizationAdapter:234/:446/:458`） |
| MANAGEMENT_CONFLICT | `X-Management-Revision` 过期（列表读取后由他口写入抬版） | 守卫层 409（`ManagementGuardExecutor:269/:299`） |
| REQUEST_CONFLICT | 同 `X-Request-Id` 换 payload 重放 | 守卫层 409、回调零执行 |
| 幂等重放 | 同 requestId 同 payload 重发 | 返回原回执，不二次落库、不重复撤会话 |
| INPUT_INVALID | 空 Body/null、notifyInsite≠"1"、status 非 0/1、authType 非 0/1/2、roleIds 空、重复 labId 变更项、ID 非十进制 | 守卫前拒绝，零触库 |
| NOT_FOUND | userId 不存在或已软删 | 锁内拒绝（不泄露存在性口径与 M02 一致） |
| CODE_CONFLICT | email/手机号撞他人 | 查重探针排除本人 |
| MANAGEMENT_BUSY | 并发锁竞争超时 | 503 retryable，整次回滚 |
| 启用→禁用联动 | status 0→1 | 提交后该用户登录令牌失效（Redis 清理，验证需真实 Redis） |

### M01-053 批量删除用户

```http
DELETE /system/user/<id1>,<id2>
Authorization: Bearer <token(system:user:remove)>
X-Request-Id: <uuid>
X-Management-Revision: <列表顶层 managementRevision>
```

**成功响应**：200，`data.applied=true`、`objectId`=首个受影响 ID（升序）、`managementRevision` 抬版；库中目标行 `del_flag='2'`、`sys_user_role`/`sys_group_member`/`sys_user_lab` 直接授权行清空、认证状态行会话撤销。

**关键失败路径**：

| 场景 | 触发 | 预期 |
|---|---|---|
| REFERENCE_EXISTS | 任一目标用户是有效实验组负责人（`sys_group_leader`）**或仍是实验室负责人（`lab_lab_leader`，含停用实验室）** | 两源任一命中均整批 409，消息点名 ID；**先经实验组/实验室各自负责人变更口解引用，不得级联清理** |
| ASSIGNMENT_DENIED | userIds 含操作者本人或 admin 等受保护账号 | 守卫前拒绝 |
| MANAGEMENT_CONFLICT / REQUEST_CONFLICT / MANAGEMENT_BUSY | 同 051 | 守卫层同口径 |
| INPUT_INVALID | CSV 拆分为空集合、超 100、非正 ID | 守卫前拒绝 |
| NOT_FOUND | 任一 ID 不存在/已软删 | 锁内拒绝，整批回滚（取证先于一切写，提供方拒绝时本地一行未动） |
| 缺头 | 同 051 | 绑定层终结（契约断言 `M01UserSkeletonContractTest:343/:392`、`...WiredWriteContractTest:2532`） |

## 4. 浏览器验收步骤（system-user 页）

1. 登录具备 `system:user:list/query/edit/add/remove` 的账号（**运行库前置需核验，本批未执行**：D-7 菜单种子是否已安装、上述权限是否已授权到验收角色；页面不可达先查运行库 `sys_menu` 与权限分配，不先改前端）。
2. 用户列表打开一条**既有不可管理直接授权**的用户（构造见 §5）→ 点修改。
3. 弹窗核对：授权实验室选择器**全量回显**既有授权；`manageable=false` 条目呈禁用态并带 `disabledReason` 悬浮说明；负责人派生项不作为可勾选项混入提交集。
4. 只改昵称提交 → 成功提示 → 重开弹窗：不可管理授权仍在（保存不丢项）；`Network` 记录 PUT /system/user 的请求头（X-Request-Id/X-Management-Revision）、payload、response body。
5. 版本过期路径：双开两个浏览器分别进弹窗，A 先保存成功，B 再保存 → B 应得 409 冲突提示且不伪成功；B 第三次保存前应看到兜底重取 revision 的新列表请求。
6. 无 revision 短路：断网/让列表读取失败后进弹窗保存 → 前端应提示"未获取到管理版本"且 **Network 无 PUT 请求发出**；同法在列表版本不可得时点删除 → 提示同名口径且 **Network 无 DELETE 请求发出**（`index.vue:707-743`）。
7. 候选 503 失败关闭：M02 授权依赖不可用时进弹窗 → 提交按钮禁用、提示"授权候选未就绪"。
8. 删除：分别构造两类引用源各试一次——目标用户为有效实验组负责人、目标用户为实验室负责人（其中一组用**停用状态实验室**验证同样整批拒绝）→ 均应得点名 ID 的 REFERENCE_EXISTS 提示（文案口径为"先变更负责人"）；正常路径在 revision 可得时删普通测试用户 → 成功且列表回查消失；本人/admin 行不可触发删除。
9. 全程观察后端日志无 `RequestMetaInvalidException`/非预期 `GlobalExceptionHandler`；验收数据按 §5 清理。
