## 2. 端口签名与切分理由

```
CultureInitialWeightPort#readInitialWeightForDisplay(
        CultureInitialWeightQuery query) -> CultureInitialWeightFacts
CultureInitialWeightQuery   : 仅 cultureId（String，十进制正整数）
CultureInitialWeightFacts   : recorded(boolean) + initialWeightG(BigDecimal)，两字段、final、无 setter
```

### 2.1 为什么 M07 只需要 `initialWeightG`

先读 `docs/详细设计/07-补液运行与任务执行/接口目录与契约定位.md` 定位015 补充段（2026-10-12 用户确认，
来源等级【需求已有·复核一致】）逐行核对，其表格把 M07/M03 责任切得很干净：

| M07 面板行 | 归属 | 对端口的含义 |
| --- | --- | --- |
| 面板"初始重量"显示 | M03 CU-W01 | **需要** `initialWeightG` |
| 累计补入/累计取测/当前余额 | M07 | 不属本端口 |
| 初始重量尚未录入 → 显示"未录入"、**不能补 0** | M07 呈现、M03 事实 | 需要一个**能表达"未录入"且不能被读成 0** 的返回类型 |
| 残糖确认所需版本 | M07 runtime `objectVersion` | **`weightRevision` 不得交给 M07** |

逐字段取舍（`InitialWeightView` 8 个叶子字段）：

| 字段 | 是否过端口 | 理由 |
| --- | --- | --- |
| `initialWeightG` | ✅ 过 | M07 面板唯一需要的值 |
| `cultureId` | ❌ 不过 | M07 本就持有所查培养标识；回显只多一条"把 A 的重量贴到 B 面板上"的旁路 |
| `weightRevision` | ❌ 不过 | 契约原文："残糖确认所需版本用 M07 runtime 的 `objectVersion`，**不能用 M03 的 `weightRevision` 替代**"。与其交出去靠注释约束，不如让字段在类型上**不存在** |
| `cultureVersion` | ❌ 不过 | 同上，M07 有自己的 runtime `objectVersion`，两套版本不得混用 |
| `effectiveAt` | ❌ 不过 | 定位015 补充的响应字段只含 `objectVersion`/`evidenceSources` 等，面板不展示重量生效时刻 |
| `unit` / `displayUnit` | ❌ 不过 | M03 读口当前恒为 `"g"`（容器规格属 M02 型号事实，M03 域内无可信来源，开发契约明示"规格未知仍可明确按 g 显示，不伪造规格"）。交出去等于把 M02 未定事实的占位值扩散到 M07 |
| `allowedActions` | ❌ 不过 | 变更准入是 CU-W02 写侧守卫口径，而 **M07 按契约不提供初始重量写入口**，消费方拿到可写动作也没有合法去处 |
| `issues` | ❌ 不过 | 库内由 `ck_m03_initial_weight` 约束为"全空或全备"，M03 读口当前恒返回空数组 |
| `sourceCandidateId` | ❌ 不过 | M03 自身运行变更候选的内部追溯标识，M07 不消费候选流程 |

**身份刻意不入签名**：本端口与 M03 自家 `CultureReadEligibilityPort` 不同——后者为"任意指定操作者"
代答资格，必须由调用方交来 `ActorContext`；本端口的消费方是 M07 自己的应用服务，与 M03 读口在
**同一次请求线程**内被调用。若开放 actor 入参，M07 就能传入他人上下文，让 M03 按别人的可见范围取数，
等于交出一条越权读取通道。因此身份不进签名，由 M03 读口在服务端会话内自行解析。

### 2.2 两条铁约束如何在类型层落地

**(1) 不得用 M03 `weightRevision` 充当 M07 `objectVersion`**
→ 回执**不含任何 version/revision 字段**。契约测试 `receiptCarriesNoVersionFieldSoM07HasNoWeightRevisionToMisuseAsObjectVersion`
用反射断言字段面恰为 `["initialWeightG", "recorded"]`，并逐字段拒绝任何含 `revision`/`version` 的命名。
类型上不存在候选值，比注释约束更硬。

**(2) `initialWeightGrams` 为 null 时不得补 0，且不得阻断运行版本查询**
→ 拆成两个互斥构造通道，不给"可空数字"留位置：

| 出口 | 语义 | 约束 |
| --- | --- | --- |
| `notRecorded()` | 真·未录入 | **不携带任何数值**（不是携带 0） |
| `recorded(BigDecimal)` | 已录入 | 构造期拒绝 `null`、`0`、负数 |
| `requireRecordedWeightG()` | 取值 | 未录入回执上**直接抛 `IllegalStateException`** |

因此"已录入但为 0"这种形状**根本无法被构造**；取值须先 `isRecorded()` 分支，"忘记判空就拿到 0"会立刻
炸在调用点，而不是静默污染 `initialWeightGrams` 及其下游当前净量计算。
"不阻断运行版本查询"对应：未录入走**正常返回**（无异常、回执非 null），消费方据此只跳过初始重量展示，
不影响 `objectVersion`/累计量/窗口量。

## 3. 数据范围安全

- 可见范围由 **M03 应用服务**在服务端会话内经 `SmpPermissionService.resolveScope` 实时解析，
  以 `visibleCultureIds` 形参下推到 `selectInitialWeightFacts` 的 `culture_id in (...)` 条件；
  空集合在 XML 层生成 `1 = 0` 假条件。
- 适配器**不查询、不注入 Mapper、不预置可见集合、不做任何 Java 侧集合判定**
  ⇒ 结构上不存在"全量捞回后过滤"的窗口（AGENTS.md 明禁该模式）。
- 范围外与不存在同为 `404 NOT_FOUND`，不区分 ⇒ 不可作存在性探针。
- 照搬的既有做法：`CultureReadEligibilityAdapter`（同一 `SmpPermissionService` 来源）、
  `MemberIdentityFactsAdapter`（M03 自有表 + M02 内部服务，零跨模块直读）。
- 每次调用重新解析，不缓存、不冻结为长期票据 ⇒ 权限收紧立即失效。

## 4. 失败关闭

三态严格可区分，互不冒充：

| 情形 | 出口 | HTTP |
| --- | --- | --- |
| 真未录入（`initialWeightG` 真的是 null） | 正常返回 `notRecorded()` 回执 | 200 |
| 范围外 / 不存在 | 透出 M03 的 `NOT_FOUND` | 404 |
| 范围解析或取数依赖的**任何**运行时故障 | `DEPENDENCY_UNAVAILABLE` | **503** |
| 畸形培养 ID | `INPUT_INVALID` | 400 |

要点：

1. 捕获范围**刻意宽于** `DataAccessException`——非预期故障同样落 503，不冒泡成 500，也不伪装成"未录入"。
2. M03 已定码的领域异常（400/403/404/503）**原样透出**，不重映射；把 400/403 一律改成 503 会让调用方
   无法区分"调用方错"与"依赖不可用"。
3. 依赖故障**绝不**退化为 `notRecorded()`——否则 M07 面板会把一次故障显示成业务上的"未录入"，既无失败信号
   又会被当正常结果消费。
4. `InitialWeightView` 为 null（正常路径不会出现）按不可得失败关闭，不当成"未录入"。
5. **形态校验在解析之前**：`new BigDecimal` 会宽松接受 `12.5e3`(→1.25E+4)、`+7`、`0120`、`1200.0`，
   只看解析结果的符号无法识别这些形状。故先卡 M03 契约的正整数规范串（`^[1-9][0-9]{0,13}$`，对应契约的
   1..99999999999999），非规范值一律 503，不被静默归一成"看起来合法"的重量。
6. 脱敏：异常文本与日志只含对象中文名与故障类型/长度，不回显真实克值、培养标识或范围来源明细。

## 5. 门禁白名单：本适配器**零 Mapper，故未登记**

- 门禁 `detectPortAdapterViolations` 校验的是 `import com.futurefab.system.mapper.*`；

  因此不占白名单窗口——与 `CultureReadEligibilityAdapter` 同一先例（其 Javadoc 亦明示此点）。
- 契约测试 `adapterInjectsNoMapperSoItHoldsNoMapperWhitelistSlot` 反向钉住这一状态：
  若将来有人为图省事直接注入 `M03ResourceQueryMapper`，该断言即失败并强制其走白名单评审。

骨架门禁等式未被触碰：**未新增/删除任何应用服务的公共方法**，未改任何 `skeleton-mXX.json`
（`skeleton-m05.json` 全程未碰）。`FullSystemSkeletonGateTest` 在定向与全量中均 10/10 通过。
