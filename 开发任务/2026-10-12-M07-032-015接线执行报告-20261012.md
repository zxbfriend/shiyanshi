### 2.4 ⚠️ `initialWeightGrams` 置 null 的核实过程（如实登记）

按任务要求先核实 M03 侧读口是否存在：

```
grep -rn "InitialWeightView" --include=*.java futurefab-modules/   （排除 .worktrees）
```

结果：**M03 侧读口在应用服务层存在**（`CultureChangeApplicationService#getInitialWeight` → `M03ResourceQueryReader#readInitialWeight`，行 127/140/290），**但 M07 无法合规消费**，原因有两条且各自充分：

1. **无跨模块 Port**：`service/port/m03/` 下 13 个 Port 中**无初始重量 Port**（`grep -rn "InitialWeight" service/port/` 命中 0）；
2. **骨架门禁禁止直连**：`FullSystemSkeletonGateTest#detectCrossModuleImports` 明文禁止 m0X 骨架文件 import 他模块 `service.application.*`／`domain.(dto|vo).*`，只放行 `service.port.*`。

新建该 Port 需改 `service/impl/port/m03/` 适配器**并**改共享门禁 `FullSystemSkeletonGateTest.PORT_ADAPTER_ALLOWED_MAPPERS`（m03 逐 Mapper 白名单）——两者**均在本次授权的文件范围之外**，且属共享注册表。

⇒ 故按契约置 `null`（"未录入"），**不补 0、不由袋初始量或旧 volume 列派生**；并按 M03 开发契约「首次输入未就绪前只阻止依赖初始重量的计算/执行，不阻止无此依赖的资源查询」，**本读口仍正常返回 objectVersion、累计量、窗口量、就绪状态与证据**（契约测试 `balanceReturnsRuntimeVersionAndKeepsInitialWeightNull` 逐项钉住）。

### 2.5 ⚠️ `run_ledger` / `run_calculation` 无生产写通道（验证限制，如实登记）

```
grep -rn "run_ledger" --include=*.java --include=*.xml . | grep -i insert      → 无命中
grep -rn "run_calculation" ... | grep -i insert                                  → 无命中
grep -rhn "INSERT INTO run_" --include=*.xml . | sort -u
  → run_event / run_confirmation / run_workflow_instance / run_resource_guard /
    run_culture_runtime / run_manual_result / run_workflow_step / run_command（共 8 张）
```

- `run_culture_runtime` **有**真实写通道：`insertConnectedRuntime`，调用方 `RunWorkflowApplicationApplicationServiceImpl:551`（连接完成事务）。故本读口在真实库上**能读到运行行**。
- `run_ledger` 与 `run_calculation` **全仓无 INSERT**。因此在"有运行行但无账事件"的库上，`todayFeedGrams` / `windowWithdrawalGrams` 会返回 `null`。
- 这是**数据来源缺失，不是读口缺陷**；SQL 聚合语句本身已由 `M07CultureBalanceSqlMappingContractTest` 证其形状成立。

### 2.6 其他实现选择（已登记，非静默）

- 存在性与范围：runtime 行为 null（未连接）与范围外**统一 `404 NOT_FOUND`**，不区分二者以免泄露培养存在性；会话身份缺失 `403`；路径 ID 非法/缺失 `400`。
- **未引入实验室类型 Port**：`currentNetGrams` 的小试／中试分支当前同为 `null`，若为此额外注入 M02 Port 只会制造一个无收益的 503 失败面，故不做（模式本身仍属 M02 实验室类型事实，M07 不自建模式推导）。已在方法 Javadoc 登记，待初始重量／秤读任一到货即按该分支补齐。
- `todayFeedGrams` 缺事件按"**未发生**"传 `null`，**不补 0**；但 `run_culture_runtime` 的 `total_feed_grams` 是表内真实存储值（`NOT NULL DEFAULT 0`），直读不属伪造。

### 8.3 端口 503 时该口如何表现 —— 裁决与依据

**结论：整口失败关闭，抛 503；不降级为 `null`、不返回"半个视图"；不 catch、不改码。**
而**未录入（`isRecorded()==false`）时只让这一个字段为 `null`，其余字段全部正常返回**——这两态不可合并。

裁决依据（逐条读现行契约原文，非自定）：

1. **M03 开发契约《模式与初始重量开发契约.md》§2 原文**：「首次输入未就绪前只阻止依赖初始重量的计算/执行，
   **不阻止无此依赖的资源查询或工作流步骤**；不能补 0 来解锁。」
   → 该条的适用对象是**「首次输入未就绪」即 `initialWeightGrams` 为 `null` 的业务事实**，
   对应《接口目录与契约定位.md》定位015 补充推论 1：「`initialWeightGrams` **为 null 时**不得阻断运行版本查询」。
   未录入分支正是照此实现：`objectVersion`／累计量／窗口量／就绪状态／证据**照常返回**。
2. **该条并未授权把「取数失败」也当作 `null`**，三条理由均可回溯到现行契约：
   - 同句后半「**不能补 0 来解锁**」：把依赖故障折成 `null`，等于用「未录入」这个**业务结论**顶替一次**技术故障**，
     与被禁止的"未知当 0"是同构伪装；
   - 推论 1 的前提写得很死——「`initialWeightGrams` **为 null** 时」。该豁免的输入是**确知的 null**，不是"未知"。
     端口已在类型与控制流上把两态分开（未录入走正常回执、故障抛异常），消费方若在末端再合并，
     等于把上游刚建立的可区分性就地抹掉；
   - 《错误码全集》把 `DEPENDENCY_UNAVAILABLE`(503) 定义为「依赖读取不可用；**失败关闭**，保留非敏感草稿」。
     本口是纯 GET 读口、无草稿可保留，失败关闭即整口 503。
3. **同仓既有同型先例**：本类 `listGlucoseCandidates` 对 M05 Port 也是 `Port 不可用 → 整口 503`，
   不做部分降级，口径一致。

因此面板永远看不到"故障伪装成未录入"的画面：要么是**确知的未录入**（显示「未录入」），
要么是**明确的 503 失败信号**。端口抛 404（范围外/不存在）同样**原样透出**，不重映射、不当作未录入。
