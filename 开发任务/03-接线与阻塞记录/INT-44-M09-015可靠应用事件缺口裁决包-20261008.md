## 1. 结论摘要

1. M09-015（`PUT /alarm/v2/monitor-policy`）保存链路今天**确实**同事务写配置行 `alarm_monitor_policy` 与台账 `alarm_config_revision`（KIND=MONITOR、STATE=APPLIED），守卫/审计/幂等/CAS 均已落地。
2. 该链路**不写任何面向执行侧的可靠应用事件**：实现类对 `AlarmEventMapper`/`insertCommandReceipt`/`MONITOR_APPLY` 零引用；全仓 `alarm_event` 的 COMMAND 收据生产者只有 INT05 ACK 入站服务与投递命令收据服务，均不在保存路径上。
3. `executionAck` 恒 UNKNOWN 的原因：读侧 M09-014 唯一赋值点是硬编码 `MonitorExecutionAck.UNKNOWN`（`Impl:185`），因为 ack 的事实源被设计为"M02/M07 可靠应用事件 + INT05 回写 `alarm_event.result_ref.monitorAck`"，而保存侧连收据行都不产生，读侧无任何可查事实，只能如实返回 UNKNOWN（不伪装 APPLIED/PENDING，安全属性成立）。
4. M07 侧**没有**该事件的消费/通知入口：M07 七个源码包对 `monitorPolicy`/`MONITOR_APPLY`/`AlarmEventMapper` 零引用；`service/port/m07` 的 11 个 Port 均与监控策略无关（`RunEventPublisherPort` 是 M07 自身运行事件发件、供未来 M08 消费，不是 M09→M07 通道）；`MonitorAcknowledgementPort`（INT05）方向是 M02/M07→M09 **入站 ACK**，且在 main 源码内除接口与实现类自身外零引用（未接线）。
5. 权威文档口径下，"可靠应用事件"**不是新表、不是 MQ、不是 Port 调用、不是异步任务**，而是：与修订保存同一事务、复用现有 `alarm_event` 表的一条 `commandKind=MONITOR_APPLY` CommandReceipt 收据行（详见 §3）。据此，裁决包的推荐方案为 **方案 A**（§4），且 A 只闭合"M09 同事务落收据"这一半；M07 实际消费与 `executionAck` 推进仍属开放裁决项（§5）。

## 3. 权威文档口径："可靠应用事件"是什么

引用（属 02-详细设计与 M09 模块现行契约，非历史材料）：

- `docs/详细设计/09-告警与通知管理/页面与接口契约.md:69`（API15 权威条款）：「来源操作权限；**修订保存与可靠应用事件同事务**；…」
- `docs/详细设计/09-告警与通知管理/接口目录与契约定位.md:95`（镜像行，声明条款全文以上一条为准）
- `docs/详细设计/09-告警与通知管理/Controller请求调用时序设计.md:25`（定位015）：「本地单事务；幂等/CAS/审计/**outbox同提交**」
- `docs/开发任务/00-全接口契约骨架清单.md:9646`（最具体的一句）：「修订保存与可靠应用事件同事务（**M09内部命令MONITOR_APPLY收据复用alarm_event**，CommandReceipt见JSON契约§3）；执行侧ACK经INT05（M02/M07）落`alarm_event.result_ref.monitorAck`，M07未ACK时页面区分配置已保存/执行侧待应用；保存ON清理未发送临时关闭提醒并通知M07监控程序更新修订…」
- `docs/详细设计/09-告警与通知管理/数据库JSON与事务契约.md:44`：CommandReceipt 形状（`commandKind:…/MONITOR_APPLY`），并明确「这类事件**不进入告警触发路由，不创建告警或发给自己**」
- `docs/详细设计/09-告警与通知管理/告警配置与审批生效契约.md:35`：「保存ON清理未发送的临时关闭提醒并通知所属M07监控程序更新修订；M07未ACK时页面区分'配置已保存/执行侧待应用'。监控业务事实event.result_ref记录ACK，**不能仅凭数据库保存宣布监控已启停**。」
- 表侧：`docs/开发基线/01-完整建表.sql:3838` `alarm_event`（注释"可靠事件收件与处理证据"，含 `event_kind/source_object_kind/payload_json/result_ref/process_state`）；`:3813` `alarm_config_revision`；`:3793` `alarm_monitor_policy`。**无独立 M09 outbox 表。**

**裁决定义**：文档口径的"可靠应用事件" = 在与 `alarm_config_revision` 台账同一本地事务内，向现有 `alarm_event` 插入一条 `source_object_kind=COMMAND`、`payload_json=CommandReceipt(commandKind=MONITOR_APPLY)` 的收据行（outbox 式落库，非投递）。

排除项及依据：
- 非 MQ/消息：`数据库JSON与事务契约.md:44` 明确该类事件不进告警触发路由、不发给自己；全链路口径是"同事务落库"，无 broker 语义。
- 非跨模块 Port 调用：`MonitorAcknowledgementPort`（INT05）方向是 M07→M09 入站回执（`PKG-00…设计.md:218`），文档从未定义 M09→M07 出站 Port。
- 非异步任务：时序契约要求与保存"同提交"，异步派发不满足同事务语义。

**文档留给实现裁决的开放点**（INT-32 §3.1 已预见）：M07 监控程序**如何**看到这条收据行（轮询 `alarm_event`？外部投递设施？）、以及保存收据的 `result_ref.monitorAck` 由谁回写（INT05 今天写的是 ACK 命令自身的收据行，不是 M09-015 的保存收据行），权威文档均未展开。

## 4. 三个裁决方案

### 方案 A（推荐）：M09 同事务落 `alarm_event` 收据行，M07 消费另行裁决

在 `writeMonitorPolicy` 守卫回调内、与台账和 CAS 同一事务，插入一条 `MONITOR_APPLY` CommandReceipt（复用 `AlarmEventMapper.insertCommandReceipt` 与 `数据库JSON与事务契约.md:44` 形状；幂等键建议 `M09-015|scopeKey|requestId` 形态，避免与 ACK 入站服务的 `INT05|monitorId|requestId` 键冲突）。

- 影响面：仅 M09 保存回调一处写入 + 读侧 `executionAck` 口径是否演进（见下）；语义 = "配置应用命令已可靠登记"，**不等于** M07 已被通知。
- 需要改的文件（接线批）：`AlarmMonitorPolicyApplicationApplicationServiceImpl.java`（或新增 M09 support 服务）、`M09WiredOfflineMonitorConfigContractTest`（若 ack 口径演进须同批改 `:809/856/1595`）、`M09MonitorPolicyCatalogMirrorContractTest` 不变、本 INT-44 证据测试类第 2/4/5 用例按红线改写。
- 是否涉 PKG-00 / Port 签名：**否**（无新 Port）。
- 是否涉 SQL 基线：**否**（`alarm_event` 已建，`:3838`）。
- 是否涉 M07 owner：**部分**——M07 侧消费与 ACK 回写目标行的对接方式仍需 M07/总控裁决；A 不替 M07 发明入口。
- 遗留裁决点：① 读侧 `executionAck` 是否从恒 UNKNOWN 演进为"有收据未 ACK→PENDING、`result_ref.monitorAck` 到达→APPLIED"（契约 API14 允许三值，当前 UNKNOWN 是被登记的本期口径）；② INT05 现写收据与保存收据两条 `MONITOR_APPLY` 行的语义区分与回写目标。

### 方案 B：新增 M09→M07 出站 Port / 通用事件发布设施

定义如 `MonitorPolicyApplyNotifyPort` 的跨模块契约，由 M07 或公共设施承接投递。

- 影响面：**文档不存在该 Port**，属契约新增，需先设计评审；改动落在 `02-PKG-00公共契约与Port物理签名设计.md`、`futurefab-api`/`service/port` 签名、`PortSignatureSnapshotTest` 快照、共享注册表、M07 提供方实现（M07 目前零承接面）。
- 是否涉 PKG-00：**是**（本批禁止项）。是否涉 SQL：不新增表但可能新增状态列。是否涉 M07 owner：**必须**——M07 要写真实提供方。
- 风险：把"同事务可靠落库"错做成"事务内远程调用"，违反 AGENTS.md §8"外部副作用不得被误当作本地事务一部分"；若做真 outbox 投递设施则演进为公共组件，规模远超一个接线批。
- 结论：不推荐。文档口径（复用 `alarm_event` 收据）与 INT05 既有回执通道已覆盖"可靠 + 可回执"两个诉求，B 是在没有事实需求下另造平行框架。

### 方案 C：契约降级——M09 只承诺台账，撤销"可靠应用事件同事务"

改文档措辞：`页面与接口契约.md:69`、`接口目录与契约定位.md:95`、`Controller请求调用时序设计.md:25`（015 行去 outbox）、`00-全接口契约骨架清单.md:9646` 及对应 JSON 条目、`告警配置与审批生效契约.md:35` 的"通知所属M07监控程序更新修订"半句；`executionAck` 契约上永久 UNKNOWN（或删列语义）。

- 影响面：纯文档 + 后续测试措辞，代码零改动。
- 是否涉 PKG-00 / SQL / M07：否。
- 代价：与"不能仅凭数据库保存宣布监控已启停"（生效契约 :35）的业务事实口径正面冲突；"页面区分配置已保存/执行侧待应用"能力（含 TEMP_OFF 16:00 提醒、保存ON清理临时关闭提醒等依赖已应用事件的条款）失去承载；`CommandReceipt.MONITOR_APPLY`（JSON契约 :44）成为孤儿枚举。
- 结论：仅当总控裁决"本期不落地执行侧回执链路"时选 C，且必须同步登记对生效契约 §3 的偏离，不得静默降级。

### 推荐

**方案 A**。它与现有权威契约逐句对齐、不动 SQL 基线与 PKG-00、把 M09 职责内可闭合的一半（同事务收据落库）先做实；把 M07 消费方式与 `executionAck` 推进作为两个显式开放裁决项随包移交，不越权替 M07 定义入口。
