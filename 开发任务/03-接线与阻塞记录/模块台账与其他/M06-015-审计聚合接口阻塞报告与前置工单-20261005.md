## 3 三条充分阻塞（任一条单独成立即不可诚实实现）

### B-1 拥有方"审计 QueryPort"在仓内不存在，且未在任何冻结契约中立项

- 检索：`service/port/**` 全量 grep `AuditQueryPort|DirectAudit|queryDirectAudit|ApprovalAudit` ⇒ **命中 0**。
- 端口清单实测（`service/port/mXX` 接口文件）：`m03`=10、`m06`=2（`ApprovalPolicyPort`、`ApprovalSubmissionPort`）、`m07`=11（含并发批 `18b62175` 新增的 `PlanReplacementPort`）、`m09`=6 —— 无一为审计读端口。`m09.DeliveryReconciliationPort` 是 M09 自有告警投递对账，与 M06-API13 的审计聚合无关，不能顶替。
- 冻结签名缺位：`docs/开发任务/01-契约骨架/02-PKG-00公共契约与Port物理签名设计.md:186-189` 只登记 M06-INT-API09…API12，**无 API13**。按项目口径，跨模块 Port 的物理签名以 PKG-00 为准并被 `PortSignatureSnapshotTest` 钉住；未经冻结就自行定义三模块审计端口 = M06 单方面替他模块决定契约，且新端口本身属跨模块共享文件（须窗口）。
- 结论：契约第 5 条的取数方式在代码层无法履行。M06 若要用，只能**直查 M03/M07/M09 私表**，同时违反 AGENTS.md §8"跨模块调用使用 Port 契约，不允许直接访问其他模块 Mapper、内部表或实现类"与契约自身"不直接读取拥有方业务表"。

### B-2 即使有端口也没有数据：`schemaVersion=2` 的 `DIRECT_POLICY` 审计写入方为 0

- 检索：`src/main/java` 全量 grep `DIRECT_POLICY` ⇒ **命中 0**；`schemaVersion` 相关命中只有 `service/support/m06/ApprovalPolicyRevisionLedger.java:68/98`（政策快照 schema=**1**）、`ApprovalPolicyPortProvider.java:100/311`（按 1 校验）与 `service/support/m05/**`（M05 结果 schema2，属不同类型，`审阅收尾对账与启用契约.md:58` 明令"不能混同"）。
- 即：M03 基础候选 `reason`＋`policy_evidence`、M07 `after_snapshot/decision_snapshot`、M09 revision `decision_snapshot` 的 `audit` 段**目前没有任何生产写入方**。
- 叠加约束：契约明令"任一依赖未知返回 503，**不以缺记录代替**"。因此"先返回空列表/只回 apr_request 部分"不是合法降级，而是把"未知"伪装成"无审计"。
- 结论：DIRECT / DIRECT_REASON 两种 `mode` 在当前库内**没有事实来源**。三档 `mode` 里契约默认路径（`mode` 可空 ⇒ 聚合）必然包含这两档。

### B-3 对象级读取范围缺端口，实验室级授权不等价

- 契约第 2 条要求在功能码之外**叠加 ownerModule 对应业务对象的读取范围**。
- 仓内现状：只有 M03 侧存在对象级资格端口 `service/port/m03/CultureReadEligibilityPort.java`（并发批次落地）；M07（run/task）、M09（alarm config/record）**无对应对象可见性端口**。
- M06 现有读链路用的是 M02 `LabAuthorizationService` 的**实验室级**可见性（如 `ProcessApprovalQueryApplicationServiceImpl` 的 `requireReadable` 路径）。把实验室级当作对象级使用会**放宽读取范围**（同实验室内非本人可见对象会被放出），属越权面，不得为实现接口而采用。
- 结论：不新增/不复用对象级范围事实，就无法满足权限条；而"缺权限判定"不能申报成"已判定通过"。

## 4 否决的半实现方案（已评估，明确不采纳）

**方案 P**：只接 `mode=APPROVAL` 分支——从 M06 自有 `apr_request`（经 `AprRequestMapper.selectApprovalIdBySource` / `selectRequestRows`）投影 `approvalId/approvalState/applyState/candidateHash/policyRevisionId` 等本地真值，DIRECT/DIRECT_REASON 返回 503 或空 issues。

否决理由（四条，任一充分）：

1. **账本语义会逼出虚假完成声明**。`SkeletonEngine` 规则：非 wired 条目必须既有编号 501 又有 HTTP 501 + `$.errorCode=NOT_IMPLEMENTED`；一旦接真实链路就必须把 `skeleton-m06.json` 的 M06-015 改为 `wired:true`（并把 `expectedCount` 面与 `M06SkeletonContractTest` 的"唯一骨架"断言一并推翻）。届时对外口径是"M06 15 条全部 wired"，而契约默认路径（`mode` 可空聚合）仍结构上 503 —— 直接违反 AGENTS.md §13.2 完成判定与 §13.7 禁止笼统完成措辞，也违反本批"不伪造拥有方业务结果"。
2. **`mode` 可空即三档合一**。契约里 `mode` 是可空过滤条件，不是"必须显式选档"。只实现一档的接口对合法请求（不带 `mode`）只能猜语义或恒 503，两种都不是"最小接线"，而是把一个未完成契约伪装成一个可用契约。
3. **`DIRECT/DIRECT_REASON 时 approvalId 为 null` 的分支无法测试**。没有拥有方 audit 事实来源，就无法构造"有直通原因、无审批单"的输入；对应契约测试只能是同义反复的 mock 断言，不具证伪力（与 F-1/F-5 两批"能证伪修复前行为"的测试标准不一致）。
4. **即便只做 APPROVAL，也要新增 M06 自有读语句**。实测 `mapper/AprDeliveryMapper.java` 只有 `selectDeliveryRowById`(`:36`)、`selectDeliveryRowByIdForUpdate`(`:39`)、`selectDueDeliveries`(`:76`) —— **没有按 `approval_id` 的选择语句**，而视图含 `deliveryId`。该扩展可做（属 M06 自有文件、不占共享窗口），但它不解锁 B-1/B-2/B-3，只把半实现做得更完整，因此不构成立即实施的理由。
