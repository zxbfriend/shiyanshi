## 3. 三十六个功能码的准确集合（代码推导面取证）

### 3.1 推导式与两个取值轴

唯一推导点在 `ProcessTemplateApplicationApplicationServiceImpl`：

```java
// :236-239
private static String functionCode(TemplateKind kind, String action) {
    return "process:" + kindCode(kind) + ":" + action;
}
```

- **kindCode 轴（:222-233 穷尽 switch）**：`CONFIG→config`、`PERFUSION→perfusion`、`SAMPLING→sampling`、
  `AUTO_CONTROL→autoControl`、`FEEDING→feeding`、`PUMP_SPEED→pumpSpeed`。六值与 `TemplateKind` 枚举逐一对应，
  少一个分支该类型就没有码（已被测试的「分支数 == 枚举数」判据钉住）。
- **action 轴（只来自真实调用面）**：`list` / `query` / `add` / `edit` / `changeStatus` / `remove`。
  测试用去注释后的源码正则提取 `requireFunction(<首参>, "<动作>", …)` 的第二位置字面量，
  再并入 `editingAction()` 的 `add|edit` 返回值，得集与 §9.1 冻结表逐字相等。

6 × 6 = **36**。全集（按 §9.1 顺序）：

```
process:config:list|query|add|edit|changeStatus|remove
process:perfusion:list|query|add|edit|changeStatus|remove
process:sampling:list|query|add|edit|changeStatus|remove
process:autoControl:list|query|add|edit|changeStatus|remove
process:feeding:list|query|add|edit|changeStatus|remove
process:pumpSpeed:list|query|add|edit|changeStatus|remove
```

### 3.2 动态判权映射（每个动作在哪些真实调用点被判定）

| 动作 | 调用点（Impl 行号） | 类型来源 | 说明 |
| --- | --- | --- | --- |
| `list` | `:601` | 客户端声明 `templateKind` | 列表口；六类各自成码，不共用一个 list |
| `query` | `:367` 详情、`:379` 版本分页、`:406` 版本详情、`:445` 绑定预览来源、`:670/:671` 候选来源（SAMPLING/PUMP_SPEED）、`:811/:827` 泵数/泵速下拉、`:1965` 复制来源 | **服务端读到的身份行**（`:1965` 另与预检 kind 比对） | 类型不取浏览器声明，防止用别的类型码判权 |
| `add` | `:354` 创建上下文、`:431` 预览父侧、`:657` 候选父侧、`:986` 创建回调、`:1966` 复制回调 | 声明或身份行 | 复制＝来源 `query` + 目标同类型 `add`（§9.1 原样） |
| `edit` | `:442` 预览父侧、`:668` 候选父侧、`:1032` 修改回调；`:737/:894/:950` 经 `editingAction(templateId)` 动态取 `add\|edit` | 身份行 | E（templateKind+templateId）推导，不把 add 与 edit 并成一个放行条件 |
| `changeStatus` | `:1073` 启停回调 | 身份行 | 禁用模板同样先判权再走完整校验 |
| `remove` | `:1102` 逻辑删除回调 | 身份行 | 已删除的 `STATE_CONFLICT` 口径冻结在前 |

读口用 `readPathActor()`（SEC-I01，只取服务端会话事实），写口在守卫事务内、任何写入之前用守卫交付的
`ActorContext` 复核（实时撤权）。Controller 侧 `ProcessTemplateController` **零 `@RequiresPermissions`** 是有意为之：
六类各一套码，写死任一码或取六类并集都等于放宽权限。

### 3.3 为什么这批码是硬前置（不是"锦上添花"）

`M01FunctionPermissionAdapter` 的判定链实测：

```java
:137  verifyCodeRegistered(permissionCode);   // 未登记 → INPUT_INVALID 400
:138  if (UserConstants.isAdmin(actorUserId)) // 超管短路在登记检查【之后】
```

即：**码未登记时 400 对任何账号成立，超级管理员也不能豁免**。这推翻了
`M01FunctionPermissionAdapter` 类注释第 40 行「超级管理员通配 `*:*:*` 豁免登记检查」的表述
（该文件不属批次 D 范围，只登记为缺陷供 M01 车道复核）。因此 §9.1 的
「上述 36 个功能码为待接入 M01 菜单的目标值，不能假设数据库已有这些码」在运行态是硬约束，
批次 A/B 收口的 M04 读写口在此之前不可能在真实账号下走通。

3. **绝不写 `sys_role_menu`**：本包只登记功能码。原包核验 3 继续覆盖，另加核验 9 专门对 `process:%` 复查。

### 6.2 三个候选方案

**方案 A（推荐）：头制式收口，模块契约改为"头为权威"，Body 字段降为业务字段**

  ＋ 补 1 条"缺 `X-Management-Revision` 即 400"的解析器级测试。前端零调用方 ⇒ **迁移成本现在最低**。
- 风险：`expectedManagementRevision`（业务期望版本）与 `X-Management-Revision`（SYSTEM 管理修订）语义不同，
  收口时必须是"头承担守卫、Body 保留业务期望版本"，不能把两个语义并成一个，否则 226 的按动作核准语义会丢。

**方案 B：保留 BODY-ONLY，登记为显式例外并补钉桩**
- 需要总控在 §13.3 加例外条款（AGENTS 文字由用户/总控改，本批不动），并：
  补测试钉住"本口不读头、`WriteMeta` 只由 Body 构造、Body 缺字段即 400"，
  同时在 `00-Controller与模块接口调用总设计.md` 补一条与 §46 不矛盾的例外登记。
- 代价：154 口里永久保留 1 个特例，前端建页时必须记得"这页不发头"，认知成本长期存在。

**方案 C：双源并存（头优先、Body 兜底）**
- 明确否决：契约 §1 的原意正是"避免两个版本来源"，双源会同时引入
  响应外壳 `requestId`（来自头/上下文）与幂等键 `requestId`（来自 Body）两个身份，正是补丁 1 排查过的错法形态。
