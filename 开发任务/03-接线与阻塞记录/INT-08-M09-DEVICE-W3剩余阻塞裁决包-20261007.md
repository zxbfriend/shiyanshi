## 1. B-2 归属探针字段路径——候选与影响面

问题本质：M09 只想问"这个设备是否属于这个 lab"，但 CAP-I01 的调用形状强制携带 ≥1 条拥有方登记路径，且登记面无任何归属语义路径；M09 自建"种类→路径"表即第二事实源（87 号 §1.4 禁令）。

### 候选 a：登记一条通用语义探针路径（如 `ownership.declared_lab_match`）

- 形态：契约 §3/§4 登记一条跨 9 种类通用路径，值=布尔（声明 labId 与权威表 lab_id 判决结果）；provider `columnsOf` 各分支统一供应。
- 效果：判决成功返回体可复核（非 fail-closed-only）；W3 调用形状合规。
- 代价与风险：
  - provider 行为改动（M02 owner 窗口，INT-08 禁改面）；
  - **INT-03 硬规则"白名单=所选语句能供应的字段集合"**：该合成路径不对应任何基线列，需在语句供应核对口径里显式登记为"判决合成值"，否则二次返工红线重演；
  - 若实现取"信任输入回显"（直接回显请求 labId）则是零信息反模式，契约必须禁止并要求取权威表 lab_id 比对结果；
  - 动文档：能力契约 §3/§4；动测试：INT-07 case 2/3、本类 case 1、`M09DeviceLabFactSourceContractTest` 白名单-语句供应钉桩（该例只覆盖 BENCH_CONTROLLER，其它 8 分支的语句供应核对需同批扩展）、`M02DeviceConfigurationAdapterContractTest` 加用例。
  - 签名/DTO：不动（路径是运行时字符串）。
- 适用性：若总控希望"归属判决可复核、可返回"，这是唯一能同时满足 B-2 与响应体证据的路线，但要接受 provider 白名单扩容与语句供应口径修订。

### 候选 b：允许 M09 按 kind 使用不同最小已登记路径

- 形态：M09 自建表，如 BENCH_CONTROLLER→`controller_no`、其余→`device_no/asset_no/volume_ml…`。
- 否决理由（三条都硬）：
  1. 交集为空的现实（实测）意味着没有一条路径跨 9 种类可用，必须维护"种类→路径"副本表 = 第二事实源，直接踩 87 号 §1.4 禁令；
  2. **归属信息拿不到**：返回值全是身份/规格列，判决成立与否只体现在"404 或 200"，M09 消费返回值毫无意义，等效候选 c；
  3. INT-03 已发生白名单收窄先例（BENCH_CONTROLLER 能力五列被裁掉）：M09 副本表会随白名单漂移静默 400，属静默失败面。
- 结论：不推荐。

### 候选 c：provider 支持不传 requiredFields 的 ownership-only 判决

- 形态：`requiredFields` 空 ⇒ 只做归属判决返回空投影。
- 代价：**改提供方行为**（INT-08 禁改面，须 M02 owner 批执行）+ 改契约 §3 公共口径（"1—100 项"下限）+ 为单一消费方开特例形状，与"不允许任意反射读取实体"的最小化精神相悖；`M02DeviceConfigurationAdapterContractTest` requiredFields 形状例、INT-07 case 2/3、本类 case 2 同批改写。
- 结论：不推荐（收益与候选 a 相同但语义更弱、契约改动更大）。

### 候选 b′（本批新取证）：View 回显 deviceRef（弥合契约 §4 既有声明与模型的形状差）

- 事实：契约 §4 原文声明 "DeviceConfigurationView固定deviceRef、modelRef…"，而冻结模型无该字段——**契约早已声明回显，缺的是 DTO 窗口，不是新语义**。
- 形态：DTO 窗口给 `DeviceConfigurationView` 补 `deviceRef` 回显位（值取权威表 lab_id 构造，M02 owner 批落 provider 投影）；W3 判决主形态仍靠 404 fail-closed，回显仅作复核。
- 影响面：DTO 模型 + provider 投影（M02 owner）；`PortSignatureSnapshotTest` 若快照含模型字段面则同批更值（方法签名不变）；INT-07 case 2 的 lab 路径禁令不受影响（回显不是 requiredFields 路径）；本类 case 3 翻转。
- 结论：若总控要"判决可复核"证据且不想引入合成布尔路径，这是改动面最小的路线；纯 404 fail-closed 形态则可不选。

### B-2 推荐

**W3 主形态不依赖探针路径**：归属判决按 §4 条款以 404 fail-closed 表达——M09 携带**该种类任一已登记路径**（路径只保证调用形状合法，判决看的是 200/404），M02 owner 批**可选**落候选 b′ 补复核证据。若总控要求返回值必须自证归属，则取候选 a（并接受合成路径登记的语句口径修订）。两路线都不允许候选 b。

## 2. B-3 deviceKind 值域——候选与影响面

### 候选 a：M09 服务内登记 9 值白名单（自硬编码）

- 效果：越域 kind 在进 provider 前被拒；M09 服务源码出现 `BENCH_REACTOR` 等字面量 = 值域副本。
- 风险：冻结值域变更时 M09 静默漂移；本类 case 4、INT-07 case 4（`assertFalse(service.contains("BENCH_REACTOR"))`）同批翻转。
- 评价：能落地但复制事实源，非最优。

### 候选 b：共享种类常量单一事实源（推荐）

- 形态：`DeviceRef`（port m02 model，PKG-00 载体）暴露 `Set<String> KIND_VALUES`；provider `FROZEN_KINDS` 与 M09 校验都改为消费该常量；契约 §3 登记"值域以 DeviceRef 常量为准"。
- 影响面：`DeviceRef.java` 加静态常量（**非字段、方法签名不变**）——严格说属 PKG-00 模型增量，需 PKG-00 登记窗口开；`PortSignatureSnapshotTest` 快照的是方法签名行（`m02.DeviceConfigurationPort#resolveDeviceConfiguration(...)`），常量不触快照，预期 6 例原值通过；provider `M02DeviceConfigurationAdapterContractTest` 九种类全路由例不变；本类 case 4、INT-07 case 4 同批翻正为"值域单一来源"断言。
- 评价：消除第二事实源，改动最小且方向与 87 号 §1.4"值域属 M02 域知识"一致。

### 候选 c：基线 `alarm_monitor_policy` 加 device_kind CHECK

- 属 SQL 窗口：须同步 `01-完整建表.sql`、模块字段字典、目标 DDL、`来源清单.json`（AGENTS.md §7），并提供 `03-初始化结果核验.sql` 核验；M03 已有先例（`ck_m03_culture_device`）。
- 定位：纵深防御可后行，**不应作为 W3 的接线前置**（W3 靠服务层校验即可完成判决输入约束）。

### 越域 kind 对外码：400 还是 404？

- 现状矛盾：provider 对越域 kind 回 400（入参形状），而 §4 条款（INT-06）明令归属失败不得用 400 表达；W3 若把 provider 400 原样透出，越权试探会得到"参数错误"信号。
- 裁决建议：**M09 入口白名单 + `NOT_FOUND` fail-closed（与 DEVICE 分支现行 `"作用域不存在或无权访问"` 同码同文案）**。理由：
  1. 与 §1.3 口径一致——不对外区分的对象存在性面统一 404，越域 kind 属"该作用域不可监控"，不是"请求写坏了"；
  2. 与现行分支行为同构（deviceKind=乱值 ⇒ 与不存在设备同样的 404，不泄露值域边界）；
  3. provider 的 400 保留为**内部 Port 层入参防线**（M09 值域校验通过后才可能触达），W3 不消费、不透出。
- 影响测试：本类 case 5、INT-07 case 3/4 随 W3 落码批翻正；M09 接口契约（API15 行）需登记该 404 口径；错误码 `INPUT_INVALID` 面不变。

## 3. B-4 contextRef / purpose M9 取值——候选与影响面

### 候选 a：新增 `MONITOR_POLICY` purpose（推荐）

- 落点澄清：purpose 是**契约 §4 的 context 语义值域**，不是 DTO 枚举字段——现形状只有一个 `contextRef` 字符串引用（服务端解析出 actor/purpose/businessId）。因此新增 purpose **不触** `DeviceConfigurationPort` 签名、不触 `DeviceConfigurationQuery` DTO、不触 `PortSignatureSnapshotTest`；若未来要把 purpose 提升为显式 DTO 字段，才属 PKG-00 签名/DTO 窗口（二选一，窗口里明示）。
- 文档连锁（必要但都很小）：能力契约 §4 值域扩为 `TEMPLATE_EDIT/CULTURE_PREPARE/RUN/MONITOR_POLICY`；**§4 的 "RUN 必须有合法业务ID" 规则需同时写明 MONITOR_POLICY 的业务 ID 口径**（建议=监控策略对象 ID 或允许空，总控裁）；M09 现行文档登记 contextRef 构造口径；PKG-00 CAP-I01 行可加消费语境注记（登记面，不改签名列）。
- 动测试：本类 case 6、INT-07 case 5（`assertFalse(capI01.contains("MONITOR"))` 即为此准备的绊线）随登记同批翻转。
- 评价：语义诚实，审计面可直接区分"监控资格核验"与执行准备读。

### 候选 b：复用 `TEMPLATE_EDIT` 或 `CULTURE_PREPARE`

- 否决理由：语义错配——M09 既不是模板编辑也不是培养准备；两个 purpose 在 M04/M03 消费面有各自业务上下文假设，借用语义会让 provider 未来的按 purpose 差异化校验（如 RUN 的业务 ID 规则）踩空；错误代价是静默语义污染，比登记成本大。不推荐。
- `RUN` 更不可借（"必须有合法业务ID"强加且语义错误）。

### W3 应如何构造 contextRef（照 INT-07 纪律）

- 在守卫回调内、由服务端可信上下文构造引用（actorUserId + 裁决后 purpose + 可空 businessId 的服务端解析凭据）；**不得**由前端 Body/Header 透传填充；provider 初版仅校验非空，语义诚实性由 B-4 登记保障。
