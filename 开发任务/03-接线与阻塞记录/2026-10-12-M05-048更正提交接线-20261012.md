## 三、§3.1 六步流程的落地方式

| 步骤 | 落点 |
| --- | --- |
| ① 预览生成不可变候选全文 | `candidateSnapshotOf(...)` 组装 schema2 对象：基线身份＋`changes[]`（itemId/field/newValue/unit/evidenceRefIds）＋`changedPaths[]`＋`evidenceRefs[]`＋`reason`。**不含** correctionId 与签名——那两件事发生在提交事务内，混进预览会让「预览即冻结」名不副实 |
| ② 短期保存 | `CorrectionPreviewSnapshotStore.save(...)`：以 `SecureRandom` 24 字节（192 位）生成的 **不可猜测 `previewId`** 为键，连同操作者/结果身份/基线版本/证据摘要/理由/到期时间写入 Redis，TTL 300 秒 |
| ③ 发令牌 | `issue(...)` 绑定 `previewId｜本人｜候选指纹｜基线版本｜管理版本`，独立签名域 `M05_CORRECTION_PREVIEW_V1.`，5 分钟有效 |
| ④ 提交只接收令牌 | `submitCorrection` 只读 `confirmationToken`；找回全文后 **由服务端复算指纹**（`recomputeCandidateHash(snapshot.canonical())`），与记录值、令牌绑定值三方一致才继续 |
| ⑤ 原子落库 | 守卫事务（`M05_048`）内：锁结果 → 重验基线/更正指针/未决唯一性/对象级范围 → `insertCorrection` → 审计钩子 → 管理版本 CAS → 回执写入 |
| ⑥ 过期/丢失 | `load(...)` 返回 null 即 `CONFIRMATION_EXPIRED_OR_CHANGED`，要求重新预览。提交命令的冻结形状里**没有候选字段**，页面补传内容没有任何生效路径 |

### 两条硬约束

**① 不得在提交前删除缓存。** `submitCorrection` 的顺序是：
先查 `(submitted_by, submit_request_id)` 持久键 → 再校验令牌 → 再读快照 → 守卫事务 → **事务成功返回后才** `delete` 快照。
契约要求「事务成功后即使缓存已失效，同 requestId 重试也能返回原回执」：`retryWithSameRequestIdReplaysOriginalReceiptEvenAfterSnapshotDeleted`
用例证明首次提交后承载体已空，重试仍返回原 `correctionId`/`state`，且不新增第二条申请、不递增管理版本、不重复审计。

> 实现中一度写成「命中持久键即无条件回放」，被 `sameRequestIdWithDifferentCandidateConflicts` 用例证伪（同 requestId 换候选内容本应 409）。已改为：命中持久键后若令牌仍可校验，则比对候选指纹，不同即 `REQUEST_CONFLICT`。

**② 令牌必须能表达「预览身份」。** 未套用 `ResultCorrectionTokenSupport`（它绑的是**更正申请身份**：五段 `correctionId|actorId|candidateHash|expectedVersion|expiresAt`）。
预览令牌为**独立签名域＋独立六段载荷**，首段是 `previewId`；两类令牌的签名域与段序都不同，跨用途重放一律验签失败。
更正申请身份的令牌形状保持五段不变（`correctionIdentityTokenKeepsFiveSegmentsAndCarriesCorrectionId` 钉住）。

### 建表 CHECK 的遵守

`ck_m05_corr_terminal` / `ck_m05_corr_approval` 要求 SUBMITTED 态下 `review_signature IS NULL` 且 `result_revision_id IS NULL`。
因此 **INSERT 语句刻意不列出任何终态列与 `review_signature`**——由 `submitInsertOmitsTerminalAndReviewColumns` 在语句层钉住。
`submission_signature` 只含提交者一份（userId/candidateHash/baseObjectVersion/signedAt），审核签名留待批准时生成。

### 「更正链不是所有可信结果的必经路径」

本类的 `det_result_revision` 写入只发生在**批准**（`decide`）时；接收、上传等各自生产版本快照，未把更正链当成所有可信结果的必经路径。

## 五、边界越界说明（需 owner 裁决）

本批授权的可改文件清单未包含 `controller/DetResultCorrectionController.java`，但 M05-048 接线**在技术上无法绕开**它：

`ResultCorrectionSubmitCommand` 的 `requestId` / `managementRevision` 只能由 `WriteMeta` 参数解析器从
`X-Request-Id` / `X-Management-Revision` 头回填（AGENTS.md §13.3「头权威，Body 不得覆盖头值」）。
不挂 `WriteMeta` 参数 ⇒ 两字段恒为 null ⇒ `new WriteMeta(null,null)` 抛 `RequestMetaInvalidException` ⇒ 该口对真实 HTTP **恒 400**，接线即假完成。

因此做了**最小改动**：仅 `submitCorrection` 方法加 `@ManagementGuardedWrite` + `WriteMeta` 参数 + 两行头权威回填，外加方法注释与类注释的接线状态同步。**未改该文件任何其他方法**。
请 owner 追认该文件在本批的可改性，或指定由谁补这段 Controller 接线。

### 同源但**未**做的越界：M05-048 第二枚签批码

逐接口契约 §1 要求提交为 `detect:correction:submit ＋ detect:sign:sign` 双码 AND。
本批**未叠加**，原因：叠加须同步改台账 `skeleton-m05.json` 的 `perm` 字段，而
