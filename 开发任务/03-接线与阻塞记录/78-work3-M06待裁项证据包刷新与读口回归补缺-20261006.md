### 2.1 P0：`apr_request.policy_snapshot` 的库侧键与 Java 读侧键不是同一个

- **库侧**：`docs/开发基线/01-完整建表.sql:2903` `ck_apr_request_policy` 与 `:2904` `ck_apr_request_stage` 一律按 `JSON_EXTRACT(policy_snapshot,'$.entry.reviewMode')`／`'$.entry.approveMode'` 校验，且 `$.resolutionRules.differentStageActors` 必须是 `'true'`。
- **Java 读侧**：`ProcessApprovalCommandApplicationServiceImpl:369-373`（M06-014 判二段资格）与 API05 Detail 从 `PolicySnapshot.getEntries()` 取档位。
- **VO**：`domain/vo/m06/PolicySnapshot.java:25` 声明 `List<PolicyEntry> entries`，`:43` 另声明 `PolicyEntry entry`（可空附加字段），`Javadoc:28-35` 记录了原因。
- **写侧（第六批 API09 provider）**：`ApprovalSubmissionPortProvider:653-683` 的 `policySnapshotText` 用**同一个** `PolicyEntry` 一次装配 `entry`（对象）与 `entries`（只含该条的数组），`:77-81` 类注释明确登记"该形状差异属既有 P0，本批不改动任何既有读侧判定"。
- **冻结契约面**：`skeleton-m06.json` 里 M06-011 的 `respFields` 只声明 `PolicySnapshot.entries`（`List`），**没有 `entry`**——即当前用来喂饱库侧 CHECK 的那个键并不在对外契约面上。

影响面：改任一侧都会牵动别人。
- 改 CHECK（`$.entries[0].*`）＝动 SQL 基线，属跨批次共享面，本轮禁改。
- 改读侧（`requiresSecondStage` 改读 `entry`）＝改 M06-014 已合并的判定路径，需要能证明二段资格判定不因快照里同时存在两键而漂移。
- 从对外契约删 `entry`＝收紧已在用的 VO 形状，且 provider 仍必须在落库 JSON 里给出该键，否则 CHECK 直接拒。

候选方案：
- **A**：读侧统一改读 `entry`，`entries` 降级为纯展示字段（M06 内部可闭合，但要补二段资格回归）。
- **B**：基线 CHECK 改读 `$.entries[0].*`，快照只留 `entries`（形状最干净，但动 `01-完整建表.sql` 与 `来源清单.json` 指纹，需基线窗口）。
- **C**：维持双键并存＋把 `entry` 正式登记进 M06-011 契约面（零行为风险，代价是长期保留冗余键）。

本轮处置：**零改动**。第六批的"两键同源一次装配"是目前唯一不产生虚假绿的中间态，保持它，等 A/B/C 裁决。

### 2.2 P1：`CONFLICT` 交付开不出对账单（读写口径分叉）

- 库侧允许：`01-完整建表.sql:2959` `ck_apr_delivery_state IN ('PENDING','RETRY','ACKNOWLEDGED','UNKNOWN','CONFLICT','FAILED')`。
- 执行器会真的写出来：`ApprovalDeliveryExecutor:117` `STATE_CONFLICT`、`:668` 实际 `updateDeliveryState(…, STATE_CONFLICT, …)`；`:512`/`:520` 对 `CONFLICT_KEPT` 的处置是"对账保持 RESOLVING 供异常核对"。
- 对账写侧不受理：`ApprovalReconciliationCommandApplicationServiceImpl:83` `RECONCILABLE_DELIVERY_STATES = Set.of("UNKNOWN","RETRY","FAILED")`，`:352-358` 不在集合内即 409 `SOURCE_STATE_CONFLICT`，文案逐字为"只有处于未确定结果的原交付（UNKNOWN/RETRY/FAILED）才能申请对账"。
- 对账读侧不设限：`ApprovalReconciliationQueryApplicationServiceImpl` 全文无 `CONFLICT` 字样，M06-001 预览不按交付状态收口。

后果：一张 `CONFLICT` 交付**能被预览、不能被申请**，而执行器又刻意把它留在"异常核对"语义里——最需要人处理的形态恰好没有工单入口。

候选方案：
- **A**：把 `CONFLICT` 纳入 `RECONCILABLE_DELIVERY_STATES`（一行，但会把"相反既有事实"引入对账口径，必须同时定 M06-002 的 `resolution` 白名单与 M06-003 复核语义）。
- **B**：新增独立的冲突处置出口（不动对账语义，但要新契约编号与新权限码，属跨模块裁决面）。
- **C**：维持现状＋在 UI/文档明确 CONFLICT 只能由执行器收敛，不承诺人工对账（零代码，但等于承认 §512 的"供异常核对"没有落地入口）。

本轮处置：**零改动**。A 会改状态机与幂等口径、B 会新增契约面，都不是本模块可单方面闭合的，按纪律不硬凑。
