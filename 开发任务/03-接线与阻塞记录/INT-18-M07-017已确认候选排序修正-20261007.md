## 3. 排序实现与 null 兜底口径

```java
Comparator<OffsetDateTime> completedAtDescNullsLast = Comparator.nullsLast(Comparator.reverseOrder());
views.sort(Comparator
        .comparing((GlucoseCandidateView view) -> view.getCompletedAt(), completedAtDescNullsLast)
        .thenComparing((GlucoseCandidateView view) -> Long.valueOf(view.getSourceId()),
                Comparator.reverseOrder()));
```

- **为什么不与 Port 分支共用比较器**：`orderedPortCandidates` 用 `Comparator.comparing(getCompletedAt()).reversed()`，对 null 键会抛 NPE；它安全仅因 `portCandidateView` 对 `observedAt==null` 直接丢弃候选。已确认分支的 `completedAt` 来自 `run_confirmation.source_snapshot` 解析（`confirmedCandidateView` 在缺字段/不可解析时按既有口径保留 null，"不伪造时间"），共用即引入 NPE 风险。故两条分支各自持 comparator，Port 路径字节不变。
- **为什么选择"排末尾"而不是 fail-closed**：`INT-05` 复审 `docs/开发任务/INT-05-M07检测结果事实消费方接线预评估-20261007.md:110-114` 登记的正是这个待裁点（"置尾、置首还是失败关闭"）。本任务书把可选口径限定为 fail-closed 或稳定排末尾；对只读候选列表而言，失败关闭会**丢弃真实存在的已确认值**，与"`confirmed=true` 语义不回退"和读口可用性冲突，故选排末尾 + ID 倒序保证可复现。该口径由 §4 的测试钉住。
- **ID 键**：沿用 Port 分支同源口径 `Long.valueOf(view.getSourceId())`，不另立第二套 ID 语义；已确认行的 `sourceId` 取自 `run_confirmation.source_id`（`docs/开发基线/01-完整建表.sql:3136` `BIGINT NOT NULL COMMENT '结果或手工候选ID'`），恒非空。
