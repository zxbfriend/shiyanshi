## 2. work2 交付的公共入口 API 合同（work1 依赖面，冻结如下）

```
ResourceTransactionExecutor#run(ResourceTransactionGateway gateway,
                                ResourceTransactionCommand command,
                                ResourceTransactionCallback<T> callback) -> T
```
- `gateway`：装配期为固定消费者创建的不可公开构造对象，携带固定用途；调用时按对象引用身份核验
  （同句柄实例+同用途+同消费Bean），伪造同名类/字符串/复制字段一律拒绝。装配通道唯一颁发，
  消费者经 `ResourceTransactionConsumer` SPI 的 `injectResourceGateway` 取得句柄。
- `command`（不可变）：`persistentFactId`（已提交任务/事件ID，十进制字符串，对齐 run_task/run_event/run_command 的
  BIGINT 主键）、`executorId`（**1—128 位无空白 ASCII 执行器身份**，对齐 `run_executor_assignment.executor_id
  VARCHAR(128)`；第二轮收口前曾误钉"十进制正整数"，会挡住真实执行器身份，已按 DDL 翻正并补失败测试）、
  `assignmentEpoch`（适用时，>0）、`resourceKeys`（稳定资源身份，**1—128 位 ASCII 身份字符**、非空、升序、去重、
  有界；ASCII 上界是为让声明升序与 `ORDER BY resource_key` 的 ascii_bin 字节序同一全序）、
  `expectedResourceVersions`（与 resourceKeys 同集，十进制数字串；尚无守卫行的资源以 "0" 声明首建，
  由消费者 upsert 后重读实际版本再 CAS）。用途名单：
  - `M07_RESOURCE_CLAIM`：身份=持久任务ID；epoch 必填
  - `M07_COMMAND_RECEIPT_APPLY`：身份=持久命令/事件ID；epoch 可选（按回执事实核验）
  - `M07_RESOURCE_RELEASE`：身份=持久事件ID；epoch 必填
- `callback`：事务内运行，期间 `ResourceTransactionContext.current()` 有效；只允许本地DB写与
  已登记 Port 调用；禁止 RPC/设备/文件IO（合同钉死，验收矩阵另查）。
- 行为：REQUIRED 加入/创建同数据源事务 → `SysManagementRevisionMapper.selectRevisionForUpdate()`
  锁既有 SYSTEM 行（缺行=503 DEPENDENCY_UNAVAILABLE，不补行）→ 建立上下文 → 回调 → 提交。
  不 `increaseRevision`、不写 `sys_management_request`、不调用 `GuardCallbackContext.open`；
  已有守卫回调或后台上下文并存 → 拒绝（嵌套/双上下文失败关闭）。
- 错误：锁等待超时/死锁 → 503 MANAGEMENT_BUSY 整组回滚；配置开关/预算缺失 → 能力不启用，
  网关调用显式拒绝（不虚构默认值）。

上下文公开面（供 Port 提供方与消费者复核）：
`current()/isActive()/requirePurpose(ResourcePurpose)/getPurpose()/getPersistentFactId()/
 getExecutorId()/getAssignmentEpoch()/getResourceKeys()/isSystemLockAcquired()`；
建立/销毁仅执行器包内可调，普通 ThreadLocal 不向异步线程透传，finally 清理。

### 8.2 本轮真实改动（只动公共面）

  - 只取 `TransactionSynchronizationManager.getResource(dataSource)` 上的 `ConnectionHolder`；
    无活跃事务或本数据源无绑定连接即 `IllegalStateException` 失败关闭，

    并由 `ResourceLockWaitBudgetContractTest` 与 `ResourceTransactionConfigurationContractTest` 钉住。
    同批更正二.4：`SET`/恢复语句抛异常时"服务端可能已执行而响应丢失"不可区分，
    一律按会话值无法确认对待并弃池，不再以"看起来没改"放回池；读取原值失败发生在任何 SET 之前，
    会话未被改动，故照常归还不作污染处置。）

### 9.2 §二 四项残余的落实
1. **二.1 过宽映射**：新增 `service/guard/LockFaultClassifier.java`（package-private，两入口唯一共用判据）。
   `LOCK_BUSY` 仅当异常链上任一元素属 `PessimisticLockingFailureException` 族，
   或任一 `SQLException` 带 MySQL 1205 / 1213 / SQLState 40001；
   `PROVIDER_FAULT`＝无锁错误码证据的 `QueryTimeoutException`（如 3024 `max_execution_time`）与
   `DataAccessResourceFailureException`（含 `CannotGetJdbcConnectionException`）→ `DEPENDENCY_UNAVAILABLE(503)`；
   `PROPAGATE`＝其余数据库异常原样上抛不改码。只遍历 `getCause()` 链（引用集防环 + 深度 32 上界），
   不看 message 文本；`signature()` 只输出类名与错误码/SQLState 供拒绝消息使用。
   `ResourceTransactionExecutor` 与 `ManagementGuardExecutor` 都改用该分类器（旧实现按类名把
   `QueryTimeoutException` 一律当锁忙，已废）。对照测试：`ManagementGuardLockFaultContractTest` 5 例
   （锁等待超时、死锁、非锁语句超时、连接故障、其他 SQL 异常）+ `ResourceLockWaitBudgetContractTest`
   与 `ResourceTransactionCapabilityBoundaryContractTest` 的后台侧同表用例。
2. **二.2 恢复失败掩盖原异常**：`ResourceLockWaitBudget.runScoped` 为唯一作用域入口；
   body 正常返回时恢复失败即唯一故障，body 抛异常时走 `Session.restorePreserving(failure)`——
   恢复故障 `addSuppressed` 到原异常、原异常照常重抛，**最终错误码由原异常决定**，
   两条异常链完整保留（不是把恢复失败拼进字符串）；回滚与弃池照旧执行。
   弃池本身再失败时，弃池故障同样以 `suppressed` 附在依赖故障上。
3. **二.3 非 Druid 连接处置**：支持范围前移到**装配/启用期**核对——
   `ResourceLockWaitBudget` 构造器要求 `dataSource instanceof DruidDataSource`，否则 `IllegalStateException` 拒绝启用；
   `discardUntrustedConnection` 只对 `DruidPooledConnection` 走 `holder.getDataSource().discardConnection(holder)`
   （javap 实证：标记 discard 后物理关闭底层连接，`recycle()` 对该 holder 直接返回不入池），
   其余连接一律 `IllegalStateException` 失败关闭，**不把池代理 `close()` 说成物理关闭、不静默归还污染连接**。
   用例：`ResourceTransactionConfigurationContractTest`（非 Druid 数据源启动失败）、
   `ResourceLockWaitBudgetContractTest`（弃池标记 + `isDiscard()` + 无 `poolRecycle`）。
4. **二.4 设置失败的不确定性**："SET 抛异常 ⇒ 会话未改变"不成立（服务端可能已执行而响应丢失），
   设置与恢复失败一律按**会话值无法确认**对待并弃池；判据是"本作用域内是否下发过 SET"，不是猜测——
   读取原值失败发生在任何 SET 之前，会话未被本能力改动，故照常归还不作污染处置。
   新夹具在 `LockWaitJdbcTestDouble`：`failOnFirstSetAfterApplying`（首个 SET 已生效再抛错）、
   `failOnRestoreSetAfterApplying`（恢复侧同款不确定性），对应 5 例见 `ResourceLockWaitBudgetContractTest` ⑧ 段。
