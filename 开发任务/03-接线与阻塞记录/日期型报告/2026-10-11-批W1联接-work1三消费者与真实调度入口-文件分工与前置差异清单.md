### 11.2 为什么"加索引"不等于锁全序（本轮据此否决四种偷懒形态）

按 §二原话逐条落进设计，不写进注释当保证：

1. `ORDER BY` 只固定**返回顺序**，不保证 InnoDB 的**取锁顺序** ⇒ 排队必须由 Java 侧 `TreeSet` 完成，
   不依赖 SQL 计划（钉在 `enumeratedKeysAreDeduplicatedAndLockedOneByOneInAsciiOrder`）。
2. 复合索引上的范围 `FOR UPDATE` 仍会产生间隙锁 ⇒ 锁读**一律只按主键** `resource_key` 求，
   不使用 owner 范围锁读（`FOR UPDATE` 白名单钉成一条语句）。
3. 优化器未必选新增索引 ⇒ 主键锁读走的是聚簇索引，与优化器选择无关；索引只服务枚举的成本。
4. "枚举集合不会变"是不可假设的前提 ⇒ 锁内**逐行**重核 owner 二元组、`fence`、`object_version`，
   缺事实与漂移都失败关闭；不核验第一行就算通过（`requireLockedRowMatchesOwner`）。

### 11.3 锁协议落点（唯一取得处＝`M07ReleaseAuthorization#lockOwnedGuardRows`）

四步顺序与失败语言：

1. **非锁窄读枚举**：`RunResourceGuardMapper.selectOwnedResourceKeys(ownerKind, ownerId)`，
   只投影 `resource_key`、无 `FOR UPDATE`（语句层钉桩：投影列逐字 `G.RESOURCE_KEY`）。
   owner 二元组缺失或空白→`INPUT_INVALID`，**在发起任何读之前**拒绝，绝不退化成全表枚举。
2. **去重＋ASCII 排队**：`TreeSet` 按字节序；返回空引用或含空键→`RESOURCE_FACTS_UNAVAILABLE`（保持占用），
   空集合直接短路、**一次锁读都不发**。
3. **逐键单元素主键锁读**：按排队顺序对 `selectGuardsForUpdate(List.of(key))` 逐键调用，
   把跨请求的交错变成等锁等待而不是死锁；缺行或返回多行→`RESOURCE_FACTS_UNAVAILABLE`。
4. **锁内逐行重核**：主键与请求键不符、返回别的键、owner 改主（分别为
   `RESOURCE_FACTS_UNAVAILABLE`／`VERSION_CONFLICT`）、`fence`／版本缺事实→失败关闭，
   并把拒绝翻译成带 HTTP 外壳的守卫拒绝（取消链 `catch (ResourceTransactionRejectException)` 就地转
   `reject(errorCode, message)`），**整组回滚保持占用**。

残余方向的诚实登记（不谎称测试证明）：

- "枚举在后、新行改主进我名下"这一方向，同一事务内的重复一致性读**看不到**（读视图不随锁读刷新）；
  本批的保护是 SYSTEM 首锁串行化＋守卫写方登记棘轮（11.1 第三、四行实测），
  不是"再读一次比较"。该前提若被旁路写方破坏，锁内重核会显式抛 `VERSION_CONFLICT`，
  但这条只能实库并发实验，保持 `NOT_VERIFIED`。
- 取消链与后台核准释放共用同一取得处，二者不再各持一套锁集合；`releaseGuard` 的调用方仍只有统一资格件一处
  （`freeTransitionHasExactlyOneAuthoritativeWriter`）。
