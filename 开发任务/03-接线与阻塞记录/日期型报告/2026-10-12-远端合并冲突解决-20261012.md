## 1. 背景与结论

`git stash pop` 后，远端 `origin/cloud`（含 `64b90d88 feat(m05): 实现暂存删除清空并修复通讯与契约兼容`）

## 2. 逐文件冲突双方意图与合并取舍

### 2.1 `DetSampleApplicationServiceImpl.java`（主代码，最需谨慎）

**远端意图**：把六口的守卫事务、幂等指纹与持久回执、实验室/设备行锁、锁内快照重算、CAS 落库、
类型化审计全部收进新类 `M05SampleMutations`，本类退化为按操作编号委派的薄层：

```java
return json.convertValue(mutations.execute(ManagementOperation.M05_008, workbenchSampleCommand), ...);
```

**本地意图**：在同一类内自建完整写链（`ManagementGuardExecutor` + `M05WorkbenchSampleWriteMapper` +
`M05WorkbenchSnapshotReader` + `WorkbenchQueueRules`），并新增两个文件
`M05WorkbenchSampleWriteMapper.java/.xml` 与 `WorkbenchSampleWriteRow.java`；
`Action.CLEAR` 判定改为按占用状态驱动（`own.state() != State.COMPLETED` 才放行）。

**取舍**：采纳远端委派结构。理由：

1. 远端写链已带**持久回执表**（`det_sample_mutation_receipt`）与 `M05SampleMutationBehaviorTest` /
   `M05SampleMutationMySqlTest` / `M05SampleMutationEntryTest` 三个配套测试，幂等语义比本地版更完整；
2. 本地版的裁决逻辑本就依赖 `WorkbenchQueueRules`，而该规则引擎已合并并保留本地口径，
   经 `M05SampleMutations` 调用时行为等价——**本地最核心的"清空只放行已完成"没有被丢弃**；
3. 两套写链并存会产生两个可写的样品入口，属 AGENTS.md §13.8 禁止的"制造假完成"。

**保留的本地内容**（写进类 javadov 与方法注释，不影响委派结构）：

- 六口冻结链路的完整说明（头权威元数据 → 守卫管理版本与幂等指纹 → 锁内快照重算 → CAS → 类型化审计）；
- 清空口径原文："只有已完成的样品可清空……不改 `del_flag`、不重置 `queue_status`、不删 `det_result` 与签批记录"；
- R3 收窄、逐项跳过而非全成全败、编号唯一性靠结果侧事实判定等失败关闭约定；
- 本地原在 `validateClearBatch` 上登记的未验证项（"全仓无 `Purpose.CLEAR` 签发方"）。
  **该登记已失效并被翻正**：远端 `M05SampleMutations` 自带 `previewClear` 签发方（经 M05-007 只读评估口可达），
  清空口确有 `Purpose.CLEAR` 校验。类 javadoc 中据此改为"令牌链已闭合"，不再登记为缺口。

**同时清掉**：本地那套 1300 余行的私有实现（`mutateOne`/`writeDraft`/`validateXxx` 等）随委派结构一并移除，
避免同一职责存在两份实现。相应地，本地新增的 `M05WorkbenchSampleWriteMapper.java/.xml` 与
`WorkbenchSampleWriteRow.java` 在生产代码中已无引用方（详见第 6 节待裁决项）。

### 2.2 `DetWorkbenchController.java`

**远端意图**：六口加 `@ManagementGuardedWrite` + `WriteMeta` 头权威回填，新增 `requireB2Contract(contractVersion)`
强制 `X-M05-Contract-Version: 2`（旧客户端 409 `CLIENT_UPGRADE_REQUIRED`），并把六口 `@RequiresPermissions`
从 `add`/`edit` **下调为 `detect:workbench:query`**。

**本地意图**：同样加 `@ManagementGuardedWrite` + `WriteMeta`，但权限维持 `add`/`edit`，
并抽出 6 个 `withXxxHeaderMeta` 私有方法统一做头权威回填。

**取舍**：**权限取远端、头权威回填取本地**。

- 权限取 `query` 是远端的**刻意裁决**而非笔误：其 `M05SampleMutationEntryTest.controllerAllowsReadPermissionToReachDurableReceiptReplay`
  逐方法断言六口权限恰为 `{"detect:workbench:query"}`。理由是持久回执重放需要读权限才能到达，
  若沿用 `edit`，一个只有读权限的合法重试方会被挡在门外。功能权限仍在应用服务内按
  `detect:workbench:add`（暂存）/ `detect:workbench:edit`（删除与清空）二次校验，未放宽。
- `requireB2Contract` 与 `X-M05-Contract-Version` 全部保留（6 处调用 + 1 处定义，已核验计数）。
- 头权威回填改用本地的 `withXxxHeaderMeta` 系列：与远端内联的 `setRequestId/setManagementRevision`
  语义等价，但 6 个重载带注释说明"Body 无法伪造幂等键"，且与本文件既有的 `withHeaderMeta` 风格一致。

### 2.3 `M05WorkbenchAndReportBlockedEvidenceContractTest.java`

冲突最重的一个（2 块），双方各加了**不同**用例。

| 冲突 | 远端 | 本地 | 取舍 |
| --- | --- | --- | --- |
| `UNWIRED_IDS` | 同一条目集 | 同一条目集 + 更完整注释 | 取本地注释 |
| 用例 A | `sampleFamilyB2IsWiredAndSendingStillReturns501`：钉 `mutations.execute(M05_0xx)` | `sampleFamilyWiresSixEndpointsAndLeavesTwoExplicit501`：钉 `ManagementGuardExecutor`/`M05WorkbenchSampleWriteMapper`/`DetectionWorkbenchFactsPort` + 501 恰为 2 | **两个都留**，但本地那条的取样点迁到 `M05SampleMutations` |
| 用例 B | — | `clearEndpointsAreWiredWithStateBasedJudgementAndReleaseOnlyTheLeftSlot`：钉清空口径 | **保留并加强** |

**关键处理——本地用例的取样点迁移**：合并前本地用例在 `DetSampleApplicationServiceImpl` 上钉
"必须经守卫编排 / 必须经写侧 Mapper / 必须经 M02 Port"。委派结构下这三个锚点已下沉到 `M05SampleMutations`，
若照搬会**假红**。因此把这三条钉桩迁到真正的持有者 `M05SampleMutations`，并**加钉**一条
`insertReceipt`（持久回执）——断言强度不降反升。"显式 501 恰为 2" 仍钉在应用服务本体（委派层确实只抛 010/011）。

**关键处理——清空口径用例翻正**：本地原断言 `assertFalse(source.contains("Purpose.CLEAR"))`，
理由是"全仓零签发方，留着校验会成为永远拒绝的假接线"。合并后签发方已存在，该断言**已失真**，
翻正为"必须校验且绑定本次清空集合"（钉 `Purpose.CLEAR` 校验 + `CONFIRMATION_EXPIRED_OR_CHANGED` 拒绝出口）。
同时本地原按 `clearSamplePosition` 语句钉"清空不得改 `del_flag`"，而远端把清空与删除合并进同一个
`remove` 语句、用 `<if test="deleted">` 区分——断言改为**在分支结构上钉**：`del_flag='2'` 必须只出现在
`deleted` 分支内，分支之前不得出现。这比原文更强：原文只保证"清空路径没有 `del_flag='2'`"，
新写法同时保证"删除分支仍在"且"清空路径结构上无法触达 `del_flag`"。

### 2.5 `M05WorkbenchResultActionGuardedWriteContractTest.java`

`STILL_UNWIRED` 集合冲突：远端含 `047,048`，本地不含。该常量用于
`assertEquals(STILL_UNWIRED, unwired)`（"未 wired 集合必须恰为这 N 项"）——是**双向精确匹配**。
台账中 047/048 已是 `wired:true`，若按远端口径，已接线条目会被算作未接线而**必然失败**。
故**取本地方案**（6 项），并同步修正断言文案"恰为这 6 项"。

### 2.6 `M05WorkbenchOccupancyFactsContractTest.java`

`normalizerRemainsPureAndRulesHaveOnlyReviewedReadCallers` 的调用方清单冲突：
远端 `[M05SampleMutations, M05WorkbenchQueueReader, M05WorkbenchRuleEvaluationService]`，

迁至 `M05SampleMutations`"，避免后人误以为漏登记。

## 4. 验证过程中的非本次改动问题（重要）

首次按指定命令执行定向测试时**编译失败**，报错文件为
`M02DetectionCommunicationChecker.java` 与 `DeviceCommunicationHealthServiceImpl.java`，
报 `HealthCheckContext` 找不到 `getInterfaceUrl/setInterfaceUrl`。

**这 3 个报错与本次冲突解决无关**，根因是本地 Maven 仓库中的 `futurefab-common-core-3.6.8.jar`
为**旧版本**：

- 该 jar 构建时间 `2026-10-11 14:12`，而 `interfaceUrl` 字段由远端 `64b90d88` 于 `2026-10-12` 加入源码；
- `javap` 反编译该 jar 中的 `HealthCheckContext`，确认**不含** `interfaceUrl`；
- 主工作区源码 `futurefab-common/futurefab-common-core/.../HealthCheckContext.java:30` **已含**该字段。

即 `-pl` 单模块构建解析到的是过期依赖产物，而非当前源码。按 AGENTS.md §11
"后端定向测试需要依赖模块时使用 `-am`，不得把本地旧依赖造成的错误当作业务回归"，
改用 `-am` 重跑。**未修改任何 `futurefab-common` 文件**。

### 5.3 逐条根因分析

**① `M05WorkbenchSampleGuardedWriteContractTest`（19 errors，本次合并必然暴露）**

全部 19 例报同一个错：
`Could not find field 'guardExecutor' ... on DetSampleApplicationServiceImpl`。

这是本地行为测试通过 `ReflectionTestUtils.setField` 注入
`guardExecutor` / `accessSupport` / `snapshots` / `deviceFacts` / `writeMapper` / `rules`
七个字段，而这些字段属于**本地那套被委派结构取代的写链实现**，在薄委派层中已不存在。

不是断言口径问题，也不是假绿/假红问题——是测试与实现的绑定点随实现迁移而失效。
远端已有等价且更强的覆盖（`M05SampleMutationBehaviorTest` 19 例 + `M05SampleMutationMySqlTest`
+ `M05SampleMutationEntryTest`，含持久回执与令牌校验）。
**未擅自删除**（用户明确禁止删用例），列为待裁决项。

**② `FullSystemSkeletonGateTest.portAdaptersStayWithinReviewedAllowList`（远端遗留）**

报 `M02MaterialObservationAdapter` 与 `M02SamplingLiquidSlotAdapter` 注入未登记的
`BottleConfigMapper`。两文件均由远端提交 `50076843 feat(m07): implement W06 sampling liquid replenishment`
引入，与本次 6 个文件无任何交集（本次未触碰 `service/impl/port/**`、未触碰 `FullSystemSkeletonGateTest`）。
属远端提交自带的新白名单登记遗漏。

**③ ④ `M04M07UnwiredPrerequisiteContractTest` 与 `M07RunCultureRuntimeRowCreationLandingPrecheckContractTest`（远端遗留）**

两例报同一根因：M07 XML 新增了 `run_material_session` 插入语句，
而两处"写落点登记表"的基线未同步（期望 8 张表，实际 9 张）。
`git log -S run_material_session` 确认该表由远端 `50076843` 引入。
两条断言本身是**正确的防漂移门禁**（新增建行通道必须先核归属再重判登记），
红是远端改了 XML 却未同批重登记所致。**本次未修改这两个测试，也未修改任何 M07 XML**。

**⑤ `GuardCallbackContextContractTest`（已知环境噪音，已核实）**
