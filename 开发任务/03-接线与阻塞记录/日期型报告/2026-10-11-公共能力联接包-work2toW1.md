## 2. 能力句柄类型全名 / 方法签名 / 异常

### 2.1 `ResourcePurpose`（enum，固定三用途，不允许运行时追加）
- `M07_RESOURCE_CLAIM("M07_RESOURCE_CLAIM", true)` — 抢占，assignmentEpoch **必填**
- `M07_COMMAND_RECEIPT_APPLY("M07_COMMAND_RECEIPT_APPLY", false)` — 命令回执，assignmentEpoch **可选**
- `M07_RESOURCE_RELEASE("M07_RESOURCE_RELEASE", true)` — 释放，assignmentEpoch **必填**
- `String getCode()`
- `boolean isAssignmentEpochRequired()`
- `static ResourcePurpose fromCode(String)`

### 2.2 `ResourceTransactionCommand`（final，不可变；`builder()` 一次性完成形态/有界/升序校验）
- `static final int MAX_RESOURCE_KEYS = 64`
- `static Builder builder()`
- 只读：`String getPersistentFactId()` / `String getExecutorId()` / `Long getAssignmentEpoch()` / `List<String> getResourceKeys()` / `Map<String,String> getExpectedResourceVersions()`
- `Builder`：`persistentFactId(String)` / `executorId(String)` / `assignmentEpoch(Long)` / `resource(String key, String expectedVersion)` / `build()`
  - `build()` 抛 `IllegalArgumentException`：
    - `persistentFactId` 须十进制正整数（`!=0`）——对齐 `run_task.task_id`/`run_event.event_id`/`run_command.command_id` 的 BIGINT；
    - `executorId` 须 **1—128 位无空白 ASCII 执行器身份**（首字符字母/数字/下划线，其后可含 `: . / -`），
      对齐 `run_executor_assignment.executor_id VARCHAR(128)` 与 07 字段字典；`"77"` 与 `"EXEC-A1:LAB02"` 都合法，
      `"-1"`、空串、含空格、129 字符拒绝。**第二轮更正**：本包首发版误写"须十进制正整数"，
      那会拒绝真实执行器身份、直接挡住 CLAIM/RELEASE 消费者，已按 DDL 放宽并补失败测试；
    - `resourceKeys` 非空、≤64、**每键 1—128 位 ASCII 身份字符（`[A-Za-z0-9_:./-]`，不含空格）**、
      按稳定身份**严格升序去重**；ASCII 上界是为让声明升序与 `ORDER BY resource_key`（`ascii_bin` 字节序）
      成为同一全序，非 ASCII 键的两种序可能分叉，故取锁前即拒绝；
    - `expectedVersion` 须十进制数字串；**目标守卫行尚不存在时以 `"0"` 声明首建**，
      `upsertGuard` 后必须在同一事务内重读实际 `object_version`/`fence` 再 CAS（公共面不代替该资格核验）；
    - `assignmentEpoch` 若非空须 >0；抢占/释放用途必填（`requireMatchesPurpose`）。
- 包私有 `void requireMatchesPurpose(ResourcePurpose)`：用途要求必填而缺 assignmentEpoch → 抛 `ResourceTransactionRejectException(INPUT_INVALID,…)`。

### 2.3 `ResourceTransactionContext`（final，线程局部，仅事务期有效）
- `static Snapshot current()` / `static boolean isActive()`
- `static Snapshot requirePurpose(ResourcePurpose purpose)` → 无上下文或用途不符抛 `IllegalStateException`（越用途按编程错误拒绝，**不伪装业务放行**）
- 包私有 `bind(Snapshot)` / `unbind()`
- 内部 `static final class Snapshot`：`getPurpose()` / `getPersistentFactId()` / `getExecutorId()` / `getAssignmentEpoch()` / `getResourceKeys()` / `isSystemLockAcquired()`

### 2.4 `ResourceTransactionExecutor`（final，唯一实现通道）
- 包私有 `ResourceTransactionGateway bindCapability(ResourcePurpose, Object consumerBean)`：AOP 代理实例拒绝；同用途重复绑定另一实例拒绝；跨用途复用同实例/同类拒绝；密封后新增拒绝。
- 包私有 `void seal()`：三个固定用途必须**全部登记恰好一个实例**，缺一即启动期 `IllegalStateException`。
- `<T> T run(ResourceTransactionGateway gateway, ResourceTransactionCommand command, ResourceTransactionCallback<T> callback)`：
  - 抛 `IllegalStateException`：未密封 / 句柄非本通道原文物（伪造·转交·异执行器）/ 在 `GuardCallbackContext` 内进入（双上下文并存）/ 后台自嵌套 / `command.requireMatchesPurpose` 不符。
  - 抛 `IllegalArgumentException`：gateway/command/callback 任一 null。
  - 抛 `ResourceTransactionRejectException`（**第三轮更正判据**，见 §9.2.1）：SYSTEM 行缺失、锁等待预算读取/设置/恢复失败、
    以及 `LockFaultClassifier` 认定的连接/提供方故障 → `DEPENDENCY_UNAVAILABLE(503)`；
    只有悲观锁异常族或异常链上的 1205/1213/SQLState 40001 → `MANAGEMENT_BUSY(503, retryable)`；
    其余数据库异常原样上抛，本入口不改码。两类 503 都整组回滚。

### 2.5 `ResourceTransactionGateway`（final，不可公开构造/转交/序列化）
- `ResourcePurpose getPurpose()`
- 包私有 `boolean boundTo(Object candidate)`（引用同一性，非类型/Bean 名）
- 包私有 `static issue(...)`（仅执行器装配路径调用）

### 2.6 `ResourceTransactionRejectException`（extends RuntimeException）
- `(FutureFabErrorCode errorCode, String message)` / `(FutureFabErrorCode, String, Throwable)`
- `FutureFabErrorCode getErrorCode()` / `String getErrorCodeValue()` / `int getHttpStatus()` / `boolean isRetryable()`
- **抛出即整组事务回滚，禁止捕获后继续提交。**

### 2.7 `ResourceTransactionCallback<T>`（@FunctionalInterface）
- `T apply(ResourceTransactionContext.Snapshot context)` — 在 SYSTEM 行锁持有、REQUIRED 事务活跃期内执行；**禁止远程调用/设备命令/消息/文件 IO**；抛任何异常整组回滚。

### 2.8 `ResourceTransactionConsumer`（interface，消费者实现契约）
- `ResourcePurpose resourcePurpose()` — 本消费者唯一固定用途，不得 null/变更。
- `void injectResourceGateway(ResourceTransactionGateway gateway)` — 装配通道注回句柄，须存私有字段、不得再暴露/转交。

### 2.9 `ResourceTransactionConfiguration`（@Configuration）
- `@ConditionalOnProperty(name="futurefab.resource-transaction.enabled", havingValue="true")` — 缺省/非 true 则整体**不启用**（BLOCKED_DEPLOY，不降级、不内存顶替）。
- 配置键：`futurefab.resource-transaction.timeout-seconds`（事务预算）、`futurefab.resource-transaction.lock-wait-seconds`（InnoDB 锁等待预算）。两者必为正整数且 `lockWaitSeconds ≤ timeoutSeconds`，否则启动失败。
- **第三轮新增 Bean**：`@Bean ResourceLockWaitBudget resourceLockWaitBudget(DataSource, @Value("${...lock-wait-seconds}") int)`
  —— 全仓唯一一份连接级锁等待预算实例，由后台资源事务执行器与 HTTP 管理守卫**共用**（不各建一套会话预算实现）。
  构造期校验：`lockWaitSeconds > 0`、`dataSource != null`，且（在 `ResourceLockWaitBudget` 构造器内）
  数据源形态必须能公开报告出**已验证弃池策略的 Druid 池**：`DruidDataSource` 本身，或
  项目实际部署使用的 `DynamicRoutingDataSource` 且其路由表内至少有一个 `DruidDataSource` 项目池，
  否则启动失败（第五轮起路由形态已适配，见 §11）。
  未启用冻结键时该 Bean 不存在，两入口都拿不到预算 ⇒ 谁都不得声称已受已验收上界约束。
- `@Bean ResourceTransactionExecutor resourceTransactionExecutor(SysManagementRevisionMapper, PlatformTransactionManager, @Value timeout-seconds, ResourceLockWaitBudget, List<ResourceTransactionConsumer> consumers)`：
  正整数与等待≤事务预算校验 + **事务管理器与预算数据源同一 Bean 核对**（不同源即拒绝启用，防止把预算设在另一条连接上冒充生效）
  → 遍历 consumers → `bindCapability` + `injectResourceGateway` → `seal()`。
  执行器构造器签名已由 3 参变为 4 参（第三参 `timeoutSeconds`，第四参 `lockWaitBudget`，缺预算拒绝装配）；
  该构造器包私有，消费者不需要也不得自行 `new` 执行器。
- **HTTP 侧装配（第三轮）**：`ManagementGuardExecutor` 新增 9 参 `@Autowired` 构造器，
  末参 `@Nullable ResourceLockWaitBudget`（原 8 参构造器保留并委派为 null 预算，避免触碰其它车道在途调用点）；
  预算以 `withinLockWaitBudget` 作用域包住守卫事务主体，在 `selectRevisionForUpdate`（`ManagementGuardExecutor.java:287`）之前生效。
  可证明的作用范围＝本次 SET 之后、本守卫事务内这条绑定连接上的锁等待；**加入已有外层事务时，外层更早发生的等待不在范围内**，
  不得声称本次设置约束了它们。

- 构造/注入：实现 `ResourceTransactionConsumer`；容器注入 `List<ResourceTransactionConsumer>` → 配置类逐个 `bindCapability` + `injectResourceGateway` → `seal()`。句柄仅经此**唯一装配通道**颁发，消费者不得自行 `new` 或从 Bean 名领取。
- 运行：消费者持注入句柄调用 `executor.run(gateway, command, callback)`，在 `callback.apply(snapshot)` 内用 `ResourceTransactionContext.requirePurpose(...)` 断言用途边界后做本域 DB 读写。

## 5. 事务 / 锁序 / 连接级锁等待预算责任
- `run` 时序（第三轮更新，预算已落地）：装配已密封 + 句柄核验 + 双上下文检查 + 命令用途资格
  → 开 `PROPAGATION_REQUIRED` 事务（`setTimeout(timeoutSeconds)`）→ 断言事务同步已活跃
  → `ResourceLockWaitBudget.runScoped`：在**本事务绑定的连接**上先 `SELECT @@SESSION.innodb_lock_wait_timeout`
  读原值、再 `SET SESSION innodb_lock_wait_timeout = <配置字面量>` → `revisionMapper.selectRevisionForUpdate()`
  锁 SYSTEM 行（与 HTTP 管理守卫**共用同一数据源同一 SYSTEM 行互斥量**）→ 绑定 Snapshot → `callback.apply`
  → 出口先恢复原会话值（`finally` 解绑上下文）→ 提交。
- SYSTEM 行缺失 → `DEPENDENCY_UNAVAILABLE` 整组回滚（**不自愈补行**）。
- 锁等待超时/死锁 → `MANAGEMENT_BUSY(503)`，调用方可退避重试。**第三轮更正**：第二轮表述
  "`PessimisticLockingFailureException`/`QueryTimeoutException` → MANAGEMENT_BUSY" 过宽，会把无锁错误码证据的
  普通语句超时（如 MySQL 3024 `max_execution_time`）误判为可重试锁忙。现行唯一判据是 `LockFaultClassifier`：
  异常链上任一元素属悲观锁异常族，或任一 `SQLException` 带 1205/1213/SQLState 40001 才是锁忙；
  `QueryTimeoutException`（无锁错误码）与 `DataAccessResourceFailureException` → `DEPENDENCY_UNAVAILABLE(503)`；
  其余数据库异常原样上抛。两入口（HTTP 守卫与后台资源事务）用同一分类器，不得各判各的。
- **资源锁集合**：必须按稳定身份严格升序去重（由 `Command.Builder.build()` 强制），与统一锁全序一致；越序补锁被拒绝。
  统一锁全序的真实条文坐标是《00-Controller与模块接口调用总设计.md:281》
  （"按SYSTEM→lab→culture→device→occupancy锁序"）与《00-开发实现结构与事务编排约定.md:13》
  （"两条入口取得同一SYSTEM行后均须遵守相同下层锁序"）；本包首发版引用的"§5.5"在该文档中不存在，已更正。
- **SYSTEM 行互斥量同一性（第三轮重核坐标）**：HTTP 守卫 `ManagementGuardExecutor.java:287` 与本执行器首锁都是
  `SysManagementRevisionMapper.selectRevisionForUpdate()`，同一 Mapper、同一 SYSTEM 行 ⇒ 源码层互斥量同源；
  （第二轮写的 `:218` 是接入锁等待预算前的旧坐标，同批行号已下移，不作为当前证据）
  两者按类型注入同一个 `PlatformTransactionManager`（本模块未发现第二个 tx manager 或 Seata 全局事务配置）。
  守卫取得锁后 `increaseRevision`，本入口**不**递增——两条入口都在锁内重读下层事实，互斥不依赖版本号。
  真实并发是否互斥仍须实库验证（NOT_VERIFIED）。
- **下层取锁序一致性（第二轮实证）**：`RunResourceGuardMapper.xml:36`—45 以
  `ORDER BY g.resource_key ASC FOR UPDATE` 定序（`resource_key` 为 `ascii_bin`）。因此消费者必须用
  与命令声明完全相同的键集与同一键字符串；公共面的 ASCII 上界保证 Java 声明序=DB 字节序。
- **入口不得置于既有事务内**：`run` 采用 `PROPAGATION_REQUIRED`（合同禁止本入口用 `REQUIRES_NEW` 拆裂调用方事务）。
  因此触发点必须是**无 ambient 事务**的后台调度/事件线程；若在已开启事务的方法内调用，本入口会**加入**该事务，
  提交/回滚边界与之共用，不再是"新的受控资源事务"。work1 的调度入口若带 `@Transactional`，须把资源事务起点外移到
  无事务层，或在回提差异时说明该事务由谁开启、为何可共用。执行前执行器还会断言事务同步已活跃，
  否则以编程错误失败关闭（不落任何写）。
- **连接级锁等待预算（第三轮：机制已实现，不再只是"配置即契约"）**：
  `futurefab.resource-transaction.lock-wait-seconds` 由 `ResourceLockWaitBudget` 在**当前事务实际绑定的那一条连接**上生效
  （`TransactionSynchronizationManager.getResource(dataSource)` → `ConnectionHolder`），
  而**不是**另取一条连接设置后冒充；无活跃事务或本数据源未绑定事务连接一律失败关闭。
  会话变量不能绑定参数（MySQL 不为系统变量支持 `?`），故只拼接装配期校验过的正整数字面量。
  全部出口（成功、业务回调异常、锁失败、SYSTEM 行缺失、加入已有事务）都在交还事务前恢复原会话值；
  恢复由 `runScoped` 同一作用域承担，**恢复失败不掩盖原异常**——原异常为主异常决定最终错误码，
  恢复故障以 `suppressed` 附后，两条异常链都保留。恢复失败或 SET 结果无法确认时该连接按**弃池**处置：
  Druid 走 `DruidDataSource.discardConnection(holder)`（标记 discard 并物理关闭底层连接，此后 recycle 不可能入池）；
  **池代理的 `close()` 语义是"归还进池"，不是物理关闭，绝不用于冒充废弃**；
  非 Druid 且路由表内也没有 Druid 项目池的数据源在**装配期**直接拒绝启用（不等恢复失败才发现无法废弃），
  未验证过废弃策略的池不受支持；绑定连接若不是可弃的 Druid 池连接（也解不出），
  在**首个锁读之前、任何会话语句之前**失败关闭（第五轮实际池栈适配，见 §11）。
  仍属真实部署批验证项的是目标 MySQL 的实际超时行为与真实 Druid 池复用观察（NOT_VERIFIED）。
- **回调内禁止任何外部副作用**（持锁事务内耗时放大锁等待）。另因预算作用域覆盖整个回调，
  回调内不要期望"锁等待上界"能约束任何非数据库等待——它只是该连接上的 InnoDB 行锁等待上界。

## 6. PKG-00 与共享门禁登记差异
- 每个在能力内运行的 Port/写方法入口须用 `ResourceTransactionContext.requirePurpose(purpose)` 断言用途边界；无上下文/用途不符均失败关闭。
- 三消费者在 PKG-00「Port 逐方法来源分类」小节逐方法登记（参考 `docs/开发任务/01-契约骨架/02-PKG-00公共契约与Port物理签名设计.md` §4 canonical 码表）。
- 共享门禁（第二轮更正表述）：两条入口的上下文**互斥**——在 HTTP 守卫回调内 `GuardCallbackContext.isActive()` 为真时
  `executor.run` 一律拒绝（双上下文并存违反双入口合同）；在后台入口回调内 `ResourceTransactionContext.isActive()` 为真，
  此时不得再进入 `ManagementGuardExecutor.execute`，也不得自嵌套 `run`。消费者/Port 提供方按自己所在的入口断言对应上下文，
  不得用"有任一活动上下文"代替来源判定。能力句柄不可伪造/具名领取（`ResourceTransactionGateway` 非 Spring 组件）。

### 9.2 影响 work1 编码的合同变化

1. **错误码语义收紧（二.1）**：`executor.run` 的数据库故障分界改为 `LockFaultClassifier` 判据。
   `MANAGEMENT_BUSY` 与 `DEPENDENCY_UNAVAILABLE` **都是 503 且 `isRetryable()==true`**，
   因此消费者/调度器**不得用 `isRetryable()` 决定是否退避重试**，必须比较 `getErrorCode()`：
   只有 `MANAGEMENT_BUSY`（1205/1213/SQLState 40001 或悲观锁异常族）可退避重发同一 persistentFactId；
   `DEPENDENCY_UNAVAILABLE`（连接故障、无锁错误码的语句超时、SYSTEM 行缺失、预算读写失败）不得按锁忙自动重试。
   其余数据库异常（唯一键、约束等）现在**原样上抛**，不再包装成 `ResourceTransactionRejectException`；
   消费者若要转成业务结果必须自己按类型处理，不得一概当作"锁忙"。
2. **预算成为执行器的装配必需项（二.3 + §三）**：执行器构造需要 `ResourceLockWaitBudget`，
   该 Bean 只接受**能公开报告出已验证弃池策略 Druid 池**的数据源（`DruidDataSource` 本身，或路由表内含
   Druid 项目池的 `DynamicRoutingDataSource`；弃池策略唯一经过验证的池是 Druid），
   并要求与 `PlatformTransactionManager` 同一条 `DataSource`。
   不满足即**启动期失败**（`IllegalStateException`，BLOCKED_DEPLOY）。work1 不得为让消费者的测试通过而
   换用无可弃池的数据源、注入 mock tx manager 数据源，或自建第二条连接设置会话变量。
   预算生效点是"当前事务绑定的连接"，无活跃事务或无绑定连接一律失败关闭——消费者必须经 `executor.run` 进入，
   不得在 `run` 之外自己调用 `ResourceLockWaitBudget`。
3. **恢复失败不再掩盖原异常（二.2）**：`runScoped` 出口在 body 抛异常时用 `restorePreserving`，
   恢复故障以 `suppressed` 附到原异常，主异常决定最终错误码。消费者若捕获 `ResourceTransactionRejectException`
   做日志/告警，须同时检查 `getSuppressed()`，不能只看主异常就宣称"只是锁忙"或"只是恢复失败"。
   完整链留在 cause/suppressed，对外消息只给故障签名（异常类名 + 错误码/SQLState），不含驱动文本、SQL 或业务载荷。
4. **SET/恢复结果无法确认即弃池（二.4）**：`SET SESSION` 或恢复语句抛异常时，服务端可能已执行而响应丢失，
   客户端无法区分，因此该连接一律按污染处理并走 `DruidDataSource.discardConnection(holder)`，
   **不会**回收进池复用；池代理 `close()` 是归还不是物理关闭，绝不用于冒充废弃。
   读取原会话值失败发生在任何 SET 之前，会话未被本能力改动，故照常归还不作污染处置。
   消费者的回调内**禁止自行 `SET SESSION` 或修改连接会话状态**，否则本能力的恢复契约与弃池判据失效。

   双入口上下文互斥（§6）与"守卫不递增/后台不写用户管理回执"的分工**未变**；
   work1 不得因此把后台资源事务改走 HTTP 守卫，也不得新建第三套会话预算实现。
   可证明的预算作用范围＝本次 SET 之后、本事务内该绑定连接上的锁等待；

   回提差异时须说明该事务由谁开启，不得声称预算约束了外层已有的等待。

保证来自对象图而非二次选池——javap `druid-1.2.28`：`DruidPooledConnection.getConnectionHolder()` 直接

本能力正是 `holder.getDataSource().discardConnection(holder)`，全程不按路由键重新选池。

`java.sql.Wrapper` 契约（`unwrap` 返回自身包装对象）。该前提被违反时本能力无法用公开 API 发现，
本批亦无对抗用例，因此一切包装形态归 ③ 档。`standardConnectionWrapperIsResolvedThroughPublicUnwrap…`

3. 错误码：`MANAGEMENT_BUSY` 与 `DEPENDENCY_UNAVAILABLE` 同为 503 且 `isRetryable()==true`，
