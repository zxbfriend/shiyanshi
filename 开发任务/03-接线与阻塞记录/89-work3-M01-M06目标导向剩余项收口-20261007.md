## 3. M06 CONFLICT：词表级缺陷，不是分支疏漏

行为层证据已在册（`M06ReconciliationPreviewDetailWithdrawContractTest.conflictDeliveryIsPreviewableButCannotOpenANewReconciliation`：
CONFLICT 可预览、`createReconciliation` 在锁内被判 `SOURCE_STATE_CONFLICT` 且零写入即回滚），本批**不重复**该断言，
补的是三处词表互相矛盾这一从未被跨文件核对过的事实：

| 位置 | 声明 | 对 CONFLICT 的态度 |
| --- | --- | --- |
| `docs/开发基线/01-完整建表.sql:2959` `ck_apr_delivery_state` | 六态白名单 PENDING/RETRY/ACKNOWLEDGED/UNKNOWN/CONFLICT/FAILED | 承认为合法投递态（库里就该出现） |
| `ApprovalDeliveryExecutor.java:114-123` | 六个 `STATE_*` 常量＋`TERMINAL_STATES={ACKNOWLEDGED,CONFLICT,FAILED}`＋`DISPATCHABLE_STATES={PENDING,RETRY,UNKNOWN}`；`:657-663` 只对 ACK/FAILED 闭合对账 | 列为终态、不再推进、刻意让对账停在 RESOLVING（`Outcome.CONFLICT_KEPT`） |
| `ApprovalReconciliationCommandApplicationServiceImpl.java:83` `RECONCILABLE_DELIVERY_STATES` | `{UNKNOWN,RETRY,FAILED}`，拒绝文案逐字点名这三态 | 不受理：开不出新对账单 |

推论：终态且可对账的只有 `FAILED`（`ACKNOWLEDGED` 由 `ck_apr_delivery_ack` 强制回执、业务上真已闭合），
所以 CONFLICT 是唯一"最需要人工处理却没有工单入口"的形态。补充事实：CONFLICT 落库时执行器**确实携带拥有方回执**
（`conflict()` 把 `receipt` 传入 `updateDeliveryState` 的 `ownerReceipt` 位），缺口不在"没有证据"，
而在"既不闭合旧单、也开不出新单"。

新类两条断言：① 六态基线与执行器词表全等，且终态∪可推进＝六态、交集为空（这是②的反控制，防解析错觉）；
② CONFLICT ∈ CHECK ∧ CONFLICT ∈ TERMINAL ∧ CONFLICT ∉ RECONCILABLE，且终态∩可对账恰={FAILED}，
并钉住拒绝文案逐字含三态（改集合必须同批改客户端可见文案）。

收口三选一，任一都需裁决记录：把 CONFLICT 纳入受理集合（改业务口径，须同时定义它要对谁重新解释）、
让执行器停止写 CONFLICT（改 `:668` 语义与对账停留策略）、或从 CHECK 删该值（开发基线窗口，且 `ck_apr_request_state:2901`
的 `apply_state` 也含 CONFLICT，属另一处需同步的枚举）。

## 4. M06-011 policy_snapshot：收窄为两问，且两问都有了决定性证据

新类 `M06PolicySnapshotKeyShapeEvidenceContractTest`（5 条）。本批新增两条被 88 号 §4 遗漏的事实，直接改变 A/B/C 的成本判断。

| 锚点 | 实测事实（本基线） |
| --- | --- |
| ① `entry` 零 Java 读取点 | 剥注释后全模块主源码：`path("entry")` 0、`.getEntry()` 0、`putObject("entry")` 恰 1（`ApprovalSubmissionPortProvider:670`）；`path("entries")` 3（`ApprovalPolicyQueryApplicationServiceImpl:169`、`ApprovalPolicyPortProvider:317`、`ApprovalSubmissionPortProvider:585`）、`.getEntries()` 在冻结侧 2 处（`ProcessApprovalCommandApplicationServiceImpl:372-373`）。档案侧 `ApprovalPolicyRevisionLedger` 不写 `entry` |
| ② 两个生产者按表写不同形状 | 提交侧同时写 `entry`（对象）与 `entries`（数组）；修订台账只写 `entries`＋固定 `schemaVersion`；VO `PolicySnapshot` 三属性并存（entry/entries/schemaVersion），歧义面真实存在 |
| ③ `schemaVersion` 校验不对称 | 活侧两处显式 `path("schemaVersion")` 判定（API09 端口、提交前置）；M06-008 政策读口与 M06-011 详情读口源码内该 token 出现 0 次；写侧台账 `put("schemaVersion")` 固定 |
| ④ **新证：`entry` 是强制存在，不是"有就校验"** | `ck_apr_request_policy` 逐字为 `COALESCE(JSON_UNQUOTE(JSON_EXTRACT(policy_snapshot,'$.entry.reviewMode')),'') IN ('BATCH','PROJECT')`（approveMode 同型，另含 `$.resolutionRules.differentStageActors`='true'）。缺键取空串 ⇒ 判假 ⇒ 整行插不进去。同一约束**不含** `entries`、**不含** `schemaVersion` |
| ⑤ **新证：两张表基数不同** | 提交侧 `entriesNode.add(entryNode.deepCopy())`（装配顺序先 `putObject("entry")` 后 `putArray("entries")`）⇒ `entries` 永远是 `entry` 的单元素拷贝，而"单元素"只是生产端不变式，CHECK 表达不了；档案侧台账按 `for (PolicyEntry …)` 循环装配，可承载多场景 |

据此重判三案（本批不选边，只把成本写清）：

- **A 案（Java 改读 `entry`）＝净增读代码，且作用域必须按表切**。今天没有任何 `entry` 读取路径可扩展；
  若把"认 entry"当全局口径，政策读口（`apr_policy_revision` 无 `entry`）、API09 端口与提交前置会直接失败关闭。
  只需限定在消费 `apr_request.policy_snapshot` 的两口（M06-011 详情、`ProcessApprovalCommandApplicationServiceImpl:372` 的档位判定）。
- **B 案（CHECK 改读 `$.entries[0]`）＝净删代码，但语义风险被 ⑤ 精确化**。对今天由 provider 写入的行，
  `entries[0]` 与 `entry` 逐字同源，故等价；但位路径会把"只校验第一个场景"变成库侧沉默行为，
  一旦在途快照承载多场景就假绿。停双写还属开发基线窗口。
- **C 案（键名统一）不是一次全局改名**：② 与 ⑤ 合起来说明两张表基数不同，统一键名必须先回答档案侧多场景怎么表达。
- **第二问独立存在**：版本由谁承担。写侧固定、活侧校验、冻结与政策读口不校验，且库侧 CHECK 根本不读 `schemaVersion`（④），
  所以改形状若不一起决定是否 bump 版本，冻结侧没有判别新旧的任何手段。

`M06-011` 详情读口对 `policy_snapshot` 键形状**没有任何断言**这一覆盖边界维持不变，且本批仍不补：
补它只能伪造 JSON 后打 Jackson，测的是序列化器不是业务口径（同 `selectChildrenDeptById` 的"测 stub"陷阱）；
应在 A/B/C 裁决后与实现同批落。
