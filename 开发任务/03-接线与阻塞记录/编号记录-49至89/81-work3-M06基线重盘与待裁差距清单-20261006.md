### 3.1 `theThreeRejectionsShareOneHttpShellWithoutExistenceHints`

补的是**HTTP 外壳层**的泄漏取证：此前同类断言只在应用服务返回值层（`absentInvisibleAndLabIdLessScopeAreTextuallyIdentical`）比较异常文案，没有证明三种失败面经过 `ManagementGuardExceptionHandler` + `RequestMetadataResponseAdvice` 后**渲染成同一份响应体**。做法：standalone MockMvc 打真实 `GET /process/approval/requests/8100/actions`，三组桩分别给出①范围行 `null`、②`canViewLab=false`、③范围行 `lab_id=null`。

断言：
- 三条响应都 HTTP 404、`$.code=404`、`$.errorCode=NOT_FOUND`；
- `$.data` / `$.rows` / `$.total` / `$.contractId` / `$.retryable` / `$.currentManagementRevision` 一律不存在（不泄漏对象、不误导可重试、不带管理版本）；
- 归一化 `requestId` 后三条响应体**逐字节相等**；
- 三条 `requestId` 两两不同。

**本批自证的一条实现事实（曾导致首次红）**：直接断整份响应体相等会失败，差异只在 `requestId`——`RequestMetadataResponseAdvice` 在 GET 未带 `X-Request-Id` 时**逐请求新生成** requestId。这是 Advice 的既定行为，不是判定分支差异，因此断言改为"归一化 requestId 后全等 + requestId 本身两两不同"。后者反而是新的有效取证：`requestId` 不随权限判定分支变化，前端无法据此反推单据存在性。

## 7. `CONFLICT` 不在 `RECONCILABLE_DELIVERY_STATES`：精确表述与死路证据

| 坐标 | 事实 |
| --- | --- |
| `ApprovalReconciliationCommandApplicationServiceImpl.java:83` | `RECONCILABLE_DELIVERY_STATES = Set.of("UNKNOWN","RETRY","FAILED")` |
| 同文件 `:354` | 前置闸门：`deliveryState` 为 null 或不在该集合内即拒绝发起对账 |
| `01-完整建表.sql:2959` | `ck_apr_delivery_state CHECK (state IN ('PENDING','RETRY','ACKNOWLEDGED','UNKNOWN','CONFLICT','FAILED'))` → 库侧**允许** `CONFLICT` |
| `ApprovalDeliveryExecutor.java:117/121` | `STATE_CONFLICT` 计入 `TERMINAL_STATES`（与 `ACKNOWLEDGED`/`FAILED` 同列终态） |
| 同文件 `:512`（注释）与 `:520` | CONFLICT 的原交付"留在异常核对，对账保持 `RESOLVING`"，`ReconcileOutcome.CONFLICT_KEPT` |
| 同文件 `:668-670` | CONFLICT CAS 写入与 `Outcome.CONFLICT_KEPT` |
| `AprReconciliationMapper.xml:98-108` | M06-004 撤回 SQL 硬要求 `and state = 'SUBMITTED'` |
| 同文件 `:46-61` | 活动槽唯一性只覆盖 `state in ('SUBMITTED','RESOLVING')` |
| 同文件 `:121/:136/:151` | 闭合与查询只认 `RESOLVING` |

**结论必须精确**：`CONFLICT` 交付无法再新建对账（`:83/:354` 词表不含它），而已经因 CONFLICT 停在 `RESOLVING` 的对账**也不能靠撤回脱身**——撤回 SQL 只认 `SUBMITTED`（`:107`）。所以死路不是"CONFLICT 状态永远卡住"，而是：**一旦拥有方始终不给一致事实，模块内没有第三条出口**（既不能新建对账，也不能撤回既有对账）。这是 §11 差距 2 需要总控裁"是否允许 CONFLICT 发起对账 / 是否需要专门的异常收口口"的依据；单模块放宽 `:83` 词表等于让 M06 自行宣布能解决拥有方未证明的矛盾，属伪成功。
