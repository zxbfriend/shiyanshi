## 2. 登记的既有一致性问题：012/013 非法 Path ID 口径分叉（P3，不阻塞）

同一条 `approvalId` 形态非法（空/空白/0/负数/非数字/超 long 位），两个已接线只读口给出不同拒绝：

- M06-012 走 `requirePositiveIdOrNotFound` ⇒ **404 NOT_FOUND**（与"不存在/无范围"同形）；
- M06-013 走 `requirePositiveId` ⇒ **400 INPUT_INVALID**。

两侧都零触库、零写，风险只在"前端要写两套错误处理"。该差额在 `M06ApprovalActionLogWiredContractTest`
的类注释里已被登记为"待总控裁决"，本轮**不改任一侧行为**，只在
`invalidPathIdKeepsTwoDocumentedShapesAcrossTheTwoOutlets` 把它钉成断言，使任何一侧被"顺手统一"时测试面立刻变红。
另：M06-013 无 `@RequiresPermissions`（`skeleton-m06.json` 该条 `perm` 亦为 null，属冻结登记而非漏写），
功能码门禁由 Body.action 对应的三码之一在写侧 M06-014 承担；本轮不补注解（补注解＝改冻结权限语义，须裁决）。

## 3. 五项待裁正式阻塞登记（本轮零代码，只登记）

### 3.1 P0：`apr_request.policy_snapshot` 的 `$.entry`（库侧 CHECK）与 `entries[]`（读侧 VO）形状冲突

- 库侧：`docs/开发基线/01-完整建表.sql` `ck_apr_request_policy` 与 `ck_apr_request_stage`
  都以 `JSON_EXTRACT(policy_snapshot,'$.entry.reviewMode')`／`'$.entry.approveMode'` 取值（单数 `entry` 对象）。
- 写侧：唯一给 `apr_request.policy_snapshot` 落库的提供方 `service/support/m06/ApprovalSubmissionPortProvider`
  （锚点 `root.putObject("entry")`）确实产出单数 `entry` ⇒ 与 CHECK 一致。
- 读侧：`domain/vo/m06/PolicySnapshot` 只有 `List<PolicyEntry> entries`，而 M06-011 详情走
  `readSnapshot(row.getPolicySnapshot(), PolicySnapshot.class)` ⇒ **真实行读回来 `entries` 恒为 null**，
  策略维度在详情响应里静默为空（不是 500，是假绿）。
- 反向同样不成立：若把 VO 改成写 `entries[]`，落库会被 CHECK 拒绝。
- 本批不处置的理由：两个修法分属不同权威层——改读侧 VO/映射只动 M06；改 CHECK 动 `01-完整建表.sql`
  （开发基线，禁止在本轮触碰）。且"快照里究竟该存单场景一条还是整套 entries"是设计口径，不是实现细节。
- 需总控裁决二选一：
  - **A**（推荐，零基线改动）：读侧新增单数 `entry` 映射（`PolicySnapshot` 增 `entry` 字段或引入
    `RequestPolicySnapshot` 视图），CHECK 与写侧不动；同时明确 `entries[]` 只属于
    `apr_policy_revision.policy_snapshot`（`01-完整建表.sql` 该列注释即为"schema/entries/resolutionRules 完整快照"），
    两张表的快照形状本就不同，不得共用一个 VO。
  - **B**：改基线 CHECK 为按 `$.entries[0]` 取值 + 写侧改投 `entries[]`。**代价**：动 SQL 基线、
    已入库的 `apr_request` 行全部需受控迁移，且 M06-014/005 的读侧断言同步重写。
- 解锁影响：A 案落地前，M06-011 详情的策略字段不得宣称 `CONTRACT_TESTED` 之外的层级；
  当前测试用替身行喂 JSON，掩盖了这个空洞（本轮只登记，不伪造修复）。

### 3.2 P1：`RECONCILABLE_DELIVERY_STATES` 不含 `CONFLICT` ⇒ CONFLICT 交付永远开不出对账单

- 事实：`ApprovalReconciliationCommandApplicationServiceImpl` 常量为 `Set.of("UNKNOWN","RETRY","FAILED")`，
  非该集合即 `SOURCE_STATE_CONFLICT` 拒绝申请对账（M06-002）。
- 但 `docs/开发基线/01-完整建表.sql` 的 `ck_apr_delivery_state` 允许 `CONFLICT`，且执行器把它列入
  `TERMINAL_STATES`，注释口径是"CONFLICT 留在异常核对、对账保持 RESOLVING"。
- 后果：一条由投递/对账链路写成 `CONFLICT` 且**当时没有结对账行**的交付，此后无法通过 M06-002 补开对账，
  只能靠人工改库——这正是"至少一次投递"最需要人工核对的那一类事实。
- 未修复理由：把 `CONFLICT` 加进可对账集合＝改变终态语义（CONFLICT 现被当作终结态），
  会连带影响 M06-002/003/004 的状态机断言、`APPLY_RESULT` 投影与活动变更槽释放判定，
  属设计裁决而非接线；且该判定在 `ApprovalDeliveryExecutor` 与对账命令服务两处，任一侧单独改都造成漂移。
- 需裁决三选一：(a) `CONFLICT` 纳入可申对账集合；(b) 执行器不再产生裸 `CONFLICT`（必须同事务结对账行）；
  (c) 明确"CONFLICT 只允许由已有对账行推进"，并给运维一条受控入口。
