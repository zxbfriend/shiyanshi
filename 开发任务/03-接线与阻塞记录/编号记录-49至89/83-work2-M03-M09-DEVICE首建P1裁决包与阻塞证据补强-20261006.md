## 2 任务1：M09 DEVICE 首建 P1 的最终可执行裁决（优先级最高）

### 2.1 现状链路（逐条给坐标，基线 `a11b1eaf5`；与 `a033eb0e` 同值，区间内该文件零改动）

`AlarmMonitorPolicyApplicationApplicationServiceImpl`：

    —— 该语句 `select c.lab_id from res_culture c where c.culture_id = ?`，**是真归属读**；
  - DEVICE 分支 `:319` 只调 `labStatusAlarmConfigMapper.countLabVisibleV2(labId, authAdmin, authUserId)`
    —— 该语句（`mapper/lab/LabStatusAlarmConfigMapper.xml:261`）
    是 `count(*) from lab_lab ll where ll.lab_id = ? and ll.del_flag = '0'` 叠加 `sys_user_lab`，
    **参数面只有 `labId` 与 `authUserId`，不含任何设备键**。
- 写口 `writeMonitorPolicy`：无现行行时 `insertMonitorPolicyV2(policyId, scopeKey, labId, …)`（`:349`），
  其中 `labId` **逐字取自 Body**；有行时 `updateMonitorPolicyModeWithVersionV2`（`:361`）。
- 作用域键 `monitorScopeKey`：`:379`
  `String raw = "MONITOR|" + deviceKind + "|" + deviceId + "|" + (cultureId == null ? "" : cultureId)` —— **不含 labId**。
- DDL（`docs/开发基线/01-完整建表.sql:3793`起）：`alarm_monitor_policy.lab_id bigint NOT NULL`（`:3796`），
  而唯一键只有一条形如 `UNIQUE KEY uk_m09_monitor_scope (scope_key)`（`:3807`），列集合恰为 `scope_key`。

### 2.2 由此得到的两条硬结论

1. **DEVICE 资格判定在结构上不可能证明设备归属**：它读的表只有 `lab_lab` 与 `sys_user_lab`，
   没有任何设备表参与，也不接设备键。
2. **唯一键不是归属防线，首建是全库先写先得**：`scope_key` 不含 `labId`，所以同一台他人设备的
   DEVICE 作用域可以被任何人先写入自己可见的实验室；此后他人再首建才被唯一键挡住。
   —— 这更正了本类 Javadoc 原文"首建分支归属不符时由 `uk_m09_monitor_scope` 唯一键拒绝并整组回滚，
   不产生越权写"的失真表述（见 §2.4）。
