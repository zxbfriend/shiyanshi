### 2.2 D-1：聚合归属与 `READY` 语义冲突

1. §8 原文把 `checkDeviceUsage` 的"输出／所有者"列写成三方贡献：`设备实例详细设计.md:126`。同文件 `:23` 另写"是否有活动使用由对应业务模块按设备关系计算"，即**使用判定本就分模块持有**。

### 2.3 D-2：`reasonCodes` 无词表、路径清单缺失、字段面冲突

- **词表缺位**：`DeviceUsageDecision.java:27` 把取值域推给"03 错误码全集"。实读该文件：表头是 `| 错误码 | HTTP或通道 | 场景及处理 | 重试 | 定义/消费引用 |`（`错误码全集.md:7`），`:5` 引言虽写"运行原因与HTTP拒绝分开"，但全表**没有任何一行标注供 API02／`reasonCodes` 取值使用**，也没有独立的"原因码词表"层；`:44` 仅在样例构造段提到"运行事件使用其reasonCode/issues，不套HTTP外壳"，指向运行事件而非本端口。实测 `grep -n "reasonCode|API02|checkDeviceUsage"` → 只有 `:44` 那一句泛提。
- **相邻但不可挪用的码**：`错误码全集.md:16 DEVICE_INVALID/409`、`:17 DEVICE_OCCUPIED/409`（同行还含 `STATE_CONFLICT`、`PLAN_DEADLINE_PASSED :26`）是**培养提交面的 HTTP 拒绝码**（场景文字："状态已变、设备占用/失效、计划已过截止；刷新事实并重新选择"）。把它们当 `reasonCodes` 词表＝把 HTTP 外壳塞进进程内只读事实投影，且 `错误码全集.md:5` 的"跨模块复用同名码必须携调用上下文，不能仅按字符串误判所属领域"正好反对这种挪用。
- **接口目录／时序零登记**：`接口目录与契约定位.md` 对 `API02/API01/checkDeviceUsage/设备使用` 实测 **0 命中**（该目录覆盖 44 条 HTTP 口与 DD-20260917 补登记段，§7.9 的三个内部 API 未纳入）；`Controller请求调用时序设计.md` 同样 **0 命中**，且其 `:40` 明确 Controller 不得直连设备适配器。⇒ API02 只有 §7.9 那一行契约，无目录条目、无时序、无错误码映射入口。
- **可改属性路径清单未枚举**：`:1103` 要求 UPDATE 的 `changedFields`"限M02目标设备已定义可改属性路径"。M02 侧只有类别级线索（`设备实例详细设计.md:39-52` 各类型"可写业务字段"表、`:23` 的"型号、实验室、控制连接、容量、泵速/系数、通讯身份变更"）。实测检索范围与结果：`grep -rn "changedFields" docs/详细设计/ | grep -v "/history/"` **只有两处命中**——本条要求本身（`详细设计.md:1103`）与 `培养基础变更候选与生效契约.md:31`（M09 事件载荷字段，非路径清单）。⇒ 在该范围内**不存在可逐字抄录的点分路径集合**（结论限于该范围，不代表全仓文档已穷尽）。M03 无法校验也无法据此判阻断。
- **字段名／极性冲突（需裁决，不由 M03 选）**：同一个 `checkDeviceUsage`，三处三套口径——
  - §8 表 `设备实例详细设计.md:126`：返回 `allowed、reasonCodes、usageRevision`；
