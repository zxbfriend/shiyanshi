## 3. 逐文件差异详情

### 3.1 `application-dev.yml` —— 数据源与 Redis 漂移
```diff
  redis:
-  host: 127.0.0.1
+  host: 192.168.1.98
  master:
-   url: jdbc:mysql://127.0.0.1:3306/ymsw_v2?...
-   username: root
-   password: root
+   url: jdbc:mysql://101.200.152.223:6033/ymsw_v2?...
+   username: ymsc
+   password: ymsc
```
- **影响**：Nacos 实际运行时连**共享开发库**；仓库源码若直接启动（不覆盖）则连本机 `127.0.0.1:3306/ymsw_v2` —— 但本机 Docker 实例**无 `ymsw_v2` 库**（仅有 `ymsw2`）→ 仓库字面配置也不具备"本地可直接启动"的可执行性。

### 3.2 `futurefab-system-dev.yml` —— 缺 M05 token-key
```diff
   management:
     receipt-hmac-key: futurefab-dev-management-receipt-hmac-key-...
-  # ---------------- M05 受控更正一次性确认令牌 ----------------
-  # correction.token-key ...
-  correction:
-    token-key: futurefab-dev-correction-token-key-...
```
- **影响**：按 Nacos 当前配置启动 `futurefab-system`，M05 受控更正令牌签发/校验一律 `fail-closed`（`CORRECTION_TOKEN_KEY_MISSING`），M05-001/002 预览令牌不可用。

### 3.3 `futurefab-gateway-dev.yml` —— 缺 2 条路由
```diff
  - id: futurefab-system-ext
    predicates:
-     - Path=/alarm/**,/device/**,/lab/**,/detect/**,/resource/**,/smp/**,/process/**,/sdms/**,/subsystem/**,/namedpipe/**
+     - Path=/alarm/**,/device/**,/lab/**,/detect/**,/resource/**,/smp/**,/process/**,/sdms/**,/subsystem/**
  # 缺整条：
- - id: futurefab-monitor-datalog
-   uri: lb://futurefab-system
-   predicates:
-     - Path=/monitor/datalog/**
```
- **影响**：`/namedpipe/**` 透传缺失 → 相关 SDMS/NamedPipe 子系统请求 404；`monitor-datalog` 路由缺失 → `/monitor/datalog/**`（无 StripPrefix，命中 system 的 `@RequestMapping("/monitor/datalog")`）落到其它路由或 404，前端 SDK 该路径无法命中。

### 3.4 一致的 5 个
`auth` / `gen` / `file` / `job` / `monitor` 五个 `-dev.yml`：仓库与 Nacos 完全相同，无需处理。

## 4. 安全 / 适用结论（按总控补充裁决）

- `101.200.152.223:6033/ymsw_v2` = **多人共享开发测试库**，**非生产**。不因"公网/外网 IP"判生产红线。
- 但该项仍构成配置治理问题：
  - 该库**多人共享**，自动化验证（写入 / 建表 / 初始化）会污染他人工作区 → **不适合作为自动化验证目标**。后续 FULL-VERIFY 一律改本地临时库 / 本地 Docker 库。
  - 仓库源码字面配置 `127.0.0.1:3306/ymsw_v2` 指向的本机库**不存在**（本机仅有 `ymsw2`）→ 仓库配置本身也不具备"本地可直接启动"的可执行性。
- **验证状态裁定**：Nacos 配置漂移对"FULL-VERIFY 数据库验证"构成 **`BLOCKED_INPUT`**（没有安全可自动化的目标库）；对"按当前 Nacos 配置运行"构成 **`BLOCKED_DEPLOY`**（配置已发布但本批未做运行验证，且共享库不宜自动化）。**不作为 P0 安全红线**。
- 唯一真实风险：仓库与 Nacos **双源不一致**。若有人在未确认库存在性的前提下"以仓库为准回写 Nacos"或"以 Nacos 为准回写仓库"，会造成 dev 启动连库失败或误连共享库。属配置治理缺陷，非数据安全事件。

## 5. 推荐修复方案

- **A｜以仓库为权威，回写 Nacos**
  - 前提：先把仓库 `application-dev.yml` 库名由 `ymsw_v2` 改成本机存在的 `ymsw2`（或先在本地建 `ymsw_v2`），再把三个 DIFF 回写 Nacos。
  - 优点：单一事实源、仓库即真相。
  - 缺点：dev 强绑定某机/某库，团队共用不便；且 `101.200.152.223` 是大家实际在用的共享库，回写成 `127.0.0.1` 会让"按 Nacos 启动"的人连不到共享库。
- **B｜以 Nacos 为权威，回写仓库**
  - 仓库改回 `101.200.152.223` + `192.168.1.98` + 补回两段缺口。
  - 缺点：仓库基线钉死共享库地址/凭据，语义上是"本地 dev 模板"却写死远程共享库；CI / 新人克隆后直接连共享库，存在凭据外溢与误用风险。**不推荐**。
- **C｜拆分 `dev-local` / `dev-shared` 两套配置（推荐）**
  - `dev-local`（仓库默认）：`127.0.0.1:3306/ymsw2` + `127.0.0.1` Redis + 补 `token-key` + 补 2 路由，用于本地单机 / 本机 Docker 验证。
  - `dev-shared`（团队共享基线）：保留 `101.200.152.223` 共享库地址，但**凭据走 Nacos 密钥管理 / 环境变量注入，不在仓库明文**；仓库只保留占位。
  - 通过 namespace 或 profile 区分；FULL-VERIFY 一律用 `dev-local` + 本地临时库。
- **短期最小收敛（建议）**：无论选 A 还是 C，先把仓库 `application-dev.yml` 的 `ymsw_v2` 改本机存在的 `ymsw2`（否则仓库字面不可本地启），并补齐 `system` / `gateway` 两段缺口；Nacos 是否回写等总控就 A / C 拍板。
