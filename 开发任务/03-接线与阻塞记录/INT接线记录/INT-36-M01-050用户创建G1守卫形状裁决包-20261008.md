## 0. 一句话结论

本批把 R-3（`SysUserController#add` 究竟按**受管理写**还是**非守卫写**准备）收窄成三选一的可裁决项，并新增 8 条证据测试把裁决前置钉住。**核心新发现有三条，都改变裁决成本估计**：

## 3. 三个方案的裁决包

### 3.1 方案 A：`add` 纳入 G1 守卫写（与 `edit` 同制式）

**内容**：`SysUserController#add` 补 `@ManagementGuardedWrite` ＋ `WriteMeta` 形参 ＋ `X-Request-Id` 显式校验，把 `writeMeta.getRequestId()/getManagementRevision()` 回填进已存在的 `UserCreateCommand.requestId/managementRevision` 两个**已冻结字段**（台账 §十"仅字段位，不接守卫"），HTTP 层与 `edit` 一致。

**需要同批翻正的测试**：§2.5 表中 5 处 `M01UserSkeletonContractTest` 断言 ＋ `M01UserCreatePrimaryKeyEvidenceContractTest` ④ ＋ 本批新类 ①②⑦⑧（③④⑤⑥ 属公共解析器／兄弟口形状／纯标记／注册表事实，A 落地后仍为真，不翻正）。**不需要**：`PortSignatureSnapshotTest`、`ManagementOperation`/`AuditPolicyRegistry`（USR03 已在册⇒**不占共享注册表窗口**，本类⑥实测）、`UserCreateCommand` 字段面（两位已在冻结字段集内，`M01UserSkeletonContractTest#commandFieldsMatchFrozenContract` 无需改）。

**前端影响**：`user.ts:40` 的 `addUser(data)` → `addUser(data, meta?)` ＋ `headers: writeHeaders(meta)`；`user-editor.vue:375` → `addUser(form.value, writeMeta(revision))`。revision 来源＝列表页已传入的 `managementRevision` prop（`:215`），弹窗内 `useGuardedWrite`/`ensureRevision` 已就绪（`:47-58`）。⇒ **无新读口、无公共前端件改动、无菜单权限变化**。拿不到 revision 时前端必须短路（AGENTS.md §13.3），`writeHeaders` 已是"缺 revision 就不发该头、由后端 400"的既有实现（`guarded-write.ts:20-29`）。

**HTTP/浏览器验证影响**：落地即需 MockMvc 三条外壳取证（缺任一头→400 INPUT_INVALID、头齐但服务未接→501、`MANAGEMENT_CONFLICT`/409 行为）；**浏览器验收要等 050 真接线才有意义**，A 单独落地时页面提交会从"501 骨架"变成"400 缺头"或"501 骨架"，不得据此报 BROWSER_VERIFIED。

**风险**：
- **风险 A-1（制式）**：若实现批选直绑制式而非 `WriteMeta`，缺头会从 canonical 400 退化为"200＋body code=500"（该退化在 `changeStatus`/`forceLogout` 上已被实测现状钉住）。⇒ 裁决书应**同时钉制式**，推荐 `WriteMeta`。
- **风险 A-2（判据污染）**：骨架期就挂守卫标记，会让"有标记＝已接线"这条既有判据失真；须同步把 050 的完成判据改挂台账，而不是挂注解。
- **风险 A-3（假绿）**：A 之后 `add` 的形状与 `edit` 一致，容易被误读为"链路已通"；本批新类⑤已钉"标记不开守卫事务"， AUTH-I02 在无守卫事务下仍失败关闭。
- **风险 A-4（前端半侧不同步）**：只改后端则真实页面新增用户直接 400；只改前端则发多余头、后端忽略（现状 `add` 无接收位，多余头无副作用但会掩盖未裁决事实）。⇒ 必须同批，本类⑦⑧即为此设的检出力。

**判定**：技术上可行、成本小（2 个后端测试类＋1 个本批新类＋前端 2 处），但**不解锁 R-1／R-2／N-5**，所以 A 落地后 050 仍应停 `IMPLEMENTED 之前的 SKELETON` 状态。

### 3.2 方案 B：`add` 不纳入 G1，创建期授权另走机制

**内容**：`add` 保持普通写口形状（无标记、无 `WriteMeta`），创建期实验室授权改由**新机制**承担。可选实现形态有三种，都需要另行裁决：
- **B-1 显式预检口**：创建前先调一个预检/准备出口拿"草稿凭据"，`add` 携凭据落库。今天 `LabAuthorizationPort` 方法面恰 3 个（AUTH-I01/I02/I03，`PortSignatureSnapshotTest` 冻结），创建期读侧已有 AUTH-I01 的 `USER_CREATE` 场景（`:165-186` 支持 `targetUserId==null` 并给出 `authorizationVersion`），**但该版本事实集含 `targetUserId`（`:1021-1028`）**，因此预检凭据天然算不出真实 ID 上的版本 ⇒ 要 B-1 必须**新建 Port**（不能改 AUTH-I01/I02 签名，也不能收紧共享 SQL）。
- **B-2 哨兵版本**：创建期用一个登记过的哨兵串（如 `"0"`）作为 `expectedAuthorizationVersion`。今天 `replaceUserLabs:231-236` 在锁内**无条件**用真实 ID 重算并比对，且 `requireOpaqueVersion` 只放行十进制串 ⇒ 哨兵要成立必须改**M02 适配器比对语义**（跨模块，需 M02 owner 开面，不在本批授权范围）。
- **B-3 服务端自签**：`add` 内部先生成 ID，再以 `USER_UPDATE`＋真实 ID 走 AUTH-I01 自取版本后调 AUTH-I02。INT-33 §3 已判**不合法**（把契约必填位 `labAuthorizationVersion` 变成摆设，"草稿已过期"的乐观锁语义恒不触发，且 §20 时序 `:1000-1010` 要求"UI→USR07→USR03 完整提交"）。

**需要同批翻正的测试**：B-1 需要新增 Port 签名 ⇒ 动 `PortSignatureSnapshotTest`（本批禁改，且属端口轮窗口）；B-2 需要改 M02 比对 ⇒ 动 M02 适配器与其全套授权测试；B-3 无测试翻正但语义违规。**三条都不比 A 便宜**。

**前端影响**：A 的前端 2 处改为"预检凭据"传递 ⇒ 弹窗需要新的凭据装配/失效处理逻辑，成本**高于** A；且 §17.1 的"写接口必带双头"这句仍要求前端为 `add` 发头，B 若不发头就与 §17.1 文本正面冲突，必须由总控改写该句（文档变更要同步总入口，AGENTS.md §12）。

**HTTP/浏览器影响**：同 A 需要外壳取证，另需为凭据/哨兵新增失败码登记与错误码全集同步。

**风险**：
- **风险 B-1（文档正面冲突）**：§17.1 说"写接口另有 X-Request-Id 及 X-Management-Revision 必填"，§20 说 USR03 输出 `data W`（含 `managementRevision`）。B 不与"data W"自动兼容——回执外壳的 `managementRevision` 由谁产生、幂等 `requestId` 由谁承载，都要重新定义。
- **风险 B-2（越界）**：B-2/B-1 的实现点分别落在 M02 适配器与新 Port，均超出 M01 自有文件面 ⇒ 需别的 owner 开面并可能占共享窗口。
- **反控制（B 的合法性）**：`resetPwd`（API07）证明本模块确有"写口但非受管理写"的现行形状。⇒ 裁 B 不构成惯例破坏，但必须**同时**给出双头与 `data W` 的替代口径。

**判定**：可行但更贵、且落点跨模块。只有当总控认定"创建期不应占用 SYSTEM 守卫单行 CAS"（§17.1 已承认跨页面冲突风险并留 25.2 细化口）时才值得选 B。

### 3.3 方案 C：先接用户主表、不写实验室授权

**判定：必须否决。** 依据（均为现行契约文本，非实现偏好）：
1. §20 USR03 行逐字要求"**整个用户与关联原子创建**"（`:969`），`:992` 段逐字要求"调用M02而不是绕过授权"；`M01UserCreatePrimaryKeyLandingPrecheckContractTest` 的 ⑤ 已把这两句钉成断言，漏改设计文本会直接变红。
2. 冻结命令面自带 `authorizedLabIds`／`authorizationChanges`／`labAuthorizationVersion` 三个授权槽位（`M01UserSkeletonContractTest#commandFieldsMatchFrozenContract` 逐字段点名）。"保留槽位但不消费"＝**静默忽略用户输入**，属伪绿形态。
3. AUTH-I02 在无守卫事务时**失败关闭**（`:202`＋`:1137-1144`），C 若要绕过就必须给 `add` 之外另开一条无守卫写授权通道——那是比 B 更大的越权面（绕过逐口权限唯一映射 `:532-540` 与身份交叉复核 `:219-220`）。
4. 台账 `M01WiredReadContracts` 与 §13.2 的完成口径都不承认"半链接线"：只接主表而授权缺席，050 既不是 `IMPLEMENTED` 也不是 `CONTRACT_TESTED`，只会新增一个不可验收的中间态。

⇒ C 属**契约变更**，不在 R-3 的裁决空间内；若总控想采纳 C，必须先改 §20/§17.1/命令面并登记为范围裁决，本批明确不将其列为可执行方案。

## 5. 推荐

**推荐方案 A，并同时在裁决书里钉两件事**：

1. **钉制式**：采 `WriteMeta` 解析器制式（与 `edit`/`remove` 和菜单/角色/参数三处创建口一致），不采 `@RequestHeader` 直绑制式。理由：直绑制式缺头退化为"HTTP 200＋body code=500"，与 §17.1 canonical 400 不符，且该退化已被既有测试以实测现状钉住；`WriteMeta` 制式有 canonical 400 路径（本类③）。
2. **钉判据**：裁决书须明确"`add` 挂上守卫标记／双头形状"**不等于** M01-050 接线，050 的完成判据改挂台账与 `wired` 登记（AGENTS.md §13.2），并要求 A 的落地批**同时**翻正 §2.5 全清单。

推荐理由（按证据强度排序）：
- **惯例一致性**：模块内三处同为"新增"语义的口都已是守卫写（本类④），A 不需要新机制，也不需要跨模块开面；
- **文档一致性**：§17.1 双头必填、§20 USR03 输出 `data W`、§23 管理写锁序三步都直接指向 A，而 B 必须改写其中至少两句；
- **排期成本**：USR03 已在受管理写注册表与审计策略注册表在册（本类⑥实测），A **不占**共享注册表窗口——这是能立刻降低后续排队成本的一条实测事实；
- **前端就绪度**：revision 来源与守卫写 composable 都已在位（本类⑧），A 的前端半侧只有 2 处；
- **失败方向**：A 失败模式是"400 缺头／501 骨架"这种可观测的显式拒绝；C 的失败模式是静默丢授权；B-2 的失败模式是跨模块语义漂移。

**明确不做的事**：本批不要求开落码批，不宣称 M01-050 可接线，不宣称 R-1／R-2／N-5 已解除。推荐 A 只关闭 R-3 这一格。
