## 1. 问题与结论

M07-017 两条分支的排序次键此前均为 `Long.valueOf(view.getSourceId())`：

- `orderedConfirmedCandidates`：`GlucoseCandidateView.sourceId` 由 `decimal(row.getSourceId())` 写入，`run_confirmation.source_id` 为 null（或行投影缺列）时该键为 null，`Long.valueOf(null)` 抛 `NumberFormatException: Cannot parse null string`。
- `orderedPortCandidates`：`sourceId` 直接取 M05 DET-I07 的 `ResultRevisionView.resultId`（自由字符串；`ResultRevisionView.java:16-19` 只登记"必填"，未冻结十进制形态）。提供方给出空串、`"abc"` 这类值或超出 `long` 范围时抛 `NumberFormatException`。

两处都发生在 `views.sort(...)` 内，属只读列表接口的**未捕获运行时异常 → 500** 路径，且失败点在排序阶段，与筛选、鉴权、数据范围都无关。

本批把次键改为可解析性分组的兜底比较器，两条分支的读口不再因坏 `sourceId` 抛异常；行不丢、`confirmed=true` 语义不变、候选过滤不变、Port 签名与 `PortSignatureSnapshotTest` 不变。INT-18 登记的"两分支不共用比较器"结论保持：主键（`completedAt`）的空值策略仍各自持有，Port 分支对 null 完成时刻仍会 NPE（按构造不可达，`portCandidateView` 对 `observedAt==null` 直接丢候选），本批未放宽。

## 3. 实现与口径

```java
private static int bySourceIdDesc(GlucoseCandidateView left, GlucoseCandidateView right)
{
    Long leftId = sourceIdKey(left);
    Long rightId = sourceIdKey(right);
    if (leftId != null && rightId != null)
    {
        return rightId.compareTo(leftId);   // 同刻数值倒序（等价原 Comparator.reverseOrder() 键）
    }
    if (leftId != null)
    {
        return -1;                          // 数值组排在非数值组之前
    }
    return rightId != null ? 1 : 0;         // 双非数值：判定相等，由稳定排序保留输入相对次序
}

private static Long sourceIdKey(GlucoseCandidateView view)
{
    String raw = view.getSourceId();
    if (raw == null)
    {
        return null;
    }
    try
    {
        return Long.valueOf(raw.trim());
    }
    catch (NumberFormatException ex)
    {
        return null;                        // 空串/非数字/超 long 范围统一归非数值组，不猜值、不丢行
    }
}
```

选择与依据：

- **不 fail-closed**：本接口是只读候选列表，抛异常等于把整页真实候选（含已确认值）打成 500；与 INT-18 对 null 完成时刻"排末尾而非失败关闭"的同一理由一致。
- **不丢行**：坏 `sourceId` 只影响次键次序，不构成"该行不可信"的判据；丢弃会造成同一数据集返回集合随排序变化，违反契约 §2 的可复现要求。
- **不猜值**：不给坏 ID 赋 0、`Long.MIN_VALUE` 之类的哨兵数值，避免它冒充"最小 ID"参与数值倒序语义。
- **非数值组内部稳定**：`List.sort`（TimSort）稳定，比较器对双非数值返回 0，故次序即上游次序（已确认分支为 Mapper 行序，Port 分支为 DET-I07 页内序），两者本身确定，可复现。**这是本批钉住的口径**：不引入字符串字典序兜底（`"abc"` 与 `""` 的字典序会造出第二套无契约来源的 ID 语义）。若后续要改为字符串降序，须同时改动 §4 的两个断言并重新裁决。
- **trim 而非拒绝**：`" 1001 "` 视同数值 1001，与仓库既有 `pathId(...)`（`RunCultureApplicationApplicationServiceImpl.java:560-575`）的十进制解析口径一致，不另立第二套。
