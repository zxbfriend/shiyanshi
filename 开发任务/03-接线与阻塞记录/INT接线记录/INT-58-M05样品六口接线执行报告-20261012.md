## 3. M05-029 / M05-030 为什么退回 501

### 3.1 设计层：冻结规则对 CLEAR 无条件拒绝

```java
// WorkbenchQueueRules.java:94（本批未改动该文件）
if (request.action() == Action.CLEAR) common.add(Reason.RESULT_POLICY_REQUIRED);
```

既有测试 `M05QueueRulesTest:113` 已钉住该行为（用例名 `...andClearCannotReuseDelete`）。该文件 `git status` 为空，确认非本批引入。

**后果**：清空请求无论事实如何都必然带该原因。单行口径抛 `RESULT_STATE_CONFLICT`；批量口径是行级原因，逐行回执 `SKIPPED`。

**为什么不绕过**：删掉那一行就能让两口"通过"，但那等于替总控裁决「结果策略」的判定来源——而设计文档中该口径**根本不存在**（`grep "结果策略" docs/详细设计/05-检测与数据签批/` 零命中）。按 §13.8 与边界纪律，实现方不得自行默认。

### 3.2 门禁层：「落码但不登记 wired」是被禁止的中间态

首版曾采用「代码完整落码 + `wired=false`」的折中，**全模块回归直接证伪该处置**：

`FullSystemSkeletonGateTest.applicationServicesAreZeroFieldNumbered501Only` 的等式是

```
方法数 − 501 抛出数 − 未编号 GET 入口数 == wired 登记数
```

实测 `DetSampleApplicationServiceImpl`：`8 − 2 − 0 = 6`，而 `wired` 登记为 4，**差值恰为 029/030 两个方法**。
即骨架门禁要求每个公共方法**要么**抛 501、**要么**登记为 wired，不接受"已落码却两头都不算"。

同源失败还有两条（均在本批回退后消失）：

- `M05SkeletonContractTest.implThrowsNumbered501Only`：反射直调 029/030 得到 `ManagementGuardRejectException`，而期望 `SkeletonNotImplementedException`。
- `M05SkeletonContractTest.http501EnvelopeForEveryEntry`：HTTP 层 029/030 返回 200 而非 501。

**因此回退是门禁强制要求，不是保守取舍。** 回退时一并撤除全部半接线残骸：

| 撤除项 | 位置 |
|---|---|
| `@ManagementGuardedWrite` + `WriteMeta` + 两个头权威 helper | `DetWorkbenchController` |
| `M05ConfirmationTokens` 注入与 `requireClearToken` | `DetSampleApplicationServiceImpl` |
| `applyMutation` 的 CLEAR 分支（改为非 DELETE 即抛错） | `DetSampleApplicationServiceImpl` |
| `clearSamplePosition` 方法与 `<update>` 语句 | Mapper 接口与 XML |

### 3.3 防回归钉桩

- `M05WorkbenchAndReportBlockedEvidenceContractTest.clearEndpointsStayExplicitly501BecauseResultPolicyIsUndecided`
  —— 同时钉住「规则那行仍在」「两口必须显式 501」「实现中不得残留令牌链与清空写语句」三条负向断言。
- `M05WorkbenchSampleGuardedWriteContractTest.clearEndpointsRemainExplicitlyNotImplementedBecauseResultPolicyIsUndecided`
  —— 钉住 `contractId` 分别为 M05-029/M05-030，且 501 必须发生在任何写入之前。

**解锁需要**：总控裁决 `RESULT_POLICY_REQUIRED` 的判定来源（清空时对已有结果/签批的处置口径）。裁决落地后，上述两个用例应**翻正为行为测试**，而不是被绕过。

## 4. 过程中发现并修复的三个真实实现缺陷

这三个都不是测试数据问题，是写第一版时踩到规则引擎真实语义后暴露的：

| # | 缺陷 | 后果 | 修法 |
|---|---|---|---|
| 1 | `evaluateRows` 传 `profileRevision=null` | 规则用 `equals` 与 `appliedRevision` 比对，**每一次写都会被判 PROFILE_CHANGED 而整批拒绝** | 透传请求体声明值（六个 DTO 均携带该字段），并修正源码 Javadoc 里"null 会跳过比对"的错误表述 |
| 2 | 删除/清空候选传 `Position(0,0)` + 空 `clientRowKey` | `inLayout` 要求位置落在版图内且行键非空，**删除类接口必然全行 INVALID_CANDIDATES** | 重构为「先 `selectForUpdate` 取锁内真实位置 → 再构造候选 → 后判规则 → CAS」，行键按主键派生 `sample-row-<id>` |
| 3 | 单行删除的 `selectSampleForUpdate` 在守卫事务外 | `FOR UPDATE` 在事务外**不构成锁**，CAS 期望值可能来自过期快照 | 加锁与重验移入 `mutateOne`（守卫事务内）；事务外那次仅作快速拒绝与取设备号，Javadoc 如实标注 |

> 第 1 条尤其值得记住：`WorkbenchQueueRules` 的 Javadoc 声称 `profileRevision` 为 null 时跳过比对，**但实现是严格 `Objects.equals`**。注释与实现不符，按注释写必然全拒。
