## 3. 逐条展开

### Q-1　读侧是否与写侧同判 → **默认同判，契约先行**

- **依据（可复核）**：写侧判决链 `Impl:340`（可见性计数）→ `:344/:361-400`（归属判决）已经是权威口径；
  读侧只有 `xml:21-25` 的可见域，行自身的 `o.lab_id` 就是"归属"的唯一依据（`:156` 直接回填），
  这正是"把可见域当归属"的现状。默认建议要求的是**双条件并存**：可见域片段不得因追加判决而被删除或放宽。
- **落码形态（默认形状下，比 INT-12 §4.1 更小）**：
  1. 在 `getMonitorPolicy` 取到 `row` 之后、组装视图之前，仅当 `row != null && cultureId == null`
     时调用**现有** `requireDeviceOwnedByClaimedLab(monitorScopeKey(deviceKind, deviceId, null),
     deviceKind, deviceId, row.getLabId(), authUserId)`；
  2. 声明值必须取 `row.getLabId()`，**不得取查询参数/Body**（否则撞
     `M09DeviceLabFactSourceContractTest.java:295` 的"API14 面不出现 labId"禁令的立法本意：作用域由服务器推导）；
  3. 送判前对 `row.getLabId() == null`、`authUserId == null` 显式关闭（见 Q-6），不依赖推演；
  4. 估算 **6–10 行 + javadoc**，仍为单文件、零新增字段、零新增错误码、零 SQL、零 skeleton。
- **为什么不再需要"抽取返回 OWNED/NOT_FOUND/… 的判决内核"**：默认建议把失败形状定为 R3（对齐写侧），
  而写侧 `requireDeviceOwnedByClaimedLab` 本来就是 **void + 抛 `ManagementGuardRejectException`**，
  其映射码与文案（`:365-368`、`:386-392`）与 Q-2 的"对外与写侧一致"逐字相同，读口直接复用即可。
  内核抽取只在总控改裁 R1/R2（降级形状）时才必要——那属于推翻默认建议，需要重开裁决。
- **P-1 契约补齐（硬前置，不补齐不得落码）**：见 §4 草案。INT-12 §3 阻塞 ① 的性质没变：
  读侧同判是**改契约**，不是补实现；先在 API14 行落下条款，后端接线才有依据。

### Q-2　越域 / 错属的失败形状 → **默认 NOT_FOUND fail-closed**

- **依据**：写侧对"设备不存在""存在但不属于声明实验室""deviceKind 越出冻结 9 种"三类已经是
  **同码同文案**「作用域不存在或无权访问」（`Impl:365-368`、`:386-393`；提供方侧同口径见
  `M02DeviceConfigurationAdapter.java:46-48`）。默认建议 = 读侧沿用，不发明第二种形状。
- **好处**：`"BGA"` 这类越域种类的读写相反答案（INT-12 §2 的现行实例：读 `:785-814` 返回真实配置 vs
  写 `:1080-1093` 判 404）在默认形状下**自动闭合**，无需为越域种类另立规则（Q-2 的 C-2 子问被吸收）。
- **P-4 前端联动（必须派单，不能省）**：默认形状在一个已接线的只读 GET 上**新开 404 面**。
  契约里 UI07 的顺序是 `API14→API15`（`页面与接口契约.md:148`），且 `:163` 明确
  "API14/15 和 16 保持各自操作资格"——前端当前没有"读口 404"分支。本批禁改前端，
  故接线批派单必须显式含 UI07 处理项；未联动前该项登记 `BLOCKED_DEPLOY/前端联动未完成`，
  并按 AGENTS §13.4 要求浏览器验收后才可升层。
- **P-5 503 子裁决（默认可推翻，需总控点头）**：写侧在提供方缺失或事实源异常时按
  `RESOURCE_FACTS_UNAVAILABLE` 硬失败（`:369-373`、`:395-398`），立法理由是"绝不因裁判不可用而跳过校验照常落库"。
  读侧沿用即"GET 上出现 503"。取证两点供裁决：
  - 提供方 `M02DeviceConfigurationAdapter` 是同模块 `@Component`（`:64`），生产进程内恒在 ⇒
    读侧 503 实际只在事实源异常时出现，`@Autowired(required = false)` 的 null 分支基本只在单测装配中出现（`Impl:104-105`）；
  - 沿用 503 与写侧同族，**不新增错误码**（`RESOURCE_FACTS_UNAVAILABLE` 已存在）。
  若总控不接受 GET 上有 503，就必须显式裁"裁判不可用时照常返回行内容"（INT-12 的 R2），
  那等于把泄露窗口留在裁判不可用期间，属推翻默认，需要另写一条裁决。
- **明确不允许的写法**：把 404 文案写成"该设备不属于你/无权访问该设备"之类可区分存在性的表述，
  或在判决失败时返回 403（写侧词汇表里没有这一形状）。

### Q-3　CULTURE 是否一并反查 → **默认不搭车**

- **依据**：写侧 CULTURE 分支走的是**培养归属**（`Impl:326-339`：`selectCultureLabForRead`，
  不符时按 `INPUT_INVALID`「scope.labId 与培养所属实验室不一致」拒绝），与 CAP-I01 设备判决不同族；
  读侧要"一并反查"就必须在 GET 上引入 `INPUT_INVALID` 这种**泄露字段级差异**的形状，
  与 Q-2 的"不暴露存在/归属差异"直接冲突。
- **默认结论**：接线批只处理 `cultureId == null` 的 DEVICE 分支；CULTURE 读保持现状。
- **附带好处（收窄测试面）**：受影响读用例从 INT-12 §4.3 的"6 条中 3 条必改"精确化为
  **仅 3 条 DEVICE 有行用例**（`:785`、`:852`、`:863`），另 3 条不动且理由明确：
  - `:818`（CULTURE 作用域）— 默认不判 ⇒ 仍返回真实配置；
  - `:835`（无行）— `row == null` 不进判决 ⇒ 仍 UNKNOWN 同形；
  - `:875`（形状矩阵）— 校验短路零触库，早于判决（`Impl:121-134`，且该用例断言 `calls == 0`）。
- **明示残余不对称（登记，不闭）**：CULTURE 读不反查培养归属、写反查且不符即拒；写侧另有
  `monitorCultureBranchNeverAsksDeviceOwnership`（`:1151`）钉"CULTURE 不判设备"。
  这一不对称是默认建议的**后果**而非疏漏，应在契约条款里写清"CULTURE 作用域本批不做设备归属判决"（§4 草案已含）。

### Q-4　`allowedActions` 口径 → **默认整条不可见，不给 disabled**

- **依据**：现有 `allowedActions` 只表达**编辑权限裁剪**这一层（`M09WiredOfflineMonitorConfigContractTest:863`
  断言无编辑权限时为空），响应面无 disabled 语义；引入 disabled action 要改 skeleton 的 `M09-014.respFields`，
  属本批禁区，也会让前端把一个"看得到但必失败"的按钮留给用户（INT-12 的 C-3 困境）。
- **默认结论**：归属不符 → 404，无响应体 ⇒ 不存在"可点但必 404"的窗口，C-3 由形状本身闭合；
  `allowedActions` **不承担安全判决**，判决失败路径上不得返回任何 action 词。
- **P-6 同批测试改写**：`:863` 用例现在用越域种类 `"BGA"` 断言能读到 `TEMP_OFF`，默认形状下会命中
  Q-1/Q-2 的 404；改法是换冻结种类（如 `"AIR_PUMP"`，与写侧同源用例 `:955`、`:907` 同口径）
  并保留"权限裁剪"断言；另需新增"归属不符整条 404、响应无 allowedActions"负例。
  同理 `:785`、`:852` 两条必改（INT-12 §4.3 已列，本批确认坐标有效）。

### Q-5　存量错属行治理 → **默认不自动修复，排查先行/并行**

- **因果必须写进派单**：默认形状（Q-1 同判 + Q-2 硬 404）把错属行从"声明方可读、不可写"变为
  "**声明方读写皆不可**"；而真实归属方仍**不可见**（可见域过滤），且尝试首建会撞同一
  `uk_m09_monitor_scope`（DDL `:3807`）——`insertMonitorPolicyV2` 影响行数不为 1 时按
  `IllegalStateException` 整组回滚（`Impl:435`），不是用户可理解的错误码。
  ⇒ **INT-12 §2 的死路没有被读侧判决打开哪怕一寸**，反而多了一个"运维也看不到"的盲区。
- **默认结论**：接线批**不得**包含自动修复/改写 `lab_id` 的动作；先跑 §5 的只读排查 SQL 草案，
  产出报告项（存在性、条数、按 deviceKind 分布），真实执行与修复另开 SQL / 数据治理窗口，
  且写操作需总控批准。
- **排序要求（P-7）**：数据排查应与读侧接线**同批或先行**。若排在之后，接线上线期间新出现的 404
  将无法与真实故障区分（因为没人知道存量错属行有多少）。
- **层级**：`NOT_VERIFIED`——本批禁 SQL、未连库，是否存在此类行、多少条，均不可知。

### Q-6　`actorUserId` 取法 → **默认沿用当前登录用户，不新增 Port**

- **默认结论**：复用读口已有的会话三元组（`Impl:137-145`，`SecurityUtils.getLoginUser()` →
  `sysUser.userId` 即 SQL 的 `authUserId`）作为判决 `contextRef` 里的 actor；
  **不**为读侧引入 m01 `ActorContextPort` 消费，**不**新增取法。
  `contextRef` 拼装沿用写侧 `OWNERSHIP_PURPOSE + "|actor=" + actorUserId + "|scope=" + scopeKey`
  （`Impl:381`，常量 `:88`），purpose 仍为 `MONITOR_POLICY`，不新增 purpose 词汇（避免 M02 侧白名单扩展）。
- **结构性事实（供落码者知道默认建议其实近乎零成本）**：`authUserId == null` 时
  `<if test="authAdmin == null or !authAdmin">`（XML `:22`）会拼可见域片段，
  `ul.user_id = NULL` 恒不命中 ⇒ `row` 恒 null ⇒ 默认形态下判决根本不会被调用。
- **但落码要求显式判空**，不依赖上述推演（脏数据、片段条件改动、将来管理员分支重写都可能推翻它）：
  `authUserId == null` 或 `row.getLabId() == null` 直接按 Q-2 的 `NOT_FOUND` 关闭，
  并把该处置写进 javadoc（INT-12 §4.1 第 4 点在这一形状下即"硬失败"，不再是二选一）。
- **P-8 门禁缺口（诚实发现，非 INT-12 错误）**：消费面唯一禁令 `M09DeviceLabFactSourceContractTest:235`
  扫描的是 `service.port.m02` 字符串（同文件 `:229` 扫描 + `:235` 断言恰一个文件；`:219` 的 provider 面禁令同理只钉 M02 Port 方法名）。

  建议接线批顺手把该用例的扫描面扩到 `service.port.m01`（或改成扫 `Port` 类型注入清单），
  使 Q-6 的默认建议有门禁而不只有措辞。

每表 `lab_id bigint NOT NULL`；路由同源见 `M02DeviceConfigurationAdapter.java:50-56`、`:204-231`）：

| --- | --- | --- |

| BENCH_CONTROLLER | lab_bench_reactor_controller | connection_id |

草案（以 AIR_PUMP 为例，其余 8 种替换种类名、表名与主键列；也可 UNION ALL 后按 deviceKind 汇总）：

```sql
-- 只读排查：DEVICE 作用域行中，声明 lab_id 与设备权威行 lab_id 不一致（或设备已不存在）的行
SELECT p.policy_id,
       p.device_kind,
       p.device_id,
       p.lab_id  AS claimed_lab_id,
       d.air_pump_id AS matched_instance_id,
       d.lab_id  AS fact_lab_id,
       p.scope_key
  FROM alarm_monitor_policy p
  LEFT JOIN lab_air_pump d ON d.air_pump_id = p.device_id
 WHERE p.culture_id IS NULL
   AND p.device_kind = 'AIR_PUMP'
   AND (d.air_pump_id IS NULL OR d.lab_id <> p.lab_id);
```

治理批须分开统计两类，因为处置不同：`d.air_pump_id IS NULL`（设备已不存在/悬挂行）
与 `d.lab_id <> p.lab_id`（错属行，真实归属方存在且可识别）。
