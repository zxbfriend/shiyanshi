## 2. 口径结论（全部由基线 DDL 与提供方 SQL 取证，不靠推测）

| 词 | 职责层 | 权威取值域 | 基线落点 |
| --- | --- | --- | --- |
| `resultStatus` | **结果级状态** | `idle/stored/pending/testing/tested/uploaded/signed/reviewed/voided/timeout/exception/cancelled` | `01-完整建表.sql:2423`（`det_result.result_status` 注释枚举） |
| `itemOutcome` | **检测项级产出状态** | `VALUE/ERROR/NO_MEASUREMENT/UNKNOWN` | `ck_m05_rx_outcome`（同文件 2511）；05 契约 4.1 |
| `evidenceQuality` | **版本快照层证据质量** | VERIFIED/UNVERIFIED 一族 | **无数据库列**（`evidence_quality` 在基线出现 0 次），只存在于 `ResultSnapshot` JSON 顶层键；生产者 M05-048 仍 501 |
| `sign_chain_state` | **结果级签批链状态** | `VERIFIED/UNVERIFIED/CONFLICT` | `ck_m05_sign_chain`（同文件 2474），基线中唯一以 VERIFIED 为域值的列 |

四条判定：

1. **`itemOutcome=VALUE` 是「该项有可用检测值」的准入词**，不表示结果正常或异常，也不承载签批可信度；
   它不是任何质量词或状态词的别名（4.1 的「不属于本域」排除句原样保留）。
2. **「必须VERIFIED」不属 `resultStatus` 层**：基线 `result_status` 十二值里没有 VERIFIED，
   提供方窄读 SQL（`M05DetectionResultFactsMapper.xml:29-30`）把 `result_status` 与 `sign_chain_state`
   分列取出，两词在事实源上就是两列。词表上 VERIFIED 只可能落在 `sign_chain_state` 或 `evidenceQuality`。
3. **三层不得互相顶替**：`VALUE` 不能替代状态准入，`evidenceQuality` 不能充当项级产出，
   `resultStatus` 不能拿来表达证据可信度。
4. **M07 `confirmation.source_snapshot.status` 叶只承载来源结果级状态**（M05 来源取 `resultStatus` 域值，
   手工来源显示『已检测（手工登记）』）；VERIFIED 一族不得写入该叶，也不得混入 `itemOutcome` 判断。

## 3. 本批新发现：`sign_chain_state` 门与需求原文的相容性（这条以前没登记；2026-10-07 复审 P1 更正）

`ck_m05_sign_ptr_state`（基线 2476）对 `sign_chain_state='VERIFIED'` 给的是**两条**支路：

1. `result_status IN ('signed','reviewed','voided')` 配相应的非空动作指针；
2. `result_status NOT IN ('signed','reviewed','voided')` 且 `active_sign_id/active_review_id/active_void_id`
   三者全为 NULL。

⇒ 更正：本批初稿曾写成「VERIFIED 必须与 signed/reviewed/voided 之一配对，因此按 `sign_chain_state`
施加会使同段「允许 tested/uploaded」的允许面直接作废」，该推论只读了第 1 支、漏掉第 2 支，**不成立**。
`VERIFIED` 与 `tested/uploaded` 并存是合法的（第 2 支）；真正排除 tested/uploaded 的是
**`VERIFIED` 且 `active_sign_id` 非空**这一组合，而「是否连带要求 `active_sign_id` 非空」并不由
「是否施加 VERIFIED」自动决定。

⇒ 残余问题不是「VERIFIED 是哪个词」，而是两句可分别裁决的口径：
**（a）M07 准入是否施加 `sign_chain_state='VERIFIED'`**；**（b）施加时是否连带要求 `active_sign_id` 非空**。
只有 (b) 为「是」才会收窄 07 §2 的 tested/uploaded 允许面；(a) 单独为「是」不会。
不施加 (a) ⇒ 应改按快照层 `evidenceQuality` 或删除该门。本批不替总控挑，只把这两句摆成可直接裁决的形状。
后续任何消费方若采用 `VERIFIED`，都必须显式说明是否要求 `active_sign_id` 非空，否则口径不完整。

### F-1 夹具口径瑕疵（已登记，不改数据；2026-10-07 复审 P1 归因更正）

`M07ConfirmationWriteGuardedContractTest:371` 的夹具给 `resultStatus='uploaded'` +
`signChainState='VERIFIED'` + 末尾 `activeSignId=9101L`，违法原因是那个**非空签批指针**（第 2 支要求三个
指针全 NULL），不是 `uploaded`+`VERIFIED` 词表组合本身——该组合在第 2 支下合法。
对照：`M07ConfirmationSourceFieldGapContractTest:632` 的干跑夹具同键给 `activeSignId=null`，
是一行合法数据。保留前者是因为该用例刻意取「最有利前提」，且把它改成合法值只会削弱而不加强
阻塞结论（503 与失败理由都不依赖该指针）。已在该用例 Javadoc 登记同一口径。
