## 1. 结论

INT-04 落地的 `DetectionResultPort` 三个方法中，M07 侧唯一能在**不改 Port 签名、不改 SQL 基线、
不翻 skeleton wired、不依赖前端**的前提下闭合的消费点是：

- **M07-017 `GET /run/cultures/{id}/glucose-candidates`**（`RunCultureController.listGlucoseCandidates`
  → `RunCultureApplicationApplicationServiceImpl.listGlucoseCandidates`，perm `run:glucose:query`）

原因：该方法在 INT-04 之前就已经按冻结契约完整接线（游标分页 + 上海业务日过滤 + Port 缺失失败关闭），
skeleton 台账里 `wired=true`。它此前"结构性恒 503"的唯一原因是提供方零实现，而不是 M07 缺代码。
INT-04 提供方一到位，该 503 就自然不再可达，因此"接线"动作本身无需新增调用代码。

但真实提供方到位后，两条冻结契约口径立刻暴露成 M07 侧的实现偏差（只在提供方存在时才可观测），
本批按 TDD 修复了它们：

| 偏差 | 契约依据 | 修复 |
| --- | --- | --- |
| 候选列表未按"检测完成时刻倒序、ID 倒序"输出（提供方按 `result_id` 升序键集分页，消费方原样透传页序） | `docs/详细设计/07-补液运行与任务执行/计量确认与补液计算契约.md` §2 | 新增 `orderedPortCandidates(...)`，Port 候选集按 `completedAt` 瞬时倒序、同刻按数值化 `sourceId` 倒序 |
| 本日已确认候选被 `confirmed=false` 标注（原为 `!contains(...)`），消费方无法据此短路重复确认，且与 VO 字段语义相反 | `GlucoseCandidateView.confirmed` 登记："是否已确认（Boolean）：本日每类最多一个 CONFIRMED" | 改为 `confirmedKeys.contains(...)`，即保留候选并以 `confirmed=true` 标注；同步更正方法 Javadoc 中"已确认键的候选不再返回"的错误描述 |

其余候选点均**确认阻塞、未硬接**（§3）。

## 2. 两个 M07 消费方的证据核查

### 2.1 `RunCultureApplicationApplicationServiceImpl`（M07-017）

- 注入：`@Autowired(required = false) private DetectionResultPort detectionResultPort;`（L105），缺省为 null。
- 唯一调用：`detectionResultPort.queryEligibleResults(portQuery)`（L341），步长 `PORT_PAGE_LIMIT = 200`，
  最多 `PORT_PAGE_MAX_ROUNDS = 8` 轮，游标为空或超过轮数一律失败关闭。
- Port 缺失路径：L329-333 抛 `DEPENDENCY_UNAVAILABLE`（503）。
- INT-04 前：该 503 在任何运行时配置下都必然发生（PKG-00 登记 M07 侧 DET-I07 无提供方实现）。
  INT-04 后：`M05DetectionResultAdapter` 成为真实 Bean 可选组件，结构性阻塞解除。
- 仍缺：M07 运行页面、SDK 封装、路由、菜单与权限（`run:glucose:query`）都未落地 → 该接口 `NO_UI`，
  只能到 `CONTRACT_TESTED`。

### 2.2 `RunMeasurementApplicationApplicationServiceImpl`（M07-018/M07-019）

- 注入同样是可选 Port（L205），唯一调用 `getResultRevision(query)`（L738，M05 来源确认冻结源快照）。
- Port 缺失路径：L729-733 `DEPENDENCY_UNAVAILABLE`。
- **INT-04 不解除该处阻塞**：Port 到位后代码继续无条件失败关闭（L739-743），因为冻结的
  `ResultRevisionView` 只有 `resultId/revision/schemaVersion/value/observedAt/irreversible` 六个字段，
  而 `ConfirmationSourceSnapshot` 需要 `itemId/analyteKind/shortName/rawText/numericGl/originalUnit/
  completedAt/sampleNo/position`。MANUAL 分支（L695-726）逐项列出了这些叶子，M05 分支一个都拿不到。
- `value` 是 `det_result_revision.content_snapshot` 原文，其 JSON 叶子形状在权威文档中未定义
  （`CorrectionSnapshot` 明确登记"快照完整叶子未逐项展开，设计文档未定义，待补充"），
  在 M07 里解析它等于自造字段口径 → **不接**。
- M07-018（`POST /run/manual-results`）不读 M05 Port，与 INT-04 无关。

## 5. 新增契约测试覆盖的口径

`M07GlucoseCandidateDetectionPortWiringContractTest` 用 `new M05DetectionResultAdapter(factsMapper, new ObjectMapper())`
作为真实提供方注入真实 `RunCultureApplicationApplicationServiceImpl`（仅 Mapper 为替身），断言：

1. `realProviderServesEligibleCandidatesWithoutDependencyShortCircuit`：提供方在位时候选真实可读，不再 503；输出顺序按 §2 契约。
2. `consumerQueryShapePassesProviderInputValidation`：消费方查询形状能过提供方入参校验（`cultureId` 数字串、`limit=201`、首轮无游标、sample/itemCode 为空）。
3. `providerAbsentStillFailsClosed`：Port 未装配仍 `DEPENDENCY_UNAVAILABLE`，不因 INT-04 放松失败关闭。
4. `providerRejectionPropagatesInsteadOfBecomingEmptyCandidateList`：提供方对快照身份的拒绝原样上抛，不吞成空候选列表。
5. `portCandidateLoopFollowsRealProviderCursorAcrossPages`：跨页游标真实跟随（201 行首页 → 发 200 行 + 次页 1 行 = 201 候选），并锁定提供方游标语义为"最后一条**已发出**行"。
6. `portCandidatesAreOrderedByCompletionTimeDescThenIdDesc`：完成时刻倒序、同刻 ID 倒序。
7. `alreadyConfirmedCandidateIsFlaggedConfirmed`：本日已确认候选保留且 `confirmed=true`。
8. `providerSourcedLeavesStayNullWhenFrozenViewHasNoField`：冻结视图无字段的叶子保持 `null`，不伪造 GLC/LAC 归类、单位与样品位。

TDD 过程：RED 先跑（8 例，3 failures + 1 error），其中
`List.of(null, ...)` NPE、跨页游标期望值（`3201` 应为已发出的 `3200`）、快照拼接身份的错误码
（实际 `RESULT_PROJECTION_UNAVAILABLE`，提供方按行自校验，非 `RESULT_VERSION_CONFLICT`）三处为**测试侧
规格写错**，看失败原因后更正测试；`ordering` 与 `confirmed` 两处为**生产侧真实偏差**，据此写 GREEN。

## 6. 仍需裁决事项（P0/P1/P2）

- **P1｜DET-I06 字段缺口（M07-019 M05 来源确认）**：扩 `ResultRevisionView` 字段，还是新增
  M05 侧"候选明细读口"（返回 item 级 analyte 身份 + 数值 + 单位 + 样品位）？前者动 PKG-00 冻结签名，
  后者动签名快照门禁。本批两条都没动。M07-018/019 在此之前保持 503。
- **P1｜`content_snapshot` JSON 叶子形状**：`接收事件与结果字段字典` 与 `CorrectionSnapshot` 都未定义，
  需要 M05 Owner 冻结 schema（含单位、analyte 前缀归类规则来源），否则计量契约 §2 的 GLC/LAC 规则无法实现。
- **P2｜M07-015 培养物料平衡**：与 Port 无关，需要单独的字段/主数据/状态机裁决；未翻 501。
- **P2｜M07 前端与菜单**：`run:glucose:query` 等权限、运行页面与 SDK 封装缺失，属 `NO_UI`/`BLOCKED_MENU`；
  本批按工单禁改前端与菜单权限。
- **P2｜`det_result_revision` 写入路径验收**：提供方读侧已契约测试，但真实版本快照需要 INT-04 登记的
  `BLOCKED_DATA`（缺可写入 revision 的测试主数据）才能在 HTTP 层验证。
- **P2｜`onlyConfirmed=true` 分支排序未按契约 §2（work5 复审发现）**：本批只把"检测完成时刻倒序、
  ID 倒序"应用于 Port 候选集，已确认分支仍沿用 `run_confirmation` 的 confirmation_id 升序投影。
  原因是已确认候选的 `completedAt` 来自 `source_snapshot` 解析，可能为 null（"快照缺值不伪造"口径），
  直接排序需要先把 null 的兜底位置裁清楚（置尾、置首还是失败关闭）。本批**不改行为**，留待后续裁决；
  对应实现边界已登记在 `RunCultureApplicationApplicationServiceImpl` 的 M07-017 Javadoc。
