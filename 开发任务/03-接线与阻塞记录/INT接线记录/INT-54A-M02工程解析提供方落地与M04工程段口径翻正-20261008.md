## 0. 结论速览

- 现场缺陷复现链成立：补液方案内容必然声明 `applicability.modelRefs`，而 `EngineeringResolutionPort` 此前**零提供方**，`EngineeringBundleFactory` 只能失败关闭 → 保存返回 503。
- 本批落 M02 自有提供方 `M02EngineeringResolutionAdapter`（ENG-I01／SVC-M02-E01，**MODEL 作用域**），并把 M04 工程段的状态映射按《工程版本固定与评审收尾》§1 翻正：**合法资料缺项 = 400 CONTENT_INVALID 带 `path=code`**，503 只留给事实源本身不可信。
- 业务后果（如实）：型号无已核准工程资料时，保存补液方案从"503 网络故障"变为"400 且指明缺哪一项"；**要保存成功仍必须先有 M02 已核准（VERIFIED）工程资料版本**，而核准写口 M02-226 尚未接线 → 用户可见症状的天花板仍是 `BLOCKED_DATA`，本批不宣称页面可保存。
- 层级：`IMPLEMENTED` + `CONTRACT_TESTED`。HTTP、浏览器、真实库、Nacos/网关一律 `NOT_VERIFIED`。
- 全模块闸门：`mvn -o -pl futurefab-modules/futurefab-system -am test` → **3916 tests / 0 failures / 0 errors / 0 skipped，BUILD SUCCESS**（本批前基线 3889）。

### 8.1 G-54-1 证据链与判定

### 8.2 INSTANCE 作用域判别式更正（本批自查发现的真实缺陷）

- 缺陷：`M02EngineeringResolutionAdapter.requireScope` 原要求 INSTANCE 同时携带 `modelKind/modelId`，缺席即 400。这与 `工程资料维护与解析逐接口契约.md §1`「INSTANCE必须kind/deviceKind/deviceId，modelKind/modelId为null」和 `收尾契约 §2`「INSTANCE必须只有设备对有效」直接冲突，会把**契约合法**的实例解析请求判成 400；M02-225 读侧（同模块、同判别式）早已按互斥校验（"MODEL作用域不得同时传实例键"/"INSTANCE作用域不得同时传型号键"），本类是唯一的异类。
- 更正：`requireScope` 改为判别式互斥 —— MODEL 必须带型号对且不得带设备对，INSTANCE 必须带设备对且不得带型号对；`parseRequiredId` 只解析该种类应给的 ID。型号版本由 M02 依实例身份自行取得，不接受调用方转述。
- 影响面：MODEL 路径行为不变（M04 保存只发型号对，是本批唯一已交付分支）；INSTANCE 路径在形状合法时仍是 503 失败关闭，错误码与语义不变。
- 测试：`instanceScopeWithoutModelPairIsInputInvalid`（钉住错误口径）删除，替换为 `instanceScopeWithModelPairIsInputInvalid`、`modelScopeWithDevicePairIsInputInvalid`、`instanceScopeWithoutDevicePairIsInputInvalid` 三条互斥/缺键钉桩；`instanceScopeFailsClosedWithoutTouchingProfileTable` 夹具改为契约合法的"只带设备对"。适配器契约套件 20 → 22 例。
- 注释同步：`EngineeringScope` 类注释纠正"INSTANCE 时五个判别字段均须构成唯一、互斥的作用域"这一错误表述，并登记 `modelKind` 值域依据。
