## 2. 核查②③：通讯设备种类集合 × M03/M05/M07 现有 Port

### 2.1 通讯侧设备种类集合（被判定对象）

`LabCommunicationApplicationServiceImpl.java:113-124` 冻结且**仅**三项：

```
DETECTOR        → lab_detector.detector_id        → /labs/labdetector
FLOOR_SCALE     → lab_floor_scale.scale_id        → /labs/floorscale
DOWNSTREAM_DEVICE → lab_downstream_device.device_id → /labs/downstreamdevice
```

名单外一律 400（`:1044`、`:252`），读侧孤儿行（`device_kind` 为 NULL 或在名单外）不可达（`:419`）。依据 `通讯与设备公共契约.md:13-19`（2026-10-01 需求方裁决，扩名单须另行裁决）。

### 2.2 本批新证据一：**"引用"在数据库层不存在 comm_id 反向引用面**

全量实测（不是转引）：

| 检索范围 | 命中 |
| --- | --- |
| `docs/开发基线/01-完整建表.sql` 全文件 `comm_id` | **恰好 2 处**，均在 `lab_communication` 自身：`:895` 主键列、`:931` `PRIMARY KEY` |
| `src/main/resources/mapper/**/*.xml` 全量 `comm_id` | **全部落在 `LabCommunicationMapper.xml` 内**（35 处命中，无一在他表 SQL） |

⇒ **他表没有一列引用通讯配置行**。因此 COM-05 的"引用"不可能靠"扫 `comm_id` 外键"得出——那样得到的**必然**是零计数，正落入 66 号 D-3 与 `通讯逐接口字段与加载回执.md:141` 双重禁止的形态（该句原文：「**不把依赖未知误判为空闲**」）。

⇒ 唯一的判定路径是**按设备身份 `(device_kind, device_id)` 去问业务模块"这台设备的通讯配置是否正被活动使用"**。这条路径正是 §2.3 证明不存在的那条。

### 2.3 本批新证据二：M05/M07 出向端口**没有任何**按设备身份的入参

`service/port/` 实测清单（含目录计数，反空转下限已钉进测试）：

| 目录 | 端口数 | 是否存在"入参同时携带 `deviceKind` 与 `deviceId`"的请求类型 |
| --- | --- | --- |
| `service/port/m05/` | **3**（`DetectionDeadlineFactsPort`／`DetectionExecutionPort`／`DetectionResultPort`） | **0 命中** |
| `service/port/m07/` | **11** | **0 命中** |
| `service/port/m03/` | **11** | 恰 **4** 类：`DeviceUsageQuery`（API02）、`BindingResolveQuery`、`BindingRevisionCommand`、`BindingRevisionPageQuery` |

扫描方式：`PathMatchingResourcePatternResolver` 按 classpath 实际 `.class` 产物扫描端口接口，逐方法入参沿父类链查声明字段 `deviceKind` **且** `deviceId`（§A5、§A6 已钉，端口数低于下限即红＝防扫描本身失效）。

三点关键判定：

1. **M05 的三个端口都不是设备在用事实源**。它们按 deadline／执行／结果语义组织，没有"这台检测设备当前是否有待检／检测中"这一读法。M07 的 11 个端口里最接近的是 `CultureExecutionBarrierPort`（按 cultureId，非按设备）——66 号 §2.4 的该实测结论**今日仍成立**。
2. **M03 的四类命中不能解锁删除**：
   - `DeviceUsageQuery` 是 API02 的入参，其**提供方正处于 503**（§2.4），且它的语义是"这台**设备**能不能删/改"（`operation=DELETE` 针对设备实例），不是"这条**通讯配置**是否被活动使用"——两者判定对象不同层；
   - `BindingResolveQuery`／`BindingRevisionCommand`／`BindingRevisionPageQuery` 属**在线业务观测绑定修订族**，入参除设备身份外还要求 `channelCode` 与 `observedAt`（观测通道与时刻），语义是"某时刻某通道的绑定解析/修订"，**不构成删除准入判定**，且 `在线业务观测存储与查询契约.md:49`（2026-10-04 需求方裁决）明文禁止通讯词表／M03 DDL 词表／§8 十二类 DeviceRef 三套词表**合并、互转或共用**——所以"借绑定族的设备身份入参凑一个读法"这条路被裁决直接封死。
3. **值域在 DDL 层就不相交**（66 号 D-3 复算仍成立）：M03 自有表 `res_culture`／`res_culture_occupancy` 的 `device_kind` CHECK 限 `INTEGRATED_REACTOR/CULTURE_CONTAINER/BENCH_CONTROLLER`（`01-完整建表.sql:1808/:1929`），与通讯白名单三项**零交集**。一条 `device_kind='DETECTOR'` 的占用行根本无法插入 ⇒ 走 M03 判通讯设备在用，结果恒为"零命中"。

### 2.4 M03-API02 提供方仍是失败关闭的 503（不是"可用但没接"）

`service/impl/port/m03/ResourceUsageGuardAdapter.java`：

- `:83-89` 类 Javadoc：API02 本批次**不实现**的理由（03 详细设计 §7.9 原文要求矩阵由 M02/M07 冻结；取 503 而非 501，因为 501 会被消费方读成"可以跳过检查"）；
- `:215` 起：`checkDeviceUsage(DeviceUsageQuery)` 进入即抛 `ManagementGuardRejectException(DEPENDENCY_UNAVAILABLE)`，零取数交互。

本批 §A4 已在**真实生产适配器**上钉该事实（`new ResourceUsageGuardAdapter(mock, mock)` ＋ 构造 `DeviceUsageQuery(DETECTOR, 2001, DELETE, changedFields=[])` ⇒ 断言 `DEPENDENCY_UNAVAILABLE` ＋ `verifyNoInteractions(factsMapper)`），同时 `ResourceUsageGuardAdapterContractTest:449-458` 既有断言一条未放宽。

⇒ **"接上 API02 就解锁 M02-210"这条路本批再次确认为否决项**（66 号 §5.3、10-05 M03 裁决包 G3 同口径）：即便 API02 落码，它给的是设备实例层判定，且 M03 对通讯三类设备恒零命中。

### 2.5 M02 内部确有"设备在用"窄读法先例——但不足以支撑 COM-05

这一点是本次复核最容易被误读为"其实可以落码"的地方，必须写清：

`LabDetectorMapper.xml:231-243` `countBlockingM05Usage`：按 `detector_id` 统计三片活跃占用——

```
det_sample      : queue_status in ('pending','testing') or occupancy_state in ('RESERVED','RUNNING','UNKNOWN')
det_result      : result_status in ('pending','testing')
det_dispatch_log: dispatch_lifecycle in ('PREPARED','INVOKING','UNKNOWN')
```

消费方：`LabDetectorApplicationServiceImpl.java:290`（M02-044 删除预检）、`:447`（M02-045 批量预检）——**已接线的设备删除口在用**。同型先例还有 `LabIntegratedReactorMapper#countBlockingCultures`（`:502/:718`）与 `LabBenchReactorMapper#countBlockingCultures`（`:500`）。

**为什么它仍然不够（四条，任一独立充分）：**

| 缺口 | 说明 |
| --- | --- |
| **判定对象错位** | 它回答"这台**检测设备**能不能删"；M02-210 要回答"这**几条通讯配置**能不能删"。一台设备只有一个有效通讯行（`(device_kind,device_id)` 唯一，`m02_active` 生成列），看似可平移，但"设备在用"与"该设备的通讯身份被活动使用"是两层语义（COM-05 还额外要求"删除不发送停机命令"，即判定的是**使用**而非**存在**）。把前者当后者是**自造映射**，需裁决。 |
| **只覆盖三类中的 DETECTOR 一类** | `FLOOR_SCALE`（地秤）与 `DOWNSTREAM_DEVICE`（下游设备）**没有对应的在用窄读 SQL**。`03-详细设计.md:769` 原文把"地秤"明确划给 M07（"主设备账本不替代M07对泵、**地秤**、连接单元和未知设备命令结果的检查"）；`lab_downstream_device` 侧在 M02 现有盘点里连引用计数都没有（M02-076 恒 `allowed=true`）。⇒ 三类设备里两类无来源，落码即"半边有判据、半边按空闲放行"。 |
| **跨模块私表直读的先例本身是历史遗留** | `countBlockingM05Usage` 读的是 `det_*`（M05 私表），写在 `LabDetectorMapper.xml`（M02 侧）。这是 M02 已接线口上的既成事实，**不构成可推广的授权**；AGENTS.md §8 明令跨模块不得直读他模块 Mapper/内部表。把同一形态再复制一份到通讯删除，等于把缺陷制度化。 |
| **不满足 COM-05 的"全量"** | COM-05 与 §3 契约要求"**整批**引用/活动使用重验，**全成全败**"。现有窄读法只能逐个 `detector_id` 计数，没有批形态，也没有"任一 ID 事实不可得 ⇒ 整批 503"的表达位；`apply_state`（`01-完整建表.sql:927`）是**适配器加载回执**状态（NOT_CONFIGURED/PENDING/APPLIED/FAILED/UNKNOWN），不是业务在用状态，**不得**拿来充当在用判据。 |

⇒ 正确表述不是"检测设备在用不可知"，而是：**COM-05 对通讯配置对象所需的判定条件集合尚未冻结，且其权威来源（按设备询问 M05/M07）在 Port 面上不存在。**
