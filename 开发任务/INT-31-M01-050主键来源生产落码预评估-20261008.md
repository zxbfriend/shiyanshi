## 0. 一句话结论

**不能进入生产落码批**，且理由不是"设计未定"这类笼统措辞，而是四条各自成立的实测前提：

1. **窄批没有落点**：`createUser` 的方法体逐字等于一条 501 抛掷（`UserApplicationServiceImpl:305-307`），应用服务里 `userMapper.insertUser(` 0 处、`SysUserPostMapper` 依赖不存在、`ManagementOperation.USR03` 0 处 ⇒ 在抛掷前生成 `userId` 只能是一段**没有读者的死代码**，不是"窄一点的落码"。
2. **R-1（创建期授权版本）阻塞完整落码**：AUTH-I01 准备侧在 `USER_CREATE` 场景强制 `targetUserId==null`（`M02LabAuthorizationAdapter:498-500`），而 `targetUserId` 逐字参与授权版本摘要（`:1027`）；AUTH-I02 要求非空 ID（`:207`）并无条件用真实 ID 重算比对（`:231-236`）⇒ 创建期不存在任何可与真实 ID 配对的合法期望版本，落码即**按构造 409**。
3. **R-3（守卫分类）阻塞完整落码并越出本任务文件面**：AUTH-I02 的第一条语句就是 `requireActiveGuardTransaction("AUTH-I02")`（`:202`），先于命令空值判断，且回调来源被精确限定为 USR03/USR04（`:213-214`）⇒ 没有守卫事务就没有授权写入；而开守卫事务需要改 `SysUserController#add`（今天 `:345-347` 无 `@ManagementGuardedWrite`／无 `WriteMeta`／无 `@RequestHeader`），**Controller 不在 INT-31 允许修改面内**。
4. **R-2（初始口令）阻塞完整落码，后果是失败放开**：`sys_user.password` 是 `NULL DEFAULT ''`（`01-完整建表.sql:186`，非 `NOT NULL`），而 `insertUser` 把口令列与值都写成条件列（`SysUserMapper.xml:171/:190`）⇒ 未裁口令来源时落码不会在库里失败，而是**静默落一条空口令行**；应用服务今天 `encryptPassword`／`setPassword` 各 0 处，没有任何可复用的口令装配路径。

**R-4（菜单与权限种子）不是落码阻塞**：`system:user:add` 与 `sys_menu` 播种实测仍 0 行，它只封 `BROWSER_VERIFIED` 层级（见 §6）。

本批不实现新增用户、不翻 `wired`、不改任何既有断言；M01-050 仍是显式 501 骨架。本批提升的是**"不可落码"这一结论的可检出性**，不提升任何验证层级。

## 4. 三项落码阻塞的精确归因（不含"设计未定"式表述）

### 4.1 R-1 创建期授权版本——主因，归属 M02 owner／总控（Q-a／Q-c）

86 号 §7.2 五步静态链，本批逐环重测（新增类 ②，`:169`）：

1. 契约要求 Body 带 `labAuthorizationVersion` 且"必填由 USR07 取得"（`00-全接口契约骨架清单.md:1008` 起 M01-050 明细行、`:1020` 依赖接口＝USR07）；
2. `M02LabAuthorizationAdapter:172` → `:496`（禁带分支 `:498-500`）：`USER_CREATE` 场景**禁止**携带 `targetUserId`；
3. `:185` 准备侧把该 `null` 目标直接送进摘要，`direct` 也按 `targetUserId == null ? List.of()` 取空（`:178`，`leaderLabIds` 同型 `:179`）；
4. `authorizationVersion:1021-1028` 的事实集逐字含 `factSet.put("targetUserId", targetUserId == null ? null : Long.toString(targetUserId))` ⇒ **`null` 与真实 ID 必得不同摘要**，差异与既有授权行无关；
5. `:200-236` 替换侧要求 `requireDecimalId(command.getTargetUserId())`、`requireOpaqueVersion(command.getExpectedAuthorizationVersion())`，并以真实 ID 重算后 `if (!currentVersion.equals(expectedVersion))`（该方法体内该比对**恰 1 处、无条件**）抛 `VERSION_CONFLICT`；
6. 旁路不存在：`requireOpaqueVersion:695-703` 拒绝 `null`／空串 ⇒ Q-a 的"零行用户哨兵版本"今天**没有被实现**。

⇒ 后果：显式生成的 `userId` 一旦被 AUTH-I02 消费就必然 409；不被消费则回到 §3.1 的死代码。二者不可兼得，必须先裁 Q-a（M02 侧给 create 场景合法版本口径）／Q-b（创建期不写授权，需改 FROZEN UserSave＋前端＋基线）／Q-c（同事务两段式，需裁创建者是否须同时持 `system:user:edit`）。

**层级声明**：本节是源码结构证明，不是运行期 409 实测 ⇒ `NOT_VERIFIED`（服务链未起，未发过任何请求）。既有 `M02LabAuthorizationPortProviderContractTest:440` 只钉住"create 场景按空事实集合参与摘要"与"编辑场景含事实时不同摘要"，**没有**隔离出"`targetUserId` 单独成分导致 create 期不可配对"这一环；本批补的正是这一环，且不改 M02 任何文件。

### 4.2 R-3 `add` 口守卫分类——共因，且越出本任务允许文件面

新增类 ③（`:226`）钉住适配器侧两环（不重复证据类 `:217` 已钉的 Controller 无守卫形状）：

- `replaceUserLabs` 折叠空白后以 `{ requireActiveGuardTransaction("AUTH-I02");` **开场**，且该断言位置早于 `if (command == null)` ⇒ 守卫事务是入参校验之前提；
- `requireGuardCallbackSource("AUTH-I02", requestId, UserLabOperation.USER_CREATE, UserLabOperation.USER_UPDATE)` ⇒ 端口设计上**预期**被 USR03 创建流程调用，但调用方必须先落在守卫回调里；
- 应用服务 `ManagementOperation.USR03` 0 处 ⇒ 今天没有这个事务上下文；
- 同型约束见 `removeUserLabs:379-381`（`AUTH-I03` 同样要求守卫事务）⇒ 守卫事务前提是端口惯例，不是 AUTH-I02 单点写法。

⇒ 后果：仅改应用服务无法满足端口前提。INT-21 §4 的最小文件面本就含 `SysUserController.java`，而 INT-31 任务书未授权改 Controller。因此本项按 **越界＋待裁** 双重阻塞登记（G1 逐口守卫分类仍待裁，见 86 号 §2／§7.5）。

### 4.3 R-2 初始口令——共因，后果为失败放开（M01 可自主裁，但不与主键同批默认）

新增类 ④（`:272`）钉"落码后果"这一环（既有 `M01PasswordChainBlockedEvidenceContractTest:320` 已钉"基线未播 `sys.user.initPassword`"，本批不复制）：

- `01-完整建表.sql:202` `is_initial_password char(1) NOT NULL DEFAULT '1'` ⇒ 行会带着"初始口令标记"落库，而口令本身是空串。

⇒ 后果：口令未裁就落码，产出的是**空口令用户**而不是失败。按 AGENTS.md §10（缺客户参数须标 `BLOCKED_INPUT`，不得编造默认值），这属于"落码本身不可接受"，不是"落码后待核验"。
