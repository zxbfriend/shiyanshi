## 0. 背景与阻塞链（一句话）

当前 guarded write 恒 `401 SESSION_INVALID` 的根因 = `sys_user_auth_state` 初始为空且登录链路（`M01-001`）从未调用 I01/I02 写入激活行；同时守卫执行器因 `ActorContextPort`（SEC-I01）与 `ManagementAuditHook` 缺失而 fail-closed（见 43 §0、07-PRE-01B-R1）。**批次 1 的最小闭环 = 让登录真正写入激活行 + 守卫可解析可信操作者 + 审计可落库**，从而把 guarded write 从"恒 401"推进到"版本校验/写成功"。

## 1. X-Auth-Proof 算法（建议 HMAC-SHA256）

- **建议值**：`HMAC-SHA256`（64 位小写 hex，已与 `NormalizedPayloadHasher` 的 HMAC-SHA256 实现一致）。
- **出处**：`NormalizedPayloadHasher` 已实现并固定 HMAC-SHA256（07 报告 §6）；43 §5 #2 指出契约与详细设计此前未冻结算法。
- **待确认**：是否接受 HMAC-SHA256（而非 SHA512 等）；如接受，本项即闭环，无需改代码（实现已对齐）。

## 2. proof 有效期（建议 5 分钟）

- **建议值**：`futurefab.auth.proof-ttl-seconds = 300`。
- **出处**：43 §5 #3 注明契约与详细设计已冻结有效期为 **5 分钟**（即 300s）。
- **待确认**：确认 300s 为最终值（"到期时刻"是否允许下方时钟漂移容差另行裁决，见第 3 项）。

## 3. 时钟偏差容差（建议 30 秒）

- **建议值**：`futurefab.auth.proof-clock-skew-seconds = 30`。
- **用途**：校验 `X-Auth-Proof` 签发时间/过期边界时，允许 ±30s 的服务器间时钟漂移，避免严格边界下偶发误拒。
- **出处**：43 §5 #3 提出的未决项——"到期时刻是否允许时钟漂移容差"；建议以 30s 容差收口。
- **待确认**：是否接受 30s 容差；以及"过期后挑战上下文（Redis 5 分钟）是否同源"——建议 I01 挑战上下文与 proof 有效期同源（同 Redis、同 5 分钟），一并确认。

## 4. dev 密钥策略（配置读取 + 缺失 fail-fast + 不自动随机）

- **建议策略**：
  1. 从配置 `futurefab.auth.proof-hmac-key` 读取 HMAC 服务器密钥；
  2. **缺失/空白即 fail-fast**（应用启动失败，`InitializingBean.afterPropertiesSet` 抛 `IllegalStateException`，与 `NormalizedPayloadHasher` 既有的 `receipt-hmac-key` 启动校验口径一致）；
  3. **绝不自动随机生成**密钥（避免"伪安全"默认密钥）。
- **出处**：43 §5 #1/#4（密钥来源与 dev 临时密钥未决）；07 报告 §7（启动 fail-fast、源码无默认密钥值）。
- **待确认**：dev/test 是否统一用受控配置键（占位固定值）而非"自动生成临时密钥"；prod 必须经受控密钥注入（KMS 或 Nacos 加密配置），不落地明文默认值。

## 5. 配置项清单（3 项，新增于 Nacos application-dev.yml / 对应环境）

| 配置键 | 含义 | 建议默认值 | 缺失行为 |
|---|---|---|---|
| `futurefab.auth.proof-hmac-key` | HMAC 服务器密钥 | 无（必填） | 启动失败（fail-fast） |
| `futurefab.auth.proof-ttl-seconds` | proof 有效期 | `300` | 缺失可给 300 兜底 **或** fail-fast（建议与 key 同口径 fail-fast，避免静默默认） |
| `futurefab.auth.proof-clock-skew-seconds` | 时钟漂移容差 | `30` | 缺失给 0（严格）或 fail-fast（建议 fail-fast） |

- **出处**：43 §5 #1（密钥存放位置/来源）；本清单在第 1/2/3 项给出建议值。
- **待确认**：三项是否全部"缺失即 fail-fast"（更安全的口径），还是仅 key 强制、其余给默认值。

## 6. 密钥轮换（批次 1 单 active key；keyId/多 key 后续）

- **建议**：批次 1 仅支持**单一 active key**（无 keyId、无多 key 并行）；轮换机制（`keyId` 字段、旧 key 宽限期、双 key 验签）留待后续批次。
- **出处**：43 §5 #2 指出"密钥轮换/版本机制"未冻结。
- **待确认**：是否接受批次 1 不做轮换（单 key）；如需预留 `keyId` 字段，是否在本批次引入（建议不引入，保持最小）。

## 7. 口令政策（批次 1 不扩大实现复杂政策/历史密码）

- **建议**：批次 1 **不实现**口令历史表（`sys_user_password_history`）校验、复杂口令政策（长度/字符类/过期强制改密等）；仅做登录链路 I01/I02 与 `current_session_key`/`session_version` 写入。口令改密完成（I04）与历史/政策属**批次 2**（43 §4）。
- **出处**：43 §5 #5（口令历史表/政策参数来源未决）；43 §4 将 I04/改密吊销列为批次 2。
- **待确认**：确认批次 1 仅打通会话激活、不触碰口令历史/复杂政策；并确认批次 2 所需的 `sys_user_password_history` 表与全局口令政策参数（validDays/remindDays 来源）届时由谁初始化。

## 8. 批次 1 目标（最小闭环定义）

- **链路**：`M01-001` 登录重写 —— 调 I01 `verifyCredential`（密码/锁定/失败计数 + 签发 authProof）→ 调 I02 `activateSession`（写 `sys_user_auth_state.current_session_key` / `session_version+1` / 登录计数 / 登录日志）→ **I02 成功后才签 Redis 会话 + JWT**；Redis 写入失败**不放行**（避免"有激活行却无可用会话"半状态）。
- **数据**：`sys_user_auth_state` 不改建表，仅补 `SysUserAuthStateMapper/XML` 写语句（upsert，因首登行可能不存在）；初始为空保持，未登录用户无行是正确语义（43 §6）。
- **验收**：guarded write 从 `401 SESSION_INVALID` 推进到"会话复核通过 → 进入管理写版本校验（`MANAGEMENT_CONFLICT`/权限判定）/ 写成功"；旧 token 场景仍 `401 SESSION_REPLACED`。
- **配套（守卫基座）**：`ActorContextPort`（SEC-I01 适配器）落地 + `ManagementAuditHook` 真实实现（sys_data_change_log 白名单快照/脱敏），解除守卫执行器 fail-closed（43 §0 + 07 报告 §5/§6）。
- **非目标**：登出/续期（I05/I03）、改密完成（I04）、失败计数/锁定策略化与压测——均属批次 2（43 §4）。

## 9. 仍需用户/项目负责人确认的 BLOCKED_INPUT（开工会前必须拍板）

| # | 待确认项 | 本清单建议 | 不确认的后果 |
|---|---|---|---|
| B1 | HMAC 算法是否锁定 HMAC-SHA256 | 是 | 算法不定 → I01/I02 验签实现无法定稿 |
| B2 | proof TTL = 300s 是否最终 | 是 | 有效期不定 → 安全窗口与 Redis 同源策略无法对齐 |
| B3 | 时钟漂移容差 = 30s 是否接受 | 是 | 严格边界可能误拒正常请求 |
| B4 | dev/prod 密钥均经 `futurefab.auth.proof-hmac-key` 受控注入，不自动生成 | 是 | 否则 dev 跑不通登录、prod 有伪安全默认值风险 |
| B5 | 三项配置缺失是否一律 fail-fast | 建议是 | 静默默认可能绕过安全校验 |
| B6 | 批次 1 单 active key、不做 keyId/轮换 | 是 | 否则引入未定义的轮换语义 |
| B7 | 批次 1 不实现口令历史/复杂政策（I04 延后） | 是 | 否则扩大批次 1 范围、引入未决表/参数 |
| B8 | I01 挑战上下文与 proof 有效期同源（同 Redis/5 分钟） | 建议是 | 否则过期后挑战状态不一致 |
| B9 | Redis 写入失败 → 不签 JWT（fail-closed） | 是（43 §3 已定） | 否则出现半状态会话 |

> 除 B9 已在 43 §3 设计为 fail-closed 外，B1–B8 均需用户/项目负责人在开工前确认；任一未决即落入 43 报告的 BLOCKED_INPUT 红线，**开工后会返工**。
