## 1. 改了什么

### 1.1 应用服务（`ResBatchApplicationServiceImpl.insertResBatch`）

原抛点 `throw new SkeletonNotImplementedException("M03-011")`（:160-162）改为真实守卫写链路，
形态完全照搬同模块已接通的 M03-004（`ResProjectApplicationServiceImpl.insertResProject`）契约方言模式：

| 段落 | 落点 | 语义 |
| --- | --- | --- |
| 守卫前形态校验 | `requireBatchCode/requireAlias/optionalIdList/requireCreateChangeSet/requireMutationChangeSetsEmpty` | 零触库、不消耗回执、不推进管理版本 |
| 守卫入口 | `guardExecutor.execute(ManagementOperation.M03_011.getCode(), writeMeta, payload, callback)` | 幂等回执 ＋ SYSTEM 版本 CAS ＋ 单一 `TransactionTemplate` |
| 事务内回调 | `writeCreate` | Q23 判权 → 编号查重 → Q24/Q29 逐条培养复核 → 四段固定写序原子写入 |
| 回执装配 | `createReceipt` | results[0]=批次、results[i+1] 对应 `cultureCreates[i]` |

关键顺序语义（AGENTS §8「全量校验后执行」）：**全部复核先于任何写入**，
因此一个越权或已占用的培养行不会留下已落库的批次。
写序固定为 **批次 → 负责人 → 培养 → RESERVED 占用**，任一影响行数 ≠ 1 直接抛出，由守卫单一事务整体回滚。
应用服务层**未声明事务注解**（`applicationServiceDeclaresNoTransactionalAnnotation` 钉桩）。

## 3. 实现期发现并修正的两个真实缺陷

均由契约测试暴露，非测试放宽：

1. **Q29 实验室操作权从未被调用**。首版实现的 Javadoc 声明按 Q29 核验 `canOperateLab`，但回调里实际没调用——
   `cultureCreateRequiresLabOperateRightOnTopOfProjectIdentity` 用例直接失败（"Expected ... to be thrown, but nothing was thrown"）。
   已补 `requireLabOperate`，并加 `q23RejectionHappensBeforeAnyCultureFactIsRead` 钉住判权顺序。
2. **幂等重放会返回一批新培养ID**。守卫回执 `result_json` 只冻结 `applied/id/affectedIds/managementRevision` 四键，
   重放时回调不执行，若回执读冻结计划里"重新生成的主键"就会破坏 §7.2「重试返回首次结果」。
   已改为回执**只以 `outcome.affectedIds` 为权威**（首跑即本次写入值，重放由 `result_json` 复原），
   并显式断言"回执培养ID按提交顺序升序"这一位次回填前提，不默认成立。

## 8. 门面补齐（同批追加，2026-10-12）

### 8.1 为什么补

§5.1 登记的过渡态（台账已 `wired:true`、运行态仍走 legacy 载体）在本次补充任务中获得授权并消除。
`ResBatchController#add` 若不改，`POST /resource/batch` 在运行期**进不了**本次实现的守卫链路——
应用服务与 Mapper 链路再完整也只是无生产调用方的孤链，`wired:true` 属台账先行。

### 8.2 改了什么（照搬 M03-004 先例，`ResProjectController#add`，commit `ed77deb6`）

改造后（`controller/ResBatchController.java:185-193`）：

```java
@RequiresPermissions("resource:batch:add")
@ManagementGuardedWrite
@PostMapping(value = "")
public AjaxResult add(@RequestBody BatchCreateCommand batchCreateCommand, WriteMeta writeMeta)
{
    batchCreateCommand.setRequestId(writeMeta.getRequestId());
    batchCreateCommand.setManagementRevision(writeMeta.getManagementRevision());
    return success(resBatchApplicationService.insertResBatch(batchCreateCommand));
}
```

- 入参由 legacy 实体 `ResBatch` 改为契约命令 `com.futurefab.system.domain.dto.m03.BatchCreateCommand`；
- 加 `@ManagementGuardedWrite`（`service.guard.ManagementGuardedWrite`）；
- 加 `WriteMeta` 形参（`common.core.meta.WriteMeta`），把 `X-Request-Id` / `X-Management-Revision`
  两个请求头值透传进命令（**头为权威，Body 同名字段被覆盖**）；
- 返回由 `toAjax(...)` 改为 `success(...)`，直接回 `BatchMutationResult`；
- **权限注解保持 `resource:batch:add` 不变**（与台账 `perm` 字段一致）；
- 新增 import：`WriteMeta`、`ManagementGuardedWrite`、`BatchCreateCommand`。

### 8.3 ⚠️ 移除 `@Log`（按先例，避免一次新增两条操作日志）

原 `add` 挂 `@Log(title = "批次", businessType = BusinessType.INSERT)`，**本次已移除**。

理由（M03-004 先例原文）：守卫审计钩子与业务写在**同一个事务**内写 `sys_oper_log` ＋
`sys_data_change_log`；再挂 `@Log` 会让 `@Log` 的 AOP 切面**另外**写一条操作日志，

### 8.6 连带改写的契约测试（M03 范围内）

1. **`M03SkeletonContractTest.dialectAndDelegationDetectorsThemselvesWork()`——必须换载体，否则会"靠巧合通过"**

   `methodBody` 会把两者方法体拼接取证，同样不唯一。`export` 为单重载、与新增口无关、委派唯一可复核。

2. **`M03BatchCreateWiredContractTest`——补 3 条门面取证用例**（原 27 条 → 现 30 条）：
