## 6. 推荐结论

1. **不建议第9步业务开发前重命名；本事项不阻断第9步**（属长期可读性优化，非契约/正确性缺陷）。
2. 第9步补偿措施（可执行）：
   - ① 在 33 增补 §7『模块编号↔业务名权威映射表』（按 §4 校正后口径），任务包标题/文件命名强制带模块中文名；
   - ② 各开发包触碰某 m0x 包时顺手补 `package-info.java`（Javadoc 模块正式名+职责+interface_id 段）——零移动获得 IDE 可读性；
   - ③ 任务包范围一律以 `interface_id` 圈定（33 规则 1/4），包名仅作落点不作检索主键；
   - ④ 26 清单 md 视图由 gen26.js 增派模块名标题行（不新造权威）。
3. 若未来确要重命名：时点=对应模块真实实现验收稳定后；单元=单模块 IDE refactor；形态=推荐 **C**（保留编号前缀使包↔interface_id 映射可机检）；范围=§9 六件套一体同步（Java 源码＋测试＋skeleton JSON＋26/00 清单＋生成器＋门禁），缺一不得合入；00 冻结清单勘误与提交策略须用户裁决。

## 7. 禁止事项（任何时点执行重命名均适用）

1. 不允许只改部分包名（半 m0x 半业务名 ⇒ 门禁判定双口径并存，必漏检）。
2. 不允许只改 Java 不改 skeleton JSON（`SkeletonEngine` 按资源 FQCN 反射定位，不同步即 463 红）。
3. 不允许只改文档不改生成器（生成链再生会把 m0x 写回，形成回潮性双源漂移）。
4. 不允许让包名和 `interface_id` 映射失联（任何形态须保留可机检的 M0x↔包对应，并配反例 fixture 证明门禁可检出——命中 0 不得称已验证）。
