## 1. 前端 SDK list 解包模板

### 1.1 契约形状

新系统冻结分页出口返回的是 `AjaxResult.data = PageResult<Row>`，管理版本在**顶层外壳**：

```jsonc
{
  "code": 200,
  "msg": "操作成功",
  "requestId": "…",              // RequestMetadataResponseAdvice 注入
  "managementRevision": "0",     // @CurrentManagementRevision 出口才有
  "data": { "pageNum": 1, "pageSize": 10, "rows": [ … ], "total": 3 }
}
```

旧若依是顶层 `rows`/`total`（`TableDataInfo`）。**直接沿用旧形状会把有数据的列表判成"无数据"并中断滚动追加**——这是 T2 第一条实测失败。

### 1.2 单一实现，禁止页面复制解包逻辑

`packages/sdk-smp-api/src/page.ts`：

```ts
pageRows<Row>(result)              // 不需要管理版本的列表
pageRowsWithRevision<Row>(result)  // 守卫写配套的列表：额外透出顶层 managementRevision
dataList<Row>(result)              // 树 / 下拉等不分页出口
collectAllPages(loadPage, base, { maxRows })  // 必须拿满候选时按白名单翻页 + 熔断
```

模块 API 里的写法（`packages/sdk-smp-api/src/dictType.ts:86-91`）：

```ts
list: (query: DictTypePageQuery, signal?: AbortSignal) =>
  request<ApiResult<PageData<DictTypeRow>>>("/system/dict/type/list", {
    query: { ...query },
    signal,
  }).then(pageRowsWithRevision),
```

### 1.3 类型与参数规则

- `ApiResult` 必须声明 `requestId?` 与 `managementRevision?: string | number`（`sdk-smp-api/src/types.ts:3-13`）。缺字段不会报错，只会让守卫写静默拿不到期望版本。
- `total` 按 `number | string` 兼容（后端 `long` 序列化成十进制字符串是既定口径）。
- 行类型用**冻结 Row**，不复制实体：建改信息收在 `audit`，按钮可用性用服务端每次重算的 `allowedActions`，前端不再自行判权限串（`dictType.ts:38-49`）。`isEditable='N'` 的行后端不给 EDIT，前端也就不会显示修改入口。
- 查询参数按 §17.1 平铺：`keyword` / `beginDate` / `endDate` / `status`；旧 `searchKey`、`params[beginTime]`、`orderByColumn` 已废弃（字典批次第二次实测失败点）。日期成对提交——只传单边等于不过滤（`use-dict-type-list.ts:40-45`）。
- `pageSize` 只允许 10/20/50/100，后端直接拒绝其他值；需要全量候选时用 `collectAllPages`，禁止 `pageSize=999/2000`。
- 详情按主键路径取资源，ID 是**十进制字符串**，不做 `Number()` 拆箱。

### 1.4 列表 hook 模板（滚动分页 + 版本持有）

`use-dict-type-list.ts` 的形状，后续页面照搬：

```ts
const submittedQuery = ref<Conditions>();              // undefined = 还没查询过，页面据此延迟挂表格
const managementRevision = ref<string>();              // 外壳或守卫写回执携带的当前版本

function fetchPage({ query, pageNum, pageSize, signal }) {
  const page = await api.list({ ...query, pageNum, pageSize }, signal);
  if (page.managementRevision != null) managementRevision.value = page.managementRevision;
  return page;
}
function applyWrittenRevision(revision?: string | number) {   // 写回执是当前版本权威来源
  if (revision != null && revision !== "") managementRevision.value = String(revision);
}
```

- 草稿条件只在"查询/重置"时替换已提交快照；触底追加沿用快照（否则改一个字就把在途翻页条件换掉）。
- `search()` 每次给**新对象**：`SmpScrollGrid` 靠浅层替换重载第一屏。
- 页面把版本透传给编辑器：`<XEditor :revision="managementRevision" @saved="onSaved" />`，`onSaved` 里先 `applyWrittenRevision(rev)` 再 `reload()`。

## 2. 守卫写（PRE-01B）前端模板

### 2.1 请求头：Header 是唯一权威

```ts
function writeHeaders(meta?: WriteMeta): Record<string, string> {
  const headers: Record<string, string> = { "X-Request-Id": meta?.requestId ?? requestId() };
  if (meta?.revision != null && meta.revision !== "")
    headers["X-Management-Revision"] = String(meta.revision);
  return headers;
}

save: (data: XFields & { id?: Id }, meta?: WriteMeta) =>
  request<ApiResult>(`/system/<module>/<resource>`, {
    method: data.id == null ? "POST" : "PUT",
    data,
    headers: writeHeaders(meta),
  }),
```

`requestId()` 见 `sdk-smp-api/src/requestid.ts`（`crypto.randomUUID`，非安全上下文回退时间戳+随机）。

- **不要**把 `requestId`/`managementRevision` 塞进 Body：后端 `WriteMetaArgumentResolver` 只认 Header，Controller 再用 Header 值覆盖 Body 自报值（`SysDictTypeController.java:124-125`）。契约测试专门构造了 `"requestId":"HACKED"` 的 Body 来证明覆盖生效（`M01WiredWriteDictTypeContractTest.java:756-774`）。
- 缺 `X-Management-Revision` → **400 `INPUT_INVALID`**，不进业务；非法 requestId → 400。前端不能"缺版本就不发头"地绕过，必须保证发得出值（见 2.2）。

### 2.2 编辑器侧：期望版本 + 同一会话复用 requestId

`dict-type-editor.vue:157-171` 的三件套，后续页面照搬：

```ts
/** 正常路径用列表外壳透传的 props.revision；缺失或本地已判定过期时补一次单页读取取当前版本。 */
async function ensureRevision(): Promise<string | undefined> {
  const cached = props.revision;
  if (cached != null && cached !== "" && !revisionStale) return cached;
  return (await api.list({ pageNum: 1, pageSize: 10 })).managementRevision;
}

/** 同一弹窗会话复用 requestId：失败重试命中同一幂等键，由后端回执决定重放还是拒绝。 */
function writeMeta(revision?: string): WriteMeta {
  if (!writeRequestId) writeRequestId = requestId();
  return { requestId: writeRequestId, revision };
}
```

`show()` 打开时必须 `writeRequestId = undefined; revisionStale = false;` 复位。

### 2.3 409 统一提示与恢复

```ts
function isRevisionConflict(e: unknown) { return e instanceof ApiError && e.code === 409; }
function conflictMessage(e: unknown) {
  if (isRevisionConflict(e)) { revisionStale = true; return t("<ns>.<entity>SaveConflict"); }
  return errorMessage(e);
}
```

- 冲突提示 key 固定一句话："数据已被他人修改，请刷新后重试"（`settings-dict.dictTypeSaveConflict` / `dictDataSaveConflict`），不暴露后端异常名。
- 置 `revisionStale` 后**下一次**保存会走 `ensureRevision()` 补读，不需要额外弹窗。
- 409 有两类，都是 409，都不要重试同一 requestId 之外的动作：
  - `MANAGEMENT_CONFLICT`：期望版本落后，响应带 `currentManagementRevision`；
  - `REQUEST_CONFLICT`：同 requestId 不同内容（指纹不符）。
- 幂等重放是安全的：同 requestId 同内容返回**原回执**（原 `objectId`、原提交版本），不二次落库——所以"保存失败后用户再点一次保存"必须复用 requestId，不得重新生成。

### 2.4 写回执回填（MutationResult）

后端返回 `data = MutationResult{ applied, requestId, managementRevision, objectId }`，顶层外壳同样回显提交后版本。前端两步都不能省：

1. `emit("saved", result.managementRevision)` → 列表页 `applyWrittenRevision` 覆盖本地版本；
2. `reload()` 刷新列表，读回服务端派生列（如 `custom_<id>` 生成的类型键、`audit`、`allowedActions`）。

保存失败时**不得**乐观更新本地版本或本地行；状态类字段要回退到原值（见 §6.4 停用确认的 `revertStatus`/退回口径）。

## 3. 后端 Controller 模板

```java
/** 读：分页与详情都要标 @CurrentManagementRevision，作为受管写期望版本的契约来源。 */
@RequiresPermissions("system:<x>:list")
@CurrentManagementRevision
@GetMapping("/list")
public AjaxResult list(XPageQuery query) { return success(xApplicationService.pageXs(query)); }

@RequiresPermissions("system:<x>:query")
@CurrentManagementRevision
@GetMapping(value = "/{id}")
public AjaxResult getInfo(@PathVariable("id") String id) { … }

/** 写：@ManagementGuardedWrite + WriteMeta 形参 + 三属性全关的 @Log。 */
@ManagementGuardedWrite
@Log(title = "字典类型", businessType = BusinessType.INSERT, recordSuccess = false,
        isSaveRequestData = false, isSaveResponseData = false)
@RequiresPermissions("system:<x>:add")
@PostMapping
public AjaxResult add(@RequestBody XCreateCommand command, WriteMeta writeMeta) {
    command.setRequestId(writeMeta.getRequestId());
    command.setManagementRevision(writeMeta.getManagementRevision());
    return success(xApplicationService.createX(command)); }
```

规则与踩过的坑：

1. **`@CurrentManagementRevision` 只标查询出口**。守卫写出口标它会直接被注解语义拒绝（`CurrentManagementRevision` 只允许 QUERY_CURRENT），也不能"顺手"标到未登记出口——未标注出口必须**没有** `managementRevision` 字段，伪造版本比缺字段更糟（`M01WiredReadContractTest.java:1086-1089` 断言 tree 出口 `doesNotExist()`）。
2. **`WriteMeta` 用形参接**，由 `WriteMetaArgumentResolver` 从 Header 解析；Body 自报值一律被覆盖（上面 124-125 两行是契约要求，不是可选写法）。
3. **`@Log` 三属性必须关**：`LogAspect` 在 501 时也会写 `sys_oper_log`（外部副作用），守卫链路已在同事务内写审计；不关就是双写。canonical 入口也不要把 `@Log` 当审计用。
4. **不发明签名**：`BLK-03` 之类未冻结的跨模块 Port 不做检查也不伪造通过（`DictTypeApplicationServiceImpl.java:178-179` 的口径写明"不做 DICT_KEY_IN_USE 检查"）。缺客户参数按 `BLOCKED_INPUT` 标注，不编默认值。
5. **旧路由不要顺手改**。未登记旧路由（导出、`check*Unique`、`DELETE /{ids}`、`refreshCache`、`optionselect`）处置归 TASK-ROUTE；字典批次有门禁测试逐条锁定这些注解与实现调用不变（`M01WiredWriteDictTypeContractTest.java:850-855`、`M01DictSkeletonContractTest.java:265-272,369-376`）。改了门禁就红，且会把未评审的写能力"顺带"接上公网。
6. Controller 只做鉴权/参数/映射，不编排 Mapper（AGENTS.md §8）。

## 4. 后端应用服务模板

参照 `DictTypeApplicationServiceImpl.java`（同构实现还有 `SysConfigController` M01-068/069、`SysDeptController` M01-019/020 等，可交叉比对）。

### 4.1 骨架顺序（每个写方法一致）

```java
public MutationResult createX(XCreateCommand command) {
    if (command == null) throw reject(INPUT_INVALID, "请求体不能为空");
    String name = required(command.getName(), NAME_MAX, "名称");      // ① 形态校验（守卫外）
    String code = optionalType(command.getCode());
    String status = requiredStatus(command.getStatus());
    WriteMeta writeMeta = new WriteMeta(command.getRequestId(), command.getManagementRevision());
    ObjectNode payload = payload(name, code, status, remark);          // ② 规范化幂等载荷
    GuardExecutionResult execution = guardExecutor.execute(            // ③ 交给守卫
        ManagementOperation.XX02.getCode(), writeMeta, payload,
        actor -> writeCreate(name, code, status, remark, actor));      // ④ 守卫事务内回调
    return receipt(execution, writeMeta.getRequestId());               // ⑤ 回执 → MutationResult
}
```

### 4.2 校验分两层，位置不能换

- **形态校验在守卫外**：必填、长度上限、枚举取值、ID 必须 `^[1-9][0-9]*$`。失败报 `INPUT_INVALID`，**零 DB touch**（契约测试专门断言这点：`malformedBodiesAreRejectedBeforeGuardWithZeroDbTouch`）。
- **落库判定在守卫事务内回调里**：存在性 `NOT_FOUND`、内置只读 `READ_ONLY_FIELD`、双唯一 `NAME_CONFLICT`/`CODE_CONFLICT`。放在守卫外就会与并发写产生 TOCTOU。
- 唯一性是"名称全局唯一 + 类型键唯一"两个**独立域**，更新时各自排除自身（`writeUpdate` :276-287）。缺省与显式同值要走同一判定分支。
- 写影响行数必须显式校验：`if (service.updateX(row) != 1) throw new IllegalStateException(...)`，靠守卫事务整体回滚，不留半提交（:297-300）。

### 4.3 服务端派生列：客户端一律不得赋值

| 列 | 口径 | 出处 |
|---|---|---|
| 主键 | 雪花 `snowflakeId.nextId()`，Body 带 ID 的新增请求要拒绝 | :239、契约测试 `createKeepsExplicitTypeAndRejectsClientDictId` |
| 缺省类型键 | `custom_<dictId>` 服务端生成 | :240 |
| `isEditable` | 新增固定 `Y`；更新保留库内原值 | :246,294 |
| `createBy`/`updateBy` | 取可信 `ActorContext.getActorName()`，不取客户端值 | :248,296 |
| 字典键变化的级联 | 复用既有 Service（缓存与 `sys_dict_data.dict_type` 级联口径一致），不直连 `DictUtils`、不建第二套写路径 | :249,297 |

### 4.4 幂等载荷（payload）白名单——最容易做错的一处

```java
/** 幂等四元组之规范化载荷：白名单 = 客户端可提交的业务字段。 */
private ObjectNode payload(String dictName, String dictType, String status, String remark) {
    ObjectNode node = objectMapper.createObjectNode();
    node.put("dictName", dictName);
    putNullable(node, "dictType", dictType);   // 缺省写 null 键，不省略键
    node.put("status", status);
    putNullable(node, "remark", remark);
    return node;
}
```

- 排除服务端推导列（主键、`isEditable`）与全部审计列：否则"同一请求"每次指纹都不同，重放判不了。
- **可缺省字段必须显式写 null 键**（`putNullable`），且缺省值要在进指纹**之前**归一（状态缺省 `"0"`、字符串 trim）。字典批次实测：`dictType` 缺省请求与"显式同值"请求必须识别为同一幂等请求，否则第二次点击保存会撞 `REQUEST_CONFLICT`（:334-348，测试 `idempotencyFingerprintCoversOnlyWhitelistedSaveFields`）。
- 更新场景要把主键也 `payload.put("dictId", Long.toString(id))`（:198），使同 requestId 换目标被识别为不同内容。
- `ObjectMapper` 注入项目统一的，不自行 `new`；`NormalizedPayloadHasher` 用生产实现，密钥来自配置。

### 4.5 守卫执行器：唯一的写入口

`ManagementGuardExecutor.execute` 已承载：可信 Actor 解析（fail-closed）→ 指纹 → `FOR UPDATE` 系统版本行 → 回执查找 → 期望版本 CAS → 业务回调 → `sys_oper_log`/`sys_data_change_log` 同事务审计 → CAS+1 → 回执 → 顶层 `putCommittedManagementRevision`。

接入时要知道的行为（都是本批次取证过的）：

- 身份解析在**守卫事务与 CAS 之前**：拒绝路径零写库、零版本推进。
- `ActorContextPort`/审计实现未接线时**显式抛 IllegalStateException**，不降级、不退回 `SecurityUtils.getUserId()`、不建第二套身份。
- 锁等待/超时/死锁 → `MANAGEMENT_BUSY`，语义是"提交结果未知，请用原 requestId 查询或重试，不要生成新的 requestId"；普通数据库故障**不得**伪装成 `MANAGEMENT_BUSY`（只 catch `PessimisticLockingFailureException`/`QueryTimeoutException`）。
- 审计快照字段白名单按 `21-TASK-GATES §1.4` 登记序渲染，缺列由写入端省略键；before/after 成对（新增只有 after）。
- 错误 → HTTP 状态映射不要自己写：`ManagementGuardExceptionHandler` 统一给 `status + errorCode + retryable (+ currentManagementRevision)`。**注意通道差异**：旧 `ServiceException` 走 `GlobalExceptionHandler` → HTTP 200 + `code:500` + 无 `errorCode`。同一页面存在两套错误通道时，前端 `errorMessage()` 要能兼容（这也是"错误提示不统一"的历史原因）。个别 canonical 映射不直观：`READ_ONLY_FIELD` 是 **400**，不是 403（`M01WiredWriteDictTypeContractTest.java:844`）。

### 4.6 读装配

分页/详情走统一的只读装配器（字典是 `M01ManagementQueryReader`），排序用冻结的 `coalesce(update_time, create_time) DESC`，软删过滤与 `allowedActions` 每次重算；外部 ID 以十进制字符串出参；查无统一 `NOT_FOUND`，不泄露对象是否存在。

## 5. 后端契约测试模板

一个页面一套 `M01WiredWrite<域>ContractTest`，命名与断言直接抄 `M01WiredWriteDictTypeContractTest`。必备用例（用户口径的 5 条 + 本批次补的 4 条）：

| # | 用例 | 关键断言 |
|---|---|---|
| 1 | 缺 `X-Management-Revision` | HTTP **400** + `errorCode=INPUT_INVALID` + `requestId` 回显 + **版本行未推进** |
| 2 | 旧 revision | HTTP **409** `MANAGEMENT_CONFLICT` + `currentManagementRevision` 回显 + `data` 不存在 + 零落库零回执 |
| 3 | 重放同回执 | 同 requestId 同内容：`applied=true`、`objectId` 与原提交一致、版本不再推进、表行数不变、审计仍 1 条 |
| 4 | 同 requestId 不同 payload | 409 `REQUEST_CONFLICT`、零落库、**零审计**、版本不变 |
| 5 | list/detail 外壳带 revision | 顶层 `managementRevision` 等于桩版本源；**`data=PageResult` 结构不变**（`data.rows[0].x`、`data.total`）；未标注出口 `managementRevision` **doesNotExist** |
| 6 | 形态校验在守卫外 | 非法 Body 逐条 `INPUT_INVALID`，断言内存表零访问 |
| 7 | Header 权威 | Body 自报 `requestId/managementRevision` 被 Header 覆盖 |
| 8 | 唯一性双域 | `NAME_CONFLICT` / `CODE_CONFLICT` 各自独立；更新排除自身；跨域组合仍成功 |
| 9 | 只读目标与派生列 | `isEditable=N` → `READ_ONLY_FIELD`；客户端 `isEditable/createBy` 不生效；`custom_<id>` 生成 |

## 6. 浏览器验收模板（逐页固定动线）

前置：前端 :5581（`/dev-api` → 网关 :9090 → system :9201）、真实登录态、目标库为开发基线安装出来的库。全程用 Network 面板取证，不用"看起来对了"。

### 6.1 查询

1. 首屏：`GET …/list?pageNum=1&pageSize=10` → 200，`data.rows` 有真实行、`data.total` 正确，顶层有 `managementRevision`。
2. 触底追加：页码递增、条件不变（改草稿不参与）、不重复行。
3. `keyword` 命中名称与键两域；`status` 单选；日期成对生效、单边等于不过滤；重置后空条件整个缺省。
4. 内置行（`isEditable=N`）无修改/删除入口（服务端 `allowedActions` 驱动）。

### 6.2 新增

1. 填最小必填保存 → Network 里确认**两个头都在**，且 Body 不含 `requestId/managementRevision`。
2. 响应：`code=200`、`data.applied=true`、`data.objectId` 是十进制字符串、`data.managementRevision` 比保存前大 1、顶层 `managementRevision` 同步。
3. 列表自动刷新并出现新行；服务端派生列（生成键、`audit`）回显正确。
4. 幂等：保存失败（断网/后端 500）后**再点一次保存**，仍是同一 `X-Request-Id`，结果只有一条记录、一条审计。

### 6.3 编辑

1. 打开弹窗即固化本会话 `requestId`；改派生列无入口。
2. 保存成功后 `objectId` 不变、版本 +1、读回一致。
3. 名称/键改成与他人重复 → 409 且界面显示业务提示，不显示后端异常名。

### 6.4 冲突与状态类交互

1. **双标签页冲突**：A/B 同开一条记录，B 先保存成功；A 再保存 → 409 `MANAGEMENT_CONFLICT`，提示"数据已被他人修改，请刷新后重试"；A 重试时补读到新版本后能成功。
2. 状态从正常改停用：**保存前**二次确认，取消则不发请求且表单退回原状态；确认才提交（`1→0` 不弹）。
3. 保存失败必须回退界面状态，不能显示"已停用"而库里还是启用。
4. 校验类预检接口（`check*Unique`）在重名时仍返回 200，由调用方判 `data`；同时保存路径要能兜住 409，两条通道都得工作。

### 6.5 只读旁证

- 详情页 URL 直达、深链、返回列表不丢条件。
- 控制台 0 error；失败请求有 canonical `errorCode`。
- 对照老系统逐字段核（项目口径：字段差按补齐）。

### 6.6 PKG-01 阻塞标注模板（当前真实状态）

当前环境**所有** PRE-01B 守卫写的真实 HTTP 路径不可通过：`sys_user_auth_state` 没有权威写入方（I01/I02 未接线），`M01ActorContextAdapter.verifySessionStillActive` 在 `state == null` 时 fail-closed → **401 `SESSION_INVALID`**「账号无已激活的认证状态记录」。拒绝发生在守卫事务与 CAS 之前，所以**零写库、零版本推进**，探针可安全单发。

因此每批页面验收结论必须写成下面这样，不得写"浏览器写验收通过"：

```markdown
- 列表 / 详情 / 树：HTTP + 浏览器读验收 **通过**
- 新增 / 修改 / 状态变更：单元与契约测试 **通过**；真实 HTTP/浏览器写验收 **未完成**，
  标记 **BLOCKED_BY_PKG01**（认证状态链，见 docs/开发任务/02-骨架验收与任务包/43-PKG-01-TP-M01-06开发拆包报告.md）
- 解除条件：TP-M01-06 按 I01→I02 正式接线（不得在登录链路直写 sys_user_auth_state 作最小修复）
```

判据区分：**机制未生效**（缺头 400、缺 auth_state 401、版本不符 409 都不出现，或 501 还在）vs **规则未配置**（链路通但数据/权限不满足）。401 没有后端日志行，只能靠响应 `msg` 分支区分，需要时用断点或一次性探针请求，不要反复重试。
