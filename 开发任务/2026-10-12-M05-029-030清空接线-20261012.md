# M05-029 / M05-030 检测工作台清空接线（2026-10-12）

## 0. 一句话结论

把「清空」从显式 501 变成真实守卫写：`WorkbenchQueueRules` 的 `Action.CLEAR` 判定来源由**无条件拒绝**改为**按锁内占用状态判定**（只有 `COMPLETED` 可清空），应用服务按删除同族骨架接线，落库只置 `clear_flag=1` 释放左侧位置、右侧检测结果与签批记录一律不动；台账 `skeleton-m05.json` 的 `M05-029`/`M05-030` 登记 `wired: true`。

状态层级：`IMPLEMENTED + CONTRACT_TESTED`；HTTP / 浏览器 / 真实 MySQL / 设备联调 / 生产验收一律 `NOT_VERIFIED`。

## 1. 规则判定怎么改的

### 1.1 改前

`WorkbenchQueueRules.java` 第 94 行原为：

```java
if (request.action() == Action.CLEAR) common.add(Reason.RESULT_POLICY_REQUIRED);
```

`common` 是**请求级**原因，会被原样复制进该请求**每一行**的 `RowDecision.reasons()`。因此只要动作是 `CLEAR`，整批必然全拒——无论这一行是已完成还是检测中。这正是 501 无法解除的根因。

### 1.2 注入点判断：不需要扩展输入结构

先读了 `WorkbenchQueueRules` 全文（无状态纯函数，不注入、不做 IO）与其现有输入：

- `Snapshot.occupants()` 已经携带**每行**的归一占用态 `Occupant.state()`（九个标签与 `State` 逐字同名，由 `M05WorkbenchSnapshotReader.occupant()` 从 `det_sample.occupancy_state` / `queue_status` 归一而来）；
- `evaluate()` 的 decisions 循环里已经按 `item.sampleId()` 取出该行的 `own = byId.get(...)`，并已在用 `own.state()` 做 `active()`、`NOT_OWNER`、`POSITION_OCCUPIED` 三项判断。

所以「当前占用状态」这个输入**本来就在手边**，唯一的错配是：**判定被放在了请求级，而事实是行级的**。因此本批**没有扩展 `Snapshot`/`Facts`/`Candidate` 任何结构**，纯函数性质保持不变（仍是 `public Evaluation evaluate(Snapshot, Request)`，无字段注入、无 Mapper、无 Port）。

### 1.3 改后（请求级 → 行级）

请求级只留下一个**标记**，逐行结论在 decisions 循环内给出：

```java
// WorkbenchQueueRules.evaluate()
final boolean clearByOccupancyState = request.action() == Action.CLEAR;
...
// decisions 循环内，else if (own != null) 分支中
if (clearByOccupancyState && own.state() != State.COMPLETED) reasons.add(Reason.RESULT_POLICY_REQUIRED);
```

要点：

1. **原行没有删除、没有绕过**。`RESULT_POLICY_REQUIRED` 仍是 `CLEAR` 的判定出口，原因码逐字未变；只是产生位置从请求级移到行级。
2. **判定来源变了**：从「动作＝CLEAR 就拒」变成「这一行不是 `COMPLETED` 就拒」。
3. **仍在规则引擎内**，没有挪到应用服务里自己判——应用服务不新增任何业务规则分支。
4. 保持纯函数：只读入参、无 IO、无注入、未引入任何新依赖。

### 1.4 副作用与连带修正

- `common` 里不再有 `CLEAR` 原因 ⇒ `DetSampleApplicationServiceImpl.requestDenied()` 里那段 `RESULT_POLICY_REQUIRED → CONFIRMATION_EXPIRED_OR_CHANGED("请先完成清空预检并提交确认凭据")` 映射**已成死代码且语义错误**（会误导为「缺令牌」）。已删除该分支，改为注释说明 `RESULT_POLICY_REQUIRED` 是行级原因、走 `requireAllAllowed` 的「该样品当前不允许清空：<原因码>」。
  保留它会有实质危害：若留在请求级分支，批量清空会把「部分行不可清空」误报成整批拒绝，与 M05-Q06「逐项跳过并反馈原因」冲突。
- `M05QueueRulesTest` 原 `duplicatesAndCrossColumnCandidatesAreRequestErrorsAndClearCannotReuseDelete` 中的 `assertReason(evaluate(snapshot, Action.CLEAR, candidate(1, 1)), RESULT_POLICY_REQUIRED)` 已翻正（见 §4）。

补充事实：

- 已完成样品清空时若该位置仍被遮挡（`POSITION_OCCLUDED`）或同列仍有 active 占用（`COLUMN_LOCKED`），仍按既有列锁/圆盘遮挡规则拒绝——这与设计「解除列锁与遮挡后可移除占位」一致，本批未放宽。
- `active()` 判定仍生效：`COMPLETED` 不属 active，故清空不受「设备已接受/运行中」那一层阻断；其余 active 态同时命中 `ACTIVE_REQUEST` 与 `RESULT_POLICY_REQUIRED` 两个原因码（去重后并存）。

## 3. 接线骨架（复用删除同族链路）

两口的链路与 012/013 完全同族，**照搬骨架、未另写一套**：

```
事务外：validateRowTarget / validateClearBatch   ← 只做快速拒绝 + 取设备号（审计载荷用）
        ⚠️ 此处 selectSampleForUpdate 在事务外，不构成锁
   ↓
守卫 ManagementGuardExecutor.execute(...)        ← 单一 TransactionTemplate 事务开始
   ↓
事务内：lockSample(id)  / 逐行 selectSampleForUpdate（按 sampleId 升序，锁序稳定）
        → candidateOf(own, ...)                  ← 位置取锁内真实行，不填 Position(0,0)、不传空行键
        → evaluateRows(Action.CLEAR, ...)        ← 锁内快照重算规则（见 §4 两道冻结门禁）
        → applyMutation → clearSamplePosition     ← CAS，影响行数 0 即整批回滚
        → 类型化审计（跳过项不进 affectedIds）
   ↓
守卫事务提交
```

要点核对：

- **`FOR UPDATE` 在守卫事务内**：`mutateOne`/`mutateBatch` 由守卫回调触发，位于 `ManagementGuardExecutor` 的 `TransactionTemplate` 内，`M05WorkbenchSnapshotReader.lock` 是 `Propagation.MANDATORY`，事务外调用会直接失败——结构上保证了「锁在事务内」。
- **候选位置取锁内真实位置**：`candidateOf(own, ...)` 从 `own.columnNo()/channelNo()` 取值；行键按主键派生 `sample-row-<id>`。
- **`profileRevision` 必须透传非 null**：规则用 `Objects.equals` 与锁内 `appliedRevision` 严格比对，null 也拒 ⇒ 走 `requireManagementRevision`/`trimToNull` 之外的透传路径，未声明与声明错同样按刷新重试，不当作「跳过比对」。
- **权限**：清空沿用 `detect:workbench:edit`（与 Controller `@RequiresPermissions` 同码），在守卫回调内经 `M05AccessSupport.requirePermission` 复算。
- **Controller**：加 `@ManagementGuardedWrite` + `WriteMeta` 头权威回填（`withClearHeaderMeta`/`withClearBatchHeaderMeta`），与 012/013 同制式；Body 的 requestId/managementRevision 一律被头解析值覆盖。
- **批量语义**：请求级不允许整批不写；行级不允许只跳过该行回 `SKIPPED` + 原因码（M05-Q06），审计只含实际清空的 sampleId（与 013/029/030 注册表的「跳过项不审」一致）。

## 5. 未验证项 / 仍需裁决

### 5.1 `Purpose.CLEAR` 令牌：**仍为零签发方**，且**不阻塞**清空

- 事实：`M05ConfirmationTokens.Purpose.CLEAR` 在 `src/main/java` **零签发、零校验方**（仅枚举存在）。唯一的签发位应��� M05-047/048 规则评估口（`WorkbenchRuleEvaluationResult.confirmationToken`，仅 action=CLEAR 时返回），该评估口目前未接线。
- 本批决定：**不校验该令牌**，并在 `validateClearBatch` 的 javadoc 中显式登记该缺口。
- 理由：若此时强制校验，令牌无从取得 ⇒ 该口将成为**永远拒绝**的假接线，比不校验更糟（AGENTS.md §13.8 禁止「把 501 换成空结果、假成功」）。
- 该断言已机器化：`M05WorkbenchAndReportBlockedEvidenceContractTest#clearEndpointsAreWiredWithStateBasedJudgementAndReleaseOnlyTheLeftSlot` 钉住「服务层不得出现 `Purpose.CLEAR`」，一旦有人补了半条令牌链即失败。
- **待 owner 裁决**：请求 DTO 的 `confirmationToken` 是否必填。若必填，须先接线 M05-047/048 评估口（产生令牌），再同批给 029/030 补校验。当前按「不阻塞」处理。
