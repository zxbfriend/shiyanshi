## 二、逐项任务

### BE-R01：补齐反应器 / 培养到在线指标的映射

**主责与现有能力**

- M02 主责观测映射及读数，M03 提供培养与设备绑定的有效区间。
- 已有 `GET /lab/observations/current`，权限 `lab:observation:query`。已经具备 `value/unit/observedAt`、current/lastGood、质量及可用状态，**不需要重建这些通用字段**。
- 已有 `GET /resource/culture/{id}/observation-bindings`，权限 `resource:culture:query`，提供观测设备、通道和绑定区间。
- 限制：当前观测读取只接受 DETECTOR、FLOOR_SCALE、DOWNSTREAM_DEVICE；不能直接传入概览的 BENCH_CONTROLLER 或 INTEGRATED_REACTOR。当前培养绑定未给出 pH、温度、O₂ MFC1 对应的 itemId/稳定语义映射。

**需要补充**

1. 提供普通有权用户可读的映射：`cultureId`、反应器类型/ID → 观测 `deviceKind/deviceId/channelCode` → `metricCode/itemId`，含绑定/映射版本和生效区间。可扩展现有绑定投影，不要求给概览用户授予映射维护权限。
2. 明确三个指标的稳定语义码及规范单位。O₂ MFC1 必须是对应通道的氧气流量，不能拿 DO/溶氧或其他 MFC 通道替代。
3. 复用 current 接口的质量、冲突、过期和不可用语义；若实际采集来源尚不支持这三个指标，应补采集适配及核准映射，不能只返回空 DTO 后称为完成。

**验收**：同一培养三项读数能追溯至明确设备、通道、指标和采集时间；换绑后不读旧通道；跨实验室/无权培养不可读；断采、冲突及过期明确返回状态，不将 lastGood 冒充当前有效值；真实 0 保留。

### BE-R02：提供按培养读取的当前有效 VCD

**主责与现有能力**

- M05 主责，沿用 M03 培养数据范围。
- 已有 `GET /detect/workbench/results`，权限 `detect:workbench:query`，含 `cultureId`、Vicell `vcd`、结果状态和检测时间；已有 `GET /detect/detresult/list`，权限 `detect:detresult:list`。
- 当前工作台结果按检测中置顶、上样时间倒序，不是“培养最新有效 VCD”排序。结果读取已有更正投影及作废项过滤，不应在概览复制另一套签批规则。

**需要补充**

1. 明确概览接受哪些结果状态、是否必须签名/审核、按哪个时刻取最新，以及更正、撤销、作废后的选择规则。由 M05 契约定义，前端不自行选第一条或重做状态机。
2. 提供按明确 `cultureId` 读取（建议支持有上限的批量）的有效 VCD 投影；可扩展现有结果接口，避免前端遍历全实验室历史检测记录。
3. 建议返回：`cultureId`、`value`、`unit`、`completedAt`、`resultId`、`itemId`、结果有效版本/更正引用、`resultStatus`、`availability/reasonCode`。规范单位需明确，不能仅照搬原 Mock 的 E06 文案。

**验收**：同一培养多个检测批次、检测中记录、已更正/作废记录均按核准规则选值；结果可追溯；数值 0 与无结果可区分；无权限结果不影响可见计数、不泄漏来源 ID；只存在样品名称相似的记录不能被误关联。

### BE-R03：补充当前液量或可用液位比例

**主责与现有能力**

- M02 主责设备观测和液位表示，M07 提供计量事实，M03 提供培养身份。
- 已有 `GET /lab/labbenchreactor/list`、`GET /lab/labintegratedreactor/list`：规格/额定容量，后者还含地秤引用。
- 已有 `GET /run/cultures/{id}/balance`：计量账 `currentNetGrams`；已有 M02 当前观测接口可供合规地秤读取复用。
- 计量账净重、地秤重量、额定容量和当前体积不是同一个值。中试 capacity 契约为 g，不能直接作为 L 使用。

**需要补充**

1. 先在契约中确定当前液量来源：直接体积观测、核准的质量—体积换算，或仅返回有明确分母的液位比例。没有可信来源时显式不可用，不要求开发方凭空生成数据。
2. 建议返回：`cultureId/deviceRef`、`volumeLiters` 或 `fillRatio`、比例分母/容量依据、`sourceKind/sourceId`、`observedAt/asOf`、`quality/availability/reasonCode`。
3. 若按质量换算，必须明确净重/皮重处理、密度及单位、密度适用范围和版本；计算在业务后端完成。来源是推算值时必须可辨识，不能标记成实时实测。

**验收**：同设备不同容量/单位不混用；缺密度、未知皮重、无采样时不生成液位；异常越界有明确处理；前端能保留容器轮廓，仅在有效数据下显示液体填充。

### BE-R04：返回实际培养天数与阶段

**主责与现有能力**

- M03 主责培养读投影，M07 提供真实开始培养及运行阶段事实；跨模块按现有 Port 交付，不在两个模块各维护一套阶段状态机。
- 已有 `GET /resource/culture/list`、`GET /resource/culture/{id}` 和开始培养工作流详情 `GET /run/workflows/{id}`。
- 培养列表包含 state、计划起止日期；源码 `CultureRow.startTime/endTime` 也明确标注为旧列表的**计划**时间，不能作为实际开始时间直接计算 D 天数。

**需要补充**

1. 接通实际开始事实的权威来源，建议返回 `actualStartedAt`、`cultureDayNumber`、`phaseCode`、`phaseChangedAt`、`asOf`；无法判定时保持空值并说明原因。
2. 明确 D0/D1 起算、按自然业务日还是累计时长、时区，以及暂停/延期/结束培养后的显示规则。按模块确认后的规则统一计算。
3. 明确培养生命周期 state 与运行 phase 的关系，不能把所有 RUNNING 映射为“准备阶段”。优先在现有培养读取中增加投影。

**验收**：计划开始与实际开始不同的样例不混淆；跨午夜、暂停/恢复、延期、未开始和已结束样例可复现；列表与详情一致；前端不需要自行计算业务天数或猜阶段。

### BE-R05：返回有证据的当前补料执行状态

**主责与现有能力**

- M07 主责当前执行摘要，M02 提供设备命令状态及可核实的回读。
- 已有 `GET /run/tasks`、`GET /run/tasks/{id}`、`GET /run/tasks/{id}/executions`。
- 已有 `GET /run/executions/{id}`、`/{id}/commands`、`/{id}/samples`；已知 workflowId 可读 `GET /run/workflows/{id}`。
- 执行详情的读取资格区分任务来源和工作流来源，沿用服务层的对应权限及对象范围；不能以有任务列表权限代替所有执行读取资格。

**需要补充**

1. 提供按 `cultureId` 获取当前相关补料执行摘要的能力，建议支持有上限的批量。包含 `feedingState`、`taskId/workflowId`、`stepInstanceId`、`executionId`、必要的通道/泵关联、`stateAt/asOf`、`evidenceSource`、`availability/reasonCode`。
2. 核准“正在补料”的证据和时效：排队、已受理、实际执行、暂停、停止请求、停止已确认、未知/超时必须可区分。任务业务状态、培养 RUNNING、命令受理成功都不能单独证明物理运行。
3. 多通道/多任务并存时返回准确关联和一致的摘要规则；刷新后仍可通过 executionId 恢复实际量、命令及停止证据。
4. 与既有工作流缺口 G03“工作流到 executionId 关联返回”合并实施或建立依赖，避免重复造执行查询接口。

**验收**：只有符合契约证据的执行才显示“补料中”；停止超时/失联显示未知或对应异常，不直接显示已停止；跨培养执行不会串卡；重复执行、并发通道、刷新恢复及权限变化可验证。真实设备状态需要另行实机验证，单元测试不能替代。

### BE-R06：提供按培养的工作流实例数量

**主责与现有能力**

- M07 主责，复用培养可见范围。
- 已有 `GET /run/workflows/candidates` 和 `GET /run/workflows/{id}`，权限 `run:workflow:query`；启动/步骤/取消接口已存在。
- 候选是可启动对象，不是已产生的工作流实例。现有已知实例详情不能用于发现某培养全部实例。

**需要补充**

1. 提供按 `labId + cultureId`（或有上限的 cultureIds）查询可见实例列表或数量的能力；优先复用现有实例持久化查询及范围校验。
2. 明确卡片角标统计“全部实例”还是“未完成实例”，包括取消、失败、安全收尾中的处理口径。建议返回 `cultureId`、`total`、`activeCount`、`asOf`，前端只绑定最终确定的口径；不要把可启动工作流种类数混入实例数。
3. 若提供列表，至少包含 `workflowId`、`subflowCode`、`status`、`createdAt/updatedAt` 及正规分页总数。列表、角标和打开实例的权限必须一致。

**验收**：多个实例和超过一页的记录统计准确；无权实例不进入总数；真正没有实例返回 0，依赖不可用明确报错；点击后的可见实例范围与角标一致。

## 三、统一交付与验收要求

1. 每项任务先交付现有接口扩展方案、字段语义和真实 JSON 样例；新字段注明类型、单位、可空条件、枚举及错误语义。新增 URL 或权限码须同步模块现行契约和前端 SDK，不能仅更新 Controller 注释。
2. 服务端执行当前用户、实验室、培养/设备对象范围校验。批量读取先按对象权限处理；无权对象不泄漏 ID、值或计数。授权依赖不可用不能伪装为空数据或权限不足。
3. 统一区分真实 0、无采集、过期、冲突、依赖不可用；有效值应附来源和时间。对本来已存在的质量/版本语义应复用，不平行创造同义字段。
4. 交付对应模块单元/契约测试及登录态 HTTP 样例，至少包含正常、有权但空、无权/跨实验室、失效/失败、真实 0。涉及设备物理状态的任务单列设备联调结果。
5. 后端 HTTP 验证完成后，前端移除相应“—”或隐藏状态并进行原卡片布局联调。提交测试报告时分开标注源码、HTTP、浏览器和设备证据。
