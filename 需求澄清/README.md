# 需求澄清（现行统一入口）
> 本文件是该模块需求澄清的现行登记处：新增澄清事项直接追加在文末"新增事项"区（规则见 README.md 第六节）。2026-11-10 之前的事项由《需求澄清决策记录》等历史来源整理而成，来源只读。

> 本目录是需求澄清事项的**唯一集中查阅入口**。每条事项只回答四件事：
> 当时在问什么、依据哪一行原文得出的结论、哪些分支仍未闭合、结论被哪条后续裁决替代。
> 本目录**不重新裁决业务规则**，也不替代需求说明书与模块契约；原文以被引用的原文件为准。

## 三、单条事项的九段结构

每条事项固定编号 `RC-<模块>-<序号>`，正文九项固定为：

1. **模块与主题**：所属模块、关联模块、对应 V5.1 章节、原始编号（原生第 N 问 / M0x-Qnn / Q-x-xx）。
2. **原始背景**：原文摘录 + `文件:行号`，不改写。
3. **澄清问题**：当时实际要回答的问题；无独立问句时说明“原文只记录结论”。
4. **已确认结论**：按原文槽位（有效规则/用户选择/用户原话/决策/适用范围）逐条引用并标行号。
5. **待确认事项**：仍未闭合的分支；已闭合则写明“无”。
6. **冲突与差异**：原文登记的覆盖/替代关系；无则写明“无”。
7. **状态**：`CONFIRMED`/`PENDING`/`CONFLICT`/`SUPERSEDED`/`INSUFFICIENT_EVIDENCE` + 判定依据。
8. **来源与追溯**：原始文件、原文标题、起始行、日期、并列来源、分项索引。
9. **关联事项**：同主题的其他主条目编号（同一问题链）。

## 四、状态词表（本目录唯一口径）

| 状态 | 含义 | 处理要求 |
| --- | --- | --- |
| `CONFIRMED` | 原文给出明确确认依据（用户选择、客户答复、状态行“已确认”） | 可直接作为设计与实现依据，引用时带上第 8 条行号 |
| `PENDING` | 原文仍含未闭合分支，无最终结论 | 不得默认取值；需在总览第 3 节跟踪 |
| `CONFLICT` | 同一问题在不同来源给出互斥结论且均未撤回 | 停止相关实现，先裁决 |
| `SUPERSEDED` | 该结论已被后续裁决替代/撤下 | 只作历史证据，现行规则看同主题较晚条目 |
| `INSUFFICIENT_EVIDENCE` | 有关联内容但无确认也无未决措辞 | 不升级、不外推，按第 8 条行号人工复核 |

## 六、维护规则

1. 新增澄清结论直接追加到对应模块文件文末"新增事项"区；跨多个模块放 `跨模块及待分类事项.md`；编号接该文件当前最大序号。
2. 沿用九段结构，新增事项可以写简，但必须有：模块与主题、来源（日期、谁答复、载体、行号）、澄清问题、结论、待确认分支、状态、关联事项。
3. 同一业务问题只允许一个主条目；出现新来源时在该条目"来源与追溯"追加并列来源，不新建条目。
4. 结论被推翻：旧条目标 `SUPERSEDED` 并在"冲突与差异"写明被哪条替代，新结论单独建条目。
5. 状态为 `PENDING` 或 `CONFLICT` 时，同时在 `需求澄清总览.md` 第 3 节追加一行。
6. 条目不写实现状态（是否已编码/联调看 `docs/开发任务/` 与根 `AGENTS.md` 第 8 节）。
7. 引用需求章节一律写 V5.1 章号，V4.0 章号只能括注。
8. 统计数字（本文件第二节表格、各模块"事项统计"）是 2026-11-10 整理时的快照，新增事项不要求逐条维护，需要时批量重算；在表格标题处注明"截至 2026-11-10 整理"。
