四条与判定相关的静态事实：

1. **顺序固定且短路**：第 1 条命中即返回，不再执行后续 `ownsBatch`。因此三条 `ownsBatch` 的查询成本是叠加的，最坏情况是三次根查询。
2. **三个 `ownsBatch` 都先解析 ID**：开始培养用 `id(batchId)`（`:470`，非法即 `INPUT_INVALID` 400）；W08 与 W03 用 `number(batchId)`（Waste `:502`、Bench `:1151`，同为 400）。所以畸形 `batchId` 在第 1 条判定时就以 400 结束，不会落到 W02。
3. **判定不按当前用户或实验室过滤**：`StartCultureWorkflowMapper#byBatch`、`WasteClearBatchMapper#root`、`BenchConnectionBatchMapper#root` 三条语句都只按主键查一行，**没有 lab、actor 或 scope 条件**。派发只看「持久归属形状」，鉴权在各分支内部完成。
4. **查找异常不转派**：`WorkflowBatchQueryService` 没有 try/catch。任一 `ownsBatch` 或分支方法抛出的 `ManagementGuardRejectException`、`IllegalStateException` 都直接向上到 Controller。不存在「查不到就试下一个归属」的捕获式兜底。
5. **两个 `isBatch` 的 JSON 判定不完全对称**：W08 用 `value.has("batchRootWorkflowId")||value.has("batchWorkflowIds")`（`WasteClearBatchService:285`，`has` 对显式 `null` 也算存在）；W03 用 `selection.hasNonNull("batchRootWorkflowId")||selection.hasNonNull("batchWorkflowIds")`（`BenchConnectionBatchService:153`）。理论上一个「键存在但值为 null」的 selection 会被判为 W08 而不是 W03。本轮未在真实数据中观察到这种行，**登记为静态差异，不判缺陷**。

**W02 为什么是兜底**：`replacement` 没有 `ownsBatch` 方法，被写成 `bench.ownsBatch(batchId) ? bench.getBatch(batchId) : replacement.getBatch(batchId)`。这是代码结构上的 else，**不代表业务上「默认按中试更换处理」**；它的实际效果是「既不是开始培养、也不是 W08、也不是 W03 的可见工作流 id」都会进入 W02 分支，然后由该分支自己的批次形状校验拒绝（见 §6.5）。

### 4.2 正常路径（实际调用顺序）

`StartCultureApplicationService#batch:222`，方法带 `@Transactional`（`:221`），因此下一步的 `FOR UPDATE` 在事务内生效。

1. `:222` `store.byBatch(id(id))` 取会话行；为空 `require(...,"NOT_FOUND")` → 404。
2. `authorizedSession(actor(), row.sessionId, true, false)`（`:447`）：
   - `store.session(id, lock=true)` → `SELECT * FROM run_start_culture_session WHERE session_id=#{id}` ＋ `<if test="lock">FOR UPDATE</if>`（XML `:5-7`）；为空 → 404。
   - `scope(actor, row.labId)`（`:448`）：`permissions.resolveScope(id(actor.getActorUserId()))`，要求 `isAllAccess()` 或 `operableLabIds` 含该 lab。
   - 第三参数 `write=false`，故**跳过会话归属人校验**（写路径才校验 `PAGE_SESSION_OWNER_MISMATCH`）。
   - 逐成员 `permissions.canViewCulture(actorUserId, cultureId)`（`SmpPermissionServiceImpl:257-261`，内部再调 `resolveScope`），任一不可见即 404。
3. `aggregate(row)`（`:415`）：`state(row)` 从 `state_json` 反序列化为 `StartCultureSessionState`；`store.members(sessionId)` 取成员行；因 `byBatch` 保证 `row.batchId` 非空，返回聚合视图 `{batchId, groupVersion, pageSessionId, state, members[], issues:[]}`。
4. 聚合 `state` 由 `aggregateState(state)`（`:466`）推导四值：`completed()` → `COMPLETED`；`interactionState=CLOSED` → `CANCELLED`；`CANCEL_REQUESTED` → `NEEDS_RECONCILIATION`；其余 → `IN_PROGRESS`。
5. 每个成员经 `instance(row,state,w,actor)`（`:416-436`）组装，关键推导：
   - 解析 `selection_snapshot` 取 `deviceKind` / `deviceId`，调 `devices.readiness(ref, labId, workflowKind)` 得到 `reasonCodes`，转成 `issues[{code,message}]`。
   - `expired = !now().isBefore(deadlineAt)`。
   - `allowedActions` 只在「当前用户是该会话创建人 **且** `interactionState=ACTIVE` **且** 未完成」时计算：恒加 `CANCEL`；未过期且该成员无未决命令时，按 `currentStep` 加 `BACK` / `VALIDATE_NEXT` / `SKIP` / 完成类动作；模拟模式下追加 `SIMULATE_*`；只要组内任一成员处于预填充运行中，则移除 `VALIDATE_NEXT` 与 `BACK`。

   - `alarmSource`：仅中试（`START_CULTURE_PILOT`）、未完成、未过期、`ACTIVE` 时调 `alarms.inherit`。
   - `completionRecord`：仅 `state.completed()` 时从第 2、3 步表单快照取接种与告警事实。

因此：

- 典型非 W02 批次（如普通 W03 单实例、W08 成员、W01 工作流）进入兜底后，得到的是 **503**，不是 403、404 或空结果。
- 该 503 发生在**任何成员查询之前**，所以不会读取或泄露其他批次的成员行。
- 「`rows.size()!=manifest.size()` 的 503」只在「根行确为 W02 模拟批次、但成员行缺失或混入额外成员」时发生，是另一种数据不一致场景。
- 状态码选择（用 503 而非 404/400 表示「不是本类批次」）设计未作规定，登记为观察，不判缺陷，也不据此改码。
